# 089 — Places Cost and Yield Quick Wins

## Verdict

The low-cost ceiling is imposed by query breadth, not monthly spend: Text Search returns at most 60 places per query, and this code has 67 queries, so its theoretical current ceiling is 4,020 raw result slots per monthly run before cross-query duplicates and filters. The cheapest material increase is to split saturated nationwide queries into city/category queries; at the current Enterprise SKU's 1,000-call monthly free cap, the theoretical ceiling is about 20,000 raw result slots (not 20,000 new qualified leads). Dropping only rating and review count does **not** lower this code's SKU, because the field mask also requests other Enterprise-tier fields.

## Findings

### S2 — Broad queries strand businesses behind the 60-result ceiling
- **Where:** `scrapers/google_places.py:45-124` (query lists), `:203-278` (pagination); `main.py:172-181` (filter and dedup).
- **Breaks:** The Lebanon list uses broad country-wide searches (for example, `restaurants in Lebanon`), and the API returns no more than 60 results across pages for any one query. Additional pagination cannot recover the rest of a dense category. The code currently contains **33 Lebanon + 34 KSA = 67** queries (also consistent with `README.md:12`); the brief's stated 68 is off by one. Thus the absolute current Places ceiling is 67 × 60 = **4,020 raw hits per run**, assuming every query fills all three 20-result pages. Results are deduplicated globally by place ID in `google_places.py:170-188,227-235`, then category-filtered and merged in `main.py:172-181`; unique new CSV records must be lower, and the repository contains no run data from which to estimate the actual fraction.
- **Trigger:** A saturated country-wide query such as `restaurants in Lebanon` finds over 60 matches; only its first 60 can be returned, regardless of how many pages are fetched.
- **Fix:** Shard only saturated high-value queries into city × category searches (and retain broad queries for lower-density categories). Start with Lebanon's major population centers (Beirut, Tripoli, Jounieh, Byblos, Zahle, Sidon, Tyre, Baalbek) for the categories whose current query logs show 60 results; give Jeddah and Dammam more city-specific coverage rather than adding still more Riyadh-only variants. A first +80 fully paginated query expansion would lift the *gross slot ceiling* from 4,020 to 8,820 (2.2×) at 441 calls; this is a planning scenario, not a forecast of unique leads.

### S2 — There is substantial zero-cost request headroom, but not unlimited scale
- **Where:** `scrapers/google_places.py:29-42,138-142,203-278`; `.github/workflows/scrape.yml:3-6`.
- **Breaks:** Under Google's current global pricing table, Text Search Enterprise includes 1,000 free billable events per month; Text Search Pro includes 5,000. The current field mask triggers Enterprise (see next finding). A fully saturated run of the existing 67 queries makes at most 67 × 3 = **201 API requests**, leaving at most 799 Enterprise requests of free monthly headroom, assuming no other project usage. With 1,000 requests, the hard query-result ceiling is 20,000 hits: 333 full three-page queries (19,980 hits) plus one final page (up to 20). So about **266 additional fully paginated queries**, plus one page, fit before paid usage. This is a provider-imposed ceiling under free usage, not a prediction: city searches overlap, most queries may not fill 60 slots, and downstream dedup/filtering removes more. Also, the workflow's monthly schedule is commented out, so “per month” currently means one manually triggered run unless scheduling is restored.
- **Trigger:** Adding query shards without tracking the *number of requests/pages* could exhaust the free SKU cap if other project traffic consumes it, or generate far fewer distinct leads than raw result slots suggest.
- **Fix:** Spend the free headroom on measured query shards first: prioritize searches whose existing result pages reach 20/20/20, then expand in batches and compare unique whitelist-passing IDs per additional request. Use **~8–9k gross hits** as a plausible first expansion envelope (+80 queries), **~20k gross hits** as the no-other-usage free-cap ceiling, and report unique new records separately; no defensible unique-lead/month forecast is possible without observed run results.

### S2 — Removing rating fields alone does not reduce this request's billed SKU
- **Where:** `scrapers/google_places.py:31-42`.
- **Breaks:** `places.rating` and `places.userRatingCount` are Enterprise-tier fields, but so are `places.nationalPhoneNumber` and `places.websiteUri`, both also requested here. The highest-tier requested field determines the Text Search SKU, so removing rating and review count alone leaves this request at **Text Search Enterprise**. Current global list pricing is $35 per 1,000 Text Search Enterprise events in its first paid band, versus $32 per 1,000 for Pro; the respective free monthly caps are 1,000 and 5,000. The current 201-call maximum is below either free cap, so a field-mask change does not save current monthly spend.
- **Trigger:** Keep phone and website in the field mask but remove just `places.rating` / `places.userRatingCount`; billing remains Enterprise because the other two requested fields still trigger that tier.
- **Fix:** Keep fields that support lead contact and scoring while traffic is under the free cap. If usage later exceeds 1,000 monthly calls, evaluate dropping **all** Enterprise fields to move the search to Pro—but that also loses Places phone, website, rating, and review count. Recovering those fields selectively through Place Details is a two-stage design/cost tradeoff, not a no-architecture quick win. `rating` is consumed by scoring/recommendation (`enricher.py:303-306`, `pitch_recommender.py:42-73`); assess review-count usefulness separately rather than assuming its removal changes billing.

### S3 — Query growth should correct market and language imbalance, not multiply synonyms blindly
- **Where:** `scrapers/google_places.py:44-124,126-135`.
- **Breaks:** The 33 Lebanon searches are broad and English-only; KSA has 34 searches, with only three Dammam-specific queries and more Riyadh coverage. Blindly adding close synonyms burns calls on overlapping results. Also, `_country_from_query()` defaults to Lebanon unless the query contains English `saudi`, `riyadh`, `jeddah`, or `dammam`; a new Arabic-only Saudi query would therefore be tagged `LB`.
- **Trigger:** Adding `مطاعم في الدمام` as-is retrieves Saudi places but `country` is assigned `LB` at lines 126-135.
- **Fix:** Prefer geo-sharding high-yield categories; add Arabic/local-language variants only when query-level results justify the extra overlap, and include an English Saudi anchor in Saudi query strings (for example, an Arabic phrase plus `Dammam Saudi Arabia`) so existing country inference remains correct. Avoid spending free calls on city/category combinations whose parent query does not approach its 60-result cap.

## Not a bug, but worth knowing

- Google documents Text Search (New) as a maximum of 60 results across all pages, normally 20 per page: [Text Search (New), result limits and pagination](https://developers.google.com/maps/documentation/places/web-service/text-search). More pages do not raise the per-query ceiling.
- Current SKU/field tiers and global pricing are documented at [Place Data Fields (New)](https://developers.google.com/maps/documentation/places/web-service/data-fields) and [Google Maps Platform pricing](https://developers.google.com/maps/billing-and-pricing/pricing). Pricing and free caps can change; the figures above reflect the pages checked 2026-10-03. Monthly free caps are shared at the applicable billing-project/SKU level, not reserved for this scraper.
- The code fetches at most 60 unique **within-query results per text query**, but it cannot claim 4,020 monthly new businesses: duplicates across queries and OSM/Wikidata, whitelist exclusions, and already-known master rows reduce incrementality (`main.py:172-181`).

## Recommended order of work

1. Confirm billing usage for the Places Text Search Enterprise SKU and record per-query pages/results; current max is 201 calls per monthly scrape, well below the 1,000 free cap if the project has no other use.
2. Add a small set of city × category shards for queries that demonstrably hit 60, then measure deduplicated, whitelist-passing *new* records per added call. Expand toward +80 queries (~8,820 gross slots) only if yield stays useful.
3. Use the remaining no-cost call headroom as an upper limit, not a target: the no-other-usage theoretical ceiling is about 20,000 gross hits/month at Enterprise. Revisit an all-Pro field mask only if that cap is exceeded and the cost of losing native phone/website/rating data is acceptable.
4. Restore/verify monthly scheduling separately; `.github/workflows/scrape.yml:3-6` currently has only manual dispatch enabled.
