# 213 — cmd_run cost model at 500k: O(n) per run, O(k²) across runs, and one HTTP GET per historical record

## Verdict

`cmd_run` (`cli.py:33`) is a 5-line wrapper, so its entire cost is `main.main()`.
**Within a single run the pipeline is strictly O(n) — there is no quadratic term
anywhere in it** (measured scaling exponents 0.82 and 0.70), and it allocates
Θ(n) with a *very* small constant. The problem is not the complexity class; it is
the constant. One O(n) term is an HTTP GET: `enricher.py:231` enqueues **every
row in the master that has a website, on every single run, with no "already
checked" filter**, and `enricher.py:250` then overwrites the `website_live` the
previous run already paid for. At 500k rows that is 210,423 GETs per run, which
is 2.92 h at a 2 s median and 5.83 h at 4 s — and `scrape.yml:25` kills the job
at `timeout-minutes: 300`. So the run dies inside `check_websites`, **before
`main.py:209` writes a single CSV**, and the master never grows again.

The single change with the largest speedup is **make enrichment a delta over
`scraped_at` instead of a sweep over history**: 210,423 GETs → ~4,200, cutting
10,290 s of a 10,562 s run (**97.4%**). Every CPU optimisation I measured is
worth 10 s or less. Do not touch the CPU until the GET count is down.

## Complexity verdict, stated plainly

| Question | Answer |
|---|---|
| O(1), O(n) or O(n²) in businesses, per run? | **O(n)**, with 6 sequential O(n) passes. Measured exponent 0.82 (10k→100k) and 0.70 (100k→500k) — sub-linear because fixed costs dominate at small n. |
| Any quadratic term? | **No.** Every pass is a flat `for` over the list with a dict/array indexed by a constant-time key. `_merge` (dedup.py:190) does not recurse into nested containers. `sorted()` calls (main.py:233, main.py:241) run over ≤13 distinct regions/services, not over records. |
| Does it allocate proportionally? | **Yes, Θ(n)**, at ≈2.6 KB/row. Peak RSS 1,318 MB at 500k. Plus one avoidable Θ(n) term: `dedup` deep-copies all 500k records (416 MB) even though most need no merge. |
| Is the *cumulative* cost quadratic? | **Yes.** The master is append-only (main.py:150 loads it, main.py:179 merges it, main.py:209 rewrites it in full), so run *k* redoes Θ(n_k) work over all history. Σn_k = Θ(k²/m). |

`main.write_csv` called directly on synthetic masters at the target sizes.

somewhat slower. No network was touched.

## Findings

### S1 — Every run re-fetches every website in history, and the run is killed before it can write anything

- **Where:** `cli.py:37` → `main.py:187` → `enricher.py:337` → `enricher.py:231`,
  with the unconditional overwrite at `enricher.py:250`. Timeout:
  `.github/workflows/scrape.yml:25`.
- **Breaks:** `enricher.py:231` is
  `targets = [(i, r["website"]) for i, r in enumerate(records) if r.get("website")]`.
  There is no filter on `r.get("website_live")` already being populated from the
  master, and no freshness test. `enricher.py:250` then assigns
  `r["website_live"]` for every target regardless of what the master already
  knew. So a row that was successfully checked 6 months ago is re-fetched
  forever, one GET at a time, 40 at a time. At 500k rows / 42% with a site that
  is 210,423 GETs every run. Once the median lands above ~3.4 s the GET queue
  alone exceeds `timeout-minutes: 300` (5.00 h), the runner kills the job, and
  that kill happens *inside* `check_websites` — i.e. before `main.py:209` writes
  `all_businesses.csv`. Nothing is uploaded, the Drive master is unchanged, and
  the next weekly run (`scrape.yml:9`) walks into exactly the same wall. The
  pipeline is permanently stuck at whatever n it already reached, while
  `main.py:152` cheerfully prints `Loaded 500000 records` each time.
- **Trigger:** a `data/all_businesses.csv` with 500,000 rows and 210,423
  non-empty `website` cells. Measured 210,423 GETs / 2.92 h at a 2 s median
  against a 5.00 h budget that also has to cover `osm.py:44`'s 200 s Overpass
  timeout and `wikidata.py:75`'s 90 s SPARQL timeout.
- **Fix:** only enqueue sites whose `website_live` is not already known, or whose
  URL changed / whose check is older than a TTL — pass a `since` boundary into
  `enrich()` instead of re-checking all of history.

### S2 — Linear per run, quadratic across runs: the append-only master means nothing is ever skipped

- **Where:** `main.py:150` (load), `main.py:179` (`combined = raw_filtered + master`),
  `main.py:180` (`dedup(combined)`), `main.py:209` (rewrite the whole master).
- **Breaks:** this is the structural answer to the O(n²) question. No single run
  is super-linear, but each run repeats Θ(n) work over the *entire* accumulated
  history. With a weekly cron and an append-only master, total work across the
  lifetime is Σ n_k, which is quadratic in the number of records ever ingested.
  Cost never plateaus: run 1 pays for 5,000 rows, run 100 pays for 500,000, and
  every run after that pays the same 500,000-price again. Combined with S1 this
  is what turns a 30-second pipeline into one that cannot finish.
- **Trigger:** any two consecutive weekly runs — the second one re-does all of
  the first one's per-record work plus everything before it.
- **Fix:** same fix as S1. Incremental enrichment is the only thing that breaks
  the Θ(k²) accumulation.

### S2 — `dedup` deep-copies all 500k records, including the ones it never touches: 416 MB and 10 s

- **Where:** `dedup.py:210` (`phone_index[key] = dict(record)`) and `dedup.py:218`
  (`name_index[key] = dict(record)`).
- **Breaks:** every record on first sight of its key is copied with `dict(record)`
  — measured `sys.getsizeof` of a 22-key dict is **832 B**, so 500,000 rows cost
  **416 MB of dicts that are byte-identical to the ones already in memory**. RSS
  goes from 437 MB (master loaded) to 1,141 MB the moment `dedup` runs. On a
  steady-state run only ~5,000 of 500,000 records are actually merged; the other
  495,000 copies are pure waste. A by-reference variant (`idx[key] = record`,
  copying only inside the `if k in idx:` merge branch) measured **20.85 s → 10.81 s
  (×1.93)** on the same 500k input, with identical output.
- **Why it is safe:** `_merge` (dedup.py:190) already builds a fresh dict, so
  nothing downstream mutates the stored record. Callers get the same objects they
  passed in, which is what they already hold.
- **Why S2 and not S1:** it does not corrupt anything and 416 MB fits easily in
  the 7 GB runner. It is the largest CPU win available, and it is still only 10 s
  of a 10,562 s run — which is exactly the point: the CPU is not where the time
  goes.
- **Trigger:** any master with ≥ ~200k rows.
- **Fix:** store the record by reference on first insert; copy only on merge.

### S2 — `cmd_run` exits 0 even when every source failed, so a dead pipeline looks healthy

- **Where:** `cli.py:33-37`, `cli.py:315`, `main.py:148` (`-> None`),
  `main.py:162-168`, and the fail-soft returns at `osm.py:52-56`,
  `wikidata.py:80-85`, `google_places.py:169-171`.
- **Breaks:** all three scrapers swallow their own failures and return empty;
  `main.py:162-168` additionally catches every exception from every future and
  prints to stderr. `main.main()` is annotated `-> None`, never raises, and never
  returns non-zero. `cmd_run` therefore returns `None`, and `cli.py:315`'s
  `int(args.func(args) or 0)` evaluates to `int(0)` → **0**.
- **Trigger:** unset `GOOGLE_PLACES_API_KEY` (prints "skipping" at
  `google_places.py:170`) + Overpass returns 504 + Wikidata times out. `raw` is
  empty, `main.py:179` merges in the stale master, all five CSVs are rewritten
  from old data, `main.py:220` prints `Total unique businesses : 500000`, exit
  code 0. Nothing in the exit status distinguishes this from a good run.
- **Why this belongs in a cost report:** the entire reason `run` costs 2.9 h is
  that it is meant to run unattended, weekly, at 3am. A command that cannot
  report failure cannot be the thing you alert on, and the 5 h timeout at
  `scrape.yml:25` makes "did it produce anything new?" the single most important
  question about this command. Note that `scrape.yml:78-83` had to bolt a
  row-count assertion on *outside* the CLI precisely because the CLI cannot do it.
- **Fix:** have `main.main()` return an `int`, track per-source outcomes from the
  futures it already collects at `main.py:162`, and have `cmd_run` return it.

### S2 — The five exports are 343 MB and 43 s per run, and the master stops opening in Google Sheets above 454,545 rows

- **Where:** `main.py:199-213` (builds 5 lists, writes 5 files);
  `main.py:118-120` justifies `utf-8-sig` with "so Excel and Google Sheets detect
  UTF-8"; `main.py:129` fsyncs each file; `scrape.yml:88-89` uploads the whole
  `data/` directory twice.
- **Breaks:** measured at 500k rows:

  | file | rows | MB | seconds |
  |---|---|---|---|
  | `all_businesses.csv` | 500,000 | 102.3 | 11.57 |
  | `qualified_businesses.csv` | 437,769 | 89.5 | 12.30 |
  | `with_websites.csv` | 210,423 | 45.6 | 5.69 |
  | `without_websites.csv` | 289,577 | 56.7 | 7.91 |
  | `sales_ready.csv` | 235,078 | 49.1 | 5.49 |
  | **total** | | **343.2** | **42.97** |

  `qualified_businesses.csv` is 87% of the master because
  `main.py:206` (`completeness_score >= 1`) is satisfied by a single phone number.
  It is close to a duplicate of the master and doubles the write volume for
  almost no selectivity.
- **The hard threshold:** 22 columns × the 10,000,000-cell Google Sheets limit =
  **454,545 rows**. At 500,000 the master is 11,000,022 cells, 1.1× the limit —
  the primary product can no longer be opened by the tool the code comment at
  `main.py:119-120` names as the reason for its encoding. This is a silent
  operability cliff, not an error: the CSV is fine, the viewer is not.
- **Trigger:** `data/all_businesses.csv` at 500,000 rows.
- **Fix:** stream the 5 exports in one pass over `records` instead of
  materialising 4 subset lists and re-serializing 343 MB; shard the historical
  master by year so no single file crosses the Sheets ceiling; prune
  `gdrive:leads/data/$TIMESTAMP/` or stop writing to it.

### S3 — `check_websites` materialises one Future per site up front: 210,423 work items

- **Where:** `enricher.py:238` —
  `futures = {pool.submit(_fetch_website, url): idx for idx, url in targets}`.
- **Breaks:** the whole queue is built before the first result is consumed.
  Measured: the index dict alone is **10.5 MB** for 210,423 entries, and each
  Future + work item + args is ≈500 B → **≈105 MB**. More importantly, submitting
  200,000 tasks through a `ThreadPoolExecutor` costs **20.9 µs/task of pure
  scheduler overhead** (4.19 s for the 200k batch, vs 0.03 s done inline), and
  going from 1 worker to 40 made it *slower* (3.23 s → 4.19 s) — that is lock and
  GIL contention, not useful work. On a 2-vCPU runner the contention is worse.
- **Trigger:** any master with ≥100k rows carrying websites.
- **Fix:** keep at most `workers * 4` tasks in flight and refill as futures
  complete. Removes the last O(n)-memory term and most of the scheduler overhead.

### S3 — `_fetch_website` allocates every email match on the page before looking at any of them

- **Where:** `enricher.py:199-200` —
  `for addr in mailto_hits + _EMAIL_RE.findall(html)`.
- **Breaks:** Python evaluates the right-hand side eagerly, so
  `_EMAIL_RE.findall(html)` runs over the entire decoded body **even when
  `mailto_hits` already contains a valid address** — the loop then breaks on the
  first good one and the whole list is discarded. On a page at the 200,000-byte
  cap (`httpclient.py:54`) with contacts in the markup, that is 1,400 match
  strings allocated and immediately thrown away (measured on a representative
  200 KB sample). Compounding it, `enricher.py:188-189` decodes the full capped
  body to a `str` per fetch (measured 106 KB str from a 67 KB sample; up to
  ~400 KB for Arabic content), so the transient garbage across 210,423 fetches is
  tens of GB per run.
- **Trigger:** a site whose HTML contains ≥1 valid `mailto:` link plus many
  plain-text addresses.
- **Fix:** `itertools.chain(mailto_iter, (m.group(0) for m in _EMAIL_RE.finditer(html)))`
  so the second scan is lazy and short-circuits on the first usable address.

### S3 — `cmd_run` ignores `args`; there is no way to skip the enrichment sweep

- **Where:** `cli.py:33-37` — `args` is accepted and never read; the `run`
  subparser at `cli.py:285-286` adds no options at all.
- **Breaks, and it matters specifically because of this lens:** at 500k the
  command's only behaviour is the full 2.92 h rescrape. You cannot ask it to
  re-score, re-export, or enrich only the new rows. `cmd_score` (`cli.py:247`)
  covers the re-score case and nothing covers the other two, so during a
  5-hour-OUT window there is no cheap way to inspect or republish the data you
  already have — you fall back to reading the CSVs by hand.
- **Trigger:** `leadminer run` at 500k rows when you only wanted
  `data/sales_ready.csv` regenerated.
- **Fix:** add `--skip-enrich` and `--since <ISO8601>` to the `run` subparser and
  thread them into `enrich()` / `check_websites()`.

## Not a bug, but worth knowing

- **Memory is not the constraint at 500k.** Peak RSS measured **1,318 MB**
  (master 437 MB + `combined` list + 10,000 fresh rows) against `ubuntu-latest`'s
  7,000 MB — roughly 5.7 GB of headroom. At the observed ~2.6 KB/row the ceiling
  is about 2.5M rows. Do not spend effort on streaming or a database here before
  the network fix; 33% of RAM used is a healthy pipeline.
- **`dedup` is not the bottleneck.** The floor with zero collisions is
  **10.0 µs/row** (0.10 s / 1.00 s at 10k / 100k). A collision costs **52 µs**
  measured in isolation and up to **384 µs** at 500k purely from cache misses on
  a 500k-record working set — not from anything algorithmic. At ~5,000 merges per
  steady-state run that is 0.3-2 s. The S2 above is about the 416 MB of
  unnecessary copies, not about `_merge` being slow.
- **`infer_region` is not the bottleneck.** Measured **9.4 µs/record → 4.6 s at
  500k**. The 8 compiled alternations (`enricher.py:52-55`) short-circuit on
  first match, and the whole regex stage is skipped for `country == "SA"`
  (`enricher.py:85`), which is the entire Saudi half of the dataset.
- **The export subset lists are references, not copies.** 1,289,688 pointers
  across the four lists at 500k = **10 MB**. Free.
- **Raising the worker count is the second-best lever, and still a weak one.**
  40 → 80 workers halves the network wall clock arithmetically (2.92 h → 1.46 h);
  160 gets to 0.73 h. But 40 threads on a 2-vCPU runner means >95% of the wall
  clock is GIL wait rather than network wait, so the real multiplier is well
  below 2×, and it does not help at all if the problem is 210,423 GETs. Fix the
  GET count first, then consider the pool.
- **Three separate `re.sub(r"\D", "", ...)` runs per record** — `main.py:138`,
  `main.py:194`, `enricher.py:285`. Hoisting to a module-level compiled pattern
  measured 0.42 s → 0.32 s per 200k calls, i.e. ~0.8 s saved per 500k-row run
  across all three passes. Real, measurable, and 0.008% of the run.
- **Ranked by wall-clock saved at 500k** (base = 10,500 s network + 62 s CPU):

  | change | saves | share of run |
  |---|---|---|
  | **skip refetch of unchanged websites** (`enricher.py:231`) | **~10,290 s** | **97.4%** |
  | workers 40 → 80 | ~5,250 s | 50% |
  | write 5 exports in one streaming pass (`main.py:199-213`) | ~20 s | 0.2% |
  | `dedup` by reference (`dedup.py:210`) | 10.0 s | 0.1% |
  | batch the executor (`enricher.py:238`) | ~4 s + 105 MB | 0.04% |
  | hoist `re.sub` patterns | 0.8 s | 0.008% |

## Recommended order of work

1. **Make enrichment incremental** (`enricher.py:231`, `enricher.py:250`). Fetch
   only sites that are new, whose URL changed, or whose last check is older than
   a TTL. This is the only change that matters; it also fixes S2's Θ(k²)
   accumulation. Everything below is noise until this lands.
2. **Make `cmd_run` able to fail** (`cli.py:37` → `main.py:148`). Return an exit
   code derived from the per-source futures `main.py:162` already has. Do this
   *with* step 1, so that the incremental run's "0 new rows fetched" outcome is
   distinguishable from "the master is empty".
3. **Cut the 343 MB of exports and shard the master** (`main.py:199-213`). One
   streaming pass, drop or tighten `qualified_businesses.csv` (87% of the master
   at `main.py:206`), and shard by year so no file passes 454,545 rows and breaks
   Google Sheets.
4. **`dedup` by reference** (`dedup.py:210`, `dedup.py:218`). Ten seconds and
   416 MB, one-line change, no behaviour change.
5. **Batch the executor** (`enricher.py:238`) and **make the email scan lazy**
   (`enricher.py:199`). Small, safe, and they stop the last O(n) allocation.
6. **Add `--skip-enrich` / `--since`** to the `run` subparser
   (`cli.py:285-286`) so the command is operable at 500k.
