# 231 — `cmd_stats` (cli.py:79): a diagnostic that cannot detect the failure it exists to detect

## Verdict

`cmd_stats` is a **shape reporter, not a health check**. It prints twelve counters and
four frequency tables and then unconditionally `return 0` (`cli.py:132`), with no
freshness signal, no schema check, no internal-consistency assertion, and no threshold.
Its own docstring claims "This is the first thing to check" (`cli.py:80`), yet it cannot
tell a healthy run from a file that is four months stale, from a run in which all three
scrapers returned zero, or from a file whose columns have been renamed — **in all three
cases it prints a report that looks exactly as healthy as yesterday's and exits 0.**

The single most important consequence: because `main.py:150` accumulates the master
across runs and `data/` is never rotated, the file `cmd_stats` reads is *always*
populated, so "the report printed" carries zero information about "the run worked".
Ranked by how long a human takes to notice, the failures are in
[Silent-failure ledger](#silent-failure-ledger-ranked-by-notice-latency).

Scope note: `_fmt` (`cli.py:29`) and its formatting are already covered in
`200-x.md`. Nothing here re-litigates them.

---

## What it prints

Exactly this, and nothing else (`cli.py:93-131`), 30–40 lines:

```
<path>  (N rows)
  with phone / email / website / instagram / whatsapp / region : _fmt(count(...))   # 98-103
  website live / website dead / unreachable                      : raw f"{n:,}"     # 111-113
  by priority:   Counter(industry_priority).most_common()  ← UNCAPPED              # 116-117
  by source:     Counter(source).most_common(8)                                      # 120-121
  by region:     Counter(region or "Unknown").most_common(12)                         # 124-126
  top pitches:   Counter(recommended_service).most_common(8)                         # 129-131
```

Fourteen of the 22 contract columns are **never mentioned**: `name`, `category`,
`country`, `address`, `lat`, `lon`, `facebook`, `linkedin`, `rating`, `review_count`,
`completeness_score`, `lead_score`, `scraped_at` (verified by string-inspecting the
compiled source of `cmd_stats`). So the report has no quality score distribution, no
category breakdown (the thing a lead-gen pitch actually pivots on), no country split,
and **no freshness** — even though `scraped_at` is column 22 in `FIELDS` (`main.py:39`)
and is set on every record (`scrapers/base.py:27`).

`cmd_stats` is not invoked anywhere in `.github/workflows/scrape.yml`; the CI gate is
inline `wc -l` bash. So this function's only consumer is a human running it by hand,
either after something looks wrong or on a schedule, interpreting free text.

## What it swallows

- **Every schema mismatch.** No header check exists. `count()` (`cli.py:96`) is
  `sum(1 for r in rows if (r.get(field) or "").strip())` — a missing key yields `None →
  "" → falsy → 0`. Exit code is still 0.
- **Every non-canonical `website_live` token.** The checks at `cli.py:107-108` are exact
  string equality against `"True"` / `"False"`. Anything else matches no bucket at all.
- **The long tail.** `.most_common(8)` / `(12)` at `cli.py:120,125,130` with no
  `+N more` line and no reconciliation against the row total.
- **Blank cells.** `""` is a truthy `Counter` key distinct from `None`, so blank
  `industry_priority` / `source` / `recommended_service` become unlabelled buckets.
- **All filesystem and decode errors** are *not* swallowed but *unhandled*: `main()`
  catches only `KeyboardInterrupt` (`cli.py:314-318`), so `IsADirectoryError`,
  `UnicodeDecodeError` and `csv.Error` escape as raw tracebacks from a function that
  otherwise has a clean three-level exit-code contract (0 / 1 / 2).

## The five production scenarios

| Scenario | Behaviour | Verdict |
|---|---|---|
| **Network drops halfway through the 6-hour run** | `cmd_stats` makes **zero** network calls, so it cannot observe one directly. It reports on network-derived data with no provenance column, no run id, no error count. The *only* difference in the output is a larger `unreachable` — no denominator, no percentage, no threshold. And the damage is already permanent: `check_websites` overwrites `website_live` on every run (`enricher.py:250`) and `write_csv` atomically replaces the master (`main.py:130`), so the previous good verdicts are gone. Stats can report the loss but can never date it. | **unanswerable by design** |
| **A dependency returns garbage** | The only dependency is stdlib `csv`. Garbage *structure* (renamed/blank columns) → silent zeros, exit 0. Garbage *bytes* (a Latin-1 name from a scraped source) → `UnicodeDecodeError` traceback. A NUL byte in a field parses fine (checked — no finding). A plain-text log file passed by mistake → a full, plausible, all-zeros report, exit 0. | **worst case** |
| **Called with an empty list** | Handled correctly: `rows == []` → `"… is empty"` on stderr, return 1 (`cli.py:88-90`). Both a header-only file and a 0-byte file hit it. Verified exit 1 for both. | **correct** |
| **Called with a path that does not exist** | Handled correctly: return 2 (`cli.py:82-84`). Verified. | **correct** |
| **Interrupted** | Depends entirely on which signal. Measured (subprocess, blocked mid-read on a fifo, stdout redirected to a file): **SIGINT → rc 130, stderr `"\ninterrupted\n"`. SIGTERM → rc 143, stdout 0 bytes, stderr empty. SIGKILL → rc 137, stdout 0 bytes, stderr empty.** The reason is structural: the first `print` is at `cli.py:93`, six lines *after* the entire file has been materialised at `cli.py:87`. 100% of the wall time is the read; 0% produces output. **The only realistic production kill produces an empty log.** | **asymmetric** |

## Findings

### S1 — No freshness signal: a months-old file and a healthy file produce byte-identical reports

- **Where:** `cli.py:79-132` (nowhere); contrast `scrapers/base.py:27` and `main.py:39`
- **Breaks:** the report contains no timestamp, no file mtime, no file size, and no
  `max(scraped_at)`. `all_businesses.csv` is a **cumulative** master (`main.py:150`
  `load_master` merges every prior run), so the file `cmd_stats` opens is non-empty and
  plausible forever. Three distinct production failures all render identically to a
  healthy week: (a) the weekly cron has silently stopped for two months;
  (b) last night's run scraped **zero** records from all three sources — the master is
  unchanged, so every counter matches; (c) the run succeeded but every website probe
  returned `UNKNOWN`.
- **Trigger (verified, executed):** two 1-row files identical except
  `scraped_at=2026-10-03T00:00:00Z` vs `scraped_at=2024-01-01T00:00:00Z`. Both
  produced **byte-identical** 495-byte reports, both exit 0. Combined with
  `.github/workflows/scrape.yml`'s `cron: '0 3 * * 1'`, nothing in the output changes
  when the schedule stops firing.
- **Notice latency:** **unbounded.** The report carries no information that varies with
  age, so no amount of reading it surfaces the problem. This is the finding that makes
  the others dangerous rather than merely annoying.
- **Severity defence:** S1 because it is silent data loss in the reporting layer — the
  product's own QA gate is blind to a dead pipeline.
- **Fix:** three lines after `cli.py:93` — print `path.stat().st_mtime`, print
  `max(r.get("scraped_at") or "" for r in rows)`, and `return 1` if either is older
  than `2 × 7 days`.

### S1 — A renamed or dropped column makes all six contact counters read 0, and the command still exits 0

- **Where:** `cli.py:95-103` (`count` and its six call sites); no header validation
  anywhere in the function
- **Breaks:** `count()` is `(r.get(field) or "").strip()`. A missing column returns
  `None` for **every** row, so the sum is `0` — indistinguishable from "no business in
  this market has a phone number". The report still prints a header, a priority table
  and a region table, so it is *shaped* like a report. Nothing warns. Exit 0.
- **Trigger (verified, executed):** a 2-row file whose six counted headers were
  uppercased (`PHONE`, `EMAIL`, `WEBSITE`, `INSTAGRAM`, `WHATSAPP`, `REGION`):
  ```
  with phone      : 0     with email      : 0     with website    : 0
  with instagram  : 0     with whatsapp   : 0     with region     : 0
  ... by priority: high 2 ... by region: Unknown 2 ... >>> exit code = 0
  ```
  Sharper: renaming **only** `website` (leaving `website_live` alone) produces
  `with website: 0` on line 100 and `website live: 1 / website dead: 1` on lines 111-112
  — **live and dead sites for businesses that have no website**, in one report, six
  lines apart, exit 0.
- **Notice latency:** **weeks to never.** The reader must already suspect the schema to
  distrust a `0`; and because `0` also means "no phone numbers found", the natural
  reading is that the *data* is bad, not the *tool*.
- **Fix:** `expected = set(FIELDS)` (import is cheap — `cmd_stats` imports nothing today
  and `cmd_validate` has the same hole); `missing = expected - set(rows[0])`; print to
  stderr and `return 2` if non-empty. That also satisfies the schema check 037
  (`docs/audits/037-cli-design.md:335`) specified and never implemented.

### S1 — The report contradicts itself: `with website` and `unreachable` use two different definitions of "has a website", and nothing checks the sum

- **Where:** `cli.py:96` (strips), `cli.py:107-108` (does not require a website),
  `cli.py:110` (`r.get("website")`, **does not strip**) — three predicates, one column
- **Breaks:** the three website counters are computed independently of the
  `with website` counter, so `live + dead + unreachable ≠ with website` and the report
  never notices. `enricher.py:151-156` and `main.py:215-217` go to real trouble to keep
  `live/dead/unknown` honest; `cli.py` reinvents the arithmetic with looser predicates
  and drops the invariant. Note the divergence is inherited: `main.py:199`
  (`with_websites`) is unstripped like `cli.py:110`, while `cli.py:96` strips.
- **Trigger (verified, executed):**
  - `website="   "` (whitespace-only) + blank `website_live` →
    `with website: 0` **and** `unreachable: 1`.
  - Three rows with **no** website, two carrying `website_live="True"` and one `"False"`
    → `with website: 0`, `website live: 2`, `website dead: 1`. Three verdicts for zero
    websites. Exit 0.
  - `website_live` vocabulary drift (below) makes the sum short by 6 on a 10-row file.
- **Notice latency:** **days**, and only if the reader happens to do the arithmetic. A
  reader who trusts `unreachable` as "sites we failed to reach" will pitch rebuilds at
  businesses that have no site.
- **Fix:** derive all four numbers from one predicate, then assert it —
  `if live + dead + unreachable != count("website"): print(..., file=sys.stderr)`.

### S2 — Non-canonical `website_live` tokens fall into no bucket at all, silently converting `DEAD` into `UNKNOWN`

- **Where:** `cli.py:107-110`, exact `== "True"` / `== "False"` string comparison
- **Breaks:** a row whose `website_live` is `TRUE`, `FALSE`, `true`, `1`, `0`, `yes`,
  `Y`, or `"None"` is counted in **none** of live / dead / unreachable. This is not
  cosmetic: `main.py:118-119` deliberately writes these files as `utf-8-sig` "so Excel
  and Google Sheets … render Arabic business names correctly", i.e. the pipeline's own
  design **invites a human to open and edit them on Drive**. A Google Sheets autocorrect
  or a manual tidy that rewrites `False` → `FALSE` reclassifies a server-confirmed dead
  site as unknown, which `enricher.py:297-304` is explicit must **not** happen: a DEAD
  verdict is worth `+20` lead_score, the single largest signal in the model.
- **Trigger (verified, executed):** 10 rows with a website and
  `website_live` ∈ {`True`,`False`,`TRUE`,`FALSE`,`true`,`1`,`0`,`yes`,``,`None`}:
  ```
  with website    : 10
  website live    : 1
  website dead    : 1
  unreachable     : 1
  >>> exit code = 0
  ```
  Six verdicts vanish. `main.py:103` has the identical string coupling in `load_master`,
  so stats and the pipeline agree on the corruption — which means it is undetectable
  from either side.
- **Notice latency:** **weeks.** The report shows fewer dead sites, which reads as an
  improvement.
- **Fix:** parse tolerantly and count the unparseable residue:
  `v = raw.strip().lower(); if v in {"true","1","yes"} … elif v in {"false","0","no"} …`
  else count into a fourth `unrecognised: N` bucket and warn on stderr.

### S2 — `.most_common(8)` / `(12)` with no `+N more` line: the long tail is invisible, including a whole dead source

- **Where:** `cli.py:120` (source, cap 8), `cli.py:125` (region, cap 12),
  `cli.py:130` (pitches, cap 8)
- **Breaks:** dropped buckets are not counted anywhere else in the report, and no line
  reconciles the shown counts against `total`. A reader cannot distinguish "8 sources"
  from "14 sources, 6 hidden". The realistic production failure is worse than the
  cosmetic one: if `google_places` dies but OSM and Wikidata keep returning, `by source`
  simply loses a line and the remaining two grow — **which looks like progress.**
- **Trigger (verified, executed):** 114 rows over 14 distinct sources →
  ```
  by source:
    src_00  101 … src_07  1          # src_08 … src_13, silently dropped
  ```
  Same file: 14 regions → 12 shown, 14 pitches → 8 shown. Exit 0, no note.
- **Notice latency:** **unbounded** — the *absence* of a line is indistinguishable from
  the absence of data.
- **Fix:** `mc = Counter(...); shown = mc.most_common(8); print(shown); hidden = len(mc) - len(shown); if hidden: print(f"    … and {hidden} more ({sum(mc.values()) - sum(v for _, v in shown)} rows)")`.

### S2 — SIGTERM and SIGKILL produce a zero-byte log; every diagnostic is on stderr, so `>>` capture sees nothing

- **Where:** `cli.py:86-87` (read) vs `cli.py:93` (first print); `cli.py:83, 89`
  (both `file=sys.stderr`); `cli.py:314-318` (`except KeyboardInterrupt` only)
- **Breaks:** `cmd_stats` is advertised as interruptible — `main()` catches
  `KeyboardInterrupt`, prints `"\ninterrupted"` and returns 130 (`cli.py:316-318`). But a
  cron scheduler does not send SIGINT. `timeout(1)`, systemd `RuntimeMaxSec=`, Docker
  `stop`, and the OOM killer all send **SIGTERM or SIGKILL**, which Python cannot catch,
  and because stdout is block-buffered when redirected (verified:
  `sys.stdout.isatty() == False`, `line_buffering == False`) the unflushed buffer is
  discarded. Measured on a subprocess deliberately blocked mid-read:

  | Signal | returncode | stdout | stderr |
  |---|---|---|---|
  | SIGINT | `130` | **0 bytes** | `"\ninterrupted\n"` |
  | SIGTERM | `143` | **0 bytes** | *(empty)* |
  | SIGKILL | `137` | **0 bytes** | *(empty)* |

  Compounding it: the only two messages the function can emit (`cli.py:83`, `cli.py:89`)
  are both stderr. Verified — `leadminer stats data/all_businesses.csv > log.txt` writes
  **0 bytes** to `log.txt` (exit 2), and `leadminer stats <empty> > log.txt` writes
  **0 bytes** (exit 1). A cron that captures stdout only and does not test `$?` records
  an empty file for every failure mode in this report.
- **Notice latency:** **unbounded** unless the wrapper checks exit codes — and the log
  contains no hint of *why*.
- **Fix:** `signal.signal(signal.SIGTERM, lambda *_: sys.exit(143))` in `main()`, plus
  `sys.stdout.reconfigure(line_buffering=True)` at entry so partial reports survive.

### S2 — Blank cells render as unlabelled numbers; ragged rows render the literal string `None`

- **Where:** `cli.py:116` (`industry_priority`), `cli.py:120` (`source`),
  `cli.py:129` (`recommended_service`) — all use `r.get(field)` with no `or "Unknown"`,
  unlike `cli.py:124-125` which does have the `or "Unknown"` fallback
- **Breaks:** `csv.DictReader` yields `""` for a present-but-empty cell and `None` for a
  cell missing from a short row. `""` is a valid, truthy `Counter` key, distinct from
  `None`, so one logical bucket splits into two unlabelled ones and both print as a bare
  right-aligned number.
- **Trigger (verified, executed):**
  ```
  by priority:            by source:                 top pitches:
    high       4            osm           4           SEO audit          4
                 3                        3                         3      ← no label at all
  ```
  Ragged row (`name,phone,region` header, row of 8 fields against 23):
  ```
  by priority:  None       2
  by source:    None                         2
  top pitches:  None                                                 2
  ```
  Both exit 0. Note the inconsistency is inside one function: `by region` labels its
  missing bucket `Unknown`, the other three do not.
- **Notice latency:** **days.** A bare `3` next to `high 4` reads as a formatting
  artefact, not as "three businesses have no priority tag".
- **Fix:** factor `_label(v) = (v or "").strip() or "Unknown"` and use it at
  `cli.py:116, 120, 129` and `cli.py:124`.

### S2 — 1.07 GB peak RSS at 500k rows, 13 full passes, against a master that only ever grows

- **Where:** `cli.py:87` — `rows = list(csv.DictReader(f))` materialises every row as a
  23-key `dict`, then `count()` is called six times (`cli.py:98-103`), the live/dead/
  unknown block scans three more times (`cli.py:107-110`), and the four `Counter`
  comprehensions scan four more. Nothing is streamed; nothing is computed in one pass.
- **Breaks:** peak RSS is linear in a file that is itself monotonic — `main.py:150`
  accumulates every prior run and nothing in the repo ever rotates `data/` (it is
  gitignored). Measured on this machine, 23-column rows of realistic width:

  | rows | file size | peak RSS | wall |
  |---|---|---|---|
  | 1,000 | 0.3 MB | 18.9 MB | 0.02 s |
  | 200,000 | 65.5 MB | 437 MB | 2.55 s |
  | 500,000 | 165 MB | **1.07 GB** | 7.00 s |

  ≈2.1 kB/row. On `ubuntu-latest` (16 GB) this is fine today; in a 1 GB container or on
  a small cron VPS it OOMs at ~470k rows, and per the finding above the OOM kill is
  `SIGKILL` → **exit 137 and a 0-byte log**. `cmd_validate` (`cli.py:143`) has the
  identical pattern, so an operator running `stats` then `validate` pays it twice, and
  `cmd_score` (`cli.py:259` → `main.load_master`) a third time.
- **Notice latency:** **one bad cron night**, and the symptom (empty log) is
  indistinguishable from every other empty-log cause.
- **Fix:** fold all thirteen passes into one loop with a single `collections.Counter`
  per dimension, and iterate the reader rather than materialising it. This is the same
  conclusion 052 (`docs/audits/052-memory-streaming.md`) reached for the pipeline.

### S3 — The error surface is inconsistent: three unhandled exception types escape as tracebacks from an otherwise clean-exit-code command

- **Where:** `cli.py:81-87` (`path.exists()` then `open()`), `cli.py:314-318`
- **Breaks:** the function establishes a 0/1/2 exit-code contract for *two* failure
  modes and has no handler for the rest, so `main()`'s single `except` lets tracebacks
  through. Verified by execution:
  - path is a directory → `IsADirectoryError: [Errno 21] Is a directory: 'adir'`
    (`path.exists()` at `cli.py:82` returns `True` for directories).
  - a Latin-1 byte anywhere in the file → `UnicodeDecodeError: 'utf-8' codec can't
    decode byte 0xe9 in position 224`, raised lazily at `cli.py:87` *after* `open()`
    succeeded, so the traceback points at a `list()` call rather than at "bad file".
  - `path.exists()` followed by `open()` is a TOCTOU window; benign today only because
    `main.write_csv` replaces atomically (`main.py:130`), so the reader always sees a
    complete file.
  A NUL byte in a field was checked and parses fine — no finding.
- **Notice latency:** seconds, but the traceback is 15 lines of noise instead of the
  two-line message the function already has for a missing file.
- **Fix:** `except OSError as e` / `except UnicodeDecodeError` / `except csv.Error`
  around the open+read, each printing one line to stderr and returning 2.

### S3 — `"is empty"` is the wrong diagnosis for a header-only file, and `by priority` is the one uncapped loop

- **Where:** `cli.py:88-90`; `cli.py:116`
- **Breaks:** a CSV with a valid 22-column header and zero data rows is not empty —
  it is a *schema-correct, data-empty* master, which is precisely the shape of a run
  where every source returned nothing. The message conflates it with a 0-byte file. And
  `Counter(...).most_common()` at `cli.py:116` has **no cap at all**, unlike its three
  siblings: a hand-edited or corrupted `industry_priority` column makes that section
  unbounded, which is the only way `cmd_stats` can produce megabytes of stdout.
- **Trigger:** verified — both the header-only and the 0-byte file print
  `"<path> is empty"` and return 1; a 1-row file whose `industry_priority` cell is blank
  prints an unlabelled row.
- **Fix:** distinguish `len(reader.fieldnames or []) == 0` from `len(rows) == 0`, and
  cap `cli.py:116` at 12 for consistency with the region table.

## Not a bug, but worth knowing

- **`cmd_stats` importing nothing is the right call and should be preserved.** Verified:
  the compiled source contains zero `import` statements, so `stats` and `validate` run on
  a bare interpreter while `cmd_run` (`cli.py:35`) and `cmd_score` (`cli.py:249`) require
  `main`, which requires `requests` (`httpclient.py:43`). This is exactly why the
  operator reaches for `stats` when the environment is broken — so any fix must not
  introduce an import. (Reading `FIELDS` should therefore either come from a new
  dependency-free constants module or be duplicated as a literal with a test asserting
  it matches `main.FIELDS`.)
- **Atomic writes make the read side safe.** `main.write_csv` writes `.tmp`, `fsync`s,
  then `os.replace` (`main.py:121-133`), so `cmd_stats` can never observe a torn file.
  The TOCTOU at `cli.py:81-86` is therefore theoretical, not a live bug.
- **The tri-state `website_live` design is right and the comment at `cli.py:105-106`
  records the right historical bug.** Collapsing blank into `False` really was the
  original defect (see `enricher.py:145-156`). My complaint is the *string* coupling in
  S2 #4 and the missing sum assertion in S1 #3, not the three-bucket split.
- **`count()` is correct and should not be changed.** Verified across a ragged row, a
  blank cell and a whitespace-only cell: `(r.get(f) or "").strip()` is the right
  predicate for a contact-fill count. The bug is that `cli.py:110` does *not* use it.
- **A plain-text log file passed by mistake produces a full, plausible, all-zeros report
  at exit 0** (verified). Header validation (S1 #2) is the only thing that catches it.
- **`DATA_DIR` is CWD-relative** (`cli.py:26`, default at `cli.py:294`). From the wrong
  directory `leadminer stats` correctly prints `no such file: data/all_businesses.csv` and
  returns 2 (verified). Loud, therefore not a bug — but it means a cron's
  `PATH`/`cwd` is load-bearing, and the error names a path that may not be the one the
  operator meant.
- **The numbers are not machine-parseable.** `_fmt` emits thousands separators
  (`cli.py:30`) and there is no `--format json`, so the alert that would catch ledger
  rows 1-3 cannot be built from this output. 037 specified `--format json`/`markdown`
  (`docs/audits/037-cli-design.md:396`) and it was not implemented.
- **Only one test touches `cmd_stats`**
  (`tests/test_lead_signal.py:211-226`, the happy tri-state path) plus one asserting
  exit 2 on a missing file (`:255-264`). Nothing covers a renamed column, a ragged row,
  a blank priority, or a signal.

## Recommended order of work

1. **Add the freshness line and the missing-schema check.** Two guards, both a few
   lines, both turning ledger rows 1-4 from "never" into "seconds":
   print `path.stat().st_mtime` and `max(scraped_at)`; compare `set(rows[0])` against the
   22 contract columns and return 2 on a miss. Nothing else in this list matters as much.
2. **Assert the website invariant.** Derive `live`/`dead`/`unreachable` from the *same*
