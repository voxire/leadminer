# 075 — Containerisation for reproducible runs

## Verdict

Containerising `leadminer` is technically straightforward — a hash-pinned, non-root
`python:3.12-slim` image is a day's work — but for a `workflow_dispatch`/cron job on
GitHub's ephemeral `ubuntu-latest` runners it buys almost nothing over the existing
`setup-python@v5` + `uv pip install` path (`scrape.yml:17-26`), and it adds real cost.
The single genuinely valuable artifact in this lens is the **hash-pinned lockfile**, which is
independent of Docker and should be adopted first. Containerise only if you also want
local-dev parity or a long-lived worker; if you do, reuse the lockfile as the dependency
source and be aware of the non-root UID-vs-bind-mount gotcha on Linux hosts.

## The deliverable

### `requirements.in` (top-level pins, human-edited)

```
requests==2.32.3
beautifulsoup4==4.12.3
lxml==5.2.2
```

### Generate the hash-pinned lockfile (do this once, commit the result)

```bash
# in dev only — not inside the image, not in CI as a build step
pip install pip-tools
pip-compile --generate-hashes --output-file requirements.lock requirements.in
```

`pip-compile --generate-hashes` emits a `--hash=sha256:...` for **every** available artifact
(all wheels + the sdist) of all 8 resolved packages, so the single lockfile installs on
`linux/amd64` (the runner) *and* macOS dev boxes. The 8 packages are: the three direct pins
plus transitive `certifi`, `charset-normalizer`, `idna`, `urllib3`, `soupsieve`.

**Do not hand-copy hashes from this report or from a random blog.** The hash values are the
whole point of the mechanism; a wrong hash fails the build by design. Regenerate them with
the command above. The structure looks like this (hashes elided):

```
# This file is autogenerated by pip-compile with --generate-hashes.
requests==2.32.3 \
    --hash=sha256:<generated> \
    --hash=sha256:<generated>
beautifulsoup4==4.12.3 \
    --hash=sha256:<generated> \
    --hash=sha256:<generated>
lxml==5.2.2 \
    --hash=sha256:<generated> \
    --hash=sha256:<generated>
certifi==... \
    --hash=sha256:<generated>
# ... charset-normalizer, idna, urllib3, soupsieve
```

### `Dockerfile`

```dockerfile
# syntax=docker/dockerfile:1

# Build:  docker build --platform linux/amd64 -t leadminer .
# Run:    docker run --rm -v "$PWD/data:/app/data" \
#           -e GOOGLE_PLACES_API_KEY=... -e SCRAPER_EMAIL=... leadminer
#
# The minor tag floats on Debian patch releases. For full reproducibility pin the
# digest:  docker buildx imagetools inspect python:3.12-slim-bookworm
FROM python:3.12-slim-bookworm

# Belt-and-braces HTTPS egress. requests already ships certifi, so the scrapers
# (which use verify=True) work without this, but a CA bundle is cheap insurance.
RUN apt-get update \
    && apt-get install -y --no-install-recommends ca-certificates \
    && rm -rf /var/lib/apt/lists/*

# Non-root user with a fixed UID/GID for reproducible ownership.
RUN groupadd --gid 10001 app \
    && useradd --uid 10001 --gid app --create-home --shell /usr/sbin/nologin app

WORKDIR /app

# Dependencies FIRST so this layer caches independently of source churn.
# --require-hashes makes pip refuse any requirement that lacks a sha256, so a
# transitive dependency cannot drift without an explicit lockfile change.
COPY requirements.lock ./
RUN pip install --no-cache-dir --require-hashes -r requirements.lock

# Application source (see .dockerignore for exclusions).
COPY --chown=app:app . .

# main.py:41 writes the five CSVs to ./data relative to CWD (= /app/data here).
# Owned by app so a named volume inherits the correct owner on first use.
RUN mkdir -p /app/data && chown -R app:app /app/data
VOLUME ["/app/data"]

USER app
ENV PYTHONUNBUFFERED=1 \
    PYTHONDONTWRITEBYTECODE=1

# Ceremonial for a one-shot batch job — Docker only consults HEALTHCHECK for a
# long-running container, so this never fires on `docker run`. It confirms PID 1
# is still the scraper (detects a crash-to-shell), not that the scraper is
# making progress. See finding F3.
HEALTHCHECK --interval=30s --timeout=5s --start-period=15s --retries=3 \
    CMD grep -q main.py /proc/1/cmdline || exit 1

CMD ["python", "main.py"]
```

### `.dockerignore`

```
.git
.gitignore
data/
docs/
**/__pycache__/
*.pyc
.env
.venv/
venv/
*.egg-info/
```

`data/` is excluded deliberately: the container must not bake a stale master into the image,
and the host's `data/` is what gets mounted (or downloaded) at run time.

### `docker-compose.yml` (local dev only)

```yaml
services:
  scrape:
    build: .
    environment:
      GOOGLE_PLACES_API_KEY: ${GOOGLE_PLACES_API_KEY:?set in .env}
      SCRAPER_EMAIL: ${SCRAPER_EMAIL:-voxire.tech@gmail.com}
    volumes:
      - ./data:/app/data
```

### Running it in the cron job

```yaml
      - name: Build image
        run: docker build --platform linux/amd64 -t leadminer .

      - name: Run scraper in container
        env:
          GOOGLE_PLACES_API_KEY: ${{ secrets.GOOGLE_PLACES_API_KEY }}
          SCRAPER_EMAIL: ${{ secrets.SCRAPER_EMAIL }}
        run: |
          docker volume create leadminer-data || true
          docker run --name leadminer-run \
            -e GOOGLE_PLACES_API_KEY="$GOOGLE_PLACES_API_KEY" \
            -e SCRAPER_EMAIL="$SCRAPER_EMAIL" \
            -v leadminer-data:/app/data \
            leadminer
          docker cp leadminer-run:/app/data ./data
          docker rm leadminer-run
```

The named volume is owned `app:app` from the image (no host-UID coupling), and `docker cp`
hands the five CSVs back to the runner so the existing rclone upload steps
(`scrape.yml:46-50`) keep working unchanged.

## Findings

### F1 (S2) — The lockfile, not the Dockerfile, is the reproducibility fix

- **Where:** `requirements.txt:1-3` — three direct pins, no lockfile, no hashes, no transitive
  pins.
- **Breaks:** "Reproducible" in the Docker sense. Pinning `requests==2.32.3` does **not** pin
  `urllib3`, `certifi`, `idna`, `charset-normalizer`, or `soupsieve`; a `pip install` today and
  next month can resolve different transitive versions, and any of them is an unpinned supply
  chain surface. This is true *inside* the container exactly as much as it is today on the
  runner.
- **Trigger:** `pip install --require-hashes -r requirements.lock` fails loudly the moment any
  requirement lacks a hash — which is precisely the behaviour you want, and which the current
  `requirements.txt` cannot provide.
- **Fix:** generate `requirements.lock` with `pip-compile --generate-hashes` (above) and commit
  it. This is the artifact that makes both the Docker build *and* the existing `uv` install
  reproducible, so do it first and let the Dockerfile consume the same file.

### F2 (S2) — Non-root UID collides with the runner's bind-mount ownership

- **Where:** `Dockerfile` `USER app` (uid 10001) vs. the GitHub runner user (uid 1001) vs.
  `scrape.yml:35-50` which reads/writes `data/` on the host.
- **Breaks:** If you bind-mount the host's `data/` (`-v "$PWD/data:/app/data"`), the directory
  is owned by the runner's uid 1001, but the process runs as uid 10001, so
  `main.py:208` (`DATA_DIR.mkdir`) and every `write_csv` (`main.py:122-130`) fail with
  `PermissionError`. macOS Docker Desktop hides this (VirtioFS lets the write through), so it
  shows up only on the Linux runner — the worst place for it to surface.
- **Trigger:** any bind-mount of a host-owned directory into the non-root container on a Linux
  host.
- **Fix:** don't bind-mount. Use a Docker named volume (owned `app:app` from the image) and
  `docker cp` the CSVs out, exactly as in the workflow snippet above. The alternative
  (`--user "$(id -u):$(id -g)"` plus a world-writable `/app/data`) also works but couples the
  image to the runner's uid and needs a `chmod 0777`.

### F3 (S2) — A HEALTHCHECK is a no-op for a batch job; liveness is the exit code

- **Where:** `Dockerfile` `HEALTHCHECK` vs. the job model (`main.py` runs, writes CSVs, exits;
  `scrape.yml:11` bounds it at 300 minutes).
- **Breaks:** nothing, but it is cargo-cult. Docker only executes a `HEALTHCHECK` for a
  container started detached (`docker run -d` / compose / swarm). A one-shot `docker run`
  — which is what a GitHub Actions step does — runs the container to completion and looks at
  the exit code; the healthcheck is never consulted. Even if it were, `grep main.py
  /proc/1/cmdline` proves the process is *alive*, not that it is *progressing*: a scraper hung
  in a socket read still passes.
- **Trigger:** running `docker run leadminer` in CI — the healthcheck is silently ignored.
- **Fix:** treat the healthcheck as documentation, not a control. The real liveness signals are
  (a) a non-zero exit code, (b) the job `timeout-minutes: 300`, and (c) progress output already
  printed by `main.py` (`[Enricher] … done` at `enricher.py:254`, per-source counts at
  `main.py:164-170`). If you genuinely need a heartbeat (self-hosted long-lived worker), have a
  wrapper touch a `/tmp/heartbeat` file and point the healthcheck at that — but for the cron
  this is over-engineering.

### F4 (S3) — rclone still lives outside the container

- **Where:** `scrape.yml:26,28-50` installs `rclone` via apt and stages the Drive credential in
  `~/.config/rclone`; the Dockerfile does not (and should not need to) contain rclone.
- **Breaks:** the clean story "one container = one reproducible unit." The container produces
  CSVs; downloading the master and uploading the result is still host-side `rclone`, so
  containerising the scrape removes none of the credential-handling concerns raised in
  `039-github-actions-hardening.md` (plaintext `rclone.conf`, un-bounded transfer times). You
  *could* bake rclone into the image, but then the non-root user must be able to read the
  mounted config and you have a second thing to rebuild/audit.
- **Trigger:** any change to the Drive upload flow still has to touch the workflow, not the
  image.
- **Fix:** keep rclone on the host. The container is only responsible for the pure Python
  scrape → CSVs; Drive I/O stays exactly where it is today.

### F5 (S3) — Egress must stay wide open, which caps how "hardened" the image can be

- **Where:** the scrapers POST/GET to Overpass (`osm.py:8`), Wikidata (`wikidata.py:8`), and
  Google Places (`google_places.py:29`), and the enricher fetches **one arbitrary business
  website per record** at 40 workers (`enricher.py:217-254`).
- **Breaks:** any idea of a network-restricted container. You cannot sandbox egress to a small
  allowlist — the whole point is to hit tens of thousands of unknown third-party hosts. A
  non-root user and a slim image are fine, but they buy little against the actual risk surface
  (SSRF / hostile HTML), which is a code-level problem already covered in
  `008-enricher-ssrf-security.md` and `054-politeness-and-ssrf.md`, not a container problem.
- **Trigger:** someone adds `--network=none` or a tight egress policy "for security" and the
  run silently returns zero `website_live` signals.
- **Fix:** don't attempt egress restriction. If you containerise, keep `network: default`; spend
  the security budget on the SSRF hardening, not the image.

## Is this worth it? (the honest tradeoff)

For a **cron job on GitHub Actions**, containerising is *not* worth it. Here is the accounting.

**What a container actually gives you here:**

| Claim | Reality |
|---|---|
| "Pinned Python" | Already pinned: `setup-python@v5` with `python-version: '3.12'` (`scrape.yml:18-20`). A digest-pinned `python:3.12-slim` pins the *patch*, which is marginally stronger but nobody has reported a Python patch regression here. |
| "Reproducible deps" | Only the **lockfile** delivers this — and it works identically with `uv pip install` on the runner, no container needed. |
| "Non-root" | The runner already runs your job as a non-root `runner` user; `sudo` is used only for the rclone install (`scrape.yml:26`). Real, but marginal. |
| "Same everywhere" | Genuine value: local dev and CI run the identical interpreter + OS. This is the one defensible reason to containerise. |
| "Immutable artifact" | Genuine but low-value for a 1,402-LOC script with zero tests that already resolves deps in ~10s. |

**What it costs:**

- A build/push pipeline for the image (or a ~1–2 min cold `docker build` inside every run,
  since GitHub's layer cache across runs is weak without buildx + a cache backend).
- The non-root/bind-mount UID trap (F2) and the `docker cp` dance to get CSVs back to the
  runner for rclone.
- A second place to update when Python or deps change, and an extra artifact to audit
  (`039`'s pip-audit gate still has to point at the lockfile, not the image).
- The false confidence of a `HEALTHCHECK` that never runs (F3).

**Bottom line:** the valuable, low-risk change is the hash-pinned `requirements.lock`, adopted
in the *existing* workflow via `pip install --require-hashes -r requirements.lock` (or
`uv pip install --require-hashes`). That alone makes runs reproducible, shuts the transitive
supply-chain gap, and costs one committed file. Containerise only if and when one of these
becomes true: you want local-dev/CI parity, you move off GitHub hosted runners to a
self-hosted host where image immutability matters, or the job grows into a long-lived worker.
If you containerise, the Dockerfile above is correct and the lockfile is the shared source of
truth — so do the lockfile first either way.

## Not a bug, but worth knowing

- The Docker volume **cannot** provide persistence for the cron. `ubuntu-latest` runners are
  ephemeral, so a named volume dies with the runner. The cumulative master already persists
  through the rclone download/upload (`scrape.yml:35-38,46-50`) — that is the real persistence
  layer, and it must stay. The volume is just scratch space for the run.
- `enricher.py:167` still does `verify=False`. Inside a container this is unchanged — the
  image is not a mitigation. It is already flagged in `038-ci-cd-pipeline.md` (S3) and should
  be fixed at the source regardless of packaging.
- `main.py:129` calls `os.fsync` on the CSVs. On overlayfs this still works (it forces a write
  to the backing store), so the atomic-write behaviour in `write_csv` (`main.py:108-134`)
  survives containerisation with no change.
- `scrapers/google_places.py:26` imports `from enricher import infer_region` (a top-level
  import above the package). It works with `WORKDIR=/app` because the repo root is on
  `sys.path`, but it means the image is not a self-contained installed package — `COPY . .` of
  the whole tree, which the Dockerfile does, sidesteps this. Don't try to install a wheel into
  the image until the package is properly laid out (`038` already plans this).

## Recommended order of work

1. **Add `requirements.in` + generate `requirements.lock` with hashes** (`pip-compile
   --generate-hashes`) and commit it. Switch the existing workflow to
   `pip install --require-hashes -r requirements.lock` (or `uv pip install --require-hashes`).
   This is the reproducibility fix and it is container-independent.
2. **Decide: do you actually need a container?** If the only goal is reproducible cron runs,
   stop at step 1. Revisit the Dockerfile only when local-dev/CI parity or a self-hosted/long-lived
   worker becomes a real requirement.
3. If containerising: add the `Dockerfile` + `.dockerignore` + `docker-compose.yml` above,
   build with `--platform linux/amd64`, and run via a named volume + `docker cp` (never a
   bind-mount on the Linux runner) per F2.
4. Keep rclone on the host (F4); do not try to bake Drive credentials into the image.
5. Treat `HEALTHCHECK` as documentation only (F3); rely on exit codes + the 300-min job timeout,
   and fix `verify=False` (`enricher.py:167`) at the source rather than hoping the image helps.
