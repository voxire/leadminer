# 218-x — `cmd_scrape` (`cli.py:40`): the operator's only per-source diagnostic, and the test cases it still needs

## Verdict

`cmd_scrape` is the one command whose stated job is to answer "did this source break?"
(`cli.py:41-45`), and it cannot. Three materially different outcomes — the source answered and
genuinely had nothing, the transport failed, the API key is missing — all collapse to
`return 1` and the single message `"WARNING: zero records. The source may be broken or blocked."`
(`cli.py:63-66`). On top of that, its two headline quality numbers (`cli.py:69-70`) are provably
wrong: `"---"`, `"n/a"`, `"  "` and `"ext 4"` all count as phones, `normalize_phone` maps every one
of them to `""` (`dedup.py:30,45-46`), and `cmd_stats` on the *same rows* prints a *different*
number. `tests/test_lead_signal.py` has **zero** tests for this function (`087-SYNTH-test-gap.md:19`
already flagged the omission); 13 test cases are specified below, 11 of which pin a bug this
repository has already paid for once.

---

## Findings

### S1 — Zero records is reported identically for "broken", "empty" and "unconfigured"

- **Where:** `cli.py:63-66`
- **Breaks:** All three scrapers swallow failure and return an *empty generator*:
  `osm.py:47-56` (`print("[OSM] FAILED after N attempts…"); return`),
  `wikidata.py:79-85`, and `google_places.py:169-171`
  (`"[Google] GOOGLE_PLACES_API_KEY not set, skipping."; return`). `cmd_scrape` receives `[]` in
  every case and has no way to tell them apart, because the failure signal was consumed as a
  `print`. This is the exact bug the shared HTTP layer was built to kill
  (`httpclient.py:16-19`: *"Everything was `print` then a silent `return`, so a source that stopped
  working looked exactly like a source that had nothing to return"*) — and it is alive again in the
  one command whose docstring promises to detect it.
- **Trigger (verified locally, no network):** a `GooglePlacesScraper` whose `scrape()` does exactly
  what `google_places.py:169-171` does, with `GOOGLE_PLACES_API_KEY` unset. Output:
  ```
  [Google] GOOGLE_PLACES_API_KEY not set, skipping.
  [google_places] 0 records
    WARNING: zero records. The source may be broken or blocked.
  ```
  `rc == 1`. An operator who runs `leadminer scrape --source google_places` before a paid run gets a
  *network-sounding* message for a *missing environment variable*, and the generic code `1` instead
  of `3` (`EX_CONFIG`) from the project's own exit-code matrix (`037-cli-design.md:461`).
  Same collapse for `osm.py:51-55`'s `FAILED after 3 attempts: HTTP 504`.
- **Fix:** Have the scrapers return a typed outcome (or accept an injected `on_status` callback) and
  make `cmd_scrape` exit `3` for config, `4` for transport (`037-cli-design.md:462`), `1` only for a
  source that answered with zero rows — each with its own message.

### S1 — `with phone` / `with site` are not fill rates, and `cmd_stats` disagrees with them

- **Where:** `cli.py:69-70`
- **Breaks:** `if r.get("phone")` is a bare truthiness test, so `"---"`, `"n/a"`, `"  "`, `"ext 4"`,
  `"info"`, `"0"`, `"+"`, `"tel:"` all count as contactable. Every one of them is junk by the
  repository's own definition: `normalize_phone` returns `""` for all of them
  (`dedup.py:30` `_MIN_DIGITS = 7`, `dedup.py:45-46`) and that invariant is already pinned by
  `tests/test_lead_signal.py:103-108` (regression for audit 001, where `"---"` and `"..."` both
  normalized to `"+"` and merged unrelated businesses into one dedup row).
- **Trigger (verified locally, no network):**
  ```python
  ROWS = [{"name": "A", "phone": "70123456", "website": "https://a.example", "country": "LB"},
          {"name": "B", "phone": "  ",     "website": "  ",               "country": "LB"},
          {"name": "C", "phone": "n/a",    "website": None,               "country": "LB"}]
  ```
  ```
  cmd_scrape rc: 0        cmd_stats |   with phone      : 2
  [osm] 3 records                        cmd_stats |   website live    : 0
    with phone : 3
    with site  : 2
  ```
  The same three rows, written to a CSV and read back (`load_master` preserves `"  "` because
  `main.py:88` only maps `""` → `None`), give **`with phone : 3` from `scrape` and `with phone : 2`
  from `stats`**. Two offline commands, same data, same predicate, different answers. That is the
  same defect class as `resolve_country` (`main.py:54-57`: *"`record.get("country", "LB")` looks
  correct but is not"*), pinned at `tests/test_lead_signal.py:126-133`.
- **Consequence beyond the report:** the identical unvalidated truthiness slices the exports —
  `main.py:199` (`with_websites`) and `main.py:202-205` (`sales_ready` via `has_any_contact`,
  `main.py:137-145`). A whitespace-only "phone" gets a row into `with_websites.csv` and a phantom
  completeness point (`enricher.py:103-104`).
- **Fix:** Extract one `_is_present(value)` predicate and use it in `cmd_scrape`, `cmd_stats`
  (`cli.py:96`), `main.py:199-205` and `completeness_score`; for phones specifically, gate on
  `normalize_phone(v, country)`.

### S2 — `with site` is presented as a quality metric that does not exist at scrape time

- **Where:** `cli.py:70`
- **Breaks:** Every scraper hard-codes `website_live=None` (`osm.py:109`, `wikidata.py:117`,
  `google_places.py:292`) because liveness is only known after enrichment
  (`enricher.py:225-276`). So at scrape time the number is *always* "unchecked", yet it prints as a
  bare `with site : 4,000`, one line above a category table an operator will read as a quality
  ranking. `liveness` is the tri-state this codebase treats as its most important signal
  (`enricher.py:145-156`, `tests/test_lead_signal.py:71-99`, `cli.py:105-113`: *"Collapsing blank
  into False was the original bug"*). `cmd_scrape` drops the axis entirely rather than labelling it.
- **Trigger:** `[{"website": "https://a.example", "website_live": None}]` → `with site : 1`, no hint
  that the site was never fetched.
- **Fix:** Print `with site  : 4,000  (liveness not yet checked)`.

### S2 — No exception handling: any scraper failure is a traceback, not an exit code

- **Where:** `cli.py:61`, and `cli.py:314-318` which catches only `KeyboardInterrupt`
- **Breaks:** `list(registry[args.source]().scrape())` propagates anything the generator raises.
  Note this is the *opposite* of `main.py:167-168`, which catches the worker exception, prints to
  stderr and **continues** — the reason a full pipeline reports success while a source is dead
  (`037-cli-design.md:17-21`, "exits 0 in CI"). The diagnostic command has no diagnostic behaviour.
- **Trigger A (verified locally):** `scrape()` yields one record then `raise RuntimeError("overpass 504")`
  → `RuntimeError: overpass 504` escapes `cmd_scrape`; `main()` does not catch it; Python exits 1
  with a stack trace. The one record already produced is discarded (the raise happens at
  `cli.py:61`, before any `print`).
- **Trigger B (verified locally, the subtle one):** any **2xx** response whose body is not JSON.
  `fetch_with_retry` sets `ok = resp.status_code < 400` (`httpclient.py:184`), so a `200` carrying
  `b"<!DOCTYPE html><html>Overpass: rate limited…"` passes the gate, and `osm.py:58`'s
  `result.json()` then raises `json.JSONDecodeError: Expecting value: line 1 column 1 (char 0)`.
  `wikidata.py:87` has the same shape. A corporate proxy or captive portal produces a traceback
  instead of "wikidata returned HTML, not JSON".
- **Fix:** Wrap `cli.py:61` in `try/except Exception` → print `f"[{source}] FAILED: {type(e).__name__}: {e}"`
  to stderr and return `4`.

### S2 — The report cannot be reconciled with `data/all_businesses.csv`

- **Where:** `cli.py:62`, `cli.py:68` — versus `main.py:172` and `main.py:204`
- **Breaks:** `cmd_scrape` applies no whitelist filter and never says it didn't, so `N records` is a
  pre-filter number. Measured against a hand-built vocabulary of 41 realistic Google types, 10 are
  dropped by `is_business_category` at `main.py:172` and would still be counted and categorised by
  `cmd_scrape`:
  `lebanese_restaurant`, `seafood_restaurant`, `fast_food_restaurant`, `pizza_restaurant`,
  `italian_restaurant`, `hair_care`, `doctor`, `event_venue`, `photographer`, `coworking_space`
  (still-live residue of `087-SYNTH-test-gap.md:31-52`). Worse, two of the survivors are
  *silently deprioritised*: `industry_priority("real_estate_agency") == "low"` while
  `industry_priority("real_estate_agent") == "high"` (verified), and Google emits the `_agency`
  spelling — so `leadminer scrape --source google_places` prints a top-10 table led by
  `real_estate_agency` while `main.py:204` excludes every one of those leads from
  `sales_ready.csv`. This is the exact cost of the whole `087` whitelist class, and `cmd_scrape` is
  the only place an operator would ever notice it.
- **Fix:** Print both numbers, e.g. `41 records (31 after whitelist, 12 lead-priority)`.
  (My 41-type vocabulary is my own, so treat the *ratio* as indicative, not as a production number.)

### S3 — The category table is non-deterministic on ties and silently truncates

- **Where:** `cli.py:68`, `cli.py:74`
- **Breaks (two independent defects):**
  1. `Counter.most_common` is stable on *insertion* order, so ties print in input order. Verified:
     `[{"category":"aaa"}]*5 + [{"category":"bbb"}]*5` prints `aaa` first; the permutation prints
     `bbb` first — `identical? False`. For `google_places` the input order is thread-completion
     order (`google_places.py:194-199`), so two runs over identical data print different tables. The
     repository has an explicit, tested determinism standard elsewhere: `dedup.py:184`
     (`str(value),  # deterministic final tiebreak`) and `tests/test_lead_signal.py:292-295`
     `test_merge_is_order_independent`, added in commit `99493b9`
     (*"fix: per-field merge survivorship instead of whole-record richness"*).
  2. `most_common(10)` with no remainder line. Verified: 12 distinct categories → prints `c0..c9`
     and drops `c10`, `c11` with no indication. Google emits hundreds of distinct `_pick_category`
     outputs (`google_places.py:324-328`).
- **Fix:** `sorted(by_cat.items(), key=lambda kv: (-kv[1], str(kv[0])))[:10]` and print
  `f"  ... and {len(by_cat) - 10} more categories"`.

### S3 — `from scrapers.base import BaseScraper  # noqa: F401 (import check)` checks nothing

- **Where:** `cli.py:46`
- **Breaks:** The name is never used. `scrapers.osm:5` already does `from .base import ...`, so
  `scrapers.base` is imported transitively before line 47 runs; the import cannot fail independently
  and never validates anything. It reads like a contract check and is a no-op — the dead-code /
  type-contract class from `046-dead-code-simplification.md` and `020-type-contract-import-cycle.md`.
- **Second cost:** lines 47-49 import **all three** scrapers unconditionally, even though only one
  is requested, so `leadminer scrape --source osm` breaks if `requests` is missing or broken.
  Verified in this checkout: `python3 -c "import requests"` → `ModuleNotFoundError`, so `cmd_scrape`
  is *unreachable* without a stub. That is why it has no tests today, and it is the single biggest
  obstacle to writing them.
- **Fix:** Hoist the registry to a module-level `SCRAPERS: dict[str, type[BaseScraper]]` with lazy
  per-key imports, so it is introspectable and testable, and drop the vacuous import.

### S3 — Scraper progress output is merged into the report on stdout

- **Where:** `cli.py:62` (report → stdout) versus `osm.py:33`, `osm.py:59`, `wikidata.py:88`,
  `google_places.py:176-179`, `google_places.py:257` (progress → stdout)
- **Breaks:** `leadminer scrape --source osm | tail -5` shows `[OSM] Got 18422 elements.` instead
  of the report, and `2>/dev/null` does not suppress it. `037-cli-design.md:35-39` and its
  "Not a bug but worth knowing" §1 (`037-cli-design.md:631`) require logs on stderr and stdout
  reserved for data.
- **Fix:** report → stdout, scraper chatter → stderr (a `contextlib.redirect` in the command is not
  enough; the scrapers need a logger).

## The exact test cases `cmd_scrape` still needs

**Shared fixture — mandatory, and the reason there are no tests today.** `cli.py:47-49` imports all
three scraper modules unconditionally, and `requests` is not installed in this checkout, so a test
must install fakes into `sys.modules` *before* calling:

```python
# tests/test_lead_signal.py — add to TestCli (after line 264)
    def _fake_sources(self, records):
        """Replace all three scraper modules so cmd_scrape can be exercised offline.
        Required: cli.py:47-49 imports all three unconditionally, and `requests`
        is not installed in a bare checkout (ModuleNotFoundError)."""
        import types
        for name, attr in (("osm", "OSMScraper"),
                           ("wikidata", "WikidataScraper"),
                           ("google_places", "GooglePlacesScraper")):
            mod = types.ModuleType(f"scrapers.{name}")
            cls = type(name, (), {"scrape": lambda self: iter(records)})
            setattr(mod, attr, cls)
            sys.modules[f"scrapers.{name}"] = mod
        self.addCleanup(
            lambda: [sys.modules.pop(f"scrapers.{n}", None)
                     for n in ("osm", "wikidata", "google_places")])

    def _run_scrape(self, source="osm", **ns):
        import contextlib, io
        from cli import cmd_scrape
        ns.setdefault("source", source)
        out, err = io.StringIO(), io.StringIO()
        with contextlib.redirect_stdout(out), contextlib.redirect_stderr(err):
            rc = cmd_scrape(argparse.Namespace(**ns))
        return rc, out.getvalue(), err.getvalue()
```

Each entry below gives the **test method name**, the **literal input**, the **asserted output**, and
the **past bug it pins**. Properties are stated over an explicit input domain inside one test method
— deterministic, stdlib-only, and matching the house style at `tests/test_lead_signal.py:106`.

## What genuinely cannot be tested here, and why

1. **That any real scraper returns anything.** Every test above must replace
   `sys.modules["scrapers.osm"|"wikidata"|"google_places"]`, so `cli.py:61`'s
   `registry[args.source]().scrape()` is *never* the real one. No offline test can prove
   `leadminer scrape --source osm` returns >0 rows against Overpass tonight. Only the exit-code and
   report contract is testable — that is the whole honest scope of this function's test surface,
   and it is still worth 14 tests because that contract is where every bug above lives.
2. **`BaseScraper` runtime conformance from inside `cmd_scrape`.** The registry is a function-local
   dict and the ABC (`scrapers/base.py:31-33`) is only enforced at instantiation. Testing it
   offline requires hoisting the registry (test 14). It cannot be tested through `cmd_scrape` as
   written.
3. **Wall-clock and money.** 68 queries × a 180 s per-query budget × 5 workers. Asserting
   "`scrape` returns within a minute" requires actually paying for it. The only offline proxy is
   the parser property in test 13A — the runtime half (13B) can be proven with a fake generator, but
   the *cost* claim cannot be.
4. **The exact interleaving of the real scrapers' prints with the report.** `google_places` prints
   from 5 worker threads (`google_places.py:257`, inside `fetch_query`), so byte-level output
   ordering is not reproducible offline. Test 12 pins the part that *is* deterministic — the stream
   discipline (progress → stderr, report → stdout) — with a single-threaded fake.
5. **Whether Overpass/Wikidata ever actually return HTML with a 200.** Test 5B injects a fake session
   to pin the `result.ok` + `result.json()` contract at `httpclient.py:184` / `osm.py:58`. That the
   upstream behaves this way in production is a network fact, not a code fact, and is out of scope
   for an offline suite.
6. **Property-based testing in the usual `hypothesis` sense is awkward here**, because `cmd_scrape`
   writes to the real `sys.stdout`. I have therefore expressed every property above as an explicit
   input domain inside a single `unittest` method — deterministic, stdlib-only, and matching
   `tests/test_lead_signal.py:106`. `hypothesis>=6.100` is available (`pyproject.toml` dev extras)
   and is the natural upgrade once the report is emitted as a structured value instead of
   `print` calls.

**Harness hazard that will bite whoever writes test 5.** The existing `_stub_requests()` shim
(`tests/test_lead_signal.py:23-63`) sets `mod.Session` and `mod.exceptions` but **not**
`mod.RequestException` (verified: `hasattr(mod, "RequestException") == False`). Both
`httpclient.py:176` and `google_places.py:250` say `except requests.RequestException:`, so any
failure-path test that goes through those handlers will raise `AttributeError` instead of the
exception it means to test. Extend the shim before writing test 5, or the failure path stays
untestable.

## Not a bug, but worth knowing

- **`cli.py:56-59` is dead code in production and alive only in tests.** Argparse `choices`
  (`cli.py:290`) rejects an unknown `--source` before `cmd_scrape` runs (verified `SystemExit: 2`).
  Do not "clean it up" — it is the only thing between a future refactor that drops `choices` and a
  `KeyError` at `cli.py:61`, and test 6 is the only thing that covers it.
- **`with site` counting `"  "` is a `main.py` defect, not a `cli.py` one.** `main.py:199`
  (`with_websites = [r for r in records if r.get("website")]`) puts whitespace-only URLs in the
  export, and `enricher.py:107-108` awards them a completeness point. `cmd_scrape` only makes it
  visible. Fix it in one place (`main.py`) and both commands follow.
- **Nothing runs these tests.** `.github/workflows/scrape.yml` has no test step; its only execution
  step is `run: python main.py` (`.github/workflows/scrape.yml:69`). The CLI is not what CI uses, so
  even a perfect test suite is unenforced until a job runs
  `python3 -m unittest discover -s tests -v`. That job is worth more than any single test here.
- **Keep new tests stdlib-only.** `pyproject.toml` sets `[tool.pytest.ini_options] testpaths = ["tests"]`
  and the suite is `unittest`-based with a manual `sys.path.insert` (`tests/test_lead_signal.py:20`),
  matching `087-SYNTH-test-gap.md:620`. Do not introduce a pytest-only import.
