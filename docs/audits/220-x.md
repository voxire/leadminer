# 220 — `cmd_scrape` contract drift: declared types vs. actual vs. what the diagnostic reports

## Verdict

`cmd_scrape` (`cli.py:40-76`) is the project's only per-source health instrument, and it
reports a shape the pipeline never produces. It applies none of the four acceptance
criteria `main()` applies — whitelist, dedup, `normalize_phone`, URL validity — so a source
that contributes **zero** rows to `sales_ready.csv` prints a healthy record count and
**exits 0**. Simultaneously it is the only caller of `BaseScraper.scrape()` with no
`try`/`except`, so a mid-iteration scraper failure escapes as a traceback whose exit code
is indistinguishable from "zero records". Both directions make the same exit code mean
"fine" or "broken" depending on which failure occurred.

Underneath: the `BusinessRecord` contract it claims to depend on is enforced by nothing.
`TypedDict` is runtime-inert (proven below), the JSON envelope is typed `Any`
(`httpclient.py:110`), and `pyproject.toml:64-68` declares `mypy strict = true` while the
only CI job runs `python main.py` with **no lint, typecheck, or test step at all**.

---

## Declared vs. actual: field by field

`cmd_scrape` reads exactly three keys — `category` (`cli.py:68`), `phone` (`cli.py:69`),
`website` (`cli.py:70`) — plus `len(records)` (`cli.py:62`). All three are in
`BusinessRecord`. For those three the declared types are *honoured* by all three scrapers:

| Key | Declared (`scrapers/base.py`) | OSM | Wikidata | Google Places |
|---|---|---|---|---|
| `category` | `str \| None` (:7) | `str \| None` (`osm.py:72-78`) | `str \| None`, **genuinely `None`** — `?categoryLabel` is OPTIONAL (`wikidata.py:35-39, 100`) | `str`, never `None` (`_pick_category` falls back to `"business"`, `google_places.py:328`) |
| `phone` | `str \| None` (:13) | raw tag (`osm.py:89`) | `_strip_prefix` → `str \| None` (`wikidata.py:97`) | `nationalPhoneNumber` (`google_places.py:289`) |
| `website` | `str \| None` (:15) | raw tag, `https://` prefix only if missing (`osm.py:91-96`) | same (`wikidata.py:103-104`) | `websiteUri` (`google_places.py:291`) |

So for the three fields it reads, **the declared types are correct**. The mismatch is not
in the schema of these three keys — it is in what a `str | None` value *means* downstream
(S2-1, S2-2) and in the 20 keys it ignores (S3-3).

For completeness, the other 20 keys at scrape time (all `BusinessRecord(...)` construction
sites: `osm.py:98-122`, `wikidata.py:106-130`, `google_places.py:281-305`):

- **Hardcoded constants declared as definite, non-nullable types** —
  `lead_score: int` (:25) is literal `0` at all three sites (`osm.py:118`,
  `wikidata.py:126`, `google_places.py:301`); `completeness_score: int` (:28) likewise
  (`osm.py:121`, `wikidata.py:129`, `google_places.py:304`).
- **Always `None` at scrape time** — `website_live` (:16), `industry_priority` (:23),
  `recommended_service` (:24). Plus `region` (:9) is `None` for OSM (`osm.py:102`) and
  Wikidata (`wikidata.py:110`), and `whatsapp` (:19) / `linkedin` (:20) are `None` for
  those two sources even though OSM carries a `contact:whatsapp` tag that
  `osm.py:112` never reads.
- **Declared `str | None` but never `None`** — `name` (guarded non-empty at `osm.py:64`,
  `wikidata.py:92`, `google_places.py:269`) and `country` (always `"LB"` or `"SA"`,
  `google_places.py:127-136`). `country: str | None` is the exact declaration that caused
  the documented `resolve_country` bug (`main.py:53-58`): if it had been `country: str`,
  the `record.get("country", "LB")` mistake would have been a type error instead of a
  silent `None` across the whole master.
- **`lat` / `lon` / `rating` / `review_count` are unchecked `Any` in practice** — they come
  from `FetchResult.json() -> Any` (`httpclient.py:110`), so `el.get("lat")` (`osm.py:68`),
  `row.get("coord", {}).get("value")` (`wikidata.py:101`) and `place.get("rating")`
  (`google_places.py:297`) are all `Any` flowing straight into a `float | None` /
  `int | None` slot. `disallow_any_expr` is **not** part of `mypy --strict` and is not set
  in `pyproject.toml:64-68`, so the checker will not flag it either. In practice all three
  APIs do emit JSON numbers, so I could not construct a live violation here — but nothing
  in the codebase *verifies* that, and `enricher.infer_region` (`enricher.py:92`,
  `lat_min <= lat <= lat_max`) is the first thing that would explode, from inside
  `google_places.py:275`, which would then kill all 67 queries through
  `f.result()` (`google_places.py:197`).

## Findings

### S1 — `cmd_scrape` applies none of the pipeline's acceptance criteria, so exit 0 does not mean the source works

- **Where:** `cli.py:61-76`, versus `main.py:172` (`is_business_category`), `main.py:180`
  (`dedup`), `main.py:194` (`normalize_phone`), `main.py:202-205` (`sales_ready` gate).
- **Breaks:** `cmd_scrape` reports raw scraper output. `main()` then applies four filters
  before a record becomes product. Any of them can reduce a healthy-looking source to
  nothing while `cmd_scrape` prints a plausible distribution and returns `0`.
  The largest known gap is the whitelist: `docs/audits/093-whitelist-reality-test.md`
  measures >36% of commercial Google Places types and ~28% of commercial OSM tag values
  dropped at `main.py:172`. `--source wikidata` is worse: the SPARQL query
  (`wikidata.py:24-44`) selects every `wdt:P17 wd:Q822` item with no `wdt:P31` constraint
  in a `WHERE` clause — only an OPTIONAL `?category` — so the result set is dominated by
  humans, historic buildings, monuments and political entities, and
  `is_business_category` (`whitelist.py:105-130`) rejects almost all of them.
- **Trigger:** `leadminer scrape --source wikidata` against a healthy endpoint returns
  5,000 rows. Output:
  ```
  [wikidata] 5000 records
    with phone : 41
    with site  : 610
    top categories:
      historical event            901
      human                       803
      church                      512
  ```
  Exit code **0**. `main.py:172` keeps 0 of those 5,000; the run adds zero new leads and
  exits 0 as well.
- **Fix:** Apply `is_business_category` to the record set before counting, and return
  non-zero when *kept* is 0; print both `n raw` and `n kept`.

### S1 — `cmd_scrape` is the only caller of `scrape()` that cannot survive a scraper raising

- **Where:** `cli.py:61` (`records = list(registry[args.source]().scrape())`), versus
  `main.py:162-168`, which wraps `future.result()` in `try/except Exception`.
- **Breaks:** `BaseScraper.scrape()` (`base.py:33`) raises on at least three ordinary
  paths: `result.json()` on a non-JSON body (`osm.py:58`, `wikidata.py:87`), a `TypeError`
  from `enricher.infer_region` on a non-numeric coordinate (`google_places.py:275`), and
  any `f.result()` re-raise from a query worker (`google_places.py:197`). `main()` absorbs
  all of them and continues with 0 records from that source. `cmd_scrape` — the command
  whose entire purpose is running one source to see whether it works — lets them
  propagate out of `cli.main()`, which only catches `KeyboardInterrupt` (`cli.py:316`).
  Result: a Python traceback and exit status 1, the **same** exit status as
  "the source legitimately returned nothing" (`cli.py:66`).
- **Trigger** (reproduced): a `scrape()` that yields one record then raises.
  ```
  $ python3 -c "...cmd_scrape with a raising scraper..."
  [raiser] 1 records
  !! UNCAUGHT ValueError: simulated scraper blowup mid-iteration   (cli.py:61 has no try/except)
  ```
  Exit status 1 — byte-identical to the `return 1` at `cli.py:66`.
- **Compounding:** for `--source osm` the first scraper output is emitted only after
  `fetch_with_retry(..., timeout=200, retries=3)` (`osm.py:39-46`) settles — up to ~10
  minutes of silence before `cli.py:62` prints anything at all. An operator watching a
  hung `leadminer scrape --source osm` has no signal that the command is alive.
- **Fix:** wrap `cli.py:61` in `try/except Exception`, print the traceback to stderr, and
  return a distinct code (e.g. 3) reserved for "the scraper crashed", keeping 1 for
  "zero records".

### S2 — `with phone` and `with site` are truthiness counts, not the pipeline's validity predicate

- **Where:** `cli.py:69-70` (`sum(1 for r in records if r.get("phone"))` /
  `r.get("website")`), versus `dedup.normalize_phone` (`dedup.py:33-63`) and
  `dedup._validity` / `_URL_OK` (`dedup.py:117, 126-127`).
- **Breaks:** `cmd_scrape` runs *before* any normalisation, so it counts every non-empty
  string. The pipeline's effective contract is `normalize_phone(phone) != ""`
  (≥ 7 digits, `dedup.py:30, 45`) and `_URL_OK.match(website)` (must match
  `^https?://[^\s/]+\.[^\s]+`). Both are strictly narrower, so the reported coverage is a
  consistent **overstatement** — precisely on the two fields that decide
  `sales_ready.csv` membership (`main.py:137-145`, `202-205`).
- **Trigger** (reproduced):
  ```
  phone='12345'                 cmd_scrape counts=True   normalize_phone=''
  phone='03 123 456 ext. 12'    cmd_scrape counts=True   normalize_phone='+961312345612'
  website='http:/example.com'   cmd_scrape counts=True   _URL_OK=False
  website='ftp://x.com'         cmd_scrape counts=True   _URL_OK=False
  ```
  `website=http:/example.com` reaches `cmd_scrape`'s counter because `osm.py:95` /
  `wikidata.py:103` only prepend `https://` when the value does not already `startswith("http")`
  — a single-slash typo passes the guard. During dedup that record's `website` scores
  `_validity == 0` and loses to any other source's value (`dedup.py:187`).
- **Fix:** count with the real predicates — `if normalize_phone(r.get("phone") or "", r.get("country") or "LB")`
  and `if _URL_OK.match(...)` — and label the lines `with usable phone` / `with valid url`.

### S2 — `category` is read as a short non-null string but is `str | None`, unbounded-length, and unhashable-if-not-str

- **Where:** `cli.py:68` (`collections.Counter(r.get("category") ...)`) and
  `cli.py:75` (`f"{str(cat):<28} {n}"`).
- **Breaks — three distinct symptoms, one root cause:**
  1. **`None` renders as a row labelled `None`.** `wikidata.py:100` reads the OPTIONAL
     `?categoryLabel`; a binding with no category yields `category=None`. The Counter key
     is `None` and `str(None)` prints the word `None` in the *category* column, where an
     operator reads it as a category name. (Confirmed: `wikidata.py:35-39` makes this the
     expected case, not an edge case.)
  2. **Long labels break the column.** `:28` is a minimum width, not a maximum. A
     Wikidata `?categoryLabel` such as `Arabic-language television station` (34 chars)
     pushes the count column right and misaligns the whole table.
  3. **A non-`str` category is fatal.** `collections.Counter` hashes its input; a `list`
     category raises `TypeError: unhashable type: 'list'`, which — per the S1 above —
     escapes as a traceback. (Reproduced.) Note `cli.py:75` is *not* the problem: the
     `str(cat)` wrapper makes the formatting total. The crash is at `:68`.
- **Trigger:** any scraper revision that sets `category=place["types"]` (a list) instead of
  `_pick_category(types)`. One such line kills the whole command.
- **Fix:** `cat = r.get("category") or "(none)"` then `str(cat).replace("\n"," ")[:28]`,
  and coerce with `isinstance(cat, str)` before counting.

### S2 — The `BusinessRecord` contract is enforced by nothing: runtime-inert TypedDict, `Any` envelope, and no typechecker in CI

- **Where:** `scrapers/base.py:5` (`class BusinessRecord(TypedDict)`, `total=True`);
  `httpclient.py:110` (`def json(self) -> Any`); `pyproject.toml:64-68`
  (`[tool.mypy] strict = true`) vs `.github/workflows/scrape.yml`, whose only steps are
  checkout / setup-python / `uv pip install -r requirements.txt` / rclone / `python main.py`
  / validate / upload — **no `ruff`, no `mypy`, no `pytest`**. `requirements.txt:1-3` pins
  three packages and does not include any of them.
- **Breaks:** `BusinessRecord(...)` is a plain `dict` constructor. Reproduced:
  ```
  partial = BusinessRecord(name="x")          # 22 of 23 keys absent  -> no TypeError
  extra   = BusinessRecord(**partial, osm_id="node/1", bogus=object())
                                                 # 2 keys not declared  -> no TypeError
  BusinessRecord.__required_keys__ -> all 23 keys
  ```
  So *any* caller can violate the contract silently: omit keys, add keys, or put a value
  of the wrong type, and nothing complains at runtime, and nothing checks statically. The
  only consumer that would notice is `main.write_csv`'s
  `csv.DictWriter(..., extrasaction="ignore")` (`main.py:125`), which drops undeclared keys
  silently.
- **The checker that would catch this has never been run.** `cmd_run` at `cli.py:37` is
  `return pipeline.main()` in a function annotated `-> int`, while `main.main()` is
  `def main() -> None:` (`main.py:148`) with no value-returning `return` anywhere in its
  body (verified by AST). That is a hard `mypy --strict` error at `cli.py:37` — and a
  live latent bug (S2-5 below). If mypy had ever run on this repo it would have failed
  on the first file.
- **Fix:** (a) add a `lint` job running `ruff check` + `mypy .` + `pytest`;
  (b) install the package (`pip install -e ".[dev]"`) rather than `requirements.txt`;
  (c) validate at the boundary — see the S1-1 fix note in *Recommended order of work*.

### S2 — Overpass's HTTP-200 error envelope is discarded, so a timed-out query is a normal empty yield

- **Where:** `osm.py:47` (`if not result.ok`), `osm.py:58` (`elements = result.json().get("elements", [])`).
- **Breaks:** Overpass answers a timed-out query with **HTTP 200**, an empty `elements`
  array, and a diagnostic string in `remark`. `fetch_with_retry` sets
  `ok = status < 400` (`httpclient.py:186`), so `osm.py:47` does not fire; `osm.py:58`
  reads `elements` and drops `remark`; `osm.py:59` prints the reassuring
  `[OSM] Got 0 elements.` and the generator terminates **normally**. Nothing in the
  codebase reads `remark` or `osm3s.timestamp_osm_base` — `grep -rn "remark" --include=*.py`
  returns nothing outside this report. Reproduced:
  ```
  envelope ok = True  status = 200
  osm.py:47 `if not result.ok` -> DOES NOT FIRE
  osm.py:58 elements = []
  ```
  For `cmd_scrape` specifically this is the *one* failure it happens to catch (empty list
  → `return 1`, `cli.py:66`) — but for the wrong reason, and the operator's log shows
  "Got 0 elements", not "query timed out". For `main()` it is invisible: exit 0.
  Sources: [Overpass API #382](https://github.com/drolbr/Overpass-API/issues/382),
  [python-overpy #62](https://github.com/DinoTools/python-overpy/issues/62),
  [Spatial Workflow](https://www.spatialworkflow.io/query-overpass-api-python/)
  (documents the HTTP-200 + `remark` timeout shape explicitly).
- **Trigger:** the 12-statement Overpass query at `osm.py:11-27` with
  `timeout:180` hits a loaded `overpass-api.de` mirror.
- **Fix:** `if remark := result.json().get("remark"): log.error(...)` and surface it as
  a hard failure in both `osm.py` and `cmd_scrape`.

### S2 — `int(args.func(args) or 0)` turns a missing return value into a green exit code

- **Where:** `cli.py:315`, inside `cli.main`; consumed by `pyproject.toml:33`
  (`leadminer = "cli:main"`) and `cli.py:322` (`raise SystemExit(main())`).
- **Breaks:** the `or 0` converts `None` into `0`. Any `cmd_*` that falls off the end or
  uses a bare `return` reports success. This is not hypothetical for `cmd_run`: it is
  `return pipeline.main()` (`cli.py:37`), and `main.main()` is `-> None` with no
  value-return — so `leadminer run` **exits 0 even when all three sources returned zero
  records** (401 key at `google_places.py:231`, Overpass timeout, all 67 queries
  abandoned at `google_places.py:240`). The workflow sidesteps this with a row-count
  gate (`scrape.yml`, `ROWS < 100 → exit 1`), which is a blunt proxy for exactly the
  signal `cmd_scrape` should be providing.
- **Trigger** (reproduced): a `cmd_*` returning `None` → `cli.main()` returns `0`.
- **Fix:** drop the `or 0`; assert `isinstance(rc, int)`; make `main.main()` return an
  int and have `cmd_run` propagate it.

### S3 — Fields `cmd_scrape` reads or writes that are not in the `BusinessRecord` TypedDict: **none**

Stating this plainly because it is the cleanest part of the target:

- **Reads:** `category` (`cli.py:68`), `phone` (`cli.py:69`), `website` (`cli.py:70`).
  All three are declared at `base.py:7`, `:13`, `:15`.
- **Writes:** nothing. `cmd_scrape` mutates no record and no field.
- **Envelope assumptions that are *not* declared, though:**
  1. `cli.py:62` calls `len(records)` on the result of `list(...)` — fine — but
     `BaseScraper.scrape` is typed `Iterator[BusinessRecord]` (`base.py:33`), which does
     not distinguish finite from infinite. `cli.py:61` materialises the whole thing with
     no bound: a scraper that becomes a streaming/partitioned iterator hangs
     `leadminer scrape` forever with unbounded memory and zero output. For
     `--source google_places` this is already 2× peak: `scrape()` holds `all_records`
     (`google_places.py:183, 192, 199`) while `list()` builds a second list over it.
  2. `.get()` at `:68-70` is equivalent to `[]` under mypy for a `total=True` TypedDict,
     so the defensive style buys nothing statically — while being the only thing standing
     between a schema regression and an `AttributeError`/silent `None`. The code is
     written as though `total=False`; `base.py:5` declares `total=True`. That
     disagreement is itself the drift signal.
- **Dead guard:** `cli.py:56-59` (`return 2` on an unknown source) is **unreachable** via
  `cli.main()`. `choices` (`cli.py:289-290`) and the `registry` keys (`cli.py:51-55`) are
  two hand-maintained copies of `{"osm", "wikidata", "google_places"}` and are equal
  today (verified). Add a scraper to `registry` and forget `choices` → argparse rejects a
  working source. Forget `registry`, add `choices` → argparse accepts it, then `:57`
  prints the error and returns 2. The guard that works is the one that cannot fire.
- **Dead import:** `cli.py:46` `from scrapers.base import BaseScraper  # noqa: F401
  (import check)` — `cli.py:47-49` already import all three concrete scrapers, which in
  turn import `enricher` (`google_places.py:26`) and `httpclient` (`httpclient.py:43`), so
  the "check" is paid for unconditionally by `leadminer scrape --source osm`.

### S3 — The declared types are not believed by the code that consumes them

- **Where:** four independent `str()` coercions of `phone`, a field declared
  `str | None` (`base.py:13`): `enricher.py:285`, `dedup.py:42`, `main.py:69`,
  `main.py:138`. `dedup.normalize_phone` even annotates its own parameter
  `phone: str` (`dedup.py:33`) and then defends with `raw = str(phone)` at `dedup.py:42`.
- **Also re-implemented per-field:** `dedup._validity` re-casts `lat`, `lon`, `rating`
  in `try`/`except` (`dedup.py:128-139`); `pitch_recommender.py:44-47` and `:49-52` wrap
  `review_count` and `completeness_score` in `try`/`except (ValueError, TypeError)`;
  `main.load_master` casts `lat`/`lon`/`rating`/`review_count`/`completeness_score`/
  `lead_score` on every load (`main.py:90-101`). All of these defend against a type the
  contract says cannot occur.
- **Breaks:** the type instability is real, not theoretical. Google emits `4` (not `4.0`)
  for a whole-number `rating`, so `json.loads` yields `int`; `main.load_master:90-95`
  then re-reads it from the CSV as `float`. The same logical field therefore has a
  different Python type depending on whether a record came from a scraper or from the
  master CSV — and `cmd_scrape` and `cmd_stats` see the first, while every downstream
  consumer has to handle both.
- **Fix:** make the contract authoritative (a `NotRequired`/branded-type split, or a
  validating `__init__`) and delete the four `str()` wrappers and the per-field `try`
  blocks once it is.

### S3 — `leadminer scrape --source google_places` is a 45–60 minute, billable operation, not a probe

- **Where:** `cli.py:41-45` (docstring: *"without paying for a full enrichment pass"*),
  `cli.py:61`, driving `google_places.py:194-199`.
- **Breaks:** 67 queries (`LEBANON_QUERIES` 33 + `KSA_QUERIES` 34, counted via AST — note
  `docs/audits/092` and the brief both say 68) over 5 workers
  (`google_places.py:142`) = 14 waves, each bounded by `_QUERY_BUDGET_SECONDS = 180`
  (`:152`) → ~42 min floor in the worst case, plus `time.sleep(2)` per page
  (`:310`) and up to 4 × 60 s of 429 backoff per query (`:149-151, 241-246`). It bills
  real money. `cmd_scrape` warns about nothing and takes no `--query` filter, so there is
  no cheap way to answer the question the docstring promises.
- **Fix:** add `--query/-n` / `--limit` passthrough so `--source google_places -n "dentists
  in Beirut"` is genuinely cheap, and print the estimated request count up front.

## Not a bug, but worth knowing

- **`cli.py:75`'s `f"{str(cat):<28} {n}"` is total.** It cannot raise on any type. The
  `TypeError` in S2-3 comes from `collections.Counter` at `:68`, not the format string.
  Anyone hardening this should harden `:68`, not `:75`.
- **`cli.py:62` prints the header only after the generator is fully exhausted.** Because
  `scrape()` is a generator function in all three implementations, nothing at `cli.py`
  prints until the source has finished. This is why `cmd_scrape` feels silent: the progress
  an operator sees is the scraper's own chatter (`osm.py:33, 59`,
  `google_places.py:175, 257`), which arrives *before* the `[source] N records` line. Not
  a bug, but the ordering is confusing.
- **The two scrapers that have the cleanest contracts are the two `cmd_scrape` can
  diagnose least well.** OSM and Wikidata yield a lazy `Iterator` (`osm.py:98`,
  `wikidata.py:106`), so `cmd_scrape` could stream-and-count with bounded memory and abort
  early; Google Places pre-materialises everything (`google_places.py:183, 199`) and
  cannot. If the command is ever given a cap, only `--source google_places` will need the
  `list()` removed.
- **`--source osm` and `--source wikidata` are Lebanon-only** (`osm.py:13` `ISO3166-1="LB"`,
  `wikidata.py:27` `wdt:P17 wd:Q822`). `cmd_scrape` prints no scope line, so a reader can
  reasonably assume the KSA coverage in `README`/`BRIEF` applies to whichever source they
  just probed. One line of output fixes this.
- **Per audit 092, `google_places` returns at most 60 places across 3 pages per query** and
  the code has no `page >= 3` guard (`google_places.py:216-310`), so `leadminer scrape
  --source google_places` cannot exceed ~4,020 result slots. The record count it prints is
  therefore a ceiling artefact as much as a health signal.

## Recommended order of work

1. **Add the missing `try`/`except` around `cli.py:61`** and a distinct exit code for
   "scraper crashed" (S1-2). Smallest diff, removes the worst diagnostic failure mode.
2. **Make `cmd_scrape` apply `is_business_category` and return non-zero on
   `kept == 0`** (S1-1). This is what turns the command from a record counter into a health
   gate, and it is the fix that lets CI use it instead of the `ROWS < 100` proxy.
3. **Add a `lint` job** running `ruff check`, `mypy .`, `pytest` after
   `pip install -e ".[dev]"` (S2-3). Expect an immediate failure on `cli.py:37`; fix that
   in the same PR by making `main.main()` return an `int` and dropping the `or 0` at
   `cli.py:315` (S2-5).
4. **Read Overpass's `remark`** and treat a non-empty `remark` as a hard failure in both
   `osm.py` and `cmd_scrape` (S2-4).
5. **Fix the three counter columns** (S2-1, S2-2): real validity predicates for
   phone/website, `(none)` + truncation for category. One afternoon; makes every number
   the command prints match what the pipeline does.
6. **Then, not before:** replace `BusinessRecord` with a validated record type at the
   `scrapers/` boundary. Doing this before step 3 lands means writing a validator with no
   typechecker to catch its own drift.
