# 200 — `_fmt` (cli.py:29) is correct today; its *signature* is the bug

## Verdict

`_fmt` has **no reachable defect**. All six callers pass `count(...)`, and `count()`
is `sum(1 for r in rows if <bool>)` — by construction a strictly `int`, never `None`,
never `float`, never `str`. For `int` inputs `f"{n:,}"` is total and correct
(verified across `0..10**40` in both signs plus `10**400`: never scientific, never
wrong). The one real finding is that the signature **advertises four input classes it
never receives, and three of them produce wrong output** — most sharply, floats
`>= 1e16` silently lose the comma grouping the function exists to apply. Nothing
here blocks trust in the CSVs; this is an API-surface trap for the next caller.

All results below were produced by importing the real module
(`/Users/mhomsi/dev/dummy/leadminer/cli.py`) and calling it. Python 3.14.8;
`float.__format__` `,` semantics are unchanged across the project's `>=3.12`
(`pyproject.toml:12`), so the behaviour transfers. Only the `str` error *message*
text changed in 3.12 — both variants are noted.

## Callers

`grep -n '_fmt('` finds exactly the definition plus six call sites, all in
`cmd_stats`. No test, script, or other module imports it.

## Findings

### S2 — Floats `>= 1e16` silently lose the comma grouping and print as `1e+16`
- **Where:** `cli.py:30` — `f"{n:,}{suffix}"`
- **Breaks:** for a `float`, Python's general format switches to scientific notation
  at `1e16`, and the `,` grouping spec is **silently dropped**. `_fmt`'s only job is
  comma-grouping, so for these inputs it returns a differently-shaped, ungrouped
  string with no error and no warning. The caller cannot tell the format contract
  was abandoned. Below the threshold the same function works, so the failure is
  input-dependent and invisible until it isn't.
- **Trigger (exact input → exact wrong output), confirmed by execution:**

  | Input | Output | Grouped? |
  |---|---|---|
  | `_fmt(1e15)` | `'1,000,000,000,000,000.0'` | yes |
  | `_fmt(1e16)` | `'1e+16'` | **no** |
  | `_fmt(1e17)` | `'1e+17'` | **no** |
  | `_fmt(1e18)` | `'1e+18'` | **no** |
  | `_fmt(999999999999999.8)` | `'999,999,999,999,999.8'` | yes |

  The precision case is the nastiest, because the output *looks* precise while
  being a rounded 17-significant-digit float:
  - `_fmt(1234567890123456789.0)` → `'1.2345678901234568e+18'`
  — ungrouped, scientific, and the low digits (`789` → `8e18`) are gone.
- **Severity defence:** not S1 because no current caller can pass a `float`
  (proved under "Invariant" below), so no existing run can be wrong. Not S3
  because it is a silent wrong output for an input type the signature explicitly
  admits, in a function whose entire purpose is that one formatting rule.
- **Fix:** coerce and format separately — `f"{int(n):,}"` when the value is
  integral, or narrow the annotation to `int | None` and delete the `float` arm.

### S3 — `nan` / `inf` bypass the `"n/a"` sentinel the function already has
- **Where:** `cli.py:30` — `"n/a" if n is None else ...`
- **Breaks:** `_fmt` has exactly one representation for "no value", and it fires
  only on `None`. The other two canonical no-value floats sail straight through the
  f-string and render as bare `nan` / `inf` / `-inf`. A reader scanning the report
  sees `nan` and must know CPython float repr to conclude it means "missing"
  rather than "corrupt".
- **Trigger (exact input → exact wrong output):**
  - `_fmt(float('nan'))` → `'nan'` (want `'n/a'`)
  - `_fmt(float('inf'))` → `'inf'`
  - `_fmt(float('-inf'))` → `'-inf'`
- **Fix:** `if n is None or (isinstance(n, float) and math.isnan(n))` → `"n/a"`.

### S3 — Integral floats print a spurious `.0`, breaking the report's column alignment
- **Where:** `cli.py:30`
- **Breaks:** `cmd_stats` is a fixed-width, label-aligned block. `_fmt` output is
  left-padded into `{:<20}` / `{:<28}` layouts at `cli.py:117,121,126,131`, where the
  count is expected to be a pure digit-grouped integer. A trailing `.0` widens the
  token by two characters and shifts every subsequent column.
- **Trigger (exact input → exact wrong output):**
  - `_fmt(3.0)` → `'3.0'` (want `'3'`)
  - `_fmt(1234.0)` → `'1,234.0'` (want `'1,234'`)
  - `_fmt(0.5)` → `'0.5'` — a fraction, not a count, printed as if it were one
- **Fix:** format through `int(n)` on the integral path, or drop `float` from the
  annotation so the compiler rejects it at the next call site.

### S3 — `_fmt("")` raises; `str` is the file's own "missing" sentinel and `_fmt` crashes on it
- **Where:** `cli.py:30`
- **Breaks:** the rest of `cmd_stats` treats missing data as `""` via
  `(r.get(field) or "")` — at `cli.py:96, 107, 108, 110, 124, 129`. `_fmt` is the
  only function in the file that does not follow that convention, and it does not
  merely mis-handle `""`, it raises an **unhandled `ValueError`**. `main()`
  (`cli.py:314-318`) catches only `KeyboardInterrupt`, so this would escape as a
  raw traceback rather than a clean non-zero exit.
- **Trigger (exact input → exact wrong output):**
  - `_fmt("")` → raises `ValueError: Cannot specify ',' with 's'.`
  - `_fmt("abc")` → raises `ValueError: Cannot specify ',' with 's'.`
  - `_fmt("12")` → raises `ValueError: Cannot specify ',' with 's'.` (a perfectly
    reasonable "count that came back as a string" case is still fatal)
  - (on Python 3.11 and earlier the same input raises
    `ValueError: Unknown format code ',' for object of type 'str'`; project targets
    `>=3.12`, so the message above is the applicable one.)
  - `_fmt(b"12")` → raises `TypeError: unsupported format string passed to bytes.__format__`
- **Severity defence:** would be **S1** ("a run that dies") if any caller passed a
  string. It is not, so it is filed S3 — it is a latent crash, not a current one.
- **Fix:** accept `str` and normalise: `_fmt(0 if n in (None, "") else n)`.

### S3 — Both of `_fmt`'s distinguishing features are dead, and the file uses a second idiom for the same formatting
- **Where:** `cli.py:29-30` (definition); dead arms exercised by nothing; duplicate
  idiom at `cli.py:93, 111, 112, 113, 117, 121, 126, 131, 194, 276`
- **Breaks:** two code paths that are behaviourally identical for every input that
  can occur. Confirmed by execution: `_fmt(n) == f"{n:,}"` with **zero** divergences
  across `±10**e` for `e` in `0..40`, and `_fmt(10**400)` stays comma-grouped
  (534 chars) where `int` formatting never falls back to scientific. So the reader
  of `cmd_stats` faces `f"{v:,}"` on nine lines and `_fmt(v)` on six, with no way to
  tell which is canonical or what `_fmt` adds. Meanwhile:
  - the `None → "n/a"` arm is unreachable — no caller can pass `None`;
  - the `suffix` parameter is unreachable — no caller passes it (all six calls are
    single-argument).
  Two dead arms in a three-line helper is a maintenance tax for zero behaviour.
- **Fix:** either delete `suffix` and the `None` arm and keep `_fmt` as the single
  idiom, or keep them and convert the nine inline sites — but not both.

## Not a bug, but worth knowing

- **The invariant that makes `_fmt` safe, stated precisely.** `count` at
  `cli.py:95-96` is `sum(1 for r in rows if (r.get(field) or "").strip())`. `sum`
  over a generator whose only yielded element is the `int` literal `1` returns
  `int` by construction: there is no division (so never `float`), no `None` term
  (so never `None`), no string (so never `str`), and `1` truthiness gates each
  element so the result is `>= 0`. Python's `int.__format__(',')` is total over
  arbitrary-precision integers. Therefore every `_fmt` invocation in this file
  receives an `int`, and `_fmt` is exactly correct. **The guarantee rests entirely
  on `count` keeping its current shape** — if anyone ever rewrites it as a ratio
  (`count/total`), or returns a `float`/`str`, the S2/S3 findings above turn live
  in a single line.
- **`csv.DictReader` really does inject `None` values into `cmd_stats`, and the
  file handles it correctly.** A ragged row (`name,phone,region` header, row `B,+961`)
  parses to `{'name': 'B', 'phone': '+961', 'region': None}`. The `(x or "")` guard
  at `cli.py:96` absorbs it, `with region` reports the correct `1`, and the command
  exits `0`. This is exactly the case `_fmt`'s `"n/a"` arm was presumably written
  for — but the `None` never reaches `_fmt`, because `count` has already converted
  it to an absence. The sentinel is one layer downstream of where it is needed.
- **The tri-state `website_live` handling at `cli.py:105-113` is correct** and its
  comment records the right historical bug: `blank` (unreachable) is counted
  separately at line 110 and is deliberately *not* merged into `dead`. Executed
  against a 12,345-row fixture: `live 8,230 / dead 0 / unreachable 2,057` — and
  `live + dead + unreachable` reconstructs correctly. No issue.
- **`_fmt` is private (leading underscore) yet imported by nothing but its own
  module.** Safe to change signature when you fix the findings above; there is no
  external consumer to break. Confirmed by repo-wide grep across `tests/` and
  `scripts/`.

## Recommended order of work

1. **Narrow the signature to what is actually true** — `def _fmt(n: int,
   suffix: str = "") -> str` — and delete the `"n/a"` arm, or land the string/`nan`
   normalisation from the S2/S3 findings above if you want the generality to be
   real. This one line removes all three crash/garbage paths and makes the type
   checker police the next caller. Highest value per byte of anything in this report.
2. **Pick one formatting idiom in `cmd_stats`.** Convert the nine inline
   `f"{x:,}"` sites to `_fmt(x)` (mechanically safe — verified identical for all
   `int`), so the file has one way to format a number.
3. **Pin the invariant with a test.** There is currently no direct test of `_fmt`
   (`tests/test_lead_signal.py:211` exercises `cmd_stats` only end-to-end). One
   small test asserting `_fmt(0) == "0"`, `_fmt(1234567) == "1,234,567"`,
   `_fmt(10**400)` contains no `"e+"`, and `_fmt(None) == "n/a"` locks in the
   current correct behaviour so a future "make it a percentage" rewrite cannot
   silently swap in the S2 bug.
