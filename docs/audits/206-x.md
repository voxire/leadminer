# 206 — `_fmt` (cli.py:29): dependency closure, and what it hides

## Verdict

`_fmt` is the cleanest function in this repository. Its **transitive call-time
dependency closure is five builtins and nothing else** — `None`, `int`, `float`,
`str`, plus its two parameters. Zero project modules, zero module globals, zero
third-party packages. Verified by AST extraction *and* by executing it inside a
real `src/` restructure. It **cannot** create a circular import, now or after any
restructuring, because it has no project edges to invert.

Everything interesting about this target is therefore **ambient**, not direct:
`_fmt` has no dependencies, but the module that must execute before `_fmt` is
reachable has five eager top-level imports, a CWD-relative global, and a wheel
target that does not appear to ship the file `_fmt` lives in. The one genuinely
dangerous dependency in the neighbourhood is **not** `_fmt`'s — it is
`scrapers/google_places.py:26 → enricher.py:79`, which is the single edge that
turns a future `enricher → scrapers.*` import into a verified `ImportError`.

Separately: two of `_fmt`'s three behaviours are **provably dead** (the
`None → "n/a"` branch and the `suffix` parameter), and its one live behaviour is
inlined verbatim 11 more times in the same file. `_fmt` is not the shared
formatter it looks like.

### The annotation edges are not runtime edges

`cli.py:18` is `from __future__ import annotations`, which puts the whole module
on PEP 563. Verified at runtime:

```
_fmt runtime signature object: (n: 'int | float | None', suffix: 'str' = '') -> 'str'
param annotations as runtime objects:
   n: annotation='int | float | None'
   suffix: annotation='str'
   return annotation: str
```

The annotations are **`str` instances, never evaluated**. So `int`, `float` and
`str` appear in the AST load-set but are *not* runtime dependencies, and
`int | float | None` requires no `typing` import and no PEP 604 runtime support.

Direct answer to the lens question *"anything imported only for a type
annotation?"*: **no — not in `_fmt`'s closure, and not anywhere in `cli.py`.**
`cli.py` imports nothing from `typing` and nothing from `collections.abc`. The
PEP 604 syntax at `cli.py:29` is a string by the time Python sees it. Had
`cli.py:18` been removed, `int | float | None` would still evaluate correctly on
Python 3.12 (`pyproject.toml:10`) because all three operands are builtins — the
function is safe under either policy. Note this is a property of *this* function's
annotations; the same file's `_retry_after(headers: Any) -> float | None` in
`httpclient.py:120` would **not** be, since `Any` needs a real `typing` import.

## Findings

### S1 — The wheel target does not ship the module the console script imports

- **Where:** `pyproject.toml:32-37`
- **Breaks:** The console script is `leadminer = "cli:main"` (`pyproject.toml:33`) —
  a **top-level module named `cli`**. The wheel target is
  `[tool.hatch.build.targets.wheel] include = ["scrapers/"]`
  (`pyproject.toml:35-37`). There is no `leadminer/` package directory and no
  `src/leadminer/`; `ls -d leadminer leadminer` returns *No such file or
  directory*. Hatchling infers a wheel's package set from `<normalized-name>/` or
  `src/<normalized-name>/`; neither exists, and `include = ["scrapers/"]` is a
  **filter over an inferred base set**, not a definition of one. Both plausible
  resolutions are broken:
  - hatchling cannot infer a package → `pip install .` fails at build time;
  - hatchling ships only `scrapers/` → `leadminer` console script dies on first
    invocation with `ModuleNotFoundError: No module named 'cli'`, and `cli.py`
    itself is absent from the wheel.

  The config's own comment states the intent the config does not express:
  *"The package imports a top-level sibling module, so both must ship."*
  (`pyproject.toml:36`). "Both" names two things; `include` names one. The author
  knew about the problem and the fix was never written down.

  Compounding: the six bare top-level modules that *would* land in `site-packages/`
  are `cli.py`, `dedup.py`, `enricher.py`, `httpclient.py`, `main.py`,
  `pitch_recommender.py`. Names like `cli` and `main` are close to worst-case for
  global namespace pollution — any other distribution shipping a top-level `cli`
  silently shadows one or the other.

- **Trigger:** `python -m build && unzip -l dist/*.whl` on a machine without a
  pre-existing `cli` module, then run `leadminer --help`.
- **Confidence:** **not executed.** `hatchling` and `build` are absent from this
  environment and installing them is out of scope for this lens. The config/code
  disagreement and the missing package directory *are* verified facts; the exact
  hatchling failure mode is the inference. Verify with:
  `uv build --wheel && python -m zipfile -l dist/leadminer-*.whl | grep -E '(^|/)(cli|main)\.py'`
  (a correct wheel lists `cli.py`/`main.py` at the root or under `leadminer/`).
- **Fix:** Do the `src/` layout (see "Recommended order of work") and replace
  `pyproject.toml:35-37` with `[tool.hatch.build.targets.wheel] packages = ["src/leadminer"]`,
  moving `pyproject.toml:33` to `leadminer = "leadminer.cli:main"`.

### S2 — `scrapers/google_places.py:26 → enricher.py:79`: the one verified circular-import hazard

- **Where:** `scrapers/google_places.py:26` (`from enricher import infer_region`),
  consumed at `scrapers/google_places.py:275`; defined at `enricher.py:79`.
- **Breaks:** This is a layer inversion. `scrapers/` is the acquisition layer
  (layer 1); `enricher.py` is the transformation/scoring layer (layer 2). The
  pipeline direction in `main.py` is `main → scrapers` and `main → enricher`
  (`main.py:25-31`). So `enricher` sits *between* `main` and the scraper, and a
  scraper must reach up and over into it. Consequences:
  - `infer_region` — a pure geo function over `(lat, lon, country)` — is
    unreachable to a scraper without importing the entire HTTP enrichment stack,
    including `httpclient` (`enricher.py:128`) and `requests` (`enricher.py:2`).
  - `enricher` can never be split, renamed, or tested in isolation from the
    `scrapers` package, because `scrapers` already owns a reference to it.

  **Empirically verified** on a `src/leadminer/` restructure (performed in a
  throwaway copy outside the repo, `requests` stubbed, project files untouched).
  Injecting one plausible line into `enricher.py` and then importing the scraper
  layer that `main.py:25-28` imports:

  ```
  enricher -> scrapers.whitelist:industry_priority   -> IMPORT OK (no cycle)
  enricher -> scrapers.base:BusinessRecord           -> IMPORT OK (no cycle)
  enricher -> scrapers.google_places:GooglePlacesScraper
      File ".../leadminer/scrapers/google_places.py", line 26, in <module>
        from leadminer.enricher import infer_region
      File ".../leadminer/enricher.py", line 2, in <module>
        from leadminer.scrapers.google_places import GooglePlacesScraper
      ImportError: cannot import name 'GooglePlacesScraper' from partially
      initialized module 'leadminer.scrapers.google_places' (most likely due to
      a circular import)
  ```

  The hazard is narrow and precisely characterisable: only an `enricher →
  scrapers.google_places` edge cycles, because `google_places` is the sole holder
  of the inverted dependency. Edges to `whitelist` and `base` are safe. That is
  the trap — a developer doing the natural "enricher needs the Places field
  mapping" refactor gets a confusing partial-initialisation error pointing at
  `google_places.py`, three files away from the line they edited.
- **Trigger:** add `from scrapers.google_places import GooglePlacesScraper` to
  `enricher.py`, then `import scrapers.google_places` (which `main.py:27` does).
- **Fix:** Extract `infer_region` (`enricher.py:79`) into a leaf module with no
  project dependencies (`leadminer/geo.py`), and point both
  `scrapers/google_places.py:26` and `enricher.py`'s internal callers at it. This
  removes the inverted edge and closes the cycle hazard permanently.

### S2 — `_fmt` guards with identity, not type, so any `str` raises `ValueError`

- **Where:** `cli.py:30` — `return "n/a" if n is None else f"{n:,}{suffix}"`
- **Breaks:** The guard tests `n is None`, then unconditionally applies the `,`
  thousands format spec. `,` is valid only for numeric types. Any string that
  passes the identity check crashes at the f-string:

  ```
  _fmt('1234')    -> RAISES ValueError: Cannot specify ',' with 's'.
          at cli.py:30  |  return "n/a" if n is None else f"{n:,}{suffix}"
  _fmt('3.5')     -> RAISES ValueError: Cannot specify ',' with 's'.
  _fmt('')        -> RAISES ValueError: Cannot specify ',' with 's'.
  _fmt('n/a')     -> RAISES ValueError: Cannot specify ',' with 's'.
  _fmt('1,234')   -> RAISES ValueError: Cannot specify ',' with 's'.
  _fmt(None)      -> 'n/a'
  ```

  Not reachable today: all six callers pass `count(...)`, which
  `cli.py:95-96` defines as `sum(1 for r in rows if ...)` → always `int`. So this
  is a latent defect, not an active one. **It matters because of what surrounds
  it.** `cli.py:87` and `cli.py:143` both read CSVs with
  `list(csv.DictReader(f))`, i.e. **every value in this module is a `str`**. The
  moment `_fmt` is generalised into a shared report formatter — which is the
  obvious next step for a function whose entire purpose is output formatting —
  the first thing anyone writes is `_fmt(r.get("review_count"))`, and it
  tracebacks with a message that names neither the type problem nor the function.

  The declaration `int | float | None` (`cli.py:29`) *does* forbid the string,
  so `mypy` would reject it — but `mypy` is declared at `pyproject.toml:64-68`
  (`strict = true`) and is **not installed** in this environment, and no workflow
  runs it. The protection is nominal.
- **Trigger:** `_fmt("1234")`. Or, after generalisation, any
  `_fmt(row.get("review_count"))` on a `csv.DictReader` row.
- **Fix:** `return "n/a" if n is None else f"{n:,}{suffix}"` →
  `return "n/a" if n is None else f"{n:,.0f}{suffix}"` is **not** a fix (still
  rejects `str`). Use an explicit conversion, or narrow the signature to `int`
  and let the type checker do the work once mypy is actually running.

### S3 — Two of `_fmt`'s three behaviours are dead, and its live one is inlined 11 more times

- **Where:** `cli.py:29-30`; call sites `cli.py:98-103`; inlined duplicates
  `cli.py:75, 93, 111, 112, 113, 117, 121, 126, 131, 194, 220, 276`
- **Breaks:** Neither distinguishing feature of `_fmt` is ever exercised:
  - **The `None → "n/a"` branch is unreachable.** `cli.py:95-96` —
    `count() -> int = sum(1 for ...)`. All six call sites pass an `int`. The
    branch that exists to distinguish "missing" from "zero" has never run.
  - **The `suffix` parameter is never passed.** A grep for two-argument calls
    returns exactly one hit, and it is the definition itself:
    `29:def _fmt(n: int | float | None, suffix: str = "") -> str:`. Confirmed.
    Exercised by hand for completeness: `_fmt(5, " ms") -> '5 ms'`,
    `_fmt(None, " ms") -> 'n/a ms'`, `_fmt(1234.5, " USD") -> '1,234.5 USD'` —
    all correct, all uncalled.
  - **The live behaviour is duplicated 12 more times in the same file.** `_fmt`
    is used in exactly one block (the first six field counts in `cmd_stats`),
    while the tri-state counters immediately below it — `cli.py:111-113` — and
    every other group (`cli.py:117,121,126,131`) use raw `f"{v:,}"` inline.
    `cmd_stats` therefore formats one report with two different conventions, and
    the tri-state block at `cli.py:105-113` deliberately bypasses `_fmt` because
    its values are `int`-typed and can never be `None`.
- **Trigger:** n/a — this is a maintenance finding. Read `cli.py:98-113` and note
  that the same report switches formatting strategy halfway down.
- **Fix:** Delete `suffix` and the `None` branch, rename `_fmt` to `thousands`,
  and route the remaining 12 inline sites through it. Or, if `stats`-style
  reporting is meant to be reusable, promote it to a `reporting.py` module — which
  the `src/` layout should do anyway.

### S3 — The `float` in `_fmt`'s signature silently produces scientific notation and `nan`

- **Where:** `cli.py:29`
- **Breaks:** `f"{n:,}"` does not group large floats; Python switches to
  scientific notation and the thousands separator vanishes:

  ```
  _fmt(1234.5678)          -> '1,234.5678'      (grouped=True)
  _fmt(1234567.891)        -> '1,234,567.891'   (grouped=True)
  _fmt(999999999999999.0)  -> '999,999,999,999,999.0' (grouped=True)
  _fmt(1e16)               -> '1e+16'           (grouped=False)   <-- separator gone
  _fmt(1.5e16)             -> '1.5e+16'         (grouped=False)
  _fmt(float('nan'))       -> 'nan'                          <-- not 'n/a'
  _fmt(float('inf'))       -> 'inf'
  _fmt(True)               -> '1'                           <-- bool is an int subclass
  ```

  So the function's name-level promise ("format a number with separators") holds
  for `int` and fails silently for `float`. `nan` returning `'nan'` rather than
  `'n/a'` in particular inverts the missing-value contract the function appears to
  implement. Unreachable today — the only callers pass `int` — but `float` is in
  the signature, so a type checker will happily admit `lead_score` or a
  completeness average.
- **Trigger:** `_fmt(1e16)` → `'1e+16'`; `_fmt(float("nan"))` → `'nan'`.
- **Fix:** Drop `float` from the annotation at `cli.py:29` — no caller passes one
  — or handle the non-finite case explicitly.

### S3 — `DATA_DIR` is CWD-relative and is evaluated at import, so reaching `_fmt` requires a directory

- **Where:** `cli.py:26` — `DATA_DIR = pathlib.Path("data")`
- **Breaks:** `DATA_DIR` is a **relative** path. It is evaluated during module
  import, so it binds to whatever the current working directory is at import time,
  and it feeds the `argparse` defaults at `cli.py:294, 298, 305`. Verified:

  ```
  cwd      : /private/.../opencode/cwdtest
  DATA_DIR : data | absolute? False | exists? True
  stats default file -> data/all_businesses.csv
  ```

  `leadminer stats` therefore reads `<cwd>/data/all_businesses.csv`. Run it from
  anywhere but the repo root and it reports `no such file: data/all_businesses.csv`
  (`cli.py:83`) and exits 2, while the data sits in `data/` one directory away.
  `cmd_doctor` gives the same false alarm (`cli.py:217-222`,
  `MISSING  data (no run has produced output yet)`) — a diagnostic that
  misdiagnoses its own environment. `tests/test_lead_signal.py:215` imports
  `cli`, so the suite inherits whatever CWD pytest was launched from.
  **This is not a dependency of `_fmt`** — `_fmt` never touches it — which is
  exactly why it is worth writing down: it is the module-level tax you pay to
  import a pure leaf function.
- **Trigger:** `cd /tmp && leadminer stats` with `data/` present in the repo.
- **Fix:** Resolve against a package-relative or `LEADMINER_DATA_DIR`-overridable
  base at `cli.py:26`, rather than against `os.getcwd()`.

### S3 — `cli.py:154`'s UTF-8 BOM check can never fire

- **Where:** `cli.py:154` (`bom_name = sum(1 for r in rows if (r.get("name") or "").startswith("\ufeff"))`),
  reading via `cli.py:142` (`open(path, newline="", encoding="utf-8-sig")`)
- **Breaks:** The two lines contradict each other. `utf-8-sig` **strips** a
  leading BOM on read, so by the time `cli.py:154` inspects `r["name"]` the
  `\ufeff` is already gone. Demonstrated against a real BOM-prefixed CSV
  (`b'\xef\xbb\xbfnam'`, found sitting in the repo root):

  ```
  read with encoding='utf-8-sig'  -> r['name'] = 'Cafe Beirut'
                                      startswith('\ufeff') -> False
  read with encoding='utf-8'      -> header key is '\ufeffname', not 'name'
                                      r.get('name') -> None
  ```

  So the validator's BOM guard is dead code, and the failure mode it was written
  to catch is instead silently absorbed: with a BOM-corrupted header,
  `cli.py:151` `r.get("name")` returns `None` for **every** row, so
  `cli.py:152` would fire `every row has a blank name` on a file that is full of
  names. In practice `cli.py:142` prevents that too — which is why the bug has
  stayed invisible. `main.py:118-124` writes with `encoding="utf-8-sig"`, so the
  project's own output never carries a stray BOM either.
- **Trigger:** any CSV whose first header cell is BOM-prefixed, read through
  `cmd_validate`'s own `utf-8-sig` reader.
- **Fix:** If the check is meant to warn about *foreign* writers, read the first
  3 bytes of `path` directly instead of relying on the decoded field.

## Not a bug, but worth knowing

- **No dependency in `_fmt`'s closure exists only for a type annotation, and none
  exists only for logging.** `cli.py` imports no `typing` member and no logging
  module at all; `_fmt` performs no I/O, holds no logger, and writes nothing but
  its return value. The PEP 563 directive at `cli.py:18` reduces the annotation
  edge set to *nothing at runtime*, verified via `inspect.signature` above. This
  is the cleanest part of the codebase by a wide margin.

- **A third category exists: imports kept only as smoke tests.**
  `cli.py:46` — `from scrapers.base import BaseScraper  # noqa: F401  (import check)`.
  The symbol is never referenced (ruff's `F401` is suppressed by the `noqa`); the
  import exists purely so that reaching `cli.py:47-49` proves `scrapers.base`
  imported. Under a `src/` layout this line is actively harmful: it is the only
  reason `cli.py` names `scrapers.base`, and if `scrapers` is reorganised the
  noqa hides the resulting break from every linter in the repo.

- **All of `cli`'s real dependencies are deferred, which relocates failure from
  import time to command time.** `cli.py:35, 46-49, 249-252` are function-local
  imports. In the `src/` restructure I performed, `import leadminer.cli` succeeded
  and `_fmt(1234567) -> '1,234,567'` worked — but `leadminer score` and
  `leadminer scrape --source osm` both tracebacked *at invocation*:
  ```
  File ".../leadminer/cli.py", line 249, in cmd_score
      from leadminer import main as pipeline
  ...
  ModuleNotFoundError: No module named 'requests'
  ```
  A refactor that leaves one function-local import un-namespaced passes every
  import-time smoke test and fails only in production. That is the practical
  migration hazard here — not a cycle.

- **`enricher.py:128` is a module-level import buried 127 lines into the file.**
  `from httpclient import DEFAULT_MAX_BODY_BYTES, get_session` executes at import
  time like any other top-level import, but it sits below four function
  definitions and a 12-line comment about thread-local sessions (a design note
  that has nothing to do with the import). ruff flags it as `E402 Module level
  import not at top of file`. Anyone auditing `enricher.py`'s dependencies by
  reading lines 1-4 — the natural place to look — misses its only project
  dependency. It should be at `enricher.py:4`, with the comment moved down to the
  call site it explains.

- **`enricher.py:2 import requests` is dead.** `grep -n requests enricher.py`
  returns line 2 (the import) and line 125 (a comment); there is no code use. So
  `enricher` *appears* to depend on `requests` but actually depends only on
  `httpclient` — which is exactly the shared-HTTP-layer boundary the `httpclient`
  refactor (`607e729`) established. Removing the stale import removes a phantom
  edge from the graph. Same for `urljoin`/`urlparse` at `enricher.py:4`.

- **The `src/` layout itself is not what breaks `_fmt`.** I ran the restructure
  end-to-end in a throwaway copy (`cli.py`, `main.py`, `enricher.py`, `dedup.py`,
  `httpclient.py`, `pitch_recommender.py` and `scrapers/` moved to
  `src/leadminer/`, all project-internal imports re-namespaced). `_fmt` came
  through completely unharmed. The blockers are `pyproject.toml:33` (console
  script points at top-level `cli`) and `pyproject.toml:35-37` (wheel target),
  plus the `google_places → enricher` inversion — none of which `_fmt` participates in.

- **Observation, not mine to fix:** three files named `" "`, `-` and `0` sit in
  the repository root (all mtime `2026-10-03 22:35:24`, all 374 bytes, all the
  22-column CSV header with a leading `b'\xef\xbb\xbf'`). They predate this
  report, were not created by this audit, and look like shell-redirect artifacts
  from a concurrently running agent — I left them untouched. They are, however, the
  real BOM-prefixed CSV that made the S3 finding above verifiable rather than
  theoretical.

- **Six CSVs, five writers, one reader.** `cli.py:86` and `cli.py:142` are the
  only two CSV readers in the CLI and both open `utf-8-sig`; `main.py:124` is the
  only writer and also writes `utf-8-sig`; `main.py:82-85` reads with
  `utf-8-sig` too. The encoding convention is currently consistent across the
  project. Worth preserving deliberately rather than by accident, since S3 shows
  the one place that tried to *enforce* it by inspection got it wrong.

## Recommended order of work

1. **Fix the wheel target and console script** (`pyproject.toml:32-37`) — verify
   the current failure with `uv build --wheel && python -m zipfile -l
   dist/leadminer-*.whl` first, so the fix is measured against a real baseline.
   This is the only finding on this target that can make the tool not run at all.
2. **Make the CI gates real** (`pyproject.toml:39-68`, `.github/workflows/`) — add
   a `lint` job running `ruff check .` and `mypy .`. This is a prerequisite for
   trusting every "mypy would have caught it" claim in the findings above, and it
   is what will keep the S1/S2 fixes from regressing.
3. **Break the `google_places → enricher` inversion** (S2) by lifting
   `infer_region` (`enricher.py:79`) into a dependency-free `geo` module. Do this
   *before* the `src/` move — it is the only edge that can become a circular
   import, and it is much cheaper to fix while the import paths are still flat
   and greppable.
4. **Adopt the `src/leadminer/` layout** and re-point every import. Move the six
   bare top-level modules into a package; update `pyproject.toml:33` to
   `leadminer = "leadminer.cli:main"`. I verified `_fmt` and its 6 call sites
   survive this unchanged.
5. **Decide what `_fmt` is for, then act** (S3) — either promote it to a
   `reporting.py` module used by all 18 numeric-format sites, or delete `suffix`
