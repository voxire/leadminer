# 203 — `_fmt` (cli.py:29) concurrency review

## Verdict

`_fmt` is **safe, and safe by construction rather than by luck**. It is a pure
function: it reads no global, writes no global, mutates no argument, closes over
nothing, performs no I/O, opens no session, and allocates one immutable `str`.
It is trivially reentrant, so no interleaving of any kind can change its result.

It is also **unreachable from any worker thread today**. Its only six call sites
are `cli.py:98-103`, all inside `cmd_stats` (`cli.py:79-132`), which spawns no
threads; and `cli.py` imports no concurrency primitive at all (`cli.py:20-24`:
`argparse`, `collections`, `csv`, `pathlib`, `sys`). So the literal question —
"is `_fmt` safe under this codebase's concurrency" — answers *yes, and there is
no concurrency to survive*: none of the 40-thread, 5-worker, or 3-scraper pools
in this repository can reach it.

The real problems are not in `_fmt`'s logic but in (a) the command it lives in,
which loads the entire cumulative master into memory, and (b) one of the three
pools the lens named, where an unguarded statement can discard an entire
source's results. Both are written up below, clearly labelled as **not** `_fmt`
defects.

---

## The function under review

`cli.py:29-30`

```python
def _fmt(n: int | float | None, suffix: str = "") -> str:
    return "n/a" if n is None else f"{n:,}{suffix}"
```

### Purity audit — line by line

| Dimension | Finding | Anchor |
|---|---|---|
| Shared mutable state | None. No module-level name is read or written. The only module globals in `cli.py` are `DATA_DIR` (`cli.py:26`, an immutable `pathlib.Path`) and the four imported modules — `_fmt` touches none of them. | `cli.py:26`, `cli.py:20-24` |
| Session reuse | N/A. No HTTP. `httpclient.get_session()` is never called and `httpclient` is never imported here. | `httpclient.py:61-71` |
| Dict mutation visible across threads | N/A. `_fmt` takes a scalar, not a dict. It performs no subscript assignment anywhere. | `cli.py:29` |
| Resource lifetime | Allocates exactly one `str` per call. No file handle, no socket, no `contextmanager`, nothing to leak or double-close. | `cli.py:30` |
| Reentrancy | Trivially reentrant. All state is in the call frame; there is nothing to interleave. Safe under recursion, signals, `atexit`, or being moved into a worker tomorrow. | `cli.py:29-30` |
| Mutation of arguments | None. `n` is rebound to nothing; `suffix` is only read. Both are immutables. | `cli.py:30` |

### Reachability — can `_fmt` ever run on a worker thread?

The three concurrency sites in this codebase, and whether they can reach `_fmt`:

| Pool | Anchor | Worker callable | Reaches `_fmt`? |
|---|---|---|---|
| 40 threads | `enricher.py:237` | `_fetch_website(url)` — `enricher.py:238` | **No.** Pure function of a `str`; never imports `cli`. |
| 5 workers | `google_places.py:194` | `fetch_query(query)` — `google_places.py:186`, submitted at `google_places.py:195` | **No.** Never imports `cli`. |
| 3 scrapers | `main.py:160` | `run(scraper)` — `main.py:157-158` | **No.** Never imports `cli`. |

The one CLI command that *does* drive a concurrent scraper is `cmd_scrape`
(`cli.py:61`, `list(registry[args.source]().scrape())`), which will run the
5-worker Places pool. But `cmd_scrape` prints with bare `print` and inline
f-strings at `cli.py:62-75` and never calls `_fmt`. So even that command
bypasses the function entirely.

**Conclusion: `_fmt` cannot be concurrently invoked as the code stands, and
would remain correct if it could.** No fix is required for thread safety. The
findings below are code-quality and scale issues, not races.

## Findings

### S2 — `cmd_stats`, the only caller of `_fmt`, loads the whole cumulative master and makes 13 passes over it

- **Where:** `cli.py:87` (`rows = list(csv.DictReader(f))`), reached from
  `_fmt`'s call sites `cli.py:98-103`
- **Breaks:** `all_businesses.csv` is cumulative-all-time — `main.py:150` loads
  it and `main.py:209` writes the *merged* set back, so it grows monotonically
  across every run forever. `cmd_stats` materialises every row as a dict and
  then traverses the full list **13 times**: 6× via `count()` (`cli.py:96`),
  3× for the `website_live` tri-state (`cli.py:107`, `108`, `109-110`), and 4×
  via `collections.Counter` (`cli.py:116`, `120`, `124`, `129`).
  Measured cost of the load alone (30-char values, 22 columns):

  | Rows | Resident after `list(csv.DictReader)` | Peak |
  |---|---|---|
  | 100,000 | 245 MB | 523 MB |
  | 500,000 | **1,227 MB** | **2,617 MB** |

  At 500k rows this is a ~1.2 GB resident, ~2.6 GB peak command. The GitHub
  Actions runner for `.github/workflows/scrape.yml` is 7 GB, so this is a
  genuine OOM risk, and it lands on the wrong command: `cli.py:80` describes
  `stats` as "the first thing to check" when a run looks wrong.
- **Trigger:** `leadminer stats` against a master that has accumulated to
  ~500k rows. Concrete input: 500,000 CSV rows with the 22 columns from
  `main.py:33-40`. Reproduces the numbers in the table above.
- **Fix:** accumulate counters and `Counter`s in a single pass over the
  `DictReader`, keeping only scalars; `_fmt` is already the correct place to
  format them at the end.

### S3 — `_fmt` raises `ValueError` on the only input type this CLI actually holds

- **Where:** `cli.py:30`
- **Breaks:** `cmd_stats` reads with `csv.DictReader` (`cli.py:87`), so every
  cell value is a `str`. `f"{n:,}"` applied to a `str` is an error:

  ```
  >>> _fmt("1000")
  ValueError: Cannot specify ',' with 's'.
  ```

  All six call sites survive only because `count()` (`cli.py:95-96`) coerces
  via `sum(...)` to an `int` first. The moment anyone adds the obvious next
  stat — a rating or `review_count` average — written as
  `_fmt(r.get("review_count"))`, the command dies with a `ValueError` whose
  message reads like a formatting bug rather than a type bug. The signature
  `n: int | float | None` (`cli.py:29`) promises to reject `str`, so this is
  arguably working as annotated; the issue is that the annotation does not
  match the ambient data model of the command it serves.
- **Trigger:** `_fmt("1000")` — or any future `_fmt(r.get("review_count"))`
  inside `cmd_stats`.
- **Fix:** `return "n/a" if n is None else f"{float(n):,.0f}{suffix}"` and widen
  the annotation to `int | float | str | None`, or have `count()` be the only
  door to `_fmt` and make that explicit in a comment.

### S3 — `_fmt` is half-adopted and its `suffix` parameter is dead code

- **Where:** `cli.py:29` (parameter), `cli.py:111`, `112`, `113`, `117`, `126`,
  `131` (bypass sites)
- **Breaks:** `cmd_stats` contains 13 numeric prints. 6 use `_fmt`
  (`cli.py:98-103`); 7 bypass it with raw `f"{v:,}"` (`cli.py:93`, `111`, `112`,
  `113`, `117`, `126`, `131`). Separately, **zero** call sites in the entire
  repository pass `suffix=` — the parameter at `cli.py:29` is never exercised.
  So the helper is both under-used *and* over-specified: the units feature was
  built and never wired up.
  The bypass sites are not currently broken — every one of them formats a value
  that is provably an `int` (`sum()` results at `cli.py:107-109`, `Counter`
  values at `116`/`120`/`124`/`129`, `st_size` at `cli.py:220`) — but they are
  the ones that would crash with `TypeError` on a `None`, which is precisely
  the case `_fmt` exists to handle. See "Not a bug, but worth knowing".
- **Trigger:** change `cli.py:116` to use a `most_common()` entry whose count
  is derived from an optional field and can be `None`.
- **Fix:** route all 13 sites through `_fmt` and either drop `suffix` or use it
  (`_fmt(x, " bytes")` at `cli.py:220` is the obvious candidate).

## Adjacent findings: the three pools the lens named

These are **not** `_fmt` defects. They are included because the lens asks
explicitly what could corrupt in those pools. The headline is good news: **all
three are currently correct.**

### The 40-thread pool in `check_websites` — safe, and correctly structured

- **Shared mutable state / dict mutation:** none leaks from workers to the
  shared list. `targets` is built from `enumerate(records)` at `enricher.py:231`,
  so every index is distinct; each future is mapped 1:1 to an index at
  `enricher.py:238`; and every write to `records` — `website_live` at
  `enricher.py:250`, `email` at `253`, `instagram` at `255`, `whatsapp` at `257`,
  `linkedin` at `259` — happens on the **main thread** inside the `as_completed`
  loop at `enricher.py:240-262`. Workers only compute
  `pool.submit(_fetch_website, url)` (`enricher.py:238`) and never receive the
  record. This is the correct "workers return values, parent owns the store"
  pattern. **No torn reads, no lost writes, no double-write to one record.**
- **Session reuse:** correct now. `get_session()` (`httpclient.py:61-71`) is
  backed by `threading.local()` (`httpclient.py:58`), so each of the 40 workers
  constructs its own `requests.Session` on first use. No shared cookie jar, no
  shared urllib3 pool. The old shared-module-`_SESSION` bug is documented at
  `enricher.py:124-127`.
- **Resource lifetime:** `r.close()` runs in a `finally` (`enricher.py:193-197`),
  so each response releases its connection. The 40 sessions themselves live as
  long as their worker threads and are released when the `with` block at
  `enricher.py:237` exits and the threads terminate. Cost, not correctness: 40
  fresh TLS handshakes per run with no cross-run reuse.
- **Reentrancy:** non-issue for `_fetch_website` (pure). The one reentrancy
  trap that *does* exist is in `get_session()`: the storage is per-**thread**,
  not per-pool. If `check_websites` were ever called from inside a worker
  thread, the nested calls would reuse that worker's session — which is still
  single-threaded ownership and therefore fine. It cannot be misused today
  because `_fetch_website` has no `session=` parameter.

### The 5-worker pool in `GooglePlacesScraper` — safe on shared state, unsafe on error propagation

**Safe parts:**
- Each query gets a **fresh** session created *inside* the worker at
  `google_places.py:189` (`self._make_session()`, which builds a new
  `requests.Session` at `google_places.py:160`). One session per query, 68 in
  total — wasteful, never shared. Correct.
- `seen_ids` (`google_places.py:181`) *is* genuinely shared mutable state across
  5 threads, but the check-then-add at `google_places.py:263-266` is entirely
  inside `with seen_lock:`, so no two workers can admit the same `place_id`.
  **Safe.**
- `all_records.extend(results)` is under `records_lock`
  (`google_places.py:191-192`). **Safe.**

### S1 (adjacent) — one unguarded statement discards an entire source's results

- **Where:** `scrapers/google_places.py:254-255`
- **Breaks:** the `try` block spans `google_places.py:226-252` (verified: its
  body ends at line 249, single handler at 250). Therefore
  `data = resp.json()` (**254**) and `places = data.get("places", [])` (**255**)
  sit **outside** the guarded region. Anything they raise escapes
  `_scrape_query`, escapes `fetch_query`, and is re-raised by
  `f.result()` at `google_places.py:197` ("re-raises any exception"). That
  unwinds the `with ThreadPoolExecutor` block at `google_places.py:194` and
  propagates out of `scrape()` **before** `yield from all_records` at
  `google_places.py:199` — so every Places record the other 4 workers already
  collected and appended under `records_lock` is discarded.
  In `main.py` this is caught at `main.py:167` and printed as
  `[GooglePlacesScraper] ERROR: ...`, then the run **continues and writes all
  five CSVs** (`main.py:209-213`) with zero Places data — indistinguishable in
  the output from "Google had nothing to find". That is exactly the failure
  mode this codebase twice claims to have fixed (`osm.py:48-50`,
  `httpclient.py:17-19`). `cmd_scrape` (`cli.py:61`) has the same shape with no
  handler at all, so `leadminer scrape --source google_places` dies on a
  traceback.
- **Trigger:** a **HTTP 200** response whose body is not a JSON object — an
  HTTPS-intercepting proxy or captive portal returning an HTML error page is
  the realistic case, and is common on Gulf/Levant corporate networks.
  Verified locally, no network required:
  - body `<html>502 Bad Gateway</html>` → `JSONDecodeError: Expecting value: line 1 column 1 (char 0)`
  - body `null` → `AttributeError: 'NoneType' object has no attribute 'get'`
  - body `[]` → `AttributeError: 'list' object has no attribute 'get'`
  - body `{}` → ok, 0 places (this one is fine)
  Note `raise_for_status()` at `google_places.py:249` cannot catch any of these —
  all three cases are 2xx.
- **Fix:** move lines 254-255 inside the `try` and add an explicit
  `except (ValueError, AttributeError)` that prints and returns the partial
  `records` list; do not let one query's malformed body abort the generator.

### S3 (adjacent) — generator/pool lifetime: correct today, one edit away from silent truncation

- **Where:** `google_places.py:168` (`-> Iterator[BusinessRecord]`, so `scrape()`
  is a generator) and `google_places.py:194` (the pool is created *inside* the
  generator body)
- **Breaks:** nothing today. `main.py:158` and `cli.py:61` both call
  `list(scraper.scrape())`, which drives the generator to exhaustion, so the
  `with` block closes normally and `yield from all_records`
  (`google_places.py:199`) is reached only after all 5 workers have joined. The
  trap: if anyone "improves" this to stream — e.g. moving a `yield` inside the
  `with` block, or having `fetch_query` yield directly — `all_records` is still
  empty at that moment and **every query silently returns zero rows with no
  error**. Conversely, a caller that obtains the iterator and abandons it
  without exhausting it defers `ThreadPoolExecutor.__exit__` (and its
  `shutdown(wait=True)` join) to generator finalisation at GC.
- **Fix:** make `scrape()` a normal function that returns a list (or add an
  explicit comment forbidding `yield` inside the pool block).

### S3 (adjacent) — interleaved `print` from worker threads: mechanism confirmed, no current call site triggers it

- **Where:** `google_places.py:175`, `218`, `231`, `244`, `251`, `257` and
  `osm.py:33`, `59` all print from worker threads, concurrently with main-thread
  prints at `main.py:165`, `enricher.py:235`, `enricher.py:262`
- **Breaks:** `print` is two `write()` calls (text, then newline). `TextIOWrapper`
  holds a newline-less write in `_pending_bytes` and only flushes on the
  newline, so a second thread's `print` can be flushed *inside* the first
  thread's line. Demonstrated deterministically:
  ```
  main:    sys.stdout.write("AAA-no-newline")
  worker:  print("BBB-full-line-from-worker")
  main:    sys.stdout.write("\n")
  =>  AAA-no-newlineBBB-full-line-from-worker\n
  ```
  **However**, I could not reproduce it with realistic call sites: 6,000 short
  lines from 3 threads and 180 lines of 9,000 chars each both produced **0**
  garbled lines, because the GIL is not released between the two writes of a
  short `print`, and a sub-8 KiB line never triggers an intermediate flush. The
  `[tag]` prefix on every message also preserves attribution, so only *ordering*
  is scrambled, never line integrity.
- **Trigger:** a single `print` whose text exceeds `TextIOWrapper`'s 8 KiB chunk
  size (forcing a flush between the text write and the newline write), or an
  explicit `flush=True` immediately after a long message. `flush=True` is used
  at `google_places.py:232`, `238`, `245` and `osm.py:51-55` — all currently
  short, so none trips it.
- **Fix:** move these to `logging` (`httpclient.py:45` already sets up a module
  logger, so the pattern exists). `logging` handlers emit one
  `StreamHandler.emit` call per record and are effectively atomic per line.

## Not a bug, but worth knowing

- **`_fmt` is correctly the wrong place to put shared state, and worth keeping
  that way.** If a future change makes `cmd_stats` parallel (e.g. counting
  fields concurrently), `_fmt` stays valid as-is — its purity is exactly the
  property that makes that refactor free. Do not add a cache, a memo dict, or a
  module-level format-width constant that is mutated at runtime.
- **The 6 sites that bypass `_fmt` are the ones missing its `None` handling.**
  `cli.py:111`, `112`, `113`, `117`, `126`, `131` and `cli.py:220` all format
  values that are structurally `int` today, so nothing is broken. But they are
  the ones that would raise `TypeError: unsupported format string passed to
  NoneType.__format__` if a counter could ever be `None`. Routing them through
  `_fmt` (previous finding) closes that off.
- **Thread-safety of the enricher and Places pools is already done right and
  should not be "fixed" further.** `check_websites` keeps all record mutation on
  the main thread (`enricher.py:249-259`) and `GooglePlacesScraper` locks both
  of its shared structures (`google_places.py:263-266`, `191-192`). Reviewers
  should treat these as reference patterns, not as risks.
- **`main.py:161`'s `raw.extend(batch)` at `main.py:166` runs on the main
  thread** inside `as_completed`, and each of the 3 scraper instances is touched
  by exactly one worker (`main.py:157-158`, one `pool.submit` per scraper), so
  there is no cross-thread instance sharing. Record *ordering* in `raw` is
  nondeterministic — irrelevant, since `dedup` (`main.py:180`) reorders anyway.
- **`enricher.py:327-328` mutates process-global state**
  (`urllib3.disable_warnings`) but does so on the main thread, before
  `check_websites` at `enricher.py:337`, and is idempotent. Not a race.
- **`_fmt` is untested.** `tests/test_lead_signal.py:211-226` exercises
  `cmd_stats` end-to-end via `redirect_stdout`, so the helper is only covered
  transitively and only with `total == 1` — the "n/a" branch at `cli.py:30`
  and the thousands-separator branch have no direct assertion.

## Recommended order of work

1. **Fix the unguarded parse in the Places scraper** (`google_places.py:254-255`)
   — S1, and the only finding here that can silently drop a whole source. Small
   diff, disproportionate blast radius.
2. **Make `cmd_stats` stream in one pass** (`cli.py:87` + the 13 traversals) —
   S2, and `_fmt` is already the right seam for formatting the accumulators at
   the end, so the fix reuses the function under review.
3. **Finish adopting `_fmt`**: route the 7 bypassing sites through it, then
   either use `suffix` (e.g. `cli.py:220`) or delete the parameter.
4. **Widen `_fmt`'s input contract** so `_fmt("1000")` cannot raise
   (`cli.py:29-30`) — do this before step 3, or step 3 will expose the
   `ValueError`.
5. **Convert worker-thread `print` to `logging`** across `google_places.py`,
   `osm.py`, and `enricher.py` — S3, but it removes a whole class of
   thread-interleaving questions and makes the 300-minute Actions logs readable.
6. **No concurrency work is needed on `_fmt`.** It is correct as written.
