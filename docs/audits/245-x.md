# 245 — `cli.doctor`: complexity and cost as the dataset grows to 500k

## Verdict

`cmd_doctor` (`cli.py:204-244`) is **O(1) in the number of businesses and allocates O(1) memory** — it never opens a CSV, so its cost is flat at 10k, 100k and 500k records (measured: 0.33–1.14 ms of local work, no trend across a 50× data increase). The complexity question is therefore answered cleanly and there is **no scaling bug to fix**. What *is* broken is the diagnostic value the command pays its constant price for: the exit code ignores its own probe results (`cli.py:244` returns 0 after three `FAIL` lines), the Places probe is a tautology that cannot report anything but `OK` (`cli.py:240-241`), and the Overpass probe watches the wrong endpoint and misreads the exact status codes Overpass documents for "you are being throttled" (`cli.py:234,240`). Single change with the largest speedup: run the three probes in a `ThreadPoolExecutor(3)` — measured **15.12 s → 5.04 s, a 3.00× speedup** on the failure path.

---

## Complexity analysis

Let `n` = number of business records in `data/all_businesses.csv` and `k` = number of `*.csv` files in `data/`.

| Step | Anchor | Cost | Depends on `n`? |
|---|---|---|---|
| env loop | `cli.py:210` `for var in ("GOOGLE_PLACES_API_KEY", "SCRAPER_EMAIL")` | O(2) | no — literal tuple |
| `DATA_DIR.exists()` | `cli.py:217` | 1 × `stat(2)` | no |
| `sorted(DATA_DIR.glob("*.csv"))` | `cli.py:219` | O(k) `scandir` | no — `k` is fixed at 5 by `main.py:209-213` |
| `f.stat().st_size` | `cli.py:220` | 1 × `stat(2)` per file, **file never opened** | no — returns metadata |
| probe loop | `cli.py:233-237` `for name, url in (...)` | O(3) | no — literal 3-tuple |
| `requests.get(url, timeout=5)` | `cli.py:239` | 3 network round trips | no |

**Verdict: O(1) time, O(1) space in `n`. Not O(n), not O(n²).** There is no loop anywhere in `cmd_doctor` whose bound is derived from the data. Peak allocation is a list of `k` `Path` objects plus three fully-buffered response bodies (`requests` defaults to `stream=False`, so `cli.py:239` reads each body eagerly — irrelevant here because `/api/status` is a few hundred bytes, but it is why `stream=True` is the correct hygiene at `cli.py:239`, since the code only ever reads `r.status_code`).

### Measured: local cost is flat in `n`

Synthetic 23-column master CSVs (schema from the brief), `data/` holding the 5 files `main.py` writes. `cmd_doctor`'s local block — env loop + `exists()` + `glob()` + `stat()` + the real f-string formatting, output to `/dev/null`, averaged over 200 reps (2000 for the tight figure):

| records | master size | `cmd_doctor` local work |
|---|---|---|
| 10,000 | 2.5 MB | 1.140 ms (first run, cold cache) |
| 100,000 | 25.7 MB | **0.326 ms** |
| 500,000 | 130.5 MB | **0.443 ms** (0.726 ms over 2000 reps) |

50× more records, identical cost. This is a genuine design win and worth protecting: **`doctor` is the only subcommand in `cli.py` whose cost is independent of dataset size**, precisely because it never opens a CSV. Any future "let doctor also check the master is parseable" change must stay at `readline()` + a chunked newline count (below), not `list(csv.DictReader)`.

### `cmd_doctor`'s own wall clock at 10k / 100k / 500k

The network component is an estimate — per BRIEF rule 2 I made no calls to Overpass, Wikidata or Google. The local component is measured.

| records | local (measured) | 3 probes, all healthy (est.) | **total** | worst case (est.) |
|---|---|---|---|---|
| 10,000 | 0.001 s | 0.6–2.0 s | **0.6–2.0 s** | 15.0 s |
| 100,000 | 0.001 s | 0.6–2.0 s | **0.6–2.0 s** | 15.0 s |
| 500,000 | 0.001 s | 0.6–2.0 s | **0.6–2.0 s** | 15.0 s |

The three columns are identical by construction. The "worst case" column is not: it is 15 s serially today and up to 30 s once the per-address connect-timeout amplification in S2-b applies. `doctor` is the first thing an operator runs, so 15–30 s of an unchanging screen is the entire user-visible cost of the command.

### The contrast: what the operator runs *next* is the thing that scales badly

`cmd_validate` (`cli.py:135`) and `cmd_stats` (`cli.py:79`) both begin `rows = list(csv.DictReader(f))` (`cli.py:143`, `cli.py:87`). Measured on the same files:

| records | master | `cmd_validate` total | of which the set at `cli.py:190` | peak RSS | RAM / file size |
|---|---|---|---|---|---|
| 10,000 | 2.5 MB | 0.169 s | 0.044 s (1.2 MB) | 35.7 MB | 14× |
| 100,000 | 25.7 MB | 1.148 s | 0.307 s (11.3 MB) | 208.1 MB | 8.1× |
| 500,000 | 130.5 MB | **7.851 s** | 1.674 s (48.8 MB) | **946.9 MB** | **7.3×** |

Every stage is linear (10k→100k = 6.7×, 100k→500k = 7.7×, against 10× and 5× of data — the mild superlinearity is GC pressure and page faults, not algorithmic). The dupe check at `cli.py:190` is the only proportional *allocation* inside it, and it is proportionate to a fault: `(name, phone)` is near-unique by construction, because `dedup` merges on normalised phone first, so the set holds ~`n` tuples — 48.8 MB at 500k, growing linearly forever, to answer a question (`> 5% duplicates?`) that could be decided by a hash of a *normalised* key or by sampling.

`all_businesses.csv` is documented as the cumulative all-time master (`main.py:8`), so `n` only ever grows. Extrapolating the measured 1.9 kB of RAM per record: ~1.9 GB / ~12 s at 1M, ~3.8 GB at 2M.

**And the same answer is available for 36× less.** Chunked newline count over the master, 1 MiB buffer, O(1) memory:

| records | master size | chunked row count | throughput |
|---|---|---|---|
| 10,000 | 2.5 MB | 0.004 s | 691 MB/s |
| 100,000 | 25.7 MB | 0.021 s | 1205 MB/s |
| 500,000 | 130.5 MB | **0.219 s** | 596 MB/s |

0.219 s and constant memory, versus 7.851 s and 947 MB for `cmd_validate` on the identical file. That is the single biggest efficiency fact in this neighbourhood of the codebase, and it belongs in `doctor`, not in `validate` — see S2-c.

## Findings

### S1 — `doctor` exits 0 after printing three `FAIL` lines

- **Where:** `cli.py:208`, `cli.py:214`, `cli.py:238-243`, `cli.py:244`
- **Breaks:** `ok` is initialised `True` at `cli.py:208` and set `False` at exactly one place — `cli.py:214`, the missing `GOOGLE_PLACES_API_KEY`. The connectivity loop at `cli.py:238-243` prints `OK`/`WARN`/`FAIL` but never assigns `ok`. So `return 0 if ok else 1` at `cli.py:244` returns **0 when every probe failed**. A health check whose only machine-readable output contradicts its own human-readable output is worse than no check: `leadminer doctor && leadminer run` proceeds to a full multi-hour scrape against a network that cannot reach a single upstream. The design intent is already on record — `docs/audits/037-cli-design.md:21` specifies non-zero exit codes for credential/config errors and `:653` specifies wiring `doctor` into `scrape.yml`. Whoever wires it up inherits a green light on a dead environment. It also makes the command untestable: there is no observable that distinguishes "network fine" from "network gone".
- **Trigger:** `GOOGLE_PLACES_API_KEY=x leadminer doctor` in a container with no egress, or on a laptop behind a captive-portal Wi-Fi where `overpass-api.de` resolves but the TLS handshake is intercepted. All three probes take `cli.py:242`; output is three `FAIL` lines; `echo $?` prints `0`.
- **Fix:** set `ok = False` inside the `except` at `cli.py:242` and on `r.status_code >= 400` at `cli.py:240`; use distinct exit codes (0 clean / 1 credential / 4 connectivity) per `037-cli-design.md:21`.

### S1 — the Google Places probe cannot fail: every 4xx is reported as `OK`

- **Where:** `cli.py:236` (URL), `cli.py:239` (`requests.get`), `cli.py:240-241` (classification)
- **Breaks:** two independent defects compound into a probe that is unfalsifiable.
  1. **Wrong verb, wrong auth.** Google documents Text Search as an HTTP **POST** with a JSON body and an `X-Goog-Api-Key` header: "A Text Search (New) request is an HTTP POST request of the following form: `https://places.googleapis.com/v1/places:searchText` … `-H 'Content-Type: application/json' -H 'X-Goog-Api-Key: API_KEY'`" ([Text Search (New), Places API (New)](https://developers.google.com/maps/documentation/places/web-service/text-search)). `cli.py:239` issues a `requests.get` with no body and — unlike `scrapers/google_places.py:161-165` — no `X-Goog-Api-Key` header.
  2. **The classifier treats every client error as success.** `note = "" if r.status_code < 500 else …` and `'OK ' if r.status_code < 500 else 'WARN'`. Any 4xx — 400, 401, 403, 404, 405, **429** — prints `OK   Google Places`. So the line reads `OK` with no key, a revoked key, a key with Places API disabled, billing suspended, or quota exhausted.
  The chain this hides: with no valid key, `GooglePlacesScraper.scrape()` prints "skipping" and returns an empty iterator (`scrapers/google_places.py:169-171`); the run **succeeds**, writes all five CSVs, and ships zero Google-sourced leads. `doctor` endorses that configuration. Quota exhaustion (429) is the single most likely real-world state for this project — see `docs/audits/014-google-places-quota.md`.
- **Trigger:** `GOOGLE_PLACES_API_KEY="" leadminer doctor` → prints `MISSING  GOOGLE_PLACES_API_KEY`, then `OK   Google Places`. `GOOGLE_PLACES_API_KEY=<revoked> leadminer doctor` → `OK   Google Places`. `leadminer scrape --source google_places` → 0 records, exit 1.
- **Fix:** issue the real request — `requests.post(url, json={"textQuery": "Beirut", "fieldMask": "places.id"}, headers={"X-Goog-Api-Key": key}, timeout=5)` — and require `200` + a parseable `places` key; accept `200` and `429` (with `RESOURCE_EXHAUSTED`) as distinguishable outcomes, everything else a failure. `r.status_code` is available from the headers, so this costs no extra round trip.

### S2 — the Overpass probe watches the wrong endpoint and prints `OK` for the documented throttling codes

- **Where:** `cli.py:234`, `cli.py:240-241`; contrast `scrapers/osm.py:9`, `httpclient.py:142-146`
- **Breaks:** production queries `https://overpass-api.de/api/interpreter` (`scrapers/osm.py:9`); `doctor` probes `https://overpass-api.de/api/status`, a slot-availability text page served by the web frontend. It proves the web server is up, not that a query can run. The Overpass manual states that requests shed by the rate limiter are answered **HTTP 429** and requests refused for the timeout/maxsize mechanism are answered **HTTP 504** ([Overpass API User's Manual, "Quotas"](https://dev.overpass-api.de/overpass-doc/en/preface/commons.html)), and the OSM wiki additionally instructs clients to back off on **429 or 406** ([Overpass API](https://wiki.openstreetmap.org/wiki/Overpass_API)). `406` and `429` are both `< 500`, so `cli.py:240-241` prints `OK` in precisely the state that means "stop and wait 30 seconds". Meanwhile the pipeline's own client disagrees: `httpclient.py:142-146` `_should_retry()` returns `True` for 429 — doctor and the code that does the work have opposite definitions of broken. `/api/status` also returns 200 while the instance is starved (it reports "N slots available now" in the body), so a green Overpass line does not predict whether tonight's real query gets a slot; the same manual notes requests may be **enqueued for up to 15 seconds** and then discarded. That is the failure `doctor` exists to catch.
- **Trigger:** any CI run from an IP the shared instance has rate-limited → Overpass returns 429 → `leadminer doctor` prints `OK   Overpass`, `leadminer run` then fails its only OSM query. Note also the manual's own guidance to this project: "Nowadays this server is overloaded … do not expect high reliability" and commercial use should self-host.
- **Fix:** POST the production query shape to `/api/interpreter` — `[out:json][timeout:5];node(33.89,35.50,33.90,35.51);out 1;` — require 200 plus parseable JSON, and treat 429/504/406 as failures with the status printed.

### S2 — the three probes are serial, so the worst case is 3× the timeout (measured 3.00× to fix)

- **Where:** `cli.py:233-243`, `timeout=5` at `cli.py:239`
- **Breaks:** the loop body blocks, so wall clock is the **sum** of three unrelated latencies that share no dependency. Measured against a local server that never answers, 2000 reps not needed — 3 probes × 5 s timeout:
  ```
  serial   3 probes, 5s timeout each  : 15.12s
  parallel 3 probes, 5s timeout each  :  5.04s   speedup 3.00x
  ```
  Two documented amplifiers on top:
  - The requests docs state "the connect timeout applies to each connection attempt to an IP address. If multiple addresses exist for a domain name, the underlying `urllib3` will try each address sequentially until one successfully connects. This may lead to an effective total connection timeout *multiple* times longer than the specified time, e.g. an unresponsive server having both IPv4 and IPv6 addresses will have its perceived timeout **doubled**" ([Advanced Usage § Timeouts](https://requests.readthedocs.io/en/latest/user/advanced/#timeouts)). On an IPv6-broken network — common on cloud CI — the Overpass probe alone can take 10 s, putting the worst case at **30 s**, or 10 s once parallelised.
  - Same source: "Neither the connect nor read timeouts are **wall clock**." The read timeout is the gap *between* bytes, so an intercepting proxy that trickles a response body keeps `doctor` alive indefinitely past its advertised 5 s. Name resolution is a blocking `getaddrinfo()` outside the socket timeout entirely, bounded only by the OS resolver's own retry budget.
- **Trigger:** a laptop on a VPN that blackholes outbound 443 to `query.wikidata.org` but allows `overpass-api.de`. Serial: 5 s (Overpass OK) + 5 s (Wikidata FAIL) + 5 s (Places FAIL) = 15 s of a frozen screen, then `return 0` per S1.
- **Fix:** `with ThreadPoolExecutor(max_workers=3) as pool: results = list(pool.map(probe, TARGETS))` — 3.00× measured, and it also collapses the 30 s dual-stack worst case to 10 s. Print results in the original order (`pool.map` preserves it) so output stays diffable.

### S2 — doctor's data report gets *less* useful as `n` grows; the useful version is 36× cheaper than the command that has it

- **Where:** `cli.py:217-222`
- **Breaks:** `doctor` prints `f.stat().st_size` and nothing else. At 500k the master is 130.5 MB and the question an operator actually has — "did last night's run write 500k rows, or truncate the file to a header?" — is unanswerable from a byte count. A header-only truncate is ~1.9 kB; so is a run that died on row 3. Conversely 130 MB could be 500k rows or 50k rows with long addresses. There is also no `st_mtime`, so a three-week-old master and last night's look identical, and no check that the file has the expected 23 columns (measured: 23 including the trailing empty). `doctor` is degrading exactly as the dataset grows, while the fix is essentially free.
- **Trigger:** `data/all_businesses.csv` truncated to its header by a disk-full or OOM kill during `main.py:209`. `leadminer doctor` → `all_businesses.csv  1,884 bytes`. `leadminer validate` → `every row has a blank name` (via `cli.py:151`), but only after 0.2 s at 10k, and at 500k it has to load 947 MB first.
- **Fix:** for `all_businesses.csv` only, add `st_mtime`, a `readline()` header check against the 23 expected columns, and a chunked row count (`sum(chunk.count(b"\n") for chunk in iter(lambda: f.read(1 << 20), b""))`). Measured 0.219 s and O(1) memory at 130.5 MB — 36× faster and ~900× lighter than `cmd_validate` on the same file, and it keeps `doctor`'s O(1) memory property while becoming the fastest data check in the CLI.

### S3 — `SCRAPER_EMAIL` is checked but never exercised, and `doctor` sends the wrong User-Agent to the two APIs that ask for one

- **Where:** `cli.py:210` (and `:211`) vs `httpclient.py:74-85`, `httpclient.py:66-69`, `scrapers/osm.py:35`, `scrapers/wikidata.py:73`
- **Breaks:** `SCRAPER_EMAIL` matters for exactly one reason — it is interpolated into the User-Agent at `httpclient.py:84-85`, which `get_session()` installs on every production request. `doctor` never builds that string and never sends a UA: `cli.py:239` uses a bare `requests.get`, whose default UA is `python-requests/<ver>`. So `OK   SCRAPER_EMAIL` at `cli.py:212` is a `bool(os.environ.get(...))` test of a variable whose actual effect on the two APIs' accept policies is never verified. Both upstreams ask for a descriptive UA — the OSM wiki: "Be sure to check that your app and website adds User-Agent or Referer headers to requests that uniquely identify your app", plus the self-hosting expectation for commercial use — and `query.wikidata.org` is known to reject generic clients. Note also that `ok` is not set for `SCRAPER_EMAIL` at all (`cli.py:213` gates on `var == "GOOGLE_PLACES_API_KEY"`), so its absence is reported but never fails the command; that part is defensible, since `httpclient.py:84` degrades gracefully to a UA with no contact.
- **Fix:** send `httpclient._user_agent()` (promote it to a public helper) on all three probes, and add a "UA:" line to doctor's credential block so the value is visible.

### S3 — `f.stat()` is unguarded against the invariant asserted 8 lines below it

- **Where:** `cli.py:220` vs the comment at `cli.py:228-229` ("doctor exists to diagnose a broken environment, so it must never be the thing that tracebacks")
- **Breaks:** the stated invariant is not upheld by code, and the failure mode is Python-version dependent, which makes it worse to reason about.
  - On **3.12** (the floor declared at `pyproject.toml:12`, `requires-python = ">=3.12"`), `pathlib.Path.glob` delegates to the `glob` module. `glob._iterdir()` yields entries under `if not dironly or entry.is_dir():` and, for a top-level `*.csv` pattern, `dironly` is `False`, so **no stat happens** and `_glob1`'s `fnmatch.filter` matches on name alone. A dangling symlink is therefore yielded, and `f.stat()` at `cli.py:220` raises `FileNotFoundError` — uncaught, since `cli.py:314` handles only `KeyboardInterrupt`. Result: a full traceback out of the one command that promises never to traceback.
  - On **3.14** (verified here) `pathlib` has its own `scandir`-based implementation whose docstring reads "yield all **existing** files"; the dangling entry is silently skipped. Measured: `data/` containing `sales_ready.csv` plus a dangling `all_businesses.csv` printed one line, no error — so the file is **omitted from the report with no warning**, which is the worse diagnostic outcome of the two.
  - A TOCTOU unlink between `glob()` and `stat()` raises on any version.
- **Trigger:** a `.csv` symlink in `data/` whose target was rotated away (rclone/Drive sync leaves partials and links), on Python 3.12.
- **Fix:** `try: size = f.stat().st_size except OSError: size = None` and print `<unreadable>` — or use `os.scandir()`, whose `DirEntry` already carries the needed metadata.

## Not a bug, but worth knowing

- **The complexity answer is genuinely good news, and worth stating to the team.** `cmd_doctor` is the only subcommand in `cli.py` whose cost is independent of dataset size, because it is the only one that never opens a CSV. Measured flat at 0.33–1.14 ms across 10k → 500k. Preserve that property: the temptation when adding "and check the master looks sane" is `list(csv.DictReader)`, which costs 7.851 s and 947 MB at 500k for the same file that a chunked newline count reads in 0.219 s with constant memory.
- **`try: import requests / except ImportError` at `cli.py:225-231` is exactly right.** A diagnostic command that dies with `ModuleNotFoundError` before it can report on a broken environment is worse than useless; the early `return 1` with an actionable install hint is the correct pattern, and the comment explains why. Keep it.
- **`timeout=5` is set at all.** `requests` applies no timeout by default; a bare `requests.get` in a health check is a hang. The value is short for a diagnostic and the per-address caveat (S2-b) is the only real issue.
- **The per-endpoint `try/except` at `cli.py:238-243` correctly isolates probes** — one dead host does not abort the other two, which is what you want from a triage tool. Parallelising (S2-b) keeps that property; `pool.map` preserves output order.
- **`cmd_doctor` ignores `args` entirely.** There is no `--data-dir`, `--timeout`, `--offline`, `--json` or `--strict`. `037-cli-design.md:149-154,575` designed `--strict` and exit codes 3/4. Given `DATA_DIR = pathlib.Path("data")` at `cli.py:26` is CWD-relative — consistent with `main.py:41`, so not a doctor-specific bug, but note that the message at `cli.py:222`, "no run has produced output yet", asserts a conclusion `doctor` cannot support: the real cause is usually "you are not in the repo root". Printing `DATA_DIR.resolve()` and rewording to "no `data/` directory relative to `$PWD`" costs one line.
- **Not on this lens, but adjacent:** `cli.py:190`'s `(name, phone)` set is the only proportional allocation in the validate path (48.8 MB at 500k, growing forever) and it answers a threshold question about a key that is near-unique by construction. Audits 001/002/024 cover `dedup`; this is the read-side twin.

## Recommended order of work

1. **`cli.py:244` — make the exit code reflect the probe results.** Two lines; unblocks CI wiring (`037-cli-design.md:653`) and makes every other doctor check observable in a test.
2. **`cli.py:240` — replace `< 500` with an explicit allow-list per service** (`200` and, for Places, a real authenticated POST). Removes the tautological Google probe and the `OK`-on-429 Overpass probe in one edit.
3. **`cli.py:233-243` — `ThreadPoolExecutor(max_workers=3)`.** The single largest speedup available in this function: **15.12 s → 5.04 s measured (3.00×)** on the failure path, and 30 s → 10 s in the dual-stack case, with no semantic change.
4. **`cli.py:217-222` — report `st_mtime`, header column count and a chunked row count for the master.** 0.219 s and constant memory at 130.5 MB; turns `doctor` from a file-existence check into the cheapest real data check in the CLI.
5. **`cli.py:220` — wrap `f.stat()` in `try/except OSError`.** Honours the invariant the comment already claims.
6. **`cli.py:210,239` — send `httpclient._user_agent()` on the probes** and surface the UA in the credential block.

**Reproduction.** The two benchmark scripts were written to `/private/var/folders/.../T/opencode/` (`bench_doctor.py <n>` for the scaling table, `bench_probes.py` for the serial/parallel figure) and deliberately left out of the repo. Neither installs a package nor touches the network beyond `127.0.0.1`. `bench_doctor.py` generates a synthetic 23-column master, runs `cmd_doctor`'s local block verbatim over a `data/` dir holding the five files `main.py:209-213` writes, then times `cli.py:143`/`:190`/`:151-188` for contrast.
