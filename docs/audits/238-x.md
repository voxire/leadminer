# 238 — Dependency trace of `cmd_validate` (cli.py:135)

## Verdict

`cmd_validate` has **zero project-internal dependencies**. It imports nothing from
`main`, `enricher`, `dedup`, `scrapers` or `pitch_recommender`, and it reads no
shared constant. That is not cleanliness — it is the problem. It re-derives, from
string literals, four contracts that already have owners elsewhere in the repo:
the CSV schema (`main.FIELDS`, `main.py:33`), the CSV reader semantics
(`main.load_master`, `main.py:77`), the geographic bounds
(`enricher._LB_COORD_REGIONS` / `_KSA_COORD_REGIONS`, `enricher.py:58`/`70`), and
the default data directory (`main.DATA_DIR`, `main.py:41`). Each re-derivation is
an independent copy that can drift, and one of them already has drifted into a
silent no-op: **if the `lat`/`lon` columns are renamed or dropped, the coordinate
check quietly stops running and the command still prints "all checks passed" and
exits 0** (`cli.py:168-169` swallows `KeyError`).

## Findings

### S1 — The coordinate check silently no-ops when a column is missing, and the gate still exits 0

- **Where:** `cli.py:167-169`, threshold at `cli.py:172`
- **Breaks:** `float(r["lat"])` uses `__getitem__`, not `.get()`. A `csv.DictReader`
  row has no `lat` key if the header lacks it, so `KeyError` is raised — and
  `KeyError` is explicitly listed in the `except` at `cli.py:168` and turned into
  a bare `continue` at `cli.py:169`. `bad_coords` stays at 0, no problem is
  appended, and `cmd_validate` reports `all checks passed` with exit 0. A schema
  rename (`lat` -> `latitude`) or a truncated export permanently and invisibly
  disables the single most valuable check in the file, and the one thing the
  command is trusted for.
- **Trigger:** a CSV whose header is `name,latitude,longitude,phone,rating`, every
  row at `48.85, 2.35` (Paris). Verified:

  ```
  checked 200 rows in renamed.csv
    all checks passed
  exit: 0
  ```

  Same result with the `lat`/`lon` columns deleted outright:

  ```
  checked 200 rows in no_coords.csv
    all checks passed
  exit: 0
  ```

- **Severity defence:** S1 = "wrong results, silent data loss, or a run that dies;
  blocks trust in the output." This is precisely a block on trust: a gate that
  returns green on a file with no coordinate columns is worse than no gate, because
  it converts "I did not check" into "I checked and it is fine". It is not S2 because
  no amount of human attention compensates — the output looks verified.
- **Fix:** assert the header up front. `reader = csv.DictReader(f); missing = {"lat","lon","rating","name"} - set(reader.fieldnames or [])` → hard-fail, and narrow the per-row `except` to `except (ValueError, TypeError): continue` so a `KeyError` can never be a skip.

### S2 — The gate is not wired into the pipeline that publishes the data

- **Where:** `.github/workflows/scrape.yml:69` (`run: python main.py`), `:71-82`
  ("Validate output before publishing")
- **Breaks:** the workflow never calls `leadminer validate`. The step named
  "Validate output before publishing" is hand-rolled shell: a non-empty file check
  (`scrape.yml:74`) and a row-count floor (`scrape.yml:80`, `< 100` rows). None of
  the checks in `cmd_validate` run before the CSVs are pushed to Google Drive at
  `scrape.yml:85-86`. `cli.main` is never invoked by CI either, and `pip install -e .`
  is never run (`scrape.yml:34` installs `requirements.txt`), so the `leadminer`
  console script (`pyproject.toml:33`) does not exist in that environment.
- **Trigger:** a run where every `lat`/`lon` is `0,0` and every `name` is blank
  still produces >100 rows, passes `scrape.yml:74` and `:80`, and is uploaded.
- **Severity defence:** S2 not S1 — the Drive upload is gated by *something*, and
  this does not itself corrupt data. It materially degrades operability: the
  quality gate that the audit work built is dead code in the automated path, which
  is why the S1 above has not yet caused an incident. Fixing S1 is cheap; fixing
  this is what makes the fix matter.
- **Fix:** `- run: pip install -e .` then `- run: leadminer validate data/all_businesses.csv` in place of the shell step.

### S2 — The duplicate check can only produce false positives; it is a true-negative-only instrument

- **Where:** `cli.py:190-192`
- **Breaks:** `dupes` is computed on **raw** `(name, phone)`. `dedup.dedup()` keys
  on the **normalized** phone (`dedup.py:205`, via `normalize_phone`) or on
  `(normalize_name(name), city)` (`dedup.py:212-214`). Those key spaces cannot
  contain a repeated raw `(name, phone)` pair, so for any record with a usable
  phone the count is structurally zero — the check measures a post-condition the
  pipeline already guarantees. The one configuration where it *does* fire is the
  one where it is wrong: phone-less records keyed by `(name, city)`. The same
  chain name in two different cities is two legitimate businesses
  (`dedup._extract_city`, `dedup.py:72-76`) that `dedup` correctly keeps, and
  `cmd_validate` reports them as duplicates.
- **Trigger:** 400 chains, each with 8 branches in 8 different cities, no phone
  numbers. `dedup()` keeps all 3200 as distinct. Verified:

  ```
  input 3200 -> dedup() kept 3200 (all legitimately distinct)
  checked 3,200 rows in chains.csv
    PROBLEMS:
      - 2800 duplicate (name, phone) pairs
  exit: 1
  ```

  Add a phone to each branch and `dedup` collapses the corpus first, after which
  the same check is silent:

  ```
  input 3200 -> dedup() kept 400
  checked 400 rows in chains_phone.csv
    all checks passed
  exit: 0
  ```

- **Severity defence:** S2 — it is a false-positive machine attached to the
  diagnostic tool, so a real signal ("duplicates!") is produced on healthy data
  and a real one (cross-country phone duplicates, `dedup.py:8-21`) is invisible.
  Not S1 because it does not damage the data; it wastes the operator's time and
  trains them to ignore the output.
- **Fix:** reuse `dedup.normalize_phone` and `dedup._extract_city` — i.e. `dupes = len(records) - len(dedup.dedup(rows_as_dicts))` — instead of re-keying on raw strings.

### S2 — The 1% coordinate tolerance is divided by the wrong denominator

- **Where:** `cli.py:164-172`
- **Breaks:** `bad_coords` counts only rows whose `lat`/`lon` actually parse; rows
  with blank, `None`, or non-numeric coordinates `continue` at `cli.py:169` and
  are not in the numerator. But the threshold at `cli.py:172` is
  `total * 0.01` — **all** rows. Wikidata emits `(None, None)` whenever
  `_parse_point` fails (`scrapers/wikidata.py:101`), OSM emits `None` for ways with
  no `center` tag (`scrapers/osm.py:68-69`), and Places can omit `location`
  (`scrapers/google_places.py:272-274`). So the effective tolerance on rows that
  *have* coordinates is `0.01 / (fraction with coordinates)`. As coordinate
  coverage falls, the gate gets weaker.
- **Trigger:** 1000 rows, 50 blank coordinates, 10 out-of-box. Verified:

  ```
  checked 1,000 rows in diluted.csv
    all checks passed
  exit: 0
  ```

  That is 10% of the rows that actually carry coordinates — well past the intended
  1% — and the gate is green.
- **Severity defence:** S2 — the threshold silently rescales itself against the
  data it is judging, so the gate is hardest to trip exactly when data quality is
  worst.
- **Fix:** track `checked` alongside `bad_coords` and compare against `checked * 0.01`, reporting both counts.

### S2 — `DATA_DIR` is declared twice; the two copies are CWD-relative and will diverge

- **Where:** `cli.py:26` vs `main.py:41`; consumed at `cli.py:294`, `:298`, `:305`
- **Breaks:** `cli.py:26` is `pathlib.Path("data")` — a *relative* path resolved
  against the process CWD, exactly as `main.py:41` is. `cmd_validate`'s default
  argument is `str(DATA_DIR / "all_businesses.csv")` (`cli.py:298`). This is an
  implicit dependency on an undeclared global: process CWD and the duplicated
  constant. The moment `main.DATA_DIR` becomes configurable
  (`os.environ.get("LEADMINER_DATA_DIR")`, which is the obvious next step and
  which `cmd_doctor` at `cli.py:216-222` is already shaped to report on), the
  pipeline writes somewhere `leadminer validate` will never look — and the
  operator gets `no such file: data/all_businesses.csv`, exit 2, indistinguishable
  from "no run has ever happened".
- **Trigger:** `cd /tmp && leadminer validate` after a successful run from the repo
  root.
- **Severity defence:** S2 — currently harmless because both copies are identical,
  but it is a landmine planted in the diagnostic path, and it is one line to fix
  now versus a confusing incident later.
- **Fix:** `from main import DATA_DIR` in `build_parser`, or move `DATA_DIR`/`FIELDS` into a new `storage.py` that both import.

### S3 — Three different tolerances in one gate, and the strictest is on the narrowest field

- **Where:** `cli.py:172` (1%, coords), `cli.py:187` (`if bad_rating:` — zero
  tolerance), `cli.py:191` (5%, dupes)
- **Breaks:** `rating` is populated by exactly one of three sources
  (`scrapers/google_places.py:297`); OSM (`scrapers/osm.py:114`) and Wikidata
  (`scrapers/wikidata.py:122`) hardcode `rating=None`. So the only check with no
  tolerance at all applies to the smallest, most fragile column, while the column
  that is present on every row gets a 1% allowance.
- **Trigger:** one row with `rating=7` in a 500,001-row master. Verified:

  ```
  checked 500,001 rows in one_bad_rating.csv
    PROBLEMS:
      - 1 rows have a rating outside 0-5
  exit: 1
  ```

  A single bad cell from one query fails the whole weekly run.
- **Fix:** give `bad_rating` the same 1% budget as coordinates, or hoist all three thresholds into one documented table at the top of the function.

### S3 — "N/A" is reported as "outside 0-5"

- **Where:** `cli.py:182-188`
- **Breaks:** `float("N/A")` raises `ValueError`, which increments `bad_rating`
  at `cli.py:183` and is then reported by `cli.py:188` as
  "N rows have a rating outside 0-5". The message is wrong, and it will send an
  operator hunting for a data-pipeline bug when the cause is a hand-edited or
  Sheets-exported placeholder. Verified:

  ```
  checked 1 rows in na_rating.csv
    PROBLEMS:
      - 1 rows have a rating outside 0-5
  exit: 1
  ```

  Note `dedup._validity` (`dedup.py:134-139`) already handles exactly this case
  correctly — it returns 0 for unparseable and only range-checks what parsed. That
  is the version `cli.py` should be sharing.
- **Fix:** count unparseable and out-of-range separately and say which it is.

### S3 — The BOM check is unreachable for any file this pipeline writes

- **Where:** `cli.py:154-156`, message at `cli.py:156`
- **Breaks:** the check fires when a `name` field starts with `\ufeff`. But the
  file was opened with `encoding="utf-8-sig"` at `cli.py:142`, which strips a BOM
  at byte 0 only; and the only writer, `main.write_csv`, emits `utf-8-sig`
  (`main.py:124`) via a temp-file-plus-`os.replace` (`main.py:122`, `:130`), so
  the file always has exactly one BOM, at position 0, which is always stripped.
  The check can therefore only fire on a hand-edited or foreign file — and the
  failure mode it claims to describe ("written without utf-8-sig") is already
  structurally impossible. Meanwhile the failure it could actually cause — a BOM
  glued to the first column name, turning `name` into `\ufeffname` and making every
  `r.get("name")` return `None`, which *would* trip `cli.py:151` — is only
  detectable by inspecting `reader.fieldnames`, which nothing does. (`main.py:82-84`
  documents this exact hazard in a comment.)
- **Trigger:** a BOM that appears mid-file (e.g. a file concatenated from two
  exports). Verified — it does fire here, which is the only case it can reach:

  ```
  checked 51 rows in bom_mid.csv
    PROBLEMS:
      - 1 names carry a UTF-8 BOM (written without utf-8-sig)
  exit: 1
  ```

  Note the message is also self-contradictory: a BOM in a *name* is not evidence
  that the file was "written without utf-8-sig".
- **Fix:** replace it with `if reader.fieldnames and reader.fieldnames[0].startswith("\ufeff")` and report the file, not the row count.

## Not a bug, but worth knowing

- **`cmd_validate` and `cmd_stats` require no third-party package at all.** Every
  project import in `cli.py` is function-local (`cli.py:35,46-49,206,226,249-252`),
  and the only module-level imports (`cli.py:20-24`) are stdlib. Verified: `import cli`
  succeeds in an interpreter with no `requests` installed. This is exactly the
  property you want from the commands the module docstring says you reach for
  "when a run looks wrong" (`cli.py:14-15`) — but it is accidental, not designed.
  A single module-level `from main import FIELDS` would destroy it. If you fix the
  S1/S2 duplication findings, keep the imports lazy.
- **Converse: `leadminer score` is documented as "no network" but hard-requires
  `requests`.** `cli.py:12` and `cli.py:304` both say no network, yet `cmd_score`
  imports `main` (`cli.py:249`) and `enricher` (`cli.py:250`), and `enricher.py:2`
  imports `requests` at module level. It works, but the help text is a contract the
  implementation does not honour.
- **`argparse` is used by `cmd_validate` for a type annotation only**, at
  `cli.py:135`. Because of `from __future__ import annotations` (`cli.py:18`) that
  annotation is never evaluated, so `argparse` is not needed at runtime by this
  function at all. `collections` (`cli.py:21`) is not used by `cmd_validate` either
  — only by `cmd_scrape` (`:68`) and `cmd_stats` (`:116,120,124,129`).
- **The geo boxes are deliberately looser, not contradictory.** `cli.py:160` LB is
  lat 33.0–34.8 / lon 35.0–36.9; the union of the 8 `enricher.py:60-67` LB boxes is
  lat 33.04–34.72 / lon 35.09–36.85. `cli.py:161` SA is lat 16.0–32.2 / lon
  34.4–55.7; the union of `enricher.py:71-75` is lat 21.3–26.65 / lon 39.05–50.30.
  Both CLI boxes are supersets. Two sources of truth, but they agree today — this
  one is duplication to consolidate, not a live bug.
- **`in_box` is a nested closure, correctly.** `cli.py:159-162` needs no import and
  should not have one. The only thing wrong with it is that the literals are copies.
- **The check that is missing is the one that matters most, and it is a dependency
  problem, not a logic problem.** `cmd_validate` never compares `country` against
  coordinates, even though `main.resolve_country` (`main.py:50-74`) documents that
  the `country` field silently defaulted to `None`/`"LB"` and corrupted region
  inference and phone normalization for an entire run. Because `in_box` accepts a
  row in *either* box regardless of `country`, the inconsistency is invisible:

  ```
  lat=24.7136 lon=46.6753          # Riyadh
    in_box()                  -> True   (gate says OK)
    infer_region(country='LB') -> None
    infer_region(country='SA') -> Riyadh
    leadminer validate on 500 such rows -> exit 0
  ```

  500 Riyadh businesses tagged `country=LB` with `region` blank pass the gate.
  This is precisely the bug class `resolve_country` exists to prevent, and
  `cmd_validate` — the tool built to catch it — cannot see it because it does not
  import `resolve_country` or `infer_region`. Note also
  `scrapers/google_places.py:127-136`: `_country_from_query` derives the country
  from the query string with a silent `"LB"` default, so any newly added query
  without a country keyword ships KSA rows labelled Lebanon.

## Circular imports and the `src/` layout

Today there is **no cycle**, and `cmd_validate` contributes nothing to one. The
concern is what a `src/` move exposes.

### The escaping imports

`scrapers/google_places.py:26` does `from enricher import infer_region` — an
absolute import that leaves the package — while line 28 in the same file does
`from .base import ...`, a relative one that stays inside. Same pattern in
`scrapers/osm.py:4` and `scrapers/wikidata.py:4` (`from httpclient import ...`).
Under `src/leadminer/` these must all become `leadminer.enricher` /
`leadminer.httpclient`, and `enricher.py:128` (`from httpclient import
DEFAULT_MAX_BODY_BYTES, get_session`) becomes `leadminer.httpclient`.

### The latent cycle

`scrapers/__init__.py` is **0 bytes**. That is the only reason the escaping
imports do not already cycle. The cycle that a `src/` move arms:

```
enricher.py:306   priority = record.get("industry_priority")
                    ^ enricher.lead_score READS a value owned by scrapers/whitelist.py
                      and passed in as a dict key by main.py:190 — no import needed today
```

The moment anyone replaces that string-keyed contract with a real import (to get
a default, a type, or a shared enum), the graph closes:

```
enricher -> scrapers.whitelist -> scrapers/__init__ -> scrapers.google_places
         -> enricher          (via google_places.py:26)
```

`scrapers/whitelist.py` itself imports nothing (its only import, `cli.py:9`, is
inside a docstring), so today the edge does not exist. It is one import away, and
the src-layout move is the moment someone will add it.

Two things make the move more dangerous than it looks:

1. **`cli.py` is a top-level module, not a package member.** `pyproject.toml:33`
   declares `leadminer = "cli:main"`, and `pyproject.toml:35-37` ships
   `include = ["scrapers/"]` only. The console script points at a module the wheel
   does not contain. Every `src/` change has to touch `pyproject.toml:33` and
   `:37` in lockstep with the import rewrites, or the entry point breaks in a way
   that looks like a packaging bug rather than a layout bug.
2. **`scrape.yml:69` runs `python main.py`**, which depends on the repo root being
   on `sys.path`. Under `src/` that invocation stops working outright and must
   become `python -m leadminer` or `leadminer run`. This is a workflow edit, not
   a code edit, so it is the one most likely to be missed.

### What `cmd_validate` needs for the move

Zero import rewrites. It has no project imports. Its *only* cost under `src/` is
that its string literals — column names, `"utf-8-sig"`, `"data"`, the geo bounds —
are now the only place those contracts exist outside their owners, and a scripted
rewrite of `from main import` will not touch them.

## Imports that exist only for a type annotation or only for logging

Not reachable from `cmd_validate` (which uses none), but in the same closure as
its sibling subcommands, and all three would be flagged by any import audit:

| Site | Import | Status |
|---|---|---|
| `cli.py:135` | `argparse.Namespace` | **annotation only**; unevaluated thanks to `cli.py:18` |
| `cli.py:21` | `collections` | unused by `cmd_validate`; used by `cmd_scrape`/`cmd_stats` only |
| `enricher.py:4` | `urljoin, urlparse` | **entirely dead** — zero occurrences anywhere else in the file; it is the sole `requests`-adjacent reason `cmd_score` pulls in `enricher` |
| `scrapers/osm.py:1`, `scrapers/wikidata.py:1` | `logging` | logger created at `:7` and then **never called** (`log.` has zero occurrences in either file) — the modules import a logging stack and emit nothing through it, while `cli.py`, `main.py` and `enricher.py` all use bare `print()` |

## Recommended order of work

1. **Validate the header before validating the rows** (`cli.py:142-143`). Split the
   `except` at `cli.py:168` so `KeyError` can never be a skip, and hard-fail on a
   missing `lat`/`lon`/`rating`/`name`. One edit, closes the S1, and turns the
   `type: ignore[arg-type]` at `cli.py:167` into something a type checker can verify.
2. **Wire it into CI** (`scrape.yml:69`, `:71-82`). Add `pip install -e .` and call
   `leadminer validate data/all_businesses.csv` in place of the shell step. Without
   this, fix 1 is a manual tool nobody runs under pressure.
3. **Stop duplicating the reader.** Give `cmd_validate` the same
   `main.load_master` path `cmd_score` already uses (`cli.py:259`), or move
   `load_master` / `write_csv` / `FIELDS` / `DATA_DIR` (`main.py:33,41,77,108`) into a
   new `storage.py` that `main`, `cli` and any future validator all import. That
   single extraction removes five of the seven rows in the duplication table at once
   and preserves the zero-dependency property of `validate` (keep the import
   function-local).
4. **Re-key the duplicate check** on `dedup.normalize_phone` + `dedup._extract_city`
   (`dedup.py:33`, `:72`) instead of raw `(name, phone)`, or simply call
   `dedup.dedup()` on the loaded rows and report `len(rows) - len(deduped)`.
5. **Add the country/coordinates cross-check** and the missing-column count to the
   output, importing `main.resolve_country` and `enricher.infer_region` so the gate
   agrees with the pipeline about what LB and SA are.
6. **Before the `src/` move:** make `enricher.lead_score`'s dependency on
   `industry_priority` (`enricher.py:306`) explicit, or move the priority vocabulary
   out of `scrapers/whitelist.py` into a leaf module both can import. Otherwise the
   move closes a cycle through a 0-byte `scrapers/__init__.py`.
7. **Housekeeping:** drop the dead `urljoin`/`urlparse` at `enricher.py:4`; either
   use the `log` objects in `osm.py:7`/`wikidata.py:7` or drop the `logging`
   imports; delete `collections` from `cli.py:21` if `cmd_scrape`/`cmd_stats` are
   ever split out.
