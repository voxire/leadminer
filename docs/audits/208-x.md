# 208 — `cmd_run` (`cli.py:33`) read as a contract: what each input actually produces

**Target:** `cli.py:33-37` and its callers (`cli.py:285-286` registration, `cli.py:315` dispatch)
**Lens:** function-level contract audit. Every input that reaches `cmd_run` (the `Namespace`, the
process CWD, the environment, `sys.path` state, concurrent invocations) is executed offline and
the exact stdout/exit code/bytes on disk recorded.

## Verdict

`cmd_run` is five lines and **four of them are structural lies**: it is annotated `-> int` but
returns `None` (`main.py:148` is `def main() -> None`), it accepts an `argparse.Namespace` it never
reads, it resolves its data directory against the process CWD with no way to override, and it
performs the only destructive write in the codebase with no lock and no fail-closed guard. Net
effect: `leadminer run` **cannot return non-zero for any reason whatsoever** — not a dead Overpass,
not a revoked API key, not a total source outage. The worst concrete outcome I reproduced is a
zero-byte-output run that exits `0` and leaves five freshly-timestamped, completely empty CSVs in a
brand-new `data/` directory, which is byte-for-byte what a first-ever run looks like.

Every finding below was **executed**, not reasoned about. No network was used: `requests` was
replaced in `sys.modules` with a stub before importing `main`, and the three scraper classes were
replaced on the imported module. No repository file was written; all probes ran in a scratch
directory under `$TMPDIR`.

## Findings

### S1 — `cmd_run` returns `None`, so `leadminer run` exits `0` under every possible failure

- **Where:** `cli.py:33` (`def cmd_run(args: argparse.Namespace) -> int:`),
  `cli.py:37` (`return pipeline.main()`), against `main.py:148` (`def main() -> None:`),
  laundered by `cli.py:315` (`return int(args.func(args) or 0)`).
- **Breaks:** `main.main()` has no return statement, so `cmd_run`'s single expression evaluates to
  `None`. The `or 0` at `cli.py:315` turns that into exit `0`. There is no code path — none — by
  which `leadminer run` reports failure, because the value it would report on does not exist, and
  the only consumer of the value (`or 0`) maps every falsy result to success. The failure is
  laundered three times upstream before it reaches the exit code:
  - `scrapers/osm.py:56` — Overpass failure is `print(...)` then `return`, so the scraper yields
    nothing and looks like a source with zero results.
  - `scrapers/google_places.py:169-171` — a missing/empty `GOOGLE_PLACES_API_KEY` prints
    `"[Google] GOOGLE_PLACES_API_KEY not set, skipping."` and returns.
  - `main.py:167-168` — `except Exception as e: print(..., file=sys.stderr)`, then continues.
  The pipeline then does the whole normal thing: `combined = raw_filtered + master`
  (`main.py:179`), dedup, enrich, and `write_csv` on all five outputs (`main.py:209-213`), followed
  by a complete, healthy-looking `Summary:` block (`main.py:219-226`).
- **Exact input:** all three sources fail. Reproduced offline by replacing the scrapers with a class
  whose `scrape()` raises:
  ```python
  class Boom:
      def scrape(self): raise RuntimeError("403 quota exceeded")
  pipeline.OSMScraper = pipeline.WikidataScraper = pipeline.GooglePlacesScraper = Boom
  rc = cli.main(["run"])
  ```
- **Exact wrong output** (verbatim from the probe, run in an empty directory):
  ```
  exit code: 0
  [Boom] ERROR: 403 quota exceeded          (x3, on stderr)
  Total raw records from scrapers: 0
  After merge + dedup: 0 unique businesses
    Written: data/all_businesses.csv (0 records)
    Written: data/qualified_businesses.csv (0 records)
    Written: data/with_websites.csv (0 records)
    Written: data/without_websites.csv (0 records)
    Written: data/sales_ready.csv (0 records)
    Summary:
    Total unique businesses : 0
    ...
  files written: ['all_businesses.csv', 'qualified_businesses.csv', 'sales_ready.csv',
                  'with_websites.csv', 'without_websites.csv']
  ```
  `data/all_businesses.csv` contains one line: the UTF-8 BOM plus the 23-column header.
- **Second, independent harm: the `-> int` annotation is a lie that breaks programmatic callers.**
  `rc = cli.cmd_run(ns)` gives `None`, so any caller that trusts the signature explodes:
  ```
  rc + 1  ->  TypeError: unsupported operand type(s) for +: 'NoneType' and 'int'
  rc > 0  ->  TypeError: '>' not supported between instances of 'NoneType' and 'int'
  ```
  `mypy --strict` is configured (`pyproject.toml:64-68`) and *would* catch this as
  `error: Incompatible return value type (got "None", expected "int")  [return-value]` at
  `cli.py:37` — but the CI workflow never runs `mypy` (`.github/workflows/scrape.yml:69` is the
  only execution step), so the configured gate is inert.
- **Concrete input that needs no code edit at all:** `env -u GOOGLE_PLACES_API_KEY leadminer run`.
  `google_places.py:170` prints "skipping", the run proceeds on whatever the master holds, and the
  operator gets a green result with zero new Google leads.
- **Fix:** give `main.main()` a real `-> int` built from a per-source success counter
  (`main.py:162-168`), return it, and make `cmd_run` `return pipeline.main()` after fixing
  `main.py:148` — one line each, and drop the `or 0` at `cli.py:315`.

**Overlap note:** `docs/audits/200-fn-cli-py-main-ops.md:32-60` reports the same root cause from the
dispatcher's side. The `cmd_run`-specific defect that report does not name is the `-> int`
annotation violation at `cli.py:33`, which is what makes this a *contract* bug rather than only a
missing feature.

### S2 — `args` is never read: `leadminer run` accepts no options, so there is no way to scope, rehearse, or redirect a run

- **Where:** `cli.py:33` (the `args` parameter is dead), `cli.py:285-286` (the `run` subparser is
  registered with `add_parser(...).set_defaults(func=cmd_run)` and **no** `add_argument` call).
- **Breaks:** the function's only parameter is write-only. The docstring's claim that this is a
  "thin wrapper … so there is one code path" (`cli.py:34`) is true but it means `leadminer run`
  offers *zero* control surface over a command that performs ~5 hours of paid API calls and
  overwrites the cumulative master. There is no `--source`, no `--data-dir`, no `--limit`,
  no `--dry-run`, no `--yes`.
- **Exact input:** `leadminer run --help` →
  ```
  usage: leadminer run [-h]

  options:
    -h, --help  show this help message and exit
  ```
  `leadminer run --source osm` → `SystemExit(2)`, `leadminer: error: unrecognized arguments: --source osm`.
  `leadminer scrape --source osm` *is* accepted (`cli.py:289-290`) but that code path
  (`cli.py:61-76`) **never writes anything** — it prints counts and returns. So the natural
  operator reflex, "just run one source", is either rejected (`run`) or silently discards the work
  (`scrape`).
- **Wrong output:** the parameter is provably unread. Passing garbage works and is ignored:
  ```
  cmd_run(None)                     -> None   (full pipeline ran)
  cmd_run('not-a-namespace')        -> None   (full pipeline ran)
  cmd_run(Namespace(whatever=1))    -> None   (full pipeline ran)
  ```
  So the trap for the next engineer is concrete: anyone who adds a global flag
  (`p.add_argument("--data-dir")` at `build_parser`) will find `args.data_dir` present, plausible,
  and **completely ignored by `run`** while `stats`/`score` honour their own `args.file`. Two
  subcommands, one flag, opposite behaviour, no error.
- **Fix:** either give `run` real options and read them (`data_dir`, `sources`, `dry_run`), or
  rename the parameter to `_args` and delete the parameter so the dispatcher cannot imply a
  configurability that does not exist.

### S2 — `data/` is resolved against the process CWD and `run` cannot override it, so running from any subdirectory silently starts from zero

- **Where:** `cli.py:37` → `main.py:150` (`load_master(DATA_DIR / "all_businesses.csv")`) and
  `main.py:209-213` (`write_csv(DATA_DIR / ...)`), where `DATA_DIR = pathlib.Path("data")` at
  `main.py:41` — a **relative** path, and `run` exposes no override (previous finding).
- **Breaks:** the cumulative master is the product (`all_businesses.csv` = "every business, all
  time", `README.md:45`). It is looked up relative to wherever the operator happens to be standing.
  `leadminer run` from `docs/audits/` therefore (a) does not see the real master, (b) believes it is
  a first-ever run, and (c) writes a brand-new empty `data/` there. The real master is untouched —
  so nothing is destroyed — but the operator's run is now a **zero-record run that exits 0 and
  prints a full `Summary:` block**. This is the exact scenario the workflow guards against at
  `.github/workflows/scrape.yml:57-63` (*"A missing master would be treated as first run and
  overwrite history"*), with the guard implemented only in YAML — never in `cmd_run`.
- **Exact input:** master seeded with 1 row in `<root>/data/all_businesses.csv`, then:
  ```python
  os.chdir("<root>/docs/audits")
  cli.main(["run"])            # scrapers stubbed to return 0 records
  ```
- **Exact wrong output:**
  ```
  master rows visible from repo root: 1
  `leadminer run` from docs/audits -> exit 0
  (no "Loaded N records" line at all)
  Total raw records from scrapers: 0
  After merge + dedup: 0 unique businesses
  ./data created under the subdir: True
    contents: ['all_businesses.csv','qualified_businesses.csv','sales_ready.csv',
               'with_websites.csv','without_websites.csv']
  parent master untouched, rows still: 1
  ```
  And the divergence compounds across subcommands, because `stats`/`validate`/`score` default to
  their *own* relative copy of the same string (`cli.py:26`, used at `cli.py:294,298,305`):
  ```
  `leadminer stats`            from docs/audits -> exit 1: "data/all_businesses.csv is empty"
  `leadminer stats ../../data/all_businesses.csv` -> exit 0: "...(1 rows)"
  ```
  So the two halves of the CLI disagree about where the data is, and `run` is the half that
  cannot be pointed anywhere.
- **Mitigating fact (verified):** a stray `data/` is not committed —
  `git check-ignore -v docs/audits/data/x.csv` → `.gitignore:9:data/`. The damage is confined to a
  confusing directory and a false-success log line, not to git.
- **Fix:** `DATA_DIR = pathlib.Path(os.environ.get("LEADMINER_DATA_DIR", "data")).resolve()` in one
  place, imported by both `cli.py` and `main.py`, plus a `--data-dir` flag that `cmd_run` reads.

### S2 — `import main` inside `cmd_run` is un-namespaced and unguarded: it can silently execute the wrong module, and it tracebacks in a broken environment

- **Where:** `cli.py:35` (`import main as pipeline`).
- **Breaks, branch A (silent, exit 0):** the import binds to whatever top-level module named `main`
  wins on `sys.path`, not to this repository's `main.py`. `main` is one of the most common module
  filenames in existence, and `pyproject.toml:33` exposes this code as a console script whose
  module path (`cli:main`) lives at the repo root — an editable install (`README.md:80`,
  `uv pip install --system -e ".[dev]"`) puts the repo root on `sys.path` for *every* Python
  process in that environment.
- **Exact input (branch A):** any earlier `sys.path` entry containing a `main.py`:
  ```python
  sys.path.insert(0, "<scratch>/shimdir")   # contains an unrelated main.py
  cli.cmd_run(None)
  ```
- **Exact wrong output:**
  ```
  cmd_run will import: <module 'main' from '.../shimdir/main.py'>
  cmd_run(None) rc = 0
  !!! WRONG main() executed from .../shimdir/main.py !!!
  module actually executed: .../shimdir/main.py
  ```
  `leadminer run` → exit `0`, no CSV written, no error. The one command whose job is to write the
  product reports success and produces nothing.
- **Breaks, branch B (noisy but at least loud):** no `try/except ImportError` around the import.
  This is directly observable in this checkout, because `requests` is not installed here:
  ```
  $ python3 /Users/mhomsi/dev/dummy/leadminer/cli.py run
  Traceback (most recent call last):
    File ".../cli.py", line 322, in <module>     raise SystemExit(main())
    File ".../cli.py", line 315, in main           return int(args.func(args) or 0)
    File ".../cli.py", line 35, in cmd_run        import main as pipeline
    File ".../main.py", line 25, in <module>      from scrapers.osm import OSMScraper
    File ".../scrapers/osm.py", line 4, ...       from httpclient import fetch_with_retry, ...
    File ".../httpclient.py", line 43, ...        import requests
  ModuleNotFoundError: No module named 'requests'
  EXIT=1
  ```
  The sibling subcommand written for exactly this situation guards it, with a comment explaining
  why: `cli.py:227-231` — *"doctor exists to diagnose a broken environment, so it must never be the
  thing that tracebacks."* `cmd_run`, the command that tells you whether the pipeline works, has no
  such guard and no equivalent "run `pip install -e '.[dev]'" hint beyond a traceback's last line.
- **Corroboration for branch A's other direction:** `docs/audits/020-type-contract-import-cycle.md:296`
  already records that in an installed wheel `from enricher import ...` fails with
  `ModuleNotFoundError` because the top-level modules are not laid out as a package. `cmd_run`'s
  `import main` is the same class of problem one level up, and the pyproject makes it reachable:
  `pyproject.toml:37` includes only `scrapers/` in the wheel.
- **Fix:** move `main.py`, `enricher.py`, `dedup.py`, `httpclient.py`, `pitch_recommender.py`,
  `cli.py` into a `leadminer/` package and use `from . import pipeline` — one import line at
  `cli.py:35` becomes shadow-proof and layout-proof.

### S2 — `cmd_run` takes no lock: two overlapping `leadminer run` invocations silently lose one run's leads

- **Where:** `cli.py:33-37`. The whole read-modify-write of the cumulative master
  (`main.py:150` load → `main.py:179` merge → `main.py:209-213` write) happens with no mutual
  exclusion anywhere in `cli.py`.
- **Breaks:** `write_csv`'s temp-file + `os.replace` (`main.py:121-130`) makes each individual
  write atomic, so the file is never corrupt — but the **read** at `main.py:150` happened hours
  earlier. Two overlapping runs both read master `N`, both merge their own new finds, and the
  second to finish overwrites the first. GitHub Actions guards this at the job level
  (`.github/workflows/scrape.yml:15-17`, `concurrency: group: leadminer-scrape`), but the README
  tells humans to run this command by hand (`README.md:94-97`) and nothing stops a human run from
  overlapping the weekly one, or two humans from overlapping each other.
- **Exact input:** run A starts (reads master), run B starts 10 minutes later (reads the same
  master), B finishes and writes, then A finishes and writes its stale in-memory list.
  Reproduced with the real `load_master`/`write_csv`:
  ```
  start:      ['Seed Cafe']
  after B:    ['Seed Cafe', 'Run B find']
  after A:    ['Seed Cafe', 'Run A find']
  ```
  `"Run B find"` is **gone**. Both runs exited `0`; neither log mentions the clobber.
- **Fix:** take an exclusive `fcntl.flock` on `data/.run.lock` at the top of `cmd_run` and fail
  with a non-zero code if it is already held.

### S3 — `DATA_DIR` is defined twice, independently, and `run` writes one copy while `stats` reads the other

- **Where:** `cli.py:26` (`DATA_DIR = pathlib.Path("data")`) and `main.py:41`
  (`DATA_DIR = pathlib.Path("data")`) — two separate definitions of the same literal.
- **Breaks:** nothing binds them together. A change to one (making it absolute, making it
  configurable, renaming the directory) silently desynchronises the writer from the reader:
  `leadminer run` writes `main.DATA_DIR` while `leadminer stats` with no argument reads
  `cli.DATA_DIR` (`cli.py:294`, likewise `:298` and `:305`) and `leadminer doctor` reports on
  `cli.DATA_DIR` (`cli.py:217-220`). A refactor that only touches `main.py` produces a CLI that
  cheerfully reports "no run has produced output yet" about a directory full of CSVs.
- **Fix:** define `DATA_DIR` once and `from main import DATA_DIR` in `cli.py`, or move it to a
  shared `config.py`.

## Not a bug, but worth knowing

- **The lazy `import main` at `cli.py:35` is a good decision, not an oversight.** It is what makes
  the docstring's promise true (`cli.py:14-15`: *"Commands other than `run`/`scrape`/`doctor` never
  touch the network, so they are safe to run anywhere"*). Verified in the broken-environment
  probe above: `run` hard-fails on a missing `requests`, while `stats`/`validate`/`score` import
  only `csv`/`pathlib` (`cli.py:22-24`) and `doctor` degrades to a friendly message
  (`cli.py:227-231`). Moving the import to module scope to "fix" branch B above would destroy
  that property — the fix is a package-relative import, not an eager one.
- **There genuinely is one code path.** `cmd_run` calls `pipeline.main()` with no arguments and
  nothing else, and `main.main()` takes no parameters (`main.py:148`), so `leadminer run` and
  `python main.py` produce byte-identical output. The divergence between the two entrypoints is
  only in the *return value* (`cli.py:322` raises `SystemExit(main())`; `main.py:246` discards it),
  and since `main()` returns `None` in both cases, neither is currently distinguishable by exit
  code either. This is also why `docs/audits/200-fn-cli-py-main-ops.md:210-225` warns that fixing
  `cli.py` will not change cron behaviour until `.github/workflows/scrape.yml:69` is switched over.
- **The cumulative master is not destroyed by a failed run.** Confirmed by seeding a 3-row master
  and failing all three sources: `After merge + dedup: 3 unique businesses`, all five CSVs
  rewritten, `master rows after run: 3`. `main.py:179` (`combined = raw_filtered + master`) plus
  the atomic `write_csv` mean a total scrape outage degrades to "no new leads this week", not
  "history erased". The damage is confined to the false-success exit code, the lost API spend, and
  — via the overlap case above — one run's finds.
- **`--` was not the problem; the exit code is.** `python main.py` in CI is protected against the
  empty-output case by a row-count guard (`.github/workflows/scrape.yml:74-83`) that checks the
  *cumulative* master. That guard does not detect a total source outage (the master still holds
  last week's rows), and it does not exist at all for `leadminer run`.
- **SIGTERM.** `cli.py:316-318` handles `KeyboardInterrupt` (SIGINT only). For a five-hour command
  bounded by `timeout-minutes: 300`, the signal that actually arrives is SIGTERM, so the
  `\ninterrupted` / `return 130` path is unreachable in production. Already reported at
  `docs/audits/200-fn-cli-py-main-ops.md:62-82`; recorded here only because `cmd_run` is the
  function that owns that six-hour window.

## Recommended order of work

1. **`main.py:148` + `cli.py:37` + `cli.py:315`** — make failure expressible. Give `main.main()`
   an `-> int` derived from a per-source success counter, propagate it verbatim, delete `or 0`.
   One change removes the S1 and unblocks every automated check that depends on `leadminer run`'s
   exit code. (This is the prerequisite for #2 and #5 to mean anything.)
2. **`cli.py:33`** — resolve the `-> int` lie at the same time, so `mypy --strict`
   (`pyproject.toml:64-68`) can be switched on in CI as a gate. It currently reports 8 lint
   findings across `cli.py`/`main.py` and is not run at all.
3. **`cli.py:285-286` + `cli.py:33`** — give `run` a real option surface (`--data-dir`,
   `--sources`, `--dry-run`) and read it, or delete the unused parameter. Do this before #4, since
   #4's fix is "pass a flag `run` can finally see".
4. **`cli.py:26` / `main.py:41`** — one `DATA_DIR`, absolute or env-overridable. Removes the
   wrong-directory run and the writer/reader split-brain.
5. **`cli.py:35`** — an `flock` on `data/.run.lock`, plus the missing-master fail-closed guard that
   `.github/workflows/scrape.yml:57-63` already implements in YAML.
6. **`cli.py:35`** — move to a `leadminer/` package with a package-relative import. Largest diff;
   do it once #1-#5 have CI coverage, and fix `[tool.hatch.build.targets.wheel]`
   (`pyproject.toml:37`) in the same change so the wheel stops shipping only `scrapers/`.
7. **Switch `.github/workflows/scrape.yml:69` to `leadminer run`** and delete one of the two
   entrypoints, otherwise none of the above is exercised in production.
