# 234 — `cmd_validate` (cli.py:135): a data-quality gate whose two tolerances cannot be tested with the only fixture that exists

## Verdict

`cmd_validate` is the repo's only automated data-quality gate and it has **2 tests**, both of
which use the same one-row, 22-column, BOM'd, `write_csv`-produced fixture
(`tests/test_lead_signal.py:195-209`, `:228-240`, `:242-253`). That fixture cannot express a
single malformed input, and — because `total == 1` makes `total*0.01 == 0.01` and
`total*0.05 == 0.05` (`cli.py:172`, `cli.py:191`) — it also cannot distinguish "1% tolerance"
from "zero tolerance". **The two numbers the gate's design rests on are not merely untested;
they are untestable with the fixture that exists.**

Worse, the largest hole is a missing *check*, not a missing test. `cmd_validate` never looks
at `website_live`, the one column whose CSV token set is exact and load-bearing
(`main.py:103`, `enricher.py:300-304`). I verified all **17** non-empty tokens pass with
`rc=0`; the 15 that `load_master` maps to `None` each delete a 20-point `lead_score` signal
and the "Website rebuild + maintenance" pitch from a cumulative master that is never rebuilt
(`main.py:150`). Google Sheets — where the workflow deliberately parks these CSVs
(`scrape.yml:88-89`) — writes booleans as uppercase `TRUE`/`FALSE`, so this is a scheduled,
not hypothetical, path. `validate` reports **"all checks passed"**; `stats` reports
`live 0 / dead 0 / unreachable 0` for 200 rows that all have a website (`cli.py:107-113`);
`leadminer score` then erases the signal on disk.

The tests below are written to be added to `tests/test_lead_signal.py` with the stdlib only,
matching its declared runner (`tests/test_lead_signal.py:6`).

## Findings

### S1 — `website_live` is never validated, so a Google Sheets round-trip permanently deletes the dead-site signal

- **Where:** `cli.py:135-201` (no reference to `website_live` anywhere in the function);
  the contract lives at `enricher.py:250` (writes `True`/`False`/`None`), `main.py:103`
  (parses **only** the exact strings `"True"` / `"False"`, else `None`), `cli.py:107-110`
  (`stats` also matches only those two literals), and the consequence at
  `enricher.py:300-304` (`+20` for a confirmed-dead site) and
  `enricher.py:297-300` ("Only a DEAD verdict … counts as a sales opportunity").
- **Breaks:** the CSV token set is `{"True", "False", ""}` and nothing enforces it. A
  `FALSE` token becomes `None`, i.e. "unreachable", i.e. *not* a rebuild pitch. Because
  `all_businesses.csv` is cumulative and merged forward (`main.py:150`, `main.py:179-180`),
  the loss is permanent: `leadminer score` round-trips `None` back to `""`.
  Verified on a 200-row fixture with `website_live="FALSE"`:
  `validate → rc 0`, `stats → live 0 / dead 0 / unreachable 0`,
  after `cmd_score` the raw tokens on disk are `{''}`.
- **Trigger:** open `gdrive:leads/all_businesses.csv` in Google Sheets (checkbox or
  `=TRUE()` columns export as the strings `TRUE`/`FALSE` — see
  <https://dataclean.to/use-cases/clean-booleans-from-google-sheets>, and the PapaParse
  issue trail at <https://github.com/mholt/PapaParse/issues/108> for the same Excel/Sheets
  behaviour), save. The next cron run reads every dead site as unreachable.
- **Token-by-token, all verified `validate → rc 0`:**

  | token | `load_master` yields | token | `load_master` yields |
  |---|---|---|---|
  | `True` | `True` | `0` | `None` |
  | `False` | `False` | `yes` / `no` | `None` |
  | `TRUE` / `FALSE` | `None` | `Y` / `N` | `None` |
  | `true` / `false` | `None` | `Live` / `live` / `DEAD` | `None` |
  | `1` | `None` | `unknown` / `None` | `None` |

- **Fix:** add a `website_live` check that accepts only `{"True", "False", ""}` and fails on
  anything else, and make `load_master` (`main.py:103`) raise-or-warn rather than silently
  coerce.

### S1 — the coordinate check `continue`s past every value it cannot parse, so a corrupted `lat`/`lon` column is invisible

- **Where:** `cli.py:166-169`. `float(r["lat"])` is wrapped in
  `except (ValueError, TypeError, KeyError): continue`.
- **Breaks:** the check exists to catch corrupt geometry, and corrupt geometry is precisely
  what takes the `except`. The three failure modes that matter — the column is missing from
  the header (`KeyError`), the cell holds a word (`ValueError`), the cell is blank/absent
  (`TypeError`) — all take the same path as "this row legitimately has no coordinates",
  which is a real and common state. Verified on 50 otherwise-perfect rows:
  - `lat="abc", lon="xyz"` → `rc=0`, **"all checks passed"**
  - `lat="None", lon="None"` (what a `None` becomes after a CSV round-trip) → `rc=0`
  - `lat="", lon=""` → `rc=0` (correct here, but indistinguishable from the two above)
  - the whole `lat`/`lon` columns absent from the header → `rc=0`
  By contrast `nan`, `inf`, `1e40`, `0,0` and a transposed `lat`/`lon` all *are* caught,
  because `float()` succeeds and `in_box` returns `False`. So the check works on the
  well-formed corruptions and is blind to the malformed ones.
- **Trigger:** a scraper change that starts emitting `None` for coordinates flows through
  `write_csv` (`main.py:125-127`, `restval=""`) as blanks, or a column reorder/typo drops
  `lat` from the header; the gate reports a clean file.
- **Fix:** distinguish "absent" from "unparseable": count `bad_coord_type` separately and
  fail on any non-empty unparseable cell; `KeyError` must be a schema failure, not a skip.

### S2 — both tolerances are relative to `total`, so the allowance is 0 on small files and up to 2,000 bad rows on real ones

- **Where:** `cli.py:172` (`bad_coords > total * 0.01`) and `cli.py:191`
  (`dupes > total * 0.05`), where `total = len(rows)` (`cli.py:149`).
- **Breaks:** the denominator is wrong in both cases.
  - **Coordinates:** it should be the number of rows *that have* coordinates. Verified:
    1000 rows of which only 10 are located, and **all 10** are outside both boxes →
    `rc=0`. Raise the located count to 11 bad out of 511 located → `rc=1`. The check is
    effectively inert whenever coordinate coverage is below 1%.
  - **Duplicates:** at the master's real scale the allowance is enormous. Verified
    arithmetic: at n=50,000 the gate silently accepts 500 out-of-market rows and 2,500
    duplicate excess rows; at n=200,000, 2,000 and 10,000.
  - **Small files:** with n=1 every threshold is `0.01`/`0.05`, i.e. zero tolerance. This is
    precisely the regime both existing tests run in
    (`tests/test_lead_signal.py:228-253`), which is why the thresholds are untested rather
    than merely untestable.
- **Boundary, verified:** `n=100, k=1 → rc 0`; `n=100, k=2 → rc 1`; `n=100, dupes=5 → rc 0`;
  `n=100, dupes=6 → rc 1`. (`n*0.01` and `n*0.05` are exact for every n I scanned up to
  399,999, so the `>` comparison is not float-flaky — the boundary is clean and just needs
  pinning.)
- **Fix:** divide by the count of rows in which the field is present, and treat "no rows
  have coordinates at all" as its own finding rather than as success.

### S2 — the duplicate check counts a shape `dedup.dedup` cannot produce and misses every shape it does

- **Where:** `cli.py:190` builds keys from the **raw** `r.get("name")`, `r.get("phone")`.
  The pipeline's identity function is `dedup.normalize_phone` (`dedup.py:33-63`) and
  `dedup.normalize_name` (`dedup.py:66-69`), selected at `dedup.py:205-218`.
- **Breaks, two directions, both verified:**
  - *Misses real duplicates.* A `phone`-keyed record and a `name`-keyed record for the same
    business both survive `dedup()` (`dedup.py:226-230` only drops a name-keyed row if it
    *has* a phone already captured). Input `[Cafe Nour/+96170123456, Cafe Nour/no phone,
    cafe nour/no phone]` → `dedup()` returns **2** rows. Written to CSV and validated →
    `rc=0`. The gate cannot see its own output's most likely duplicate class, because the
    two copies have different raw `(name, phone)` pairs.
  - *Misses every folding `normalize_name` performs.* Verified `validate → rc 0` for all of:
    `("Cafe", " cafe ")`, `("CAFE", "Cafe")`, `("Café", "Cafe")`,
    `("Cafe  Beirut", "Cafe Beirut")`, `("Cafe\tNour", "Cafe Nour")` — all five are equal
    under `dedup.normalize_name`. Also missed: `("70123456", "+961 7 012 3456")` and
    `("+96170123456", "0096170123456")`, both equal under `dedup.normalize_phone`.
  - *Flags what cannot occur.* Ten byte-identical rows → `rc=1`. But `dedup()` merges those
    before they are written, so this input cannot be produced by a healthy run; conversely a
    *real* duplicate pair is invisible. The check is anti-correlated with reality.
- **Past bug pinned:** the commit-`8a42a67` BOM blast radius is quoted as "every phone-less
  business in the same city collapsed into a single row" — precisely the
  `normalize_name` + `_extract_city` path (`dedup.py:66-69`, `dedup.py:72-76`,
  `dedup.py:214`) that this check cannot see. And `tests/test_lead_signal.py:103-108` pins
  that junk phones must not collapse to a shared key; the gate has no equivalent opinion.
- **Fix:** key the duplicate check with `normalize_phone` / `normalize_name` from `dedup`,
  never with raw cell text.

### S2 — `in_box` is a rectangle over five countries, and `country` is never cross-checked against it

- **Where:** `cli.py:159-162`, message at `cli.py:173`
  (`"rows have coordinates outside Lebanon/Saudi Arabia"`).
- **Breaks:** the Saudi box `16.0 <= lat <= 32.2 and 34.4 <= lon <= 55.7` is
  approximately "the whole Levant, Mesopotamia and the Gulf". Verified in-box:
  Amman (31.95, 35.91), Kuwait City (29.37, 47.98), Abu Dhabi (24.45, 54.37),
  Doha (25.29, 51.53), Manama (26.23, 50.58). The Lebanon box admits Damascus
  (33.51, 36.29). Cairo (30.04, 31.24) is rejected only because its longitude is outside
  both boxes — luck, not design. The comment at `cli.py:158` states the intent
  ("Coordinates must fall inside the two markets we claim to cover"); the code does not
  deliver it.
- **And `country` is never compared to the coordinates at all.** Verified `rc=0` for
  `country="SA"` at Beirut (33.89, 35.50) and `country="LB"` at Riyadh (24.71, 46.67). This
  matters because `country` is the field the rest of the pipeline trusts: it selects the
  phone normaliser's country code (`main.py:192-194`), gates address-based region inference
  (`enricher.infer_region`, the bug pinned by `tests/test_lead_signal.py:147-153`), and
  `resolve_country` defaults to `LB` for anything unrecognised (`main.py:47-74`).
- **Reachable, not hypothetical:** `OSMScraper` filters on the *area*
  `["ISO3166-1"="LB"]` (`scrapers/osm.py:13`) but hardcodes `country="LB"`
  (`scrapers/osm.py:103`) while taking `lat`/`lon` straight from the node. Any LB-area node
  whose geometry sits outside the LB bounding box — border areas, the Golan, or a plain OSM
  mapping error — arrives as `country="LB"` with foreign coordinates, and `in_box` cannot
  see it.
- **Fix:** cross-check `country` against the box that `country` names (`LB` rows must be in
  the LB box, `SA` rows in the SA box) and treat a disagreement as a problem; separately,
  shrink the boxes or replace them with a polygon (see "cannot be tested" below).

### S3 — the BOM check fires on the opposite of what its message says

- **Where:** `cli.py:154-156`, message
  `f"{bom_name} names carry a UTF-8 BOM (written without utf-8-sig)"`.
- **Breaks:** the reader at `cli.py:142` uses `encoding="utf-8-sig"`, which strips a BOM
  from the **header**. So the condition the message names — a file written *without*
  `utf-8-sig` — is structurally invisible to this function. Verified: 50 Arabic rows written
  with `encoding="utf-8"` (first bytes `b'nam'`) → `rc=0`, "all checks passed". Written with
  `utf-8-sig` (`b'\xef\xbb\xbf'`) → also `rc=0`, but for the opposite reason. The check only
  fires on a BOM embedded in a *data value* (verified: `rc=1`), i.e. a Sheets/manual-edit
  artefact — the opposite of the situation its message describes.
- **Why it still matters:** the BOM is the fix from commit `8a42a67` ("so Excel and Google
  Sheets detect UTF-8 and render Arabic business names correctly instead of mojibake"), and
  `write_csv` is the only writer (`main.py:124`). A master that regressed to plain `utf-8`
  renders as mojibake for every downstream consumer and the gate cannot notice. The check
  should assert the BOM is *present* (`path.read_bytes().startswith(b"\xef\xbb\xbf")`), not
  hunt for it in values.
- **Fix:** invert it — fail when the leading BOM is absent; rename the value check
  "BOM inside a name value" so it stops claiming to be about the writer's encoding.

### S3 — the gate tracebacks on four ordinary operator mistakes

- **Where:** `cli.py:137-143`; `main()` catches only `KeyboardInterrupt`
  (`cli.py:314-318`).
- **Breaks, all verified:** a **directory** as the argument → `IsADirectoryError` propagates;
  a `chmod 000` file → `PermissionError`; non-UTF-8 bytes (an `.xlsx`, a UTF-16 export) →
  `UnicodeDecodeError`; any cell over `csv.field_size_limit` (131,072 chars) →
  `_csv.Error: field larger than field limit`. Each is a full traceback from the command
  whose job is diagnosis. `cli.py:228-229` states the rule for `doctor` — "doctor exists to
  diagnose a broken environment, so it must never be the thing that tracebacks" — and
  `validate` breaks it four times over.
- **Also imprecise:** `cli.py:190-192` reports `total - len(set(...))` as
  `"N duplicate (name, phone) pairs"`. For 100 byte-identical rows it prints
  `"99 duplicate (name, phone) pairs"` when there is exactly **one** duplicate group. It is
  a count of excess rows, not of pairs.
- **Also conflated:** a valid header with zero data rows and a 0-byte file both return 1
  with `"{path} is empty"` (`cli.py:144-146`) — verified for both — though only one of them
  is a failure.
- **Fix:** wrap the read in `except (OSError, UnicodeDecodeError, csv.Error)` → return 2;
  rename the counter to "excess rows sharing a (name, phone) key"; distinguish an empty file
  (rc 1) from an empty dataset (rc 1, different message).

## The exact test cases this function still needs

### Why the two existing tests cannot be extended

`TestCli._fixture` (`tests/test_lead_signal.py:195-209`) writes through
`main.write_csv`, which hard-writes `fieldnames=FIELDS` and a `utf-8-sig` BOM
(`main.py:124-125`). So **every** test that uses it necessarily has all 22 columns, a BOM,
and a well-formed row — precisely the dimensions the gate exists to police. Both current
tests pass a single row, so `total == 1`. One fixture change fixes both problems:

```python
HDR = ",".join(FIELDS)                     # main.py:33-40

def _raw(d, text, name="f.csv", encoding="utf-8-sig"):
    """Write a literal CSV. Bypasses write_csv, which is what makes the
    malformed shapes reachable in the first place."""
    p = Path(d) / name
    p.write_text(text, encoding=encoding)
    return str(p)

def _unique(n, **over):                     # n rows that cannot trip the dupe check
    return [dict({f: "" for f in FIELDS}, name=f"Cafe{i}", phone=str(70000000 + i),
                 address=f"{i} St, Beirut", lat="33.89", lon="35.50",
                 rating="4.2", country="LB", website="https://x.example",
                 website_live="True", source="osm", **over) for i in range(n)]
```

### Group A — properties for the two tolerances (the design that has zero coverage)

**A1. `test_coordinate_tolerance_is_relative_and_bounded_by_located_rows`**
- **Form:** property over `(n, located, bad)`; use `hypothesis` (`pyproject.toml:24`) if
  installed, otherwise a `subTest` grid — the repo's declared runner is stdlib
  (`tests/test_lead_signal.py:6`).
- **Literal input:** `_unique(n)` with the first `bad` rows overridden to
  `lat="10.0", lon="10.0"`.
- **Asserted output:** `rc == (1 if bad > 0.01 * n else 0)` for
  `(1,1,1)→1`, `(99,1,1)→1`, `(100,1,1)→0`, `(100,1,2)→1`, `(1000,1,10)→0`,
  `(1000,1,11)→1`; and `"outside Lebanon/Saudi Arabia" in out` whenever `rc == 1`.
  The property that must also hold: **fails iff `bad > 0.01 * located`** — verified today
  as `rc=0` for `(n=1000, located=10, bad=10)` and `rc=1` for
  `(n=1000, located=511, bad=11)`.
- **Past bug pinned:** the two existing tests (`tests/test_lead_signal.py:228-253`) both run
  at `total=1`, where `0.01 * 1 = 0.01`; they would pass unchanged if the tolerances were
  `0`. This is the test that makes `cli.py:172` mean anything.

**A2. `test_duplicate_tolerance_boundary_is_five_percent_of_total`**
- **Form:** property over `(n, dupes)`.
- **Literal input:** `n - dupes` distinct rows plus `dupes + 1` rows sharing
  `name="D", phone=""`.
- **Asserted output:** `rc == (1 if dupes > 0.05 * n else 0)`; anchors
  `(100,5)→0`, `(100,6)→1`, `(1000,50)→0`, `(1000,51)→1`, `(3,1)→1`.
- **Past bug pinned:** same — `cli.py:191` is unexercised at any non-degenerate `n`.

**A3. `test_rating_domain_is_exactly_blank_or_zero_to_five`**
- **Form:** property over the rating cell.
- **Literal input:** `_unique(50, rating=cell)`.
- **Asserted output:** legal = `{"", "   ", "0", "5"}` → `rc 0`; illegal =
  `{"-0.0001", "5.0000001", "n/a", "nan", "None", "inf", "1e400"}` → `rc 1` with
  `"outside 0-5" in out`.
- **Past bug pinned:** `tests/test_lead_signal.py:228-240` covers only `"9.9"`. The
  dangerous members are the ones `float()` *accepts* but that are not ratings — `nan` and
  `inf` reach `float()` fine and are caught only by the `0 <= v <= 5` comparison
  (`cli.py:185`); the string sentinels reach the `except ValueError` at `cli.py:182`.
  Both branches need one test each.

**A4. `test_in_box_is_a_closed_interval_on_the_published_box_and_never_crashes`**
- **Form:** property over `(lat, lon)`; property "no input raises" over floats including
  `nan`/`inf`, plus a table of the corners.
- **Literal input / asserted output:**
  `in`: `(33.0, 35.0)`, `(34.8, 36.9)`, `(16.0, 34.4)`, `(32.2, 55.7)`,
  `(33.89, 35.50)`, `(24.71, 46.67)`, `(21.42, 39.83)` → `rc 0`.
  `out`: `(32.9, 35.0)`, `(33.5, 34.9)`, `(33.5, 37.0)`, `(15.9, 45.0)`, `(32.3, 45.0)`,
  `(20.0, 55.8)`, `(0, 0)`, `(35.50, 33.89)` [transposed], `(nan, nan)`, `(inf, inf)`,
  `("abc", "xyz")`, `("", "")` → currently `rc 0` for the last three, which is the bug.
- **Past bug pinned:** the transposed `lat`/`lon` case is the one corruption
  `083-SYNTH-s1-backlog.md:121` item 56 flags ("validate coordinate ranges and
  country boundaries… quarantine transposed or out-of-market records"), and it is the only
  *detectable* case in this list — the test's value is locking in that asymmetry so a future
  `except` widening does not lose it.

**A5. `test_tolerances_scale_monotonically_with_n`**
- **Form:** property — for a fixed bad-row *fraction* `f`, `rc` must not depend on `n`.
- **Literal input:** `_unique(n)` with `bad = int(0.005 * n)` out-of-box rows, for
  `n in (100, 1000, 10000)`.
- **Asserted output:** `rc == 0` for all three. Today `n=100` yields `bad=0` and `n=10000`
  yields `bad=50` against a limit of 100 — passes, but only because the file is 100× bigger;
  at `f = 0.02` all three fail. This property is what forces the denominator question in
  S2 to be answered rather than left implicit.

## What genuinely cannot be tested here, and why

1. **Whether 1% and 5% are the right tolerances.** That is a product decision about the
   real distribution of a real master. The master lives in gitignored `data/`
   (`.gitignore:9`) and does not exist in this checkout, and the brief says it is cumulative
   (`main.py:150`), so there is no baseline to calibrate against and no fixture could
   manufacture one honestly. Testing can pin the *arithmetic* (A1, A2, A5); choosing the
   number needs one recorded run plus an owner.
2. **Whether the coordinate boxes match the two markets.** A bounding box is not a
   boundary. Certifying it needs real geometry — an authoritative boundary polygon per
   country, or a geocoding oracle — none of which exists in the repo, and none of which a
   unit test can substitute for. B8 is therefore written as a *requirement* that will fail
   until the boxes are replaced, not as a test to be made green by widening a constant.
   Reachability (does the scraper actually emit an out-of-market row?) is answerable only
   from a recorded live response, which the brief forbids here (`BRIEF.md:72-74`) and which
   is non-deterministic besides — `032-fixtures-offline-replay.md` is the right home for it.
3. **That Google Sheets really writes `TRUE`/`FALSE`.** The behaviour is documented and
   widely reported (cited above), and the workflow does publish to Drive
   (`scrape.yml:88-89`), but a unit test cannot drive Sheets. What *is* testable — and is
   B1 — is that the gate rejects those tokens **whatever their provenance**. The token list
   should be treated as the contract; confirming it once by hand is a five-minute check.
4. **Whether the gate runs and blocks publication.** `cmd_validate` has no caller in
   automation: `scrape.yml:65-69` runs `python main.py` and `scrape.yml:71-83` re-implements
   the gate in shell (`[ -s … ]`, `ROWS < 100`) without ever calling the CLI. That is an
   integration/CI test, not a unit test, and it is the single highest-leverage change
   available (it is also `207-x.md:105-108` S2-04). Everything in this report assumes the
   gate runs; today it does not.
5. **Live scraper output.** Whether OSM/Places/Wikidata ever produce `lat="abc"`, a blank
   `website`, or a transposed coordinate pair can only be answered from recorded fixtures,
   not from synthetic ones. The gate tests above assert the gate's *response* to those
   inputs; they deliberately say nothing about how often they occur.
6. **`cmd_score`'s own contract.** `cmd_score` reads `args.out` unconditionally
   (`cli.py:274`), so calling it with `Namespace(file=p)` raises `AttributeError` — a real
   wiring bug, but it is outside this lens and belongs to whoever owns `cmd_score`.

## Recommended order of work

1. **B1 + B2 + B3** — the `website_live` token contract. Highest severity, cheapest fix,
   and it closes the exact regression class the repo already has a test class for
   (`tests/test_lead_signal.py:71-99`). Add the token check, then tighten `main.py:103` so
   an unknown token is loud instead of `None`.
2. **B4 + B5 + B6** — header validation, a counted blank-name check, and stop skipping
   unparseable coordinates. Together these turn the gate from "checks 5 things it happened
   to be handed" into "validates the file it was given". Three audits already ask for the
   header check.
3. **A1 + A2 + A5** — the tolerance properties. These exist to stop the next contributor
   from changing a constant and never noticing, and they force the denominator bug
   (S2) to be answered rather than documented.
4. **B7 + B8** — `country`/coordinate agreement, and the box-vs-reality gap. B8 will fail by
   design; land it as a tracked failure attached to the polygon-replacement work.
5. **A3 + A4 + B9 + C1–C4** — the smaller pins. Cheap, and each one currently has a
   verified wrong answer behind it.
6. **Wire it in.** `scrape.yml:71-83` should call `leadminer validate` instead of
   re-implementing two of its checks in shell. Until that happens, every test above is a
   test of a command nobody runs.
