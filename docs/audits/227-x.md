# 227 — Concurrency safety of `cmd_stats` (cli.py:79)

## Verdict

`cmd_stats` is **safe against this codebase's own three thread pools**, and that is
not luck: it shares no mutable state with them, it does not import the HTTP layer at
all, and it reads a file that `write_csv` replaces atomically, so it always gets a
consistent pre- or post-run snapshot. I verified all three claims empirically (§
Evidence).

The concurrency problem in this lens is one level out. Two `leadminer run` processes
in one checkout both derive the *same* temp path from the target name
(`main.py:122`), so they write the same file and `os.replace` a byte-level
interleaving of two different runs into the cumulative master — and `cmd_stats`, the
command whose docstring says "This is the first thing to check" (`cli.py:80`),
reports that corrupted file as a clean, self-consistent summary with **exit code 0**.
A diagnostic that cannot detect the corruption is not a safety net.

## Findings

### S1 — Racing `write_csv` calls publish a byte-interleaved master, and one of the runs dies

- **Where:** `main.py:122` (`tmp = path.with_suffix(path.suffix + ".tmp")`),
  `main.py:124` (`open(tmp, "w", ...)`), `main.py:130` (`os.replace(tmp, path)`),
  `main.py:131-133` (`except BaseException: tmp.unlink(missing_ok=True); raise`).
  Reached unguarded from `cli.py:33-37` (`cmd_run` → `pipeline.main()`) and
  `cli.py:275` (`cmd_score` → `pipeline.write_csv`). Reported through `cli.py:79`.
- **Breaks:** the temp filename is a pure function of the target filename, so two
  concurrent processes open the *same* path with mode `w`. The second `open`
  truncates whatever the first is still writing, and both then advance independent
  file offsets over one inode. The first to finish calls `os.replace` and publishes a
  file that is neither run's output — it is a byte-level interleave. The second gets
  `FileNotFoundError` from `os.replace` because the temp file it was writing has
  already been renamed away, and the exception escapes `main()` after hours of paid
  API spend. `main.py:132`'s `tmp.unlink(missing_ok=True)` then deletes a temp file a
  *third* run may still be writing, cascading the failure.
- **Verified:** two concurrent `write_csv` calls to `data/all_businesses.csv`
  (40,000 rows each, runs one week apart with different `lead_score` and different
  `website_live`):
  ```
  run outcomes: {'A': 'DIED FileNotFoundError', 'B': 'PUBLISHED'}

  $ leadminer stats data/all_businesses.csv      # rc=0
    (40,023 rows)
      website live    : 4,876
      website dead    : 35,138
      unreachable     : 1
    by priority:
      high       40,014
                 2
      True       1        <-- lead_score field
      False      1
      85         1
      30         1
      https://B34783.com 1                        <-- website field
    by source:
      B                            35,137
      A                             4,876
      3.1                          1        <-- rating field
      2026-10-08T03:00:00+00:00    1        <-- scraped_at field
    by region:
      Beirut               40,022
      LB                     1                   <-- country field

  forensic check the tool does not do:
     rows                   : 40,023
     distinct scraped_at    : 12  -> {'2026-10-08…': 35136, '': 3,
                                       '2026-10-01…': 4875, 'high': 1,
                                       '3.1': 1, 'Beirut': 1, None: 1}
     ragged rows (None key) : 11
  ```
  Both runs' leads are gone as distinct runs; the master now contains two weeks of
  scoring applied to a half-interleaved row set. Because the two batches had
  different byte lengths per row, the file is *field*-misaligned, not merely
  row-mixed. With equal-length rows the corruption is entirely invisible: a
  separate 3-way race with uniform row lengths published an `80,000`-row master
  composed of 46,044 rows from writer B, 21,045 from A and 12,911 from C, and
  `cmd_stats` reported it as `80,000 rows` with a plausible breakdown.
- **Trigger:** two `leadminer run` invocations in the same checkout. The window is
  hours wide: a full run is 68 Places queries at 5 workers plus one 40-thread
  enrichment pass at an 8 s timeout per URL (`enricher.py:175`), so a second run
  started while the first is in flight will still be in flight when it reaches
  `main.py:209`.
- **Note on likelihood:** `.github/workflows/scrape.yml:15-17` has a
  `concurrency: leadminer-scrape` group, and its comment at `scrape.yml:12-14`
  states the intent explicitly — *"Two runs must never race on data/"*. That guard
  is invisible to local runs and lives only in the workflow, not the code. There is
  no `fcntl`/`flock` anywhere in the repository (grep: zero hits). CI also invokes
  `python main.py` (`scrape.yml:69`), **not** `leadminer run`, so a lock added to
  `cli.cmd_run` would not protect CI.
- **Fix:** take an exclusive advisory lock on `data/.leadminer.lock` at the top of
  `main.main()` (`main.py:148`) — not in `cli.cmd_run` — and additionally make the
  temp name unique per process (`tmp = path.with_name(f"{path.name}.{os.getpid()}.tmp")`,
  or `tempfile.mkstemp(dir=path.parent)`). Either alone stops the interleave; do both.

### S2 — `cmd_stats` has no integrity check, so it reports a corrupt master as healthy

- **Where:** `cli.py:86-90` (read + empty check), `cli.py:107-113` (tri-state
  buckets), `cli.py:116-131` (the four `Counter` breakdowns). The function returns
  `0` at `cli.py:132` on any input that parses.
- **Breaks:** `cmd_stats` is the documented first line of defence ("This is the
  first thing to check", `cli.py:80`; "they are safe to run anywhere and are what
  you reach for when a run looks wrong", `cli.py:14-15`). It performs no structural
  validation whatsoever: it never checks that the row count matches the file's
  newline count, never checks that `len(row) == len(fieldnames)`, never inspects the
  `None` rest-key that `csv.DictReader` produces for a torn row, never validates that
  `website_live` ∈ {`True`, `False`, blank}, and never checks that `scraped_at`
  resolves to a single run. So the S1 corruption is reported as
  `website dead: 35,138` — a number a salesperson will act on — with exit code 0.
  Confirmed: every malformed input in my table below returns `rc=0`.
- **Trigger:** the S1 output above; or `leadminer stats data/qualified_businesses.csv`
  on a file exported by an older writer that omitted columns.
- **Fix:** add three cheap assertions before printing and `return 1` on failure —
  (a) `len(rows) == sum(1 for _ in open(path, "rb")) - 1`, (b) `not any(None in r for r in rows)`,
  (c) `len({r.get("scraped_at") for r in rows}) == 1`. Print `scraped_at` range and
  file mtime in the header (`cli.py:93`) so staleness is visible.

### S2 — `website live + website dead + unreachable` silently does not equal `with website`

- **Where:** `cli.py:107-110`. `live`/`dead` match the exact strings `"True"`/`"False"`
  after `.strip()`; `unknown` matches a blank `website_live` **and** a non-blank
  `website`. Any other non-blank value lands in no bucket at all.
- **Breaks:** the three buckets are supposed to partition `with website`, and the
  report prints `unreachable … (not the same as dead)` (`cli.py:113`) to draw exactly
  that distinction. A value that is neither canonical nor blank is counted as
  nothing, so the row exists in `with website: 1` and in no verdict bucket, and
  nothing tells the operator the arithmetic does not close. `cmd_validate`
  (`cli.py:135-201`) checks ratings, coordinates, names and duplicates but never
  checks this invariant either, so no command in the codebase can catch it.
- **Trigger (verified):** a master round-tripped through Excel or Google Sheets —
  `write_csv` emits Python `bool` reprs `"True"`/`"False"` (`main.py:124-127`), and
  Excel writes boolean-looking cells as `TRUE`/`FALSE`. Drive is the master's home
  (`scrape.yml:56` downloads it, `scrape.yml:88-89` uploads it), so a human touching
  the master on Drive is enough.
  ```
  website_live='True'   -> with website=1  live=1  dead=0  unreachable=0  accounted=1/1
  website_live='true'   -> with website=1  live=0  dead=0  unreachable=0  accounted=0/1   <-- ROW VANISHES
  website_live='TRUE'   -> with website=1  live=0  dead=0  unreachable=0  accounted=0/1   <-- ROW VANISHES
  website_live='1'      -> with website=1  live=0  dead=0  unreachable=0  accounted=0/1   <-- ROW VANISHES
  website_live=' False' -> with website=1  live=0  dead=1  unreachable=0  accounted=1/1
  ```
- **Fix:** parse once with a normalising helper — `v = (r.get("website_live") or "").strip().lower()`, bucket on `{"true","1","yes"}` / `{"false","0","no"}` / else — then `assert live + dead + unknown == with_website` and fail loudly if not.

### S2 — `cmd_stats` escapes with an unhandled traceback on inputs the master can actually acquire

- **Where:** `cli.py:86-87` (unguarded `open`/`DictReader`), `cli.py:314-318`
  (`cli.main` catches only `KeyboardInterrupt`).
- **Breaks:** the diagnostic command dies with a stack trace on the exact malformed
  input it exists to diagnose, and the resulting exit code `1` is indistinguishable
  from "`file is empty`" (`cli.py:90`) or "`validate found problems`" (`cli.py:201`),
  so no automation can tell "your file is unreadable" from "your data is bad".
  `cmd_doctor` has an explicit anti-traceback guard for exactly this reason
  (`cli.py:228-231`); `stats` and `validate` have none.
- **Trigger (verified):**
  ```
  oversized field (>128KiB csv limit)    EXCEPTION ESCAPED cmd_stats  csv.Error: field larger than field limit (131072)
  latin-1 bytes, not utf-8               EXCEPTION ESCAPED cmd_stats  UnicodeDecodeError: 'utf-8' codec can't decode byte 0xe9 in position 7
  directory passed as file               EXCEPTION ESCAPED cmd_stats  IsADirectoryError: [Errno 21] Is a directory
  ```
  The `UnicodeDecodeError` case is the realistic one: the master round-trips through
  Google Drive (`scrape.yml:56`, `scrape.yml:88-89`), and any Excel/Locale
  re-save or Google Sheets transcoding turns one Arabic or accented name into
  cp1252 bytes. `main.load_master` (`main.py:85`) uses the same `utf-8-sig` and
  would fail identically, so this takes out both the diagnostic *and* the run.
- **Fix:** wrap `cli.py:86-87` in `try/except (csv.Error, UnicodeDecodeError, OSError)`
  and return a distinct code (e.g. `3`) with a one-line message naming the offset
  or byte position; add `errors="replace"` with a warning counter so a single bad
  byte degrades to a warning instead of killing the report.

### S2 — `cmd_stats` output is not attributable when anything else writes to the same stream

- **Where:** `cmd_stats` has 30 `print()` calls to the bare `sys.stdout`
  (`cli.py:93`, `cli.py:98-103`, `cli.py:111-113`, `cli.py:116-131`) and no
  `stream` parameter. The concurrent writers in this codebase are the 5 Places
  workers (`scrapers/google_places.py:218, 231, 237, 244, 251, 257` — all execute
  inside `fetch_query`, submitted at `google_places.py:195`) and the run's own
  progress lines (`enricher.py:235, 262, 271, 272`).
- **Breaks:** `sys.stdout` is a single process-global object with no write lock.
  Report lines and pipeline lines land in the same stream, so `leadminer stats`
  output captured into the same terminal or `tee` target as a running pipeline has
  no recoverable boundaries. The same property makes the function untestable in
  parallel and un-capturable per call.
- **Trigger (verified):** 40 threads each calling `cmd_stats` under its own
  `contextlib.redirect_stdout`:
  ```
  threads=40  exceptions=0  calls that captured output=40
  clean captures=2/40   contaminated=38
  header-line count histogram (per capture): {0: 19, 1: 21}
  ```
  19 of 40 captures received **nothing at all**. Serialising only the stream
  (a lock around the `print` block) restores 40/40 clean captures — proving the
  corruption is the shared stream, not `cmd_stats`' internal state.
- **Fix:** give the command an injectable sink — `def cmd_stats(args, out: TextIO = sys.stdout)`
  (or a small `Report` object) — and default it at the call site in `cli.main`
  (`cli.py:315`). Nothing else in the CLI needs to change, and `pytest`/`capsys`
  stops being racy.

### S3 — `cmd_stats` is the only offline command that must hold the whole file in memory

- **Where:** `cli.py:87` — `rows = list(csv.DictReader(f))`. Every other command
  either streams or works on a subset: `cmd_validate` makes the same
  materialisation (`cli.py:143`) but only needs two columns, and `cmd_score`
  (`cli.py:259`) already needs the whole thing by design.
- **Breaks:** every field count is a full pass — `count()` runs 6 times
  (`cli.py:98-103`), plus 3 passes for the tri-state (`cli.py:107-110`) and 4
  `Counter` builds (`cli.py:116, 120, 124, 129`) — 13 passes over a materialised
  list of dicts. Peak RSS is the whole file expanded into ~23-key dicts. On a
  mature cumulative master this is the slowest thing an operator can run.
- **Measured** (synthetic master, 23 columns as per `main.py:33-40`):
  ```
  rows=  200,000  csv=  31.6 MB  rc=0  wall= 8.80s  peakRSS +96.0 MB
  rows=1,000,000  csv= 159.3 MB  rc=0  wall=37.03s  peakRSS +386.6 MB
  ```
  37 s for the "fast local diagnostic", and a +387 MB spike that lands on the same
  machine as a pipeline already holding the full `records` list (`main.py:180-213`).
- **Fix:** count in a single streaming pass — iterate `DictReader` once, bump a
  `Counter` per field, and never build the list. This also removes the 13 passes.

### S3 — A stale snapshot is indistinguishable from a current one

- **Where:** `cli.py:93` prints only the path and row count. The `scraped_at`
  column (`main.py:39`, populated by `httpclient.utc_now_iso`, `httpclient.py:220-229`)
  is in the data but never surfaced.
- **Breaks:** the CLI explicitly invites `stats` to be run while a run is in flight
  (`cli.py:14-15`). It *is* safe — verified, reader gets a consistent 2,000-row
  pre-replace snapshot with the header intact and zero tmp leftovers — but the
  report gives no hint that it describes the previous run, which is precisely the
  moment the operator most needs to know.
- **Fix:** print `scraped_at` min/max and the file mtime next to the row count.

## Not a bug, but worth knowing

- **`cmd_stats` shares nothing with any of the three pools — verified, not assumed.**
  `cli.py:20-24` imports only `argparse`, `collections`, `csv`, `pathlib`, `sys`;
  `requests` is function-local to `cmd_doctor` (`cli.py:226`). Running
  `cli.cmd_stats` on a machine with **`requests` not installed** succeeds (`rc=0`),
  and afterwards `requests`, `httpclient`, `enricher` and `main` are all still
  absent from `sys.modules`. `httpclient._local` (`httpclient.py:58`) is never even
  instantiated. So the thread-local session registry and the per-worker Sessions
  (`google_places.py:159-166, 189`) are irrelevant to this function.
- **No shared mutable state, no locks needed.** There is no `global` or `nonlocal`
  statement anywhere in `cli.py`. The one module-level binding, `DATA_DIR`
  (`cli.py:26`), is assigned once at import and only ever read (`cli.py:217-222`,
  `294`, `298`, `305`). `count()` (`cli.py:95-96`) closes over a local. 40
  concurrent `cmd_stats` calls produced **0 exceptions**.
- **`cmd_stats` never shares dicts with the pipeline.** It builds a private `rows`
  list from the file (`cli.py:87`). `check_websites` does not hand a record to a
  worker either: `enricher.py:238` submits only a URL string, and every mutation of
  `records[idx]` happens on the consumer thread inside `as_completed`
  (`enricher.py:240-259`). So there is no cross-thread dict visibility into the
  data being reported.
- **Session reuse is handled correctly in the pools, for the record.** Thread-local
  `get_session()` (`httpclient.py:61-71`) is the documented remedy for the old
  shared `_SESSION`, and each Places worker builds its own
  (`google_places.py:189`). Neither `check_websites` nor the Places pool shares a
  `requests.Session` across threads.
- **Reader-vs-writer is correct.** `write_csv` (`main.py:108-134`) writes a sibling
  temp, fsyncs, then `os.replace`s. A reader that already holds the fd keeps reading
  the old inode to completion. Verified: target grew 266 KB → 1,197 KB under the
  reader; the reader still saw exactly 2,000 data lines plus an intact header, and
  no `.tmp` was left behind. The single-reader/atomic-writer interaction is sound —
  the only failure is *writer*-vs-writer (S1).
- **Pool shutdown is correct**, so appending a stats report to the end of a run
  would be safe: `main.py:160`, `enricher.py:237` and `google_places.py:194` all
  use `with ThreadPoolExecutor(...)`, so `shutdown(wait=True)` has run before
  `main()` reaches `main.py:199`.
- **`google_places` guards both shared structures correctly**, and the `seen_ids`
  test-and-set is a single lock hold (`google_places.py:263-266`), so there is no
  TOCTOU window. The only visible effect of completion-order `all_records`
  (`google_places.py:191-192`) is nondeterministic row order, which `dedup._merge`
  is order-independent by design (asserted at `tests/test_lead_signal.py:292-295`).
- **File-descriptor lifetime is clean.** The `with open(...)` block at `cli.py:86`
  closes before any reporting; 40 concurrent runs left `/dev/fd` back at 4. `rows`
  is a local that is released at return.
- **Correction to audit 068 (worth relaying).** 068 lists `enricher.py:227, 254,
  263-267` as printing from the 40 worker threads. In the current code that is no
  longer true: the only four `print` sites in `enricher.py` (235, 262, 271, 272)
  are all in `check_websites`' own frame on the calling thread, and
  `_fetch_website` (`enricher.py:161-222`) contains none. Worker-thread `print`s
  exist only in the Places pool (`google_places.py:218, 231, 237, 244, 251, 257`).
- **`cmd_score` overwrites the master in place by default** (`cli.py:274`: `out =
  pathlib.Path(args.out) if args.out else path`, then `cli.py:275`) with no backup.
  The write itself is atomic, but a bad `lead_score`/`recommend_service` rule
  silently replaces months of history. Same root cause as S1: the code has no
  self-protection, only the workflow does.

## Evidence

All results above were produced offline — no network calls, no package installs, no
repository files modified. `requests` is absent from this sandbox, which incidentally
proved the stdlib-only claim. Scratch scripts lived in
`/private/var/folders/.../T/opencode/` (`verify_stats*.py`, `out*.txt`) and are
outside the repo.

## Recommended order of work

1. **`fcntl.flock` on `data/.leadminer.lock` at the top of `main.main()` (`main.py:148`),
   plus a per-process unique temp name at `main.py:122`.** This is the S1. Put the
   lock in `main()`, not in `cli.cmd_run` — CI runs `python main.py`
   (`scrape.yml:69`) and would bypass it.
2. **Add the three integrity assertions to `cmd_stats`** (`cli.py:87-90`): row count
   vs newline count, no `None` rest-key, single `scraped_at`. Return `1` with a
   message on failure. Without this, item 1 can still be defeated and nothing will
   say so.
3. **Normalise `website_live` parsing and assert the buckets close**
   (`cli.py:107-113`), then add the same assertion to `cmd_validate`.
4. **Wrap `cli.py:86-87` in `except (csv.Error, UnicodeDecodeError, OSError)`**
   returning a distinct exit code, matching the guard `cmd_doctor` already has at
   `cli.py:228-231`. Consider `errors="replace"` with a warning count.
5. **Give `cmd_stats` an injectable `out: TextIO`** so concurrent callers, `capsys`
   and any future "print stats after the run" feature stop sharing one global stream.
6. **Make `cmd_stats` a single streaming pass** (`cli.py:87` → iterate `DictReader`
   once, no list) and print `scraped_at` range + mtime in the header. 37 s → ~4 s and
   −387 MB on a 1M-row master.
