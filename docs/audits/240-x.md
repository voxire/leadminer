# 240 — `cmd_doctor` (`cli.py:204`): a pre-flight gate that reports success on exactly the failures it exists to catch

## Verdict

`cmd_doctor` cannot fail for any reason except a missing `GOOGLE_PLACES_API_KEY` env var.
Its HTTP probe labels **every 4xx as `OK`** (`cli.py:241`, `r.status_code < 500`), so an
invalid/revoked Google key — the single failure `google_places.py:228-233` treats as
`FATAL` — prints `OK   Google Places`; and the exit code (`cli.py:244`) ignores every
probe result, so a machine with **no egress at all** exits `0` while a machine with a
perfect network and no key exits `1`. I confirmed both by executing `cmd_doctor` with a
stubbed `requests`. The function also probes the wrong client (bare `python-requests`
User-Agent, no `X-Goog-Api-Key`, `GET` to a POST-only endpoint) and the wrong directory
(CWD-relative `data`, `cli.py:26`), so its answers frequently do not describe the run
that follows.

Context that caps the blast radius: `.github/workflows/scrape.yml:69` still runs
`python main.py` and never calls the CLI, so nothing is gated on this exit code **today**.
It matters the moment `037-cli-design.md:570-575` ("CLI Preflight Doctor", `--strict`) is
wired up, and it matters immediately for a human doing the thing the docstring promises:
"check credentials and connectivity before blaming the data".

---

## How I verified

`requests` is not installed in this environment, so I injected a stub module into
`sys.modules` (the same technique `tests/test_lead_signal.py:23-63` already uses) and
called `cli.cmd_doctor(argparse.Namespace())` under `redirect_stdout`, capturing the
return code, the printed text, and the exact `requests.get` arguments. Harness lives
outside the repo at
`/private/var/folders/x_/ljryhzvn18s0r2_1j4kf_1kc0000gn/T/opencode/{doctor_probe,s1_status,s2_datadir,s2b_pipeline,s3_ua,s4_matrix}.py`.
No network calls were made to Overpass, Wikidata or Google; no repository file other
than this report was modified.

## Findings

### S1 — Every 4xx is reported as `OK`, so a broken credential looks healthy

- **Where:** `cli.py:240-241` (the predicate `r.status_code < 500`), consumed at `cli.py:244`.
- **Breaks:** The connectivity table only distinguishes `< 500` ("OK") from `>= 500`
  ("WARN"). `400`, `401`, `403`, `404`, `405` and `429` all print `OK` with an **empty**
  note column, i.e. a credential check that reports success on an invalid credential.
  Note also that a `WARN` (5xx) does not clear `ok` either, so *no* HTTP status changes
  the exit code.
- **Trigger (executed):** stub every endpoint to return 401:

  ```
  credentials:
    OK   GOOGLE_PLACES_API_KEY

  connectivity (5s timeout each):
    OK   Overpass
    OK   Wikidata
    OK   Google Places
  ```
  return code `0`. Google rejects a bad key with `401`
  (`google_places.py:228-233`: `print("[Google] FATAL: invalid API key (401). ...")`).
  So the operator runs `leadminer doctor`, sees three green lines, and launches a
  multi-hour run whose Google Places stage collects nothing.
- **Same result for:** 400 (Google field-mask drift — see S2), 403 (Wikimedia UA policy,
  S2), 404/405 (wrong method on a POST-only endpoint, S2), 429 (throttled/billed-out
  Overpass instance — the state you most need to detect before a run).
- **Fix:** one line — `good = r.status_code == 200` and print `HTTP {r.status_code}` for
  anything else (`cli.py:240-241`), matching the spec at `037-cli-design.md:171-173`
  ("asserts HTTP 200").

### S2 — The exit code is computed from one env var and nothing else (inverted)

- **Where:** `cli.py:208` (`ok = True`), `cli.py:213-214` (the only place `ok` is ever
  cleared), `cli.py:244` (`return 0 if ok else 1`).
- **Breaks:** `ok` is set `False` only when `GOOGLE_PLACES_API_KEY` is absent. It is never
  cleared by a `FAIL` line (`cli.py:243`), never cleared by a `WARN` (`cli.py:241`), never
  cleared by a missing/unwritable `data/` (`cli.py:222`), and never cleared by a crash in
  the data-directory block. The result is precisely backwards: the condition that should
  abort a run (no egress) exits `0`, and the condition that should not abort anything (no
  Google key — `google_places.py:169-171` simply prints "skipping" and the OSM +
  Wikidata stages still produce data) exits `1`.
- **Trigger (executed):**

  | scenario | printed | return code | what `leadminer run` would do |
  |---|---|---|---|
  | no `GOOGLE_PLACES_API_KEY`, all three endpoints HTTP 200 | 3× `OK` | **1** | works, Google stage self-skips |
  | key present, all three endpoints raise `OSError` | 3× `FAIL … OSError` | **0** | zero records collected |

- **Fix:** clear `ok` (or return a distinct code, per `037-cli-design.md:176-179`: `3` for
  config, `4` for network) inside the `except Exception` branch at `cli.py:242-243` and in
  the `WARN` branch at `cli.py:241`.

### S2 — The Google probe cannot check the Google credential: wrong method, no key, no body

- **Where:** `cli.py:236` (`requests.get("https://places.googleapis.com/v1/places:searchText")`),
  `cli.py:239` (`requests.get(url, timeout=5)`).
- **Breaks:** The real call is `session.post(API_URL, json=body, timeout=30)` with headers
  `X-Goog-Api-Key` and `X-Goog-FieldMask` (`google_places.py:159-166`, `:227`).
  `places:searchText` is POST-only — Google's own reference states "The API uses POST
  requests to `https://places.googleapis.com/v1/places:searchText` with parameters in the
  request body" and documents the HTTP request as `POST …/v1/places:searchText`
  (<https://developers.google.com/maps/documentation/places/web-service/reference/rest/v1/places/searchText>).
  So the probe sends a request the endpoint does not implement, without the one header
  whose validity is in question. Executed `kwargs` for all three probes is literally
  `{'timeout': 5}` — no `headers`, no `X-Goog-Api-Key`, no `json`.
- **Consequence:** the probe can never answer "is my key valid?". It also cannot detect
  field-mask drift, which the implementation treats as fatal via
  `resp.raise_for_status()` (`google_places.py:249`) — the 400 case that S1 then prints
  as `OK`.
- **Fix:** `requests.post(url, json={"textQuery": "cafe in Beirut", "pageSize": 1},
  headers={"X-Goog-Api-Key": os.environ["GOOGLE_PLACES_API_KEY"]}, timeout=10)` — exactly
  what `037-cli-design.md:173` specified and what was not built.

### S2 — Doctor probes with a different client than the pipeline uses, and Wikimedia bans that client

- **Where:** `cli.py:239` — bare `requests.get` with no `headers=`.
- **Breaks:** Every real outbound request goes through `httpclient.get_session()`, which
  sets `User-Agent: leadminer/0.2 (+https://github.com/voxire/leadminer) (email)`
  (`httpclient.py:66-69`, `:74-85`, used by `osm.py:4`, `wikidata.py:4`, `enricher.py:128`).
  `requests.get` with no headers sends `python-requests/<version>`. Executed
  `httpclient._user_agent()`:

  ```
  SCRAPER_EMAIL=<unset>      -> 'leadminer/0.2 (+https://github.com/voxire/leadminer)'
  SCRAPER_EMAIL=ops@voxire.com -> 'leadminer/0.2 (+https://github.com/voxire/leadminer) (ops@voxire.com)'
  ```

  The Wikimedia User-Agent policy says such requests "may also be blocked" and that
  clients sending an empty or generic UA "will fail with an HTTP 403"
  (<https://foundation.wikimedia.org/wiki/Policy:Wikimedia_Foundation_User-Agent_Policy>);
  the `python-requests` "library default" was explicitly scheduled for rate-limiting then
  blocking in <https://phabricator.wikimedia.org/T400119> (library default: 5 rps from
  Aug 11 2025, 1 rps from Aug 18, **blocked from Aug 25 2025**).
- **Consequence, both directions:** if WDQS 403s the probe, the 403 prints `OK` (S1) — a
  false all-clear. If WDQS rate-limits rather than blocks, `doctor` reports `FAIL` while
  the pipeline's real, policy-compliant UA succeeds — a false alarm that trains operators
  to ignore doctor. The probe result simply does not transfer to the pipeline.
- **Fix:** probe with `httpclient.get_session()` (it already carries the correct UA and
  `Accept-Language`), i.e. `get_session().get(url, timeout=15)`.

### S2 — `DATA_DIR` is CWD-relative, so "no run has produced output yet" is a lie

- **Where:** `cli.py:26` (`DATA_DIR = pathlib.Path("data")`), used at `cli.py:217-222`
  and as the default for `stats`/`validate`/`score` at `cli.py:294`, `:298`, `:305`.
- **Breaks:** `pyproject.toml:33` installs `leadminer` as a console script, so it runs
  from whatever directory the user happens to be in. The literal at `cli.py:222` asserts
  a historical fact ("no run has produced output yet") based only on the current
  directory. Same CWD-dependence silently changes the default input file for
  `stats`/`validate`/`score`.
- **Trigger (executed):** same machine, same populated `data/`, two working directories:

  ```
  CWD = the run directory:          CWD = an unrelated directory:
    OK   data exists                  MISSING  data (no run has produced output yet)
         all_businesses.csv  7 bytes
         sales_ready.csv 4,096 bytes
  ```
  return code `0` in both cases.
- **Fix:** define it once as `DATA_DIR = pathlib.Path(__file__).resolve().parent / "data"`
  in `main.py:41` and import that from `cli.py`; or at minimum print
  `f"  MISSING  {DATA_DIR.resolve()} ..."` so the CWD dependence is visible.

### S2 — "OK data exists" for a `data/` that the pipeline cannot write to

- **Where:** `cli.py:217` (`DATA_DIR.exists()`), `cli.py:218` (the `OK` line).
- **Breaks:** `exists()` is true for a regular file, and nothing checks writability.
  `Path.glob` on a non-directory swallows the `NotADirectoryError` and yields nothing
  (verified), so the listing is silently empty rather than an error.
- **Trigger (executed), both against the real pipeline in a subprocess:**

  | `data/` state | doctor prints | pipeline does |
  |---|---|---|
  | a regular file named `data` | `OK   data exists`, no CSVs listed, rc `0` | `main.py:208` → `FileExistsError [Errno 17] File exists: 'data'` |
  | directory with mode `0555` | `OK   data exists`, CSV listed, rc `0` | `main.py:209` → `write_csv` → `PermissionError [Errno 13] ... 'data/all_businesses.csv.tmp'` |

  Both are fatal to the run, and doctor is green in both.
- **Fix:** two lines — replace `DATA_DIR.exists()` with
  `DATA_DIR.is_dir() and os.access(DATA_DIR, os.W_OK)` and print `MISSING`/`NOT WRITABLE`
  otherwise.

### S3 — `f.stat()` raises, so doctor does traceback — the one thing it promised not to do

- **Where:** `cli.py:220` (`f.stat().st_size`), contradicting the comment at
  `cli.py:228-229`: *"doctor exists to diagnose a broken environment, so it must never be
  the thing that tracebacks."*
- **Breaks:** `Path.stat()` follows symlinks, and `main()` (`cli.py:314-318`) only catches
  `KeyboardInterrupt`, so the exception escapes as a full traceback.
- **Trigger (executed):** `ln -s /nonexistent/gone.csv data/master_link.csv` →
  ```
  FileNotFoundError: [Errno 2] No such file or directory: 'data/master_link.csv'
  ```
  `cmd_doctor` raised instead of returning; the connectivity section never ran. A stale
  symlink is a normal thing to have in a `data/` directory that gets rsynced from Drive
  (`scrape.yml:56`).
- **Fix:** wrap the loop in `try: ... except OSError: print("  WARN  <name>")`, or use
  `f.stat().st_size if f.exists() else -1`.

### S3 — A 5s blanket timeout that is shorter than every real request, in both directions

- **Where:** `cli.py:224` (`"connectivity (5s timeout each):"`), `cli.py:239`
  (`timeout=5`).
- **Breaks:** The pipeline allows 200s for Overpass (`osm.py:44`), 90s for Wikidata
  (`wikidata.py:75`), 30s for Places (`google_places.py:227`), 8s per website
  (`enricher.py:175`); `httpclient.DEFAULT_TIMEOUT` is 15 (`httpclient.py:47`).
- **Trigger:** the public Overpass `/api/status` endpoint is slowest precisely when it is
  most overloaded — the moment you would run doctor. A >5s response prints
  `FAIL Overpass ReadTimeout` (and, per S2, still exits `0`). A fast 404 from a
  misconfigured endpoint prints `OK`.
- **Fix:** `timeout=httpclient.DEFAULT_TIMEOUT` and print the timeout actually used.

### S3 — Output hygiene: exception type only, findings on stdout, misaligned labels, trailing spaces

- **Where:** `cli.py:241`, `:243`, `:212`, `:218`/`:222`.
- **Breaks / concrete:**
  - `FAIL  Overpass       OSError` (`:243`) prints `type(e).__name__` and drops
    `str(e)`, so DNS failure, TLS failure, timeout, connection-refused and proxy
    misconfiguration are indistinguishable — the exact distinction a triage tool exists
    to make.
  - Every `OK` line carries 7 trailing spaces when `note == ""` (verified:
    `repr` = `'  OK   Overpass       '`), so `leadminer doctor > log` produces
    whitespace-dirty diffs.
  - `{'OK ' if present else 'MISSING'}` (`:212`) produces misaligned output:
    `  OK   GOOGLE_PLACES_API_KEY` vs `  MISSING  SCRAPER_EMAIL`.
  - `FAIL` lines go to **stdout** (`:243`), while every other subcommand writes errors to
    stderr (`cli.py:84`, `:139`, `:145`, `:261`).
- **Fix:** `print(..., file=sys.stderr)` for `FAIL`, use `{r.status_code}`/`{type(e).__name__}: {e}` truncated to 40 chars, and pad with `.rstrip()`.

## Not a bug, but worth knowing

- **The `import requests` guard at `cli.py:226-231` is complete, not partial.** I grepped
  every third-party import on the runtime path: `requests` (`enricher.py:2`,
  `google_places.py:24`, `httpclient.py:43`) and `urllib3` (`enricher.py:327`, a hard
  dependency of `requests>=2.32.3,<3` per `pyproject.toml:16-18`). `beautifulsoup4` and
  `lxml` in `requirements.txt` are imported nowhere. So checking `requests` really does
  cover the dependency surface, and the early `return 1` with an actionable message is
  the best-placed code in this function. Keep it.
- **`SCRAPER_EMAIL` correctly does not affect the exit code.** `README.md:88` documents it
  as "Recommended", not required, and `_user_agent()` degrades gracefully
  (`httpclient.py:84`). Treating its absence as non-fatal is right. What is missing is the
  *consequence*: doctor prints a bare `MISSING` with no explanation and never prints the
  User-Agent the pipeline will actually send, so an operator cannot confirm whether they
  are presenting an identifiable client to Overpass/Wikidata. One line — print
  `httpclient._user_agent()` — would close that.
- **The `data/` listing is genuinely useful, and the byte sizes are honest.**
  `f"{f.stat().st_size:,}"` (`:220`) makes a truncated or 0-byte master immediately
  visible (verified: `all_businesses.csv  0 bytes`), which is a real signal given that
  `scrape.yml:74-77` refuses to publish an empty master.
- **Two spec items in `037-cli-design.md:164-179` were simply not built**, and both are
  cheap, so they belong on the backlog rather than in this report as defects: a Python
  `>= 3.12` assertion, and master-header/BOM integrity (`:174`) — the latter matters
  because a BOM written without `utf-8-sig` is a known data-corruption class in this
  codebase (`main.py:82-84`, `cli.py:154-156`). Also unbuilt: `--data-dir`, `--strict`,
  `--format json`, `--no-check-network`, and the distinct exit codes `3`/`4`. A
  leftover `*.csv.tmp` from a crashed run (`main.py:122`) is likewise invisible to
  `glob("*.csv")` — that file's existence is the clearest evidence of a failed run.

## Recommended order of work

1. **`cli.py:240-241`** — status predicate. `good = r.status_code == 200`; print the code
   otherwise. One line, removes the S1.
2. **`cli.py:242-243` / `cli.py:244`** — propagate failures into the exit code, and
   return `3` for config / `4` for network per `037-cli-design.md:176-179`.
3. **`cli.py:236-239`** — replace the three ad-hoc `requests.get`s with the same client
   the pipeline uses (`httpclient.get_session()`), and make the Places probe an
   authenticated `POST` with `pageSize: 1`. Then the probe's answer finally means
   something.
4. **`cli.py:26` + `cli.py:217`** — one absolute `DATA_DIR` shared with `main.py:41`, and
   `is_dir()` + `os.access(..., os.W_OK)` instead of `exists()`.
5. **`cli.py:220`** — make the listing crash-proof; also surface `*.csv.tmp`.
6. Output hygiene: stderr for `FAIL`, include `str(e)`, drop trailing spaces, realign the
   credential labels.
