# 235 — cmd_validate is outside every thread pool (safe), but the file it reads is not

## Verdict

`cmd_validate` (`cli.py:135`) is **safe under this codebase's concurrency**, and for a
structural reason rather than a lucky one: it is single-threaded, read-only, and holds
zero shared mutable state. `cli.py` contains no `ThreadPoolExecutor`, no `threading`
import and no module-level mutable binding other than `DATA_DIR` (`cli.py:26`), which is
only ever read. Every pool in the project (`main.py:160`, `scrapers/google_places.py:194`,
`enricher.py:237`) is created, joined and destroyed inside a `with` block during
`main.main()`, so by the time any CLI command runs there are no worker threads in the
process at all — and in the normal case `leadminer validate` is a separate process
anyway.

The real hazard is not inside `cmd_validate` but in **its input**. `main.write_csv` derives
its temp path deterministically from the target (`main.py:122`), so two concurrent
`leadminer run` processes write the *same* temp file. I reproduced the consequence 8 times
out of 8: exactly one process always dies with `FileNotFoundError` at `main.py:130`, and
the surviving master is **not** the union of the two runs — one run's freshly scraped
records are silently discarded. `cmd_validate` returned **0 / "all checks passed"** on
every one of those corrupted masters. So the quality gate that exists to catch a bad run
is structurally incapable of catching this one.

## Concurrency inventory — what is actually shared, and can it corrupt

| Shared thing | Owner / anchor | Guarded? | Can it corrupt? |
|---|---|---|---|
| `records[i]` dicts | `enricher.check_websites` | Yes, by construction | **No** — see below |
| `futures` dicts | `enricher.py:238`, `main.py:161` | Built and read on one thread | No |
| `seen_ids` set | `google_places.py:181` | `seen_lock`, `google_places.py:263-266` | No |
| `all_records` list | `google_places.py:183` | `records_lock`, `google_places.py:191-192` | No |
| `_api_key` | `google_places.py:157` | Read-only after `__init__` | No |
| `requests.Session` | `httpclient.get_session` | `threading.local`, `httpclient.py:58-71` | No |
| `DATA_DIR` | `cli.py:26` | Constant, never rebound | No |
| `sys.stdout` | interpreter | Implicit | Cosmetically, only (see Reentrancy) |
| `data/*.csv` on disk | `main.write_csv` | **No** — fixed temp name, `main.py:122` | **Yes** — S1 below |

### Shared mutable dict mutation across threads: the pattern is correct

`check_websites` submits `_fetch_website(url)` — a **string** (`enricher.py:238`,
`enricher.py:161`). The worker never receives the record dict. Every mutation of
`records[idx]` (`enricher.py:249-259`) happens in the `for future in as_completed(...)`
loop at `enricher.py:240`, which runs on the **calling** thread. Indices come from
`enumerate` (`enricher.py:231`), so each index is submitted at most once. Result: no
write-write race, no read-while-write, no lost update. The `records` dicts are only
*mutated* on one thread and only *read* (`r["website"]`) before the pool starts.

This is the one design decision in the codebase that is load-bearing for correctness, and
it is easy to break. Passing `records[idx]` into the worker "to avoid the index lookup"
would introduce a genuine race immediately: the consumer loop at `enricher.py:249-259`
reads `r.get("email")` to decide whether to overwrite it, while another thread could be
writing that same key. Worth a comment at `enricher.py:238` so nobody "optimises" it.

### Session reuse: correct, and now per-thread

`get_session()` (`httpclient.py:61-71`) stores the session in a `threading.local`
(`httpclient.py:58`), so the 40 enrichment workers each get their own `Session`, each with
its own urllib3 connection pool. The three scrapers (`osm.py:35`, `wikidata.py:73`) run in
the 3-worker pool at `main.py:160-161` and therefore also get separate sessions. This is
the fix the module docstring at `httpclient.py:6-10` describes, and it holds. Upstream
confirms the concern: a `Session` "persists cookies" and uses urllib3 connection pooling
(https://requests.readthedocs.io/en/latest/user/advanced/#session-objects), i.e. per-request
mutable state, which is exactly what must not be shared.

### Resource lifetime: bounded, reclaimed by thread death

Sessions created by `get_session()` are never explicitly `close()`d. That is survivable
only because of *when* they die: `ThreadPoolExecutor.__exit__` joins its workers, the
thread dies, and the `threading.local` slot holding the session is released with it. No
session outlives its thread, so there is no leak across the run. It is latent fragility
rather than a live bug (S3 below).

### Reentrancy of `cmd_validate`: safe, modulo `sys.stdout`

`cmd_validate` is reentrant. Every mutable binding is function-local: `rows`
(`cli.py:143`), `problems` (`cli.py:148`), `total` (`cli.py:149`), `bom_name`
(`cli.py:154`), `bad_coords` (`cli.py:164`), `bad_rating` (`cli.py:175`), and the pure
nested helper `in_box` (`cli.py:159-162`). Two concurrent calls on different files share
nothing but the interpreter's `sys.stdout`. Every `print` in the function passes a single
f-string, i.e. one `TextIOWrapper.write`, so lines do not splice mid-line even under a
thread race. The one observable difference in a hypothetical threaded caller is that
`cli.py:194`'s summary would interleave with `[Enricher] n/total done...`
(`enricher.py:262`) and `[Google] '<query>' page n: ...` (`google_places.py:257`) — ugly,
never wrong, and unreachable today: the only callers are `cli.main` (`cli.py:315`) and the
tests (`tests/test_lead_signal.py:238`, `:252`).

**Conclusion on the lens: there is no shared mutable state to corrupt, and no reentrancy
hazard. `cmd_validate` is safe.** The findings below are about its input and its
detection power, not about threading it wrongly.

## Findings

### S1 — Two concurrent runs share one temp filename: one always crashes, and one run's records are silently lost

- **Where:** `main.py:122` (`tmp = path.with_suffix(path.suffix + ".tmp")`),
  `main.py:124` (`open(tmp, "w", ...)`), `main.py:130` (`os.replace(tmp, path)`).
  Reported here because `cmd_validate` is the detector that fails to see the damage;
  the defect itself is in `main.py`, which is read-only to this audit.
- **Breaks:** the temp name is a pure function of the target name, so it is identical in
  every process. Two `leadminer run` processes (a second `workflow_dispatch` while the
  first 300-minute job is still going, plus a manual run on a laptop) both open
  `data/all_businesses.csv.tmp` with `O_TRUNC` and write into it at independent file
  offsets. Whichever process reaches `os.replace` first renames the shared temp file out
  from under the other, which then dies with `FileNotFoundError` — a *run that dies*,
  after hours of scraping, from `cli.py:37` → `cli.main` (`cli.py:314-318`, which catches
  only `KeyboardInterrupt`) as a raw traceback. Worse than the crash: the published master
  is not the union of the two runs. `main.main()` calls `write_csv` five times
  (`main.py:209-213`), so the collision can strike the master *or* any of the four
  derived CSVs, and the winner's file may be missing the other run's entire batch.
- **Trigger:** two processes, real `main.write_csv`, barrier-synchronised, instructed to
  write 150,000 and 90,000 records. Result, identical across 3/3 trials:

  ```
  outcomes=[('AAA', 'FileNotFoundError'), ('BBB', 'ok')]
  final master census: rows_from_AAA=150,000 (run A had 150,000)
                       rows_from_BBB=0      (run B had 90,000)
                       total=150,000
  cmd_validate: "checked 150,000 rows ... all checks passed"  exit=0
  ```

  The run that reported success contributed **zero** records to the master. In an earlier
  5/5-trial set where both writers emitted the same row count, the master came out as a
  blend (1,794,928 `AAA-` tokens and 605,072 `BBB-` tokens in one file) and `validate`
  still returned 0.
- **Aggravating:** `main.py:131-133` catches `BaseException`, calls
  `tmp.unlink(missing_ok=True)` and re-raises. If the loser's cleanup runs while the
  winner is between `open(tmp, "w")` and `os.replace`, the loser deletes the winner's
  in-progress temp file and *both* runs die.
- **Fix:** make the temp name unique per process —
  `tmp = path.with_suffix(f"{path.suffix}.{os.getpid()}.tmp")` — and/or take an exclusive
  `fcntl.flock` on `data/.lock` for the whole of `main()` so a second run refuses to
  start.

### S2 — Unparseable `lat`/`lon` is silently counted as "in bounds", so the coordinate gate is a no-op on a structurally corrupt master

- **Where:** `cli.py:166-169`

  ```python
  try:
      lat, lon = float(r["lat"]), float(r["lon"])
  except (ValueError, TypeError, KeyError):
      continue          # <-- row is neither validated nor counted
  ```
- **Breaks:** every row it cannot parse is treated as good, and the failure is not
  counted anywhere. Two distinct corruptions both sail through:
  1. A CSV with no `lat`/`lon` columns at all → `KeyError` on all rows → `bad_coords`
     stays 0 → "all checks passed". Verified: exit 0 on a 200-row file whose header is
     `name,category,rating,phone`.
  2. A CSV where the columns exist but hold non-numeric text (spliced/interleaved rows
     from the S1 collision, a shifted-column export, a locale decimal comma) → `ValueError`
     on all rows → `bad_coords` stays 0 → "all checks passed". Verified: exit 0 on 500
     rows whose *only* defect is unparseable coordinates, with valid ratings and
     in-range values everywhere else. The same 500 rows with numeric-but-out-of-range
     coordinates correctly exits 1 with "500 rows have coordinates outside
     Lebanon/Saudi Arabia" — so the gate works only when the data is already
     well-formed enough to parse.
- **Why this is the finding that matters:** the corruption mode in S1 is precisely the
  one this gate is supposed to catch, and this is the reason it does not. Combined with
  the 1% tolerance at `cli.py:172` (`bad_coords > total * 0.01`), a wholly wrong
  coordinate column and a clean one are indistinguishable. Verified: 19 of 2000 rows
  (0.95%) genuinely outside the bbox → exit 0, no output at all.
- **Fix:** count unparseable rows separately and fail on any meaningful number of them:
  `except (...): bad_coords += 1; continue`, and assert the header contains `lat`/`lon`
  before iterating.

### S3 — `validate` and `stats` materialise the whole master: 1,928 B/row measured

- **Where:** `cli.py:143` (`rows = list(csv.DictReader(f))`), same pattern at
  `cli.py:87` in `cmd_stats`.
- **Breaks:** measured with `tracemalloc` over 50,000 synthetic 23-column rows written
  through the real `main.FIELDS`: **96,384,679 bytes retained = 1,928 B/row**. That is
  ~0.96 GB for a 500,000-row master and ~1.9 GB at a million. Both commands then walk
  `rows` four separate times (`cli.py:151`, `:154`, `:165`, `:176`, `:190`). These are
  the commands the module docstring tells you to reach for when a run looks wrong
  (`cli.py:14-15`, `cli.py:80`), so the diagnostic you run during an incident is a
  ~1 GB allocation on a machine that may already be tight. Not a threading bug, but it
  is the resource half of the lens and it is the same class of "silently assumes the
  dataset fits in RAM" as `check_websites` holding every record in memory.
- **Fix:** stream it — replace `list(csv.DictReader(f))` with a single generator pass
  and accumulate counters (and a `set` for the dup check at `cli.py:190`), which also
  collapses the four passes into one.

### S3 — `http_session()` looks like it manages a session and does not

- **Where:** `httpclient.py:88-91` — a `@contextmanager` that yields `get_session()` and
  has no `finally` and no `close()`.
- **Breaks:** the name and the `with` syntax say "scoped resource"; the body says
  otherwise. `with http_session() as s:` gives no cleanup guarantee whatsoever, which is
  exactly the assumption that would leak 40 sockets if someone refactored
  `_fetch_website` (`enricher.py:175`) onto it. Currently unused — the only occurrence is
  the docstring at `httpclient.py:23` — so this is a trap, not a leak.
- **Related, same class:** `google_places.py:189` builds a fresh `requests.Session` per
  *query*, i.e. 68 sessions per run (`LEBANON_QUERIES` + `KSA_QUERIES`), each with its own
  connection pool, none closed. Correct with respect to thread safety, wasteful with
  respect to resources; per-*thread* would be 5.
- **Fix:** either drop `http_session()` or make it `try: yield ... finally: session.close()`
  — but note that closing a thread-local session on every exit would break the per-thread
  reuse `httpclient.py:56-57` is built for, so the honest fix is to delete the helper.

### S3 — `leadminer run` always exits 0, which undercuts the exit-code contract `validate` is selling

- **Where:** `cli.py:37` (`return pipeline.main()`), `main.py:148` (`-> None`),
  `cli.py:315` (`int(args.func(args) or 0)`).
- **Breaks:** `main.main()` returns `None` and swallows scraper failures into
  `print(..., file=sys.stderr)` (`main.py:167-168`), so `cmd_run` yields 0 even when
  Overpass, Wikidata and Places all failed. `cmd_validate` returns a real 0/1/2
  (`cli.py:197`, `:201`, `:139`), which invites `leadminer run && leadminer validate` in
  CI. That chain is only as strong as its first link, and today the first link is
  decorative.
- **Fix:** have `main.main()` return a non-zero code when any source raised, and
  propagate it at `cli.py:37`.

## Not a bug, but worth knowing

- **The run-vs-validate read race is correctly handled, and I confirmed it.** `os.replace`
  is atomic on POSIX ("If successful, the renaming will be an atomic operation (this is a
  POSIX requirement)", https://docs.python.org/3/library/os.html#os.replace), and
  `cmd_validate` opens the *target* path (`cli.py:142`), never the `.tmp`. I ran 8
  concurrent `cmd_validate` readers against a file that a single writer was rewriting
  underneath them: **24 reads, 0 anomalies, exit code 0 every time**, each read seeing
  either exactly the old or exactly the new row count and never a torn one. The atomic
  write at `main.py:121-130` is doing its job, and it is the right foundation — it is
  only the temp *name* that is broken (S1), not the atomicity.
- `DATA_DIR` (`cli.py:26`) is a module constant, and every default path is computed at
  parser-construction time (`cli.py:294`, `:298`, `:305`). A `--data-dir` override
  threaded through `build_parser` would need care here, since the defaults are frozen
  before any command runs — but that is a design question, not a race.
- `enricher.enrich` calls `urllib3.disable_warnings(...)` (`enricher.py:327-328`), which
  is process-global, but it runs *before* `check_websites` (`enricher.py:337`), so no
  worker exists yet to observe a half-configured global.
- `check_websites` prints progress every 200 completions (`enricher.py:261-262`) from the
  single consumer thread, so that output is never interleaved with itself — the 40
  workers print nothing.
- The 3-scraper pool (`main.py:160-161`) merges results with `raw.extend(batch)` on the
  consumer thread (`main.py:166`) and each `run()` wrapper consumes its own generator
  inside the worker (`main.py:157-158`), so generator state is never shared across
  threads. Correct.

## Recommended order of work

1. **S1** — unique temp name per process (`main.py:122`), plus a `flock` on `data/.lock`
   for the duration of `main()`. This is the only finding on this lens that destroys the
   product. Everything else here degrades gracefully by comparison.
2. **S2** — count unparseable coordinates instead of `continue`-ing past them
   (`cli.py:168-169`), and require `lat`/`lon` in the header. Without this, `validate`
   cannot detect failure mode S1, and the gate's exit code is not evidence.
3. **S3 memory** — stream `cli.py:143` and `cli.py:87` into a single generator pass.
   Removes ~1 GB from the two commands operators actually run under pressure.
4. **S3 traps** — delete `http_session()` (`httpclient.py:88-91`); make
   `GooglePlacesScraper._make_session` per-thread rather than per-query
   (`google_places.py:189`).
5. **S3 exit code** — propagate a failure code out of `main.main()` so
   `run && validate` in CI means something.
6. Add a one-line comment at `enricher.py:238` recording that the worker must receive the
   URL and not the record dict. That invariant is what makes the 40-thread pool correct,
   and nothing currently says so.
