# 236 — `cmd_validate` contract audit (`cli.py:135`)

## Verdict

`cmd_validate` reads 5 of the 23 keys in `BusinessRecord`, and its one geographic
assertion silently skips every row it cannot parse — so it returns
`0 / "all checks passed"` on a 5,000-row CSV in which every record sits at
`(10.0, 10.0)` in the Indian Ocean (verified below). Nothing in `.github/` ever
invokes it: `scrape.yml:71-83` reimplements validation in shell as `wc -l`. The
type contract is fiction — `rows` is `list[dict[str, str | None]]` from
`csv.DictReader`, not `BusinessRecord`, and the `# type: ignore[arg-type]` at
`cli.py:167` is the suppressed fingerprint of that gap. The function is a
reasonable starting sketch; it is not a gate.

## The declared vs. actual contract

`cmd_validate` declares no row type at all. Its `rows` comes from
`csv.DictReader` (`cli.py:143`), whose runtime value shape is:

| shape | when |
|---|---|
| `str` | normal cell |
| `None` | row shorter than the header (missing trailing cells) |
| `list[str]` under key `None` | row *longer* than the header (the `restkey`) |
| key absent entirely | column not in the header |

`BusinessRecord` (`scrapers/base.py:5-28`) declares a different shape for the
same five fields:

| field | read by `cmd_validate` | `BusinessRecord` | in pipeline (`main.py`) |
|---|---|---|---|
| `name` | `str \| None` | `str \| None` ✓ | `str \| None` ✓ |
| `lat` | `str \| None` | `float \| None` ✗ | `float \| None` ✓ |
| `lon` | `str \| None` | `float \| None` ✗ | `float \| None` ✓ |
| `rating` | `str \| None` | `float \| None` ✗ | `float \| None` ✓ |
| `phone` | `str \| None` | `str \| None` ✓ | `str` after `normalize_phone` |

Three of five fields are `str` here and `float` everywhere else. That is not an
accident of one function: **`cmd_validate` does not use `main.load_master`**
(`main.py:77-105`), which is the only thing that casts `""` → `None` and
`_FLOAT_FIELDS`/`_INT_FIELDS` → `float`/`int` (`main.py:87-102`). There are now
three loaders for one file with three views of it — `cmd_stats` (`cli.py:86-87`),
`cmd_validate` (`cli.py:142-143`), `cmd_score` → `load_master` (`cli.py:259`).

### Fields read that are **not** in the TypedDict

**None.** `cmd_validate` reads exactly `name`, `phone`, `lat`, `lon`, `rating`
(`cli.py:151, 154, 167, 177, 190`) and all five are declared keys
(`base.py:6, 13, 11, 12, 21`). It writes no fields.

That clean answer hides the real problem: it reads by *string key* against an
open `Mapping`, so it will happily read **any** column, including ones
`write_csv` silently drops (`extrasaction="ignore"`, `main.py:125`). Nothing
asserts `set(csv.fieldnames) == set(main.FIELDS) == set(BusinessRecord.__annotations__)`,
so the gate validates a schema the exporter will not preserve. This is live
today: `places.id` is requested on **every** Google call (`FIELD_MASK`,
`scrapers/google_places.py:34`), used only as an in-run dedup key
(`google_places.py:260-262`), and never stored on the record.

### Fields declared but never read (18 of 23)

`category, address, region, country, email, website, website_live, facebook,
instagram, whatsapp, linkedin, review_count, industry_priority,
recommended_service, lead_score, source, scraped_at, completeness_score`.

Three of those decide what gets published — see S2-3.

## Findings

### S1 — The coordinate check reports success on rows it never examined

- **Where:** `cli.py:164-173`, specifically `cli.py:167-169`
- **Breaks:** `except (ValueError, TypeError, KeyError): continue` discards
  every row whose `lat`/`lon` is missing, unparseable, or under a different
  column name, and never counts it. `bad_coords` only accumulates rows that
  *parsed* and fell outside the box. "0 rows have coordinates outside
  Lebanon/Saudi Arabia" is therefore indistinguishable from "0 rows had
  coordinates at all". The function's only geographic assertion is
  unfalsifiable on the most likely inputs.
- **Trigger (verified, run against this tree):**

  ```
  # 5,000 rows, all 23 columns present and pristine, EXCEPT the coordinate
  # columns are named latitude/longitude and every point is (10.0, 10.0).
  $ leadminer validate geo_drift.csv
  checked 5,000 rows in geo_drift.csv
    all checks passed
  rc = 0
  ```

  Second verified trigger, same columns present, values unparseable:
  `lat="N/A", lon="N/A"` on 500 rows → `all checks passed`, `rc = 0`.
  Third: a two-row single-column CSV (`name` only) → `all checks passed`,
  `rc = 0` — a file with no coordinates, no phone and no rating is "valid".
- **Fix:** count the skips and fail (or at minimum print the denominator):
  `skipped` and `checked` alongside `bad_coords`, and hard-fail when
  `checked == 0` or when the header is missing any of `lat`/`lon`.

### S1 — Nothing invokes the gate; CI substitutes `wc -l`

- **Where:** `.github/workflows/scrape.yml:71-83` (step "Validate output before
  publishing"), `README.md:14`, `cli.py:136`
- **Breaks:** the only automated pre-publish check is
  `ROWS < 100 → exit 1` (`scrape.yml:78-83`) plus a non-empty test. Verified:
  `grep -rn "leadminer" scripts .github` matches nothing but a concurrency
  group name; the only workflow step runs `python main.py` (`scrape.yml:69`).
  So a run that publishes 5,000 rows of out-of-market leads, or with
  `website_live` inverted, or with 1,000 blank names, uploads to Drive
  (`scrape.yml:88-89`) and becomes next week's master (`scrape.yml:56`).
  Every S2 below is downstream of this: they are all unreached bugs.
- **Trigger:** delete the `name` column values from one run's output, or set
  `website_live` to the wrong constant — the run publishes and the next run
  dedups against it.
- **Fix:** replace `scrape.yml:71-83` with
  `leadminer validate data/all_businesses.csv` (plus the four subset CSVs,
  which nothing checks today), and add a `pull_request` job that runs it on
  fixtures so the gate itself is exercised.

### S2 — `in_box` is a country-sized box, so its message is false

- **Where:** `cli.py:159-162`
- **Breaks:** the SA box is `16.0 ≤ lat ≤ 32.2` and `34.4 ≤ lon ≤ 55.7` —
  roughly 16° of latitude and 21° of longitude. Verified against real city
  coordinates using the function verbatim:

  | passes as "inside Lebanon/Saudi Arabia" | rejected |
  |---|---|
  | Amman JO, Aqaba JO, Basra IQ, Kuwait City KW, Doha QA, Dubai AE, Abu Dhabi AE, Sinai EG | Baghdad IQ, Irbid JO, Tehran IR, Muscat OM, Cairo EG, Aleppo SY, Latakia SY, Nicosia CY, Casablanca MA |

  Five neighbouring markets that `dedup._KNOWN_CUNTRY_CODES`
  (`dedup.py:8-21`) explicitly anticipates leaking in (`962`, `971`, `965`,
  `974`) are inside the box. The failure is silent by construction: the check
  only fires above 1% of rows, and those rows would be a rounding error.
- **Trigger:** `lat=29.375, lon=47.977` (Kuwait City) →
  `bad_coords` unchanged, `problems` stays empty, `rc = 0`.
- **Compounding:** this is a *second, independent* definition of "inside our
  market" that disagrees with `enricher._LB_COORD_REGIONS` /
  `_KSA_COORD_REGIONS` (`enricher.py:58-76`), which are 8 tight Lebanese
  regions and 5 KSA city boxes. `infer_region` picks the box set from
  `country` (`enricher.py:90`), so a record the gate calls in-market is
  routinely the record the pipeline refuses to region-tag.
- **Fix:** derive the gate's bounds from one shared constant that
  `enricher.infer_region` also imports; drop the 1% tolerance and report the
  out-of-market count per country code instead of a single boolean.

### S2 — The duplicate check reimplements identity and disagrees with `dedup`

- **Where:** `cli.py:190` vs `dedup.py:197-232`
- **Breaks:** the pipeline's key is `normalize_phone(phone, country)`, else
  `(normalize_name(name), _extract_city(address))` (`dedup.py:205, 212-214`).
  The gate's key is the raw `(name, phone)` pair. Both directions are wrong.
- **Trigger, false positive (verified):** two records with the same raw phone
  but different `country` get different normalized keys —
  `normalize_phone("70123456","LB") == "+96170123456"` but
  `normalize_phone("70123456","SA") == "+96670123456"` — so `dedup` keeps both,
  and the gate reports `1 duplicate (name, phone) pair`. On a master where
  cross-border duplicates cluster this exceeds the 5% threshold
  (`cli.py:191`) and the gate fails on a **correctly deduped** file.
- **Trigger, false negative (verified):** the same business where one row has a
  phone and the other does not. `(name, "+96170123456")` and `(name, None)` are
  distinct keys → `dupes = 0`, while `dedup` merges them on
  `(normalize_name(name), city)`. The gate's "0 duplicates" says nothing about
  the pipeline's "N unique businesses" (`main.py:181`).
- **Amplifier:** if the CSV has no `phone` column at all, `r.get("phone")` is
  `None` for every row and the key silently collapses to name-only — so two
  branches of a chain become "duplicates" for the wrong reason, which is
  exactly what happens in S1-3's blank-name fixture.
- **Fix:** `from dedup import normalize_name, normalize_phone, _extract_city`
  and build the key with the pipeline's own functions. One definition of
  "duplicate", not two.

### S2 — 18 unchecked fields, including the three that gate publishing

- **Where:** `cli.py:148-192` (the whole check block); consequences at
  `main.py:204`, `main.py:206`, `main.py:215-217`
- **Breaks:** the checks that exist cover `name`, `phone`, `lat`, `lon`,
  `rating`. The three fields that decide what a salesperson sees are absent:
  - **`industry_priority`** — `sales_ready.csv` is defined as
    `has_any_contact(r) and r.get("industry_priority") in ("high","medium")`
    (`main.py:202-205`). `industry_priority()` only ever returns the exact
    lowercase literals `"high"/"medium"/"low"` (`whitelist.py:133-145`), and
    `cmd_validate` asserts none of them. One `"High"` or `"HIGH"` anywhere in
    the accumulated master — a hand edit, a re-export from Sheets, a future
    refactor — and `sales_ready.csv` silently shrinks toward empty while the
    gate reports `all checks passed`.
  - **`website_live`** — the tri-state the entire lead signal rests on
    (`enricher.py:297-304`, `pitch_recommender.py:34-36`,
    `main.py:215-217`). `cmd_stats` counts it (`cli.py:107-110`); `cmd_validate`
    never looks at it. `load_master` parses it from exactly the literals
    `"True"`/`"False"` (`main.py:103`), so any other spelling — `"true"`,
    `"1"`, `"TRUE"` — collapses to `None`, i.e. "unreachable", i.e. *no*
    rebuild pitch and *no* SEO pitch. Nothing in the toolchain notices.
  - **`country`** — drives `resolve_country` (`main.py:50-74`, which
    *fabricates* `"LB"` when it cannot decide, `main.py:74`), `normalize_phone`
    (`dedup.py:48`), and which coordinate-box set `infer_region` uses
    (`enricher.py:90`). A `country` outside `{LB, SA}` is never flagged, and
    the geometric backstop that would catch it is S2-1.
- **The `name` check is all-or-nothing and misdiagnoses.**
  `cli.py:151` fires only if *every* row is blank. Verified: a 5,000-row file
  with 4,000 named and 1,000 blank `name` cells reports
  `- 999 duplicate (name, phone) pairs` and `rc = 1` — the operator is told
  about duplicates when the actual defect is a fifth of the file having no
  name. And blank names are not harmless: `normalize_name("") == ""`
  (`dedup.py:66-69`) and `dedup.py:212` uses it as the name key, so verified —
  five nameless, phone-less, same-city records collapse to **one** row. The
  same 1,000 blank names *with* distinct phones survive dedup separately, so
  the gate then reports `0 duplicates` and passes.
- **Also cheap and missing:** `email` format (`dedup._EMAIL_OK` already exists
  at `dedup.py:116`; `_fetch_website` harvests addresses out of arbitrary remote
  HTML at `enricher.py:199-204` with only an 8-domain blacklist, and
  `has_any_contact` credits any string containing `@` and longer than 5 chars
  at `main.py:139-144`); `completeness_score` ∈ [0, 7] against
  `completeness_score()`'s seven increments (`enricher.py:101-117`);
  `lead_score` ∈ [0, 100] against `min(score, 100)` (`enricher.py:319`);
  `scraped_at` parseability — a blank one sorts as `""` (`dedup.py:156`) and so
  always loses every volatile field (`rating`, `review_count`, `website`,
  `website_live`; `dedup.py:114, 183`) to any row that has one.
- **Fix:** add four domain assertions — `country ∈ {LB, SA}`,
  `website_live ∈ {"True","False",""}`, `industry_priority ∈ {high,medium,low}`,
  `name` blank *rate* — and reuse `dedup._EMAIL_OK`.

### S2 — Ratios are reported against the wrong denominator, and the tolerances are scale-dependent

- **Where:** `cli.py:172-173`, `cli.py:187-188`, `cli.py:191-192`
- **Breaks:** every threshold is a fraction of `total` (`cli.py:149`), but the
  numerators are computed over the subset that *has* the field. Verified: a
  file with 5,000 rows of which 900 are rated and 187 of those are out of range
  prints `187 rows have a rating outside 0-5` — 3.7% of `total` but **21% of
  rated rows**, and the reader is given no way to tell which. The same applies
  to coordinates, where the "has the field" subset is the one S1-1 shows can be
  zero.
- **The tolerances themselves:** `total * 0.01` and `total * 0.05` make the
  gate's sensitivity depend on file size, so the "cheap" invocation
  (`leadminer validate sample.csv`) reaches a different verdict on identical
  data quality than the full-file invocation. Verified with two files of the
  same defect rate:
  - 4 rows, 3 out of market (75%) → fires, `rc = 1`
  - 5,000 rows, 49 out of market (0.98%) → silently passes
- **Fix:** print `bad/checked` and `checked/total` per check; replace the
  implicit tolerances with a `--max-rate` flag so the policy is visible at the
  call site.

### S3 — The BOM check is unreachable

- **Where:** `cli.py:154-156`
- **Breaks:** the file is opened with `encoding="utf-8-sig"` (`cli.py:142`),
  and that codec **strips a leading BOM on decode**. Verified:

  ```
  raw = "name,lat,lon\n...".encode("utf-8-sig")
  raw.decode("utf-8-sig") -> header ['name', 'lat', 'lon']
  raw.decode("utf-8")    -> header ['﻿name', 'lat', 'lon']
  ```

  So `r.get("name")` can never start with `﻿` and `bom_name` is
  provably always `0`. The diagnostic whose message promises to catch
  "written without utf-8-sig" cannot fire, while the real protection lives
  elsewhere and unremarked (`main.py:124` writes with `utf-8-sig`,
  `main.py:85` reads with it). Note that the `name` check at `cli.py:151` does
  *not* misfire as a result — the header parses correctly — so this is pure
  dead code and a false sense of coverage, not a wrong diagnosis.
- **Fix:** delete `cli.py:154-156`, or read with `encoding="utf-8"` in a
  dedicated header probe if the BOM really is worth checking.

### S3 — The exit-code space is ambiguous, and `None`/`False` means "pass"

- **Where:** `cli.py:135-201` (returns), `cli.py:314-318`, `cli.py:322`
- **Returns:** exactly `{2, 1, 0}` from `cli.py:140, 146, 201, 197`. Consistent
  internally. Three consumers, only one of which is documented:
  - `tests/test_lead_signal.py:238, 252` — `assertEqual(rc, 1)` and
    `assertEqual(rc, 0)`. Strict about 0/1; **the `rc == 2` missing-file path is
    untested for validate** (it is tested for `cmd_stats` at line 264).
  - `cli.py:315` — `int(args.func(args) or 0)`.
  - `cli.py:322` — `raise SystemExit(main())`.
- **Break-on-unexpected-shape, enumerated:**
  - `None`, `False`, `""`, `0` → `or 0` → **exit 0 → "gate passed"**, and
    `SystemExit(False)`/`SystemExit(None)` are also success. The entire gate
    rests on truthiness; one refactor from `return 1` to `return False` inverts
    it with no type error and no test failure.
  - a truthy non-`int` (e.g. `return problems`, the local list at
    `cli.py:148`) → `int(["a"])` → `TypeError` → traceback → exit 1.
  - an uncaught exception → traceback → exit 1. **Indistinguishable from
    "checks failed".** Verified concrete input: `path.exists()` (`cli.py:138`)
    is true for a directory, so

    ```
    $ leadminer validate docs
    IsADirectoryError: [Errno 21] Is a directory: 'docs'
    exit code = 1
    ```

    A `PermissionError` or an unreadable path behaves the same way. Any wrapper
    that reads exit 1 as "the data is dirty" will file a permissions problem as
    a data problem; any wrapper that reads exit 0 as "validated" is fine, but
    the gate has no way to say "I could not read the input".
- **Also:** `main()` (`cli.py:314-318`) catches only `KeyboardInterrupt`, so
  no exception class is converted to a code at all.
- **Fix:** reserve `0` ok / `1` data problems / `2` usage-or-IO / `3` internal
  error; wrap `args.func(args)` so anything unexpected exits 3, never 1.

### S3 — `args` is an untyped duck-typed `Namespace`, and the tests hand-build it

- **Where:** `cli.py:137` (`args.file`), `cli.py:297-299`,
  `tests/test_lead_signal.py:238, 252`, `docs/audits/037-cli-design.md:501`
- **Breaks:** `cmd_validate` reads `args.file` with no `getattr` default, so a
  caller that builds the namespace itself must supply exactly that one
  attribute. The tests already do (`argparse.Namespace(file=p)`). The proposed
  redesign adds `--schema canonical --check-geo --strict`
  (`037-cli-design.md:501`); the moment any of those land, `args.strict` is an
  `AttributeError` inside the function — and only in the tests, because the
  argparse path always sets it.
- **Fix:** give the commands a small frozen dataclass (`args.file: Path`) built
  once in `main()`, so a missing field fails at the boundary with a clear
  message instead of inside the command.

### S3 — `DATA_DIR` is CWD-relative

- **Where:** `cli.py:26`, used as the `file` default at `cli.py:294, 298, 305`
- **Breaks:** `leadminer validate` from any directory other than the repo root
  resolves to a non-existent `data/all_businesses.csv` and exits `2` with
  `no such file: data/all_businesses.csv` — which reads as "you have no data"
  rather than "you are in the wrong directory". It is at least an honest exit
  code, which is why this is S3 and not higher.
- **Fix:** resolve the default against the package location, or require the
  path with no default.

## Not a bug, but worth knowing

- **`csv.DictReader` never puts a list into a named key.** A ragged row stores
  its extras under the `None` restkey. Verified:
  `{'name':'C', ..., None: ['EXTRA','EXTRA2']}`. So `r.get("rating")` can never
  be a `list` and the `float(raw)` at `cli.py:181` (and `float(r["lat"])` at
  `cli.py:167`) cannot hit a `TypeError` from that shape. The `except
  (ValueError, TypeError)` there is still correct — `cli.py:177` already
  `.strip()`s and `(x or "")` normalises `None` to `""`. But the ragged row is
  still silently truncated on re-export (`extrasaction="ignore"`,
  `main.py:125`), and neither the gate nor the exporter reports it.
- **The `# type: ignore[arg-type]` at `cli.py:167` is over `str | None`, not
  `float | None`.** The suppression exists because `csv.DictReader` hands back a
  string where the TypedDict promises a float. It is a marker of the contract
  gap, not of a `float()` limitation.
- **The TypedDict is unenforced at runtime and in CI.** A `TypedDict`
  constructor is just `dict(**kwargs)` — `BusinessRecord(bogus=1)` returns
  `{"bogus": 1}` without complaint, and a *missing* key is equally silent, which
  is why `enricher.py:340-348` needs nine `setdefault` calls to paper over it.
  `pyproject.toml:64-68` configures `mypy strict`, but `scrape.yml:27-98` has no
  lint or type step, and no `[[tool.mypy.overrides]]` covers `cli`. So
  `BusinessRecord` is documentation, and `cmd_validate`'s un-annotated
  `rows` local means even the type checker has nothing to say.
- **`_extract_city` returns the last comma-separated part** (`dedup.py:75`).
  Verified: `"Main St, Beirut, Lebanon"` → `"lebanon"`, `"Rue Monnot, Beirut"` →
  `"beirut"`. So for most OSM-style addresses `dedup`'s name key is effectively
  `(normalize_name(name), country)`, which will merge same-named businesses in
  Beirut and Zahlé. That is `dedup`'s bug, not this function's — but it is
  unobservable *through* this function, because the merged pair differs in
  phone and therefore reads as "not a duplicate" (S2-2, false negative).
- **`_merge`'s last-resort tiebreak is alphabetical, not semantic**
  (`dedup.py:186`). For `country`, trust and validity are equal for every
  source, and `country` is not in `_VOLATILE`, so the tiebreak is
  `str(value)`. Verified: `_merge(LB_record, SA_record)["country"] == "SA"`.
  Whatever wins, it is not the fresher or the more trustworthy record.
- **Doc drift:** `BRIEF.md:18` and the brief's own column list say the
  `BusinessRecord` has 22 keys. It has 23 (`base.py:6-28`), matching
  `main.FIELDS` (`main.py:33-40`).

## Recommended order of work

1. **Fail loudly on input the gate cannot read** (S1-1). Replace the bare
   `continue` with counted `checked` / `skipped`, and assert the header
   contains every key in `main.FIELDS` before any per-row check runs. Without
   this, every other fix is cosmetic.
2. **Wire the gate into CI** (S1-2). Replace `scrape.yml:71-83` with
   `leadminer validate` over all five CSVs, and add a `pull_request` job so
   the gate is itself exercised on every change.
3. **One definition of "duplicate"** (S2-2). Import `normalize_phone`,
   `normalize_name`, `_extract_city` from `dedup`.
4. **One definition of "in market"** (S2-1). A shared `MARKET_BOUNDS` constant
   imported by both `cli.py` and `enricher.py`, derived from
   `_LB_COORD_REGIONS` / `_KSA_COORD_REGIONS`, with per-country out-of-market
   counts instead of a single boolean.
5. **Assert the four domains that gate publishing** (S2-3): `country`,
   `website_live`, `industry_priority`, and blank-`name` *rate*. These are ten
   lines and they cover the failure modes that reach a salesperson.
6. **Report denominators, drop the implicit tolerances** (S2-4): print
   `bad/checked (x% of total)` per check and take `--max-rate` from the caller.
7. **Harden the return contract** (S3-2): reserve exit code 3 for internal
   errors so a traceback can never be mistaken for dirty data, and drop the
   `or 0` truthiness trap at `cli.py:315`.
8. **Housekeeping:** delete the unreachable BOM check (S3-1); introduce a typed
   args object before the `--strict` flags land (S3-3); resolve `DATA_DIR`
   against the package, not the CWD (S3-4); add a `rc == 2` case to
   `TestCli.test_validate_*`; get a mypy/ruff step into CI so the
   `cli.py:167` suppression is actually re-checked.
