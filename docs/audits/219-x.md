# 219 — `cmd_scrape` thread safety and concurrency audit

## Verdict

`cmd_scrape` (`cli.py:40`) is **safe**. It is the only command in the CLI that runs
exactly one scraper, it materialises the generator completely with `list()` at
`cli.py:61`, and the one thread pool it can reach (`GooglePlacesScraper`, 5 workers)
is joined by `ThreadPoolExecutor.__exit__` **before** the first record is yielded. I
measured exactly one `ThreadPoolExecutor(max_workers=5)` per invocation and zero
40-worker pools: the 40-thread `check_websites` pool (`enricher.py:225`) and the
3-scraper pool (`main.py:160`) are both structurally unreachable from this function.
It cannot corrupt shared state and it is reentrant.

The real problems are not races — they are **blind spots**. The command's stated job
is to verify one source after an API change (`cli.py:41-44`), but it reports a count
that is indistinguishable between "source healthy" and "65 of 67 queries abandoned on
5xx/429", its numbers are pre-whitelist and cannot be compared to the pipeline, and a
single malformed response body throws away the other 66 queries' work as an uncaught
traceback. Separately, the one genuinely corrupting bug in the CLI's concurrency
surface is one line away, in `write_csv`, and it affects the sibling command
`cmd_score`.

## Findings

### S1 — `write_csv` uses a fixed temp filename, so two concurrent writers publish an interleaved "atomic" master

- **Where:** `main.py:122` (`tmp = path.with_suffix(path.suffix + ".tmp")`),
  `main.py:130` (`os.replace(tmp, path)`); reached from `cmd_run` (`cli.py:33-37`)
  and `cmd_score` (`cli.py:247-277`, in-place default at `cli.py:274`)
- **Scope note:** this is *not* in `cmd_scrape` — that function writes no files at all.
  It is reported here because it is the only real data-corruption path in the CLI's
  concurrency surface, it is a one-line fix, and `cmd_scrape`'s sibling `cmd_score`
  shares it.
- **Breaks:** the "atomic" write is atomic with respect to *readers*, not with respect
  to *other writers*. Two processes writing the same master both open the identical
  path `all_businesses.csv.tmp` with mode `"w"` (truncating), both write through their
  own file offsets, and both `os.replace` it over the master. The published file is a
  byte-level interleaving of two different record sets, and the rename makes it look
  deliberate. The `try/except BaseException` at `main.py:131-133` cannot help: nothing
  raises. One writer also loses the tmp out from under it and dies with
  `FileNotFoundError` at `main.py:130` *after* the other has already published.
- **Reproduced** (300 rows A, 300 rows B, same directory, exact `write_csv` algorithm):

  ```
  exceptions raised: ["FileNotFoundError: ... 'all_businesses.csv.tmp' -> 'all_businesses.csv'"]
  rows parsed: 320  -> expected 300
  mixed A/B rows: 300 A, 20 B
  master is corrupted: True
  ```

  320 rows where 300 existed, A's rows and B's rows interleaved, published to the
  master path, with one of the two writers reporting failure and the other reporting
  success.
- **Trigger:** `leadminer score data/all_businesses.csv` from two shells in the same
  checkout; or a CI job and a laptop sharing a mounted workspace; or any retry loop
  that overlaps the previous invocation's tail.
- **Why S1:** this is the cumulative master — the one file whose destruction is
  unrecoverable (`main.py:110-116` says so in its own docstring) — and the failure is
  silent. `leadminer validate` will not necessarily catch it: the file parses, names
  are present, coordinates are in range. It only shows up as a slow row-count drift.
- **Fix:** `tmp = path.with_name(f"{path.name}.{os.getpid()}.tmp")` — or better,
  `tempfile.NamedTemporaryFile(dir=path.parent, delete=False)`, then `os.replace`.

### S2 — `cmd_scrape` reports success for a source where most queries were abandoned

- **Where:** `cli.py:62` (`print(f"[{args.source}] {len(records)} records")`),
  `cli.py:76` (`return 0`); failure exits at `scrapers/google_places.py:217-220`
  (wall-clock budget), `:236-240` (429 budget exhausted), `:250-252`
  (`RequestException` from `raise_for_status()` at `:249`)
- **Breaks:** `_scrape_query` returns partial results on three different failure modes
  and none of them is distinguishable from success at the CLI boundary. `f.result()`
  at `google_places.py:197` returns normally, `fetch_query` extends `all_records`
  with whatever survived, and `cmd_scrape` prints a plausible count and returns 0.
  There is no per-query success/abandoned counter anywhere — no exception object
  escapes `_scrape_query`, nothing is stored on the scraper instance, and `cmd_scrape`
  holds no reference to anything but the finished list.
- **Reproduced** (real `_scrape_query` code path, `requests` stubbed, no network):

  | Injected fault | `cmd_scrape` output | exit code |
  |---|---|---|
  | healthy (all 67 queries) | `[google_places] 1340 records` | `0` |
  | 1 query returns HTTP 503 | `[google_places] 1320 records` | `0` |
  | 2 queries exhaust the 429 budget | `[google_places] 1300 records` | `0` |

  The faults are visible only as interleaved stdout lines
  (`[Google] Request error for '...'` at `:251`,
  `[Google] '...' still rate limited after ...` at `:237`) buried under 67 lines of
  per-page progress, and there is no ratio to read.
- **Trigger:** Google Places returns 503 to several of the 5 concurrent workers at
  once. This is the *expected* mode of failure for this scraper, not an exotic one —
  5 workers share the fate of the whole run, and there is no retry on 5xx at all
  (`:249` `raise_for_status()` raises `HTTPError`, which is a `RequestException`, so
  the query is abandoned permanently rather than retried the way `osm.py:39-46` and
  `wikidata.py:70-78` are via `fetch_with_retry`). An operator running
  `leadminer scrape --source google_places` to answer "did the API change?" gets a
  green exit code and a number 25% lower than the real one.
- **Fix:** have `scrape()` return a result object carrying `(records, queries_ok,
  queries_abandoned)`; have `cmd_scrape` print the ratio and `return 1` when
  `queries_abandoned / queries_total` exceeds a threshold (e.g. 0.1).

### S2 — One worker exception discards all 66 healthy queries as an uncaught traceback

- **Where:** `scrapers/google_places.py:197` (`f.result()` — re-raises inside the
  `with ThreadPoolExecutor` block), propagating through `cli.py:61`
  (`records = list(...)`) to `cli.py:314-318` (which catches only `KeyboardInterrupt`)
- **Breaks:** `main.main()` wraps the equivalent call in
  `try/except Exception` (`main.py:163-168`); `cli.cmd_scrape` does not. Any exception
  from any one of the 67 workers aborts the generator *before* `yield from all_records`
  at `:199`, so `all_records` — the accumulated output of the 66 queries that worked —
  is unreachable and is garbage-collected. `list()` never returns even a partial list.
- **Reproduced** (structural replica of `:194-199` + `cli.py:61`, query 42 of 67
  raising `json.JSONDecodeError`):

  ```
  cli.py:61 RAISED JSONDecodeError: Expecting value: line 1 column 1 (char 0)
  => all_records (66 good queries' worth) is discarded; no partial list returned
  ```

  Real traceback path, with `requests` stubbed so `_scrape_query` runs unmodified:

  ```
  File "/Users/.../cli.py", line 61, in cmd_scrape
      records = list(registry[args.source]().scrape())
  File "/Users/.../scrapers/google_places.py", line 197, in scrape
      f.result()  # re-raises any exception
  ```

  Exit status is Python's default `1` with a stack trace, not the `1` from
  `cli.py:66` that carries the actionable "the source may be broken or blocked"
  message.
- **Trigger:** any 200 response whose body is not JSON. `resp.json()` at
  `scrapers/google_places.py:254` sits *outside* the `try` at `:226-252`, so a
  `json.JSONDecodeError` (a `ValueError`, not a `RequestException`) from a gateway
  interstitial, a truncated body, or a captive-portal HTML page escapes untouched.
  `place.get("location")` returning a non-dict at `:272` or a `KeyError` from
  `infer_region` at `:275` do the same.
- **Fix:** wrap `f.result()` at `:197` in `try/except Exception as e:` that records the
  failure against that query and continues, and mirror `main.py:163-168` at the
  `cli.py:61` call site so a scraper failure becomes a message plus a non-zero exit,
  not a stack trace.

### S2 — `seen_ids` first-writer-wins makes `country` scheduling-dependent, and `country` is the dedup key's country

- **Where:** `scrapers/google_places.py:263-266` (`with seen_lock: if place_id in
  seen_ids: continue; seen_ids.add(place_id)`), `:187`
  (`country = _country_from_query(query)`), `:275` (`infer_region(None, lat, lon,
  country=country)`), `:285` (`country=country`); downstream `main.py:194`
  (`normalize_phone(raw_phone, r.get("country"))`) and `dedup.py:205`
- **The lock is correct — the *choice* is not deterministic.** Two things here are
  frequently flagged and are both fine: `continue` inside a `with` releases the lock
  (`__exit__` runs before the jump; I ran 8 threads × 2000 iterations, completed in
  0.01s, no deadlock), and `seen_ids` is never read or written outside
  `with seen_lock`. This finding is not about corruption of the set.
- **Breaks:** which of two threads that both hold `place_id` X acquires the lock
  first is decided by network timing, not by the query list order. `country` is a
  property of *the query*, not of the place, so the winning query's
  `_country_from_query` result (`:187`) is baked into the record and is not
  re-derivable from the place itself. `main.py:194` then turns `country` into an
  E.164 number: `normalize_phone("70123456", "LB") == "+96170123456"` but
  `normalize_phone("70123456", "SA") == "+96670123456"`. The same business therefore
  lands under two different `phone_index` keys in `dedup.py:198-210` on different
  runs, and can appear twice in `all_businesses.csv`. `infer_region` at `:275` is
  likewise country-dependent (`:90` selects `_KSA_COORD_REGIONS` vs
  `_LB_COORD_REGIONS`), so `region` flips too.
- **Trigger:** a place returned by both an LB-mapped and an SA-mapped query. The
  request at `scrapers/google_places.py:222, 227` sends only `{"textQuery": ...}` — no
  `locationBias`, no `regionCode`, no `includedRegions` — so Text Search is
  world-scoped and does return out-of-market results. The concrete case is a Gulf
  spillover place (UAE, Bahrain, Qatar) surfacing in both `LEBANON_QUERIES` and
  `perfume brands in Saudi Arabia` / `DTC brands in Saudi Arabia` /
  `SaaS companies in Saudi Arabia` (`scrapers/google_places.py:87-90, 109`).
- **Honesty about likelihood:** for two queries that agree on country (the common
  case, since every LB query contains `lebanon`/`beirut` and every KSA query contains
  `saudi`/`riyadh`/`jeddah`/`dammam` — `:127-136`), the two candidate records are
  byte-identical apart from nothing, and the race is invisible. This bites on
  cross-market overlap, which is uncommon but not hypothetical. What is *certain* is
  that the outcome is not reproducible and nothing in the test suite pins it.
- **Also certain, and cheaper to state:** a place with an `id` but no `displayName`
  adds its id to `seen_ids` at `:266` and is then dropped by the `continue` at `:270`.
  It consumes a dedup slot and produces no record.
- **Fix:** derive `country` from `lat`/`lon` via a market bounding box (both markets
  are already enumerated in `enricher.py:58-76`) and fall back to
  `_country_from_query` only when coordinates are missing; and move
  `seen_ids.add()` to immediately before `records.append()` so a place skipped for
  lack of a name stays eligible.

### S2 — `cmd_scrape` counts are pre-whitelist and will never match the pipeline

- **Where:** `cli.py:61-75` (counts raw scraper output) versus `main.py:172-181`
  (`is_business_category` filter, then dedup)
- **Breaks:** `cmd_scrape` reports the number of records a scraper emitted; `cmd_run`
  reports the number that survived the whitelist and dedup. `_pick_category`
  (`scrapers/google_places.py:324-328`) returns Google's own type strings, and the
  whitelist's vocabulary is a hand-curated internal taxonomy
  (`scrapers/whitelist.py:17-82`) that does not contain them. An operator comparing
  `leadminer scrape --source google_places` (say 1,340) against `leadminer run`
  (`all_businesses.csv` rows) sees a large unexplained gap and will conclude the
  pipeline is broken, or — worse — will conclude a *falling* scrape count proves a
  source regression when the scrape count was never the number that mattered.
- **Measured** (32 industry archetypes the query list at `:46-125` actually targets;
  `types` arrays matching what Places returns):

  ```
  PASS: 26/32   DROPPED by main.py:172: 6/32
  dropped: ['coworking_space', 'event_venue', 'lodging_hotel',
            'photographer', 'seafood_restaurant']
  ```

  Two of those are Tier-1 priority industries. `lodging_hotel` — the type for *every*
  hotel in the KSA query set (`boutique hotels in Riyadh`, `luxury hotels in Saudi
  Arabia`) — fails `is_business_category` entirely, so the entire Saudi hotel
  pipeline segment is invisible in the exports while `cmd_scrape` reports thousands
  of `lodging_hotel` rows under "top categories".
- **Trigger:** any operator triage, i.e. the exact use case the docstring advertises
  at `cli.py:41-44`.
- **Fix:** print the post-whitelist count and the dropped count next to the raw count,
  and label the raw one `raw`. Reuse `is_business_category` from
  `scrapers.whitelist.py` rather than leaving the comparison to the reader. (Related
  and separately filed: the underlying `types`-order instability is audit
  `016-google-places-category-instability.md`.)

### S3 — Sessions are created and never closed anywhere in the codebase

- **Where:** `httpclient.py:61-71` (`get_session` caches on `_local`, never closes),
  `httpclient.py:88-91` (`http_session` is a `@contextmanager` whose body never
  closes anything — the name and the docstring at `:22-24` both imply it does),
  `scrapers/google_places.py:159-166` (`_make_session`, called once per query at
  `:189`, i.e. 67 `requests.Session` objects per run, none closed)
- **Confirmed:** `http_session()` has zero call sites outside its own docstring
  (`httpclient.py:23`); `requests.Session` defines no `__del__`, and neither does
  urllib3's connection pool, so sockets are reclaimed only by the OS at process exit.
  `get_session()` returns the identical object on repeat calls within a thread, so
  repeated `cmd_scrape` invocations in one process (a test loop, a watcher, a
  `leadminer scrape` followed by `leadminer score` in one interpreter) accumulate
  warm pools rather than leaking unboundedly — but nothing is ever released.
- **Bounded today** because the CLI is one-shot: one OSM session, one Wikidata
  session, 67 Google sessions, and — on the `cmd_run` path only — 40 enricher sessions
  (`enricher.py:175`, one per pool thread). That is ~110 sessions, comfortably inside
  the default `ulimit -n`. It becomes a real FD leak the moment anyone wraps the CLI in
  a scheduler, a daemon, or a test loop.
- **Fix:** `def http_session(): s = get_session(); try: yield s; finally: pass` is
  not enough — either close in `get_session`'s consumers or register
  `threading.Thread` teardown. Simplest correct move: make `http_session()` actually
  close and migrate `osm.py`/`wikidata.py`/`enricher.py` onto it; give
  `GooglePlacesScraper.fetch_query` a `with session:` block around the
  `self._scrape_query` call.

### S3 — Google's 5 workers send no `User-Agent` and no `SCRAPER_EMAIL`

- **Where:** `scrapers/google_places.py:159-166` bypasses `httpclient` entirely, so the
  UA set at `httpclient.py:66-68` and built by `_user_agent()` (`:74-85`, which
  embeds `SCRAPER_EMAIL` for Overpass/Wikidata policy compliance) never reaches
  `places.googleapis.com`. Google sees the default `python-requests/2.32.3`.
- This is also why `cmd_scrape --source google_places` never surfaces the 401 as a
  config error: the `X-Goog-Api-Key` is present, so only the raw 401 status matters,
  and `:231-232` prints "FATAL: invalid API key" once per query — 67 times — with
  `flush=True`, forcing 67 flushes.
- **Note:** the same bypass is why Google gets no `max_bytes` cap, no `Retry-After`
  honouring and no 5xx retry from `fetch_with_retry`. See the S2 above.
- **Fix:** have `_make_session` seed `"User-Agent": _user_agent()` from
  `httpclient`, and route the POST through `fetch_with_retry` with an explicit
  `retries=1` for the 4xx-terminal semantics Google needs.

### S3 — `cmd_scrape`'s source validation is unreachable dead code, and `registry` is a second hand-synced list

- **Where:** `cli.py:56-59` vs `cli.py:289-290`; `registry` at `cli.py:51-55`
- **Confirmed:** argparse `choices=["osm", "wikidata", "google_places"]` already
  rejects anything else with exit 2 before `args.func` is ever called, so
  `if args.source not in registry` can never be `True` and `cli.py:57-59` is dead.
  The two lists are currently identical but are maintained separately: a fourth
  scraper added to `main.py:155` and imported at `cli.py:47` would be reachable from
  the pipeline and silently unreachable from the CLI, with no test failing
  (`tests/test_lead_signal.py:191-264` covers `cmd_stats` and `cmd_validate` only —
  see `087-SYNTH-test-gap.md`).
- **Fix:** delete `cli.py:56-59` and derive the choices from the registry keys, e.g.
  `choices=sorted(registry)`.

### S3 — The "zero records" warning misdiagnoses the most common cause

- **Where:** `cli.py:63-66`; cause at `scrapers/google_places.py:169-171`
- **Confirmed** with `GOOGLE_PLACES_API_KEY` unset:

  ```
  stdout: '[Google] GOOGLE_PLACES_API_KEY not set, skipping.\n[google_places] 0 records\n'
  stderr: '  WARNING: zero records. The source may be broken or blocked.\n'
  ```

  Exit code 1 is right, but the actionable line goes to stdout while the summary line
  goes to stderr, and the summary is the wrong diagnosis. A missing key is a
  configuration problem with a one-line fix, not "broken or blocked". `cmd_doctor`
  already knows this (`cli.py:210-214`) — `cmd_scrape` should call the same check
  before spending any quota.
- **Fix:** check `os.environ.get("GOOGLE_PLACES_API_KEY")` up front and return `2`
  with `missing GOOGLE_PLACES_API_KEY (see: leadminer doctor)`.

### S3 — `list()` at `cli.py:61` defeats the streaming contract and doubles peak memory

- **Where:** `cli.py:61`; the buffer is `scrapers/google_places.py:183`
- The scraper already holds every record in `all_records` (`:183`, filled at `:191-192`)
  before yielding anything, so `list()` at `cli.py:61` allocates a second full copy
  of the list while the generator is still suspended inside `yield from`. Peak memory
  is `2 × N × sizeof(record)` plus `seen_ids`. At the documented ceiling of
  ~4,020 places (`092-google-places-quota-realism.md`) that is a few MB — not a
  problem today, but it is the same double-buffering `052-memory-streaming.md` flags
  on the `main.py` path, and `cmd_scrape` inherits it. See `052` for the streaming
  design.
- **Fix:** count and summarise inside the `for` loop over the generator instead of
  calling `list()`, which also removes the `len(records) == 0` special case.

## Not a bug, but worth knowing

- **The `with ThreadPoolExecutor` before `yield from` is load-bearing and correct.**
  `scrapers/google_places.py:194` opens the pool, `:196-197` drains and joins it,
  `:194`'s `__exit__` runs `shutdown(wait=True)`, and only then does `:199` yield.
  `list()` therefore always receives a complete, frozen list. Verified with a
  structural replica: `list()` returned the full 201 records on all 5 runs, and the
  thread count was back to baseline before the first record was produced. **If anyone
  ever moves the `yield` inside the `with`, `cmd_scrape`'s `collections.Counter` and
  the three `sum()` passes at `cli.py:68-70` will start racing the workers.** Add a
  test that asserts `len(list(...)) == N` under a deliberately slow worker.

- **`continue` inside `with seen_lock` is safe.** `scrapers/google_places.py:264-265`
  looks like a lock-leak hazard and is not — `with` compiles to try/finally, so the
  lock is released before the jump. Verified: 8 threads × 2000 iterations of a loop
  whose body `continue`s half the time completed in 0.01s with no hang.

- **The thread-local session change (`httpclient.py:58`) *fixed* the urllib3 race that
  `004-enricher-thread-safety.md` filed as S2.** That finding was about a
  `PoolManager` being evicted and `closed()` while another thread held it, which
  requires two threads to share one `PoolManager`. Now each of the 40 workers gets
  its own `Session` (`httpclient.py:58-71`, consumed at `enricher.py:175`), so each
  `PoolManager` is only ever touched by its owning thread and the eviction window
  cannot be entered by a second party. That S2 should be considered resolved by the
  refactor. The urllib3 version pin that report also asked for is still worth doing,
  but the race argument no longer applies.

- **Record ordering is nondeterministic but harmless.** `all_records` is extended in
  query-completion order (`scrapers/google_places.py:191-192`), so the row order of
  every output CSV churns between runs. Verified: 5 runs produced 5 distinct
  orderings of the same 201 records. Content is unaffected — `dedup._pick`
  (`dedup.py:179-187`) is a `max` over the total order
  `(trust, validity, recency, str(value))` and `dedup._merge` is commutative and
  associative over it (`tests/test_lead_signal.py:292-295`), and `source` is unioned
  sorted at `dedup.py:173-174`. Only physical row order moves.

- **`cmd_scrape` is reentrant.** No module-level mutable state in `cli.py` is touched
  by this function: `DATA_DIR` (`cli.py:26`) is only read by `cmd_doctor`/`cmd_score`
  defaults, and `registry` (`cli.py:51-55`) is a fresh local per call.
  `GooglePlacesScraper.scrape()` allocates `seen_ids`, `seen_lock`, `all_records` and
  `records_lock` fresh on every call (`:181-184`), so calling it twice on one instance
  is equivalent to two fresh runs. `httpclient._local` is keyed by *thread*
  (`httpclient.py:58`), so two threads calling `cmd_scrape` concurrently would still
  not share a Session. Verified both properties. The only cross-call residue is that
  `get_session()` returns the identical cached object on a second call in the same
  thread (confirmed), so cookies and pooled connections persist between in-process
  invocations — benign for Overpass and the Wikidata SPARQL endpoint, both stateless
  read APIs.

- **The abandoned-generator hazard is real but not currently reachable.** If `cli.py:61`
  were ever changed from `list()` to `next(iter(...))` or an `islice`, the
  `with ThreadPoolExecutor` at `scrapers/google_places.py:194` would not exit until
  the generator is garbage-collected — so the 5 workers would keep running while the
  caller walked a partially-populated list. Any caller of `scrape()` must either fully
  drain it or call `.close()` on it. (This is the same
  GeneratorExit/`ThreadPoolExecutor` interaction that
  `concurrent.futures.thread._worker.py` handles for its own pools; a generator
  holding a pool across a `yield` does not get that protection for free.)

- **`cmd_scrape` imports `enricher` but never starts its 40-thread pool.**
  `scrapers/google_places.py:26` does `from enricher import infer_region`, so the
  module that owns the 40-worker pool is loaded on this path — but
  `check_websites()` (`enricher.py:225`) is only called from `enrich()`
  (`enricher.py:337`), which `cmd_scrape` never reaches. Instrumenting
  `ThreadPoolExecutor.__init__` for a full `leadminer scrape --source google_places`
  records exactly one construction, `max_workers=5`.

- **`DATA_DIR` is a relative path (`cli.py:26`).** Every default resolves against the
  current working directory, so `leadminer stats` in a fresh checkout looks for
  `./data/all_businesses.csv` and reports `no such file` with exit 2 rather than
  explaining that output lands in `$CWD/data`. Combined with the S1 above, this is
  what makes an accidental concurrent write easy to set up: two shells in the same
  directory resolve to the same file.

## Recommended order of work

1. **Fix `main.py:122`** — pid-unique temp filename. One line, removes the only
   silent-corruption path in the CLI. Add a test that writes the same path from two
   threads and asserts the result is exactly one writer's 300 rows.
2. **Make `cmd_scrape` report per-query outcomes** (S2 #1) and wrap `f.result()` at
   `scrapers/google_places.py:197` so one bad page cannot discard 66 good queries
   (S2 #2). These two together turn `leadminer scrape` from a number generator into a
   usable health check. A single assertion — `records and queries_ok == queries_total`
   — covers both.
3. **Derive `country` from coordinates in `scrapers/google_places.py:187`** so the
   E.164 key in `dedup.py:205` no longer depends on which thread won `seen_lock`
   (S2 #3). Coordinate bounding boxes for both markets already exist at
   `enricher.py:58-76`.
4. **Report the post-whitelist count in `cmd_scrape`** (S2 #4) so its output can be
   compared with `cmd_run`. Blocked on nothing, but it will keep showing `lodging_hotel`
   until the `types`→canonical-category mapping from
   `016-google-places-category-instability.md` lands.
5. **Close sessions** (S3): make `http_session()` actually close and migrate
   `osm.py`/`wikidata.py`/`enricher.py` onto it; wrap `self._make_session()` in a
   `with` at `scrapers/google_places.py:189`. Also seed the UA from `httpclient` in
