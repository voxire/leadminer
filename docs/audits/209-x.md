# 209 — Boundary & hostile-input audit of `cmd_run` (`cli.py:33`)

## Verdict

`cmd_run` is four lines long and has **no input surface at all** — it ignores `args`
completely, so every hostile value you can pass it (`None`, `0`, `-1`, Arabic, emoji, a
5 MB string, an object that raises on any attribute access) is correctly discarded and the
function is un-crashable by construction. That is the good news, and it is the whole story.
The danger is one level down: `cmd_run` returns `None`, `cli.main` coerces that to `0`
(`cli.py:315`), and **`leadminer run` exits 0 unconditionally** — including when all three
sources returned nothing and when a malformed master silently blanks the `name` column of
every row. The most dangerous single input is a master CSV beginning with a **doubled UTF-8
BOM** (`\xEF\xBB\xBF\xEF\xBB\xBF`): one run destroys every business name irreversibly, keeps
the row count identical so every row-count gate passes, and exits 0.

---

## The contract

```python
# cli.py:33-37
def cmd_run(args: argparse.Namespace) -> int:
    """Full pipeline. Thin wrapper over main.main so there is one code path."""
    import main as pipeline

    return pipeline.main()
```

| | declared | actual |
|---|---|---|
| parameter | `args: argparse.Namespace` | **never read** — zero attribute accesses |
| return | `-> int` | `None`, because `main.main()` is annotated `-> None` (`main.py:148`) |
| options | `sub.add_parser("run", ...)` at `cli.py:285-286` registers **none** | nothing to configure |

Its only caller, `cli.py:312-318`:

```python
args = build_parser().parse_args(argv)
try:
    return int(args.func(args) or 0)
except KeyboardInterrupt:
    print("\ninterrupted", file=sys.stderr)
    return 130
```

Two contracts collide here. The subcommand family promises "return an `int` exit code";
`cmd_run` returns `None` and survives only because of the `or 0` at `cli.py:315`. Drop
that `or 0` as a tidy-up and `cmd_run` becomes a `TypeError: int() argument must be ... not
'NoneType'` on every single invocation. Verified both ways:

```
cmd_run returns None (main.main() is annotated '-> None' at main.py:148)
int(rc or 0)  = 0      <- what cli.py:315 does today
int(rc)       = TypeError: int() argument must be a string, a bytes-like object or a real
                 number, not 'NoneType'   <- what cli.py:315 does if 'or 0' is ever dropped
```

Because `args` is inert, `cmd_run`'s *real* inputs are: the import environment, the state
file `data/all_businesses.csv` (`main.py:150`), `DATA_DIR` (`main.py:41`, `cli.py:26`),
`GOOGLE_PLACES_API_KEY` / `SCRAPER_EMAIL`, three third-party APIs, and signals. That is
where the enumeration below lives.

### Methodology

`cli.py` and its deps were copied to a scratch dir (`/private/var/.../opencode/209`) — the
repo was never modified and no scraper was executed against a real network. `requests` and
`urllib3` were replaced with hard-offline stubs that raise `ConnectionError` on every call,
which is exactly the "every source is down" condition I needed. Interpreter: CPython
3.14.8 (project targets 3.12; the behaviour relied on here — `csv.field_size_limit`,
`utf-8-sig`, `float("nan")`, `ThreadPoolExecutor.shutdown` — is identical across both).

## Findings

### S1-A — `leadminer run` exits 0 no matter how completely the pipeline fails

- **Where:** `cli.py:37` (`return pipeline.main()`) → `main.py:148` (`def main() -> None`)
  → `cli.py:315` (`int(args.func(args) or 0)`)
- **Breaks:** the pipeline has no failure accumulator. `main.py:167` catches every scraper
  `Exception` and only `print`s it; `scrapers/osm.py:53` and `scrapers/wikidata.py:82`
  print *"Continuing without … data"*; `scrapers/google_places.py:170` prints *"GOOGLE_PLACES_API_KEY
  not set, skipping."* and returns zero records. `main()` then runs to completion, writes
  all five CSVs, prints a healthy-looking summary, and returns `None`. `int(None or 0)` → `0`.
  So a run in which **every source failed** is byte-for-byte indistinguishable, to any
  caller, from a successful one.
- **Trigger (reproduced):** seeded `data/all_businesses.csv` with 3 rows, all three sources
  hard-down.
  ```
  Loaded 3 records from existing master CSV
  [OSMScraper] FAILED after 3 attempts: ConnectionError: … Continuing without OSM data.
  [OSMScraper] collected 0 records
  [WikidataScraper] FAILED after 3 attempts: … Continuing without Wikidata data.
  [WikidataScraper] collected 0 records
  Total raw records from scrapers: 0
  …
    Written: data/all_businesses.csv (3 records)
  >>> EXIT CODE: 0
  ```
  Worse, on a fresh clone with no master and all sources down:
  ```
  >>> FRESH CLONE, ALL SOURCES DEAD: EXIT CODE = 0
  >>> produced: 5 header-only CSVs, 1 line(s) each
  ```
  Five valid-looking, correctly-BOM'd, 225-byte header-only files, exit 0. `scrape.yml:74`'s
  `test -s` passes on 225 bytes; only `ROWS < 100` at `scrape.yml:80` catches that one case.
  With a real 5,000-row master and every source dead, **every** CI gate passes and the run
  publishes a master containing zero new leads.
- **Why S1:** this is the command `README.md:11` and `README.md:96` tell operators to use,
  and the whole premise at `cli.py:4` is *"something that can be scripted, scheduled and
  debugged."* Schedule it in cron, systemd, or a Kubernetes `CronJob` and it is green
  forever while producing nothing. Wrong results, no signal.
- **Aggravating:** `scrape.yml:69` runs `python main.py`, **not** `leadminer run`. The CLI
  path — the one operators are told to use — is never exercised in CI, so this cannot be
  caught by the existing workflow. `python main.py` has the identical defect via
  `main.py:245-246` (`raise SystemExit(None)`).
- **Fix:** make `main.main()` return `int`; track per-source outcomes; `return 3` if any
  source failed and `return 4` if `len(raw) == 0`, before any `write_csv`.

### S1-B — A master with a doubled UTF-8 BOM silently deletes every business name, exit 0

- **Where:** `cli.py:37` → `main.py:150` `load_master` → `main.py:85` (`encoding="utf-8-sig"`)
  → `main.py:125` (`extrasaction="ignore"`)
- **Breaks:** `utf-8-sig` strips exactly **one** BOM. A file whose first bytes are
  `EF BB BF EF BB BF` therefore leaves the first column key as `"\ufeff\ufeffname"`, so
  `row["name"]` is never populated. Then `write_csv` writes `fieldnames=FIELDS` with
  `extrasaction="ignore"`, which **drops the mangled key entirely** and emits `name` from
  `r.get("name")` → `None` → an empty cell. One run rewrites a fully populated master into
  a same-row-count master with the single most important field blank. Business names are
  the join key for dedup, the pitch, and the CRM handoff — they cannot be reconstructed
  from a phone number.
- **Trigger (reproduced, twice):**
  ```
  $ xxd data/all_businesses.csv | head -1
  00000000: efbb bfef bbbf 6e61 6d65 2c63 6174 6567  ......name,categ
  $ leadminer run; echo "exit=$?"
  after run 1: exit=0 rows=2 names=['', '']
  after run 2: exit=0 rows=2 names=['', '']
  ```
  Names `Acme Dental` and `Beta Bakery` are gone after a single run, and the damage is
  **idempotent and self-concealing**: the rewritten header is clean (`﻿name,ca…`), so
  nothing on the next run looks wrong.
- **Why S1:** silent data loss of the highest-value field, irrecoverable, invisible to
  every existing gate. `scrape.yml:78` computes `ROWS` from line count — unchanged, so the
  only automated guard passes. `scrape.yml:88-89` then uploads the blanked copy over the
  good one on Drive.
- **Aggravating:** the guard that exists for this is **dead code**. `cli.py:154`:
  ```python
  bom_name = sum(1 for r in rows if (r.get("name") or "").startswith("\ufeff"))
  ```
  When the key is mangled, `r.get("name")` is `None` → `""` → `False`, so `bom_name` is
  always `0` and the check at `cli.py:156` can never fire. `cmd_validate` does eventually
  fail — but with the misleading message *"every row has a blank name"*, i.e. it tells you
  the symptom, not the cause, and only if you remember to run it before `run`.
- **Fix:** in `load_master`, after `DictReader` construction, strip all leading `\ufeff`
  from `reader.fieldnames` in a loop; and assert `set(reader.fieldnames) == set(FIELDS)`,
  refusing the file if the header does not match.

### S2-A — `run` dies with a raw traceback when a dependency is missing; `doctor` guards this exact case

- **Where:** `cli.py:35` → `main.py:25` (`from scrapers.osm import OSMScraper`) →
  `scrapers/osm.py:4` → `httpclient.py:43` (`import requests`)
- **Breaks:** `cmd_run` imports the whole pipeline at call time, so any missing import
  becomes an unhandled traceback. `cli.main` (`cli.py:314-318`) only catches
  `KeyboardInterrupt`.
- **Trigger (reproduced on the default interpreter, which has no `requests` installed):**
  ```
  $ leadminer run; echo "EXIT CODE: $?"
  Traceback (most recent call last):
    File "cli.py", line 315, in main
      return int(args.func(args) or 0)
    File "cli.py", line 35, in cmd_run
      import main as pipeline
    File "main.py", line 25, in <module>
      from scrapers.osm import OSMScraper
    File "scrapers/osm.py", line 4, in <module>
      from httpclient import fetch_with_retry, get_session, utc_now_iso
    File "httpclient.py", line 43, in <module>
      import requests
  ModuleNotFoundError: No module named 'requests'
  EXIT CODE: 1
  ```
- **The author already knew.** `cli.py:227-231` handles precisely this for `doctor`:
  > `# doctor exists to diagnose a broken environment, so it must never be the thing that tracebacks.`
  `cmd_run` gets no such guard, and `cmd_run` is the command people actually invoke.
- **Second, worse instance:** `enricher.py:327-328` does a *function-local* `import urllib3`
  inside `enrich()`. A missing `urllib3` therefore kills the run **mid-enrichment**, after
  the scraping phase has already spent Google Places quota and hours of wall clock:
  ```
    File "main.py", line 187, in main
      records = enrich(records)
    File "enricher.py", line 328, in enrich
      urllib3.disable_warnings(urllib3.exceptions.InsecureRequestWarning)
  AttributeError: …            # or ModuleNotFoundError for urllib3 itself
  ```
- **Fix:** wrap `import main as pipeline` in `try/except ImportError as e`, print
  `f"missing dependency: {e.name} — pip install -e ."`, `return 3`; hoist the `urllib3`
  import in `enricher.py` to module scope where it fails fast.

### S2-B — `DATA_DIR` is CWD-relative, so `run` from the wrong directory silently starts from zero

- **Where:** `main.py:41` and `cli.py:26` — both `DATA_DIR = pathlib.Path("data")`,
  a **relative** path. Consumed at `main.py:150` (read) and `main.py:208-213` (write).
- **Breaks:** `leadminer run` resolves `data/` against the current working directory, not
  the package. Run it anywhere but the repo root and it finds no master, treats the run as
  a first run, and creates a *second, divergent* `data/` tree. No warning that a real
  master exists elsewhere.
- **Trigger (reproduced):**
  ```
  repo/data/all_businesses.csv has 2 rows
  $ cd elsewhere && leadminer run
  Total raw records from scrapers: 0
  After merge + dedup: 0 unique businesses
    Written: data/all_businesses.csv (0 records)
  >>> EXIT: 0
  $ wc -l repo/data/all_businesses.csv   →  3   (untouched)
  $ ls elsewhere/data/                   →  5 header-only CSVs
  ```
  The operator's next `cd repo && leadminer run` sees the original 2 rows and concludes
  nothing happened; meanwhile `elsewhere/data/` holds a decoy empty master that any later
  automation pointed at the wrong CWD will treat as real.
- **Aggravating:** `cmd_doctor` (`cli.py:216-222`) checks the same relative path, so it
  reports `MISSING data` for the one directory where the data isn't — actively pointing the
  operator at the wrong place.
- **Fix:** `DATA_DIR = pathlib.Path(os.environ.get("LEADMINER_DATA_DIR", Path(__file__).parent / "data"))`
  in both modules (or define it once in `cli.py` and import it), and hard-fail when
  `all_businesses.csv` is absent unless an explicit `--allow-first-run` is passed.

### S2-C — SIGINT is swallowed: the run finishes, rewrites the master, and exits 0

- **Where:** `cli.py:316-318` (unreachable in practice); `main.py:160-168`.
- **Breaks:** the `except KeyboardInterrupt` handler exists and returns the correct `130`,
  but it never fires. `ThreadPoolExecutor.__exit__` at `main.py:160` blocks in
  `shutdown(wait=True)` until every in-flight retry finishes; `osm.py:53` and
  `wikidata.py:82` each retry 3× with exponential backoff (`httpclient.py:44-47`), so the
  wait is tens of seconds.
- **Trigger (reproduced twice, deterministic):**
  ```
  run 1: exit=0  honoured_after=40s  'interrupted' printed: 0  master rows: 400
  run 2: exit=0  honoured_after=39s  'interrupted' printed: 0  master rows: 400
  ```
  The operator presses Ctrl-C, watches the terminal hang for 40 s, then sees a full
  success summary and exit 0. The reasonable conclusion — "I cancelled it" — is false. If
  the interrupt lands during enrichment rather than scraping, the master gets rewritten
  with a half-enriched population.
- **Fix:** install a `signal.signal(SIGINT, handler)` that sets a `threading.Event`, and
  poll it between pipeline stages (`main.py` already has clean stage boundaries at lines
  170, 181, 187, 209); return 130 from the handler path. Do not rely on an exception
  delivered inside `shutdown`.

### S2-D — A malformed master crashes `run` with an unhandled traceback

- **Where:** `main.py:85-86` inside `load_master`, reached via `main.py:150`; nothing in
  `cli.py:33-37` or `cli.py:314-318` catches it.
- **Breaks / triggers** (all reproduced through the real `load_master`):

  | master content | outcome |
  |---|---|
  | any single cell > 128 KiB | `_csv.Error: field larger than field limit (131072)` |
  | a latin-1 byte (`0xE9`) | `UnicodeDecodeError: 'utf-8' codec can't decode byte 0xe9 in position 445` |
  | binary junk / a NUL byte | `UnicodeDecodeError: … invalid start byte` |
  | a UTF-16-encoded file saved as `.csv` | `UnicodeDecodeError: … byte 0xff in position 0` |

  All four are uncaught → traceback, exit 1. The master itself survives (`write_csv` is
  atomic at `main.py:122-133` and runs *after* the load), so this is operability, not data
  loss — but it is reachable: `scrape.yml:56` `rclone copy`s *whatever* is on Drive into
  `data/`, so a mis-saved or truncated Drive object lands directly in this path.
- **Correctly handled, for the record:** empty file, header-only file, 100 000 blank lines,
  a quoted multi-line name (`"Multi\nLine\nName"` round-trips intact), ragged rows with
  extra columns (absorbed under the `None` restkey and dropped by `extrasaction="ignore"`),
  short rows, semicolon-delimited files, and an HTML error page (returns `[]`, i.e.
  degrades to "first run" rather than crashing — see the `main.py:79-80` guard).
- **Fix:** wrap the `load_master` call; on `UnicodeDecodeError`/`csv.Error` print
  `f"master unreadable: {path}: {e}"` and `return 2` without touching `data/`.

### S3-A — `nan` / `inf` survive the master round-trip as a permanent poison pill

- **Where:** `main.py:90-95` — `float(row[field])` accepts `nan`, `inf`, `-inf`; there is
  no `math.isfinite` guard.
- **Breaks:** `load_master` returns `lat=nan`, `rating=inf`, etc. `write_csv` writes the
  literal strings `nan` / `inf`, and the next `load_master` parses them back to `nan`.
  Reproduced: `[33.89, nan]` → written as `['33.89','35.5'], ['nan','nan']` → re-read as
  `[33.89, nan]`. **Permanent**, in a cumulative master that is never rebuilt from scratch.
- **Detection gap:** `cmd_validate`'s `in_box` (`cli.py:159-162`) does reject it
  (`33.0 <= nan <= 34.8` is `False`), but only if the count exceeds 1% of rows
  (`cli.py:172`). Verified: one NaN row in 500 →
  ```
  checked 500 rows in …/sparse.csv
    all checks passed
  cmd_validate exit = 0
  ```
  Scoring is *not* affected (verified: `completeness_score`/`lead_score` identical with
  `nan`/`inf` injected into `rating`, `lat`, `lon`), so the poison surfaces only in
  geospatial filtering — i.e. it silently drops leads rather than raising anything.
- **Fix:** in the `main.py:90-95` float loop, `if not math.isfinite(v): row[field] = None`.

### S3-B — `cmd_run`'s `args` annotation is a fiction

- **Where:** `cli.py:33`.
- **Breaks:** nothing at runtime (see the matrix above), but the signature promises
  `argparse.Namespace` and delivers "anything, including nothing". The natural unit test
  is `cmd_run(None)`, which is almost certainly why `087-SYNTH-test-gap.md:19` can list
  `cmd_run` among the untested commands — the signature suggests there is nothing to test.
- **Fix:** annotate `args: argparse.Namespace | None = None` and default it to `None`, or
  drop the parameter and register `cmd_run()` in `set_defaults`.

### S3-C — `run` has no preflight and never calls `doctor`

- **Where:** `cli.py:33-37`; the credential check lives at `scrapers/google_places.py:170`,
  which executes *after* OSM and Wikidata have already run.
- **Breaks:** a missing `GOOGLE_PLACES_API_KEY` costs a full scrape of two other sources,
  and the run still exits 0 having quietly produced a third-less master. `README.md:95`
  says *"leadminer doctor — check keys and connectivity first"* but nothing enforces it,
  and `doctor` is a separate manual step (`cli.py:301-302`).
- **Fix:** have `cmd_run` call the `doctor` credential checks (not the network pings) and
  `return 3` if `GOOGLE_PLACES_API_KEY` is unset, or add `--skip-google`.

## Not a bug, but worth knowing

- **No `name` collision damage from ragged rows.** Rows with more columns than the header
  land under the `None` restkey and are silently dropped by `extrasaction="ignore"` at
  `main.py:125`. Slightly lossy, but the safe direction.
- **`enricher.py:327`'s function-local `import urllib3` is an anti-pattern** independent of
  the missing-dependency traceback in S2-A: it makes an import-time concern a runtime one,
  inside the hottest loop of the pipeline. Hoist it.
- **`cli.py:230` gives the wrong install advice.** `pip install -e '.[dev]'` for a missing
  `requests`, but `requests` is a *runtime* dependency at `pyproject.toml:16-18`;
  `pip install -e .` is what actually fixes it. `[dev]` is for pytest/ruff/mypy.
- **`pyproject.toml:35-37` will bite `cmd_run` once the CLI is actually installed.**
  `[tool.hatch.build.targets.wheel] include = ["scrapers/"]` force-includes only the
  scrapers package, so `cli.py` and `main.py` — and therefore both the
  `leadminer = "cli:main"` entry point at `pyproject.toml:33` and the `import main as
  pipeline` at `cli.py:35` — are not shipped. `pip install leadminer` then yields
  `ModuleNotFoundError`. `cmd_run`'s `import main` only works from a source checkout today.
- **Overlaps `211-cmd-run-concurrency-safety.md`.** S2-C below (SIGINT swallowed by
  `ThreadPoolExecutor.shutdown` at `main.py:160`) is a concurrency finding reached from the
  input-handling direction; merge it with that report rather than filing it twice.
- **`scrape.yml:69` bypasses the CLI entirely**, so `cmd_run` has no CI coverage at all.
  Every finding in this report would have been caught by one `leadminer run` step plus a
  `leadminer validate` step.

## The single most dangerous input

**A master CSV whose first three bytes are a second UTF-8 BOM — i.e. the file begins
`EF BB BF EF BB BF` (`\ufeff\ufeffname,…`) rather than a single `EF BB BF`.**

Not the all-sources-dead case, which is more likely but far less harmful. This one:

1. **It is the only input that destroys data that already existed.** Every other finding
   yields an empty, unchanged, or truncated file that a human or a row-count gate notices.
   This one takes a populated master and returns the same number of rows with the `name`
   column blanked (`acme run 1: exit=0 rows=2 names=['', '']`).
2. **It is self-concealing and idempotent.** `write_csv` normalises the header back to a
   clean single BOM, so the second run looks identical to the first and nothing anywhere
   reports an error. `scrape.yml:78`'s `ROWS >= 100` passes on a 5,000-row
   all-blank-name master.
3. **It is a one-way door.** Business name is the dedup join key, the pitch subject, and
   the identifier a salesperson puts in an email. It is not recoverable from a phone
   number or an address, and `scrape.yml:88-89` uploads the blanked copy over the good
   one on Drive in the same job.
4. **The only available guard is dead code.** `cli.py:154` looks for a BOM in the *value*
   of `name`, but the corruption is in the *key*, so `r.get("name")` is `None` and
   `bom_name` is always `0`. `cmd_validate` fails with *"every row has a blank name"* —
   the symptom — and only if run before `run`.
5. **Exit code 0** throughout, so no scheduler, cron, or CI gate registers an event.

Concrete trigger to reproduce: prepend one extra `\xef\xbb\xbf` to
`data/all_businesses.csv` and run `leadminer run` once.

## Recommended order of work

1. **`cmd_run` must be able to fail.** Give `main.main()` an `int` return, accumulate
   per-source outcomes, and return non-zero when a source failed or `len(raw) == 0`
   (S1-A). Change `cli.py:315` to `return int(args.func(args))` once the contract holds,
   and add `cmd_run` to `scrape.yml:69` in place of `python main.py`.
2. **Make the header a contract.** In `load_master`, strip repeated leading `\ufeff` from
   `reader.fieldnames` and assert the header set equals `set(FIELDS)`; refuse the file
   otherwise (S1-B). Then fix the dead check at `cli.py:154` to inspect `reader.fieldnames`,
   not cell values.
3. **Guard the two import paths** — `cli.py:35` and `enricher.py:327` — with a friendly
   `return 3` (S2-A).
4. **Anchor `DATA_DIR`** to an env var or `__file__`, and fail closed when the master is
   absent without `--allow-first-run` (S2-B).
5. **Replace the `KeyboardInterrupt` handler with a signal-handler + stage-check flag**
   (S2-C), and wrap `load_master` so malformed masters return `2` instead of a traceback
   (S2-D).
6. **Add `math.isfinite` to the float loop** in `load_master` (S3-A), then tighten
   `cli.py:172` so any NaN coordinate fails the gate regardless of proportion.
