# 214 — `cmd_run` dependency map: a 4-line wrapper around 2,277 lines

## Verdict

`cmd_run` (`cli.py:33-37`) is two statements — `import main as pipeline; return pipeline.main()` — and that is the whole of it. Everything interesting is in what it drags in: **every first-party module in the project except `scripts/audit_status.py`**, plus a scraper layer that imports the enrichment layer, a "shared HTTP client" that the largest source silently bypasses, and a data root that is a bare relative path duplicated across two modules. `cmd_run` is declared to return `int` and returns `None`; the exit code you observe is manufactured one frame up at `cli.py:315`. And it cannot execute at all in an installed environment — `pyproject.toml:33` ships a `leadminer` console script whose target module is named by no build rule, and the import is function-local, so `leadminer --help`, `stats`, `validate` and `doctor` all succeed while the one command that runs the pipeline dies with `ModuleNotFoundError`.

The reason none of this has surfaced: `.github/workflows/scrape.yml:69` runs `python main.py`, never `leadminer`, and `scrape.yml:39` installs `requirements.txt`, never the package. The CLI is currently unexercised by CI.

## Findings

### S1 — `cmd_run` cannot execute in any installed environment; the lazy import hides it behind three commands that do nothing useful

- **Where:** `cli.py:35`; `cli.py:46-49`; `cli.py:249-252`; `pyproject.toml:32-33`; `pyproject.toml:35-37`
- **Breaks:** `pyproject.toml:33` declares `leadminer = "cli:main"`. Hatch's documented default file selection is `<NAME>/__init__.py` → `src/<NAME>/__init__.py` → `<NAME>.py` → `<NAMESPACE>/<NAME>/__init__.py` (hatch wheel-builder docs, *Default file selection*), and **none of those exist** for `NAME = leadminer`: there is no `leadminer/` directory, no `src/`, no `leadminer.py`. The only file-selection rule present is `include = ["scrapers/"]` (`pyproject.toml:37`), and setting any selection option *suppresses* the "unable to determine what to ship" error. So `pip install .` **succeeds** and produces a wheel containing `scrapers/*.py` and nothing else. `bin/leadminer` is still generated, and it dies on first use with `ModuleNotFoundError: No module named 'cli'`. Delete the `include` line to "fix" that and the build itself starts failing instead.
- **Trigger (installed):** `pip install . && leadminer run` → `ModuleNotFoundError: No module named 'cli'`.
- **Trigger (src layout — the fix 030 recommends and the only one where the project name `leadminer` is coherent):** copy `cli.py`, `main.py`, `dedup.py`, `enricher.py`, `httpclient.py`, `pitch_recommender.py` and `scrapers/` under `src/leadminer/`, add `__init__.py`, and run. Verified:

  ```
  cmd_run(Namespace()) -> ModuleNotFoundError: No module named 'main'
  ```

  Full subcommand sweep under that layout:

  | command | result |
  |---|---|
  | `stats` | rc=2 (file not found; the command itself works) |
  | `validate` | rc=2 (idem) |
  | `doctor` | rc=1 (works; needs `requests`) |
  | `scrape` | **`ModuleNotFoundError: No module named 'scrapers'`** |
  | `score` | **`ModuleNotFoundError: No module named 'main'`** |
  | `run` | **`ModuleNotFoundError: No module named 'main'`** |

  Three of six commands die, and they are precisely the three that do anything. The reason this is S1 and not S2: the imports at `cli.py:35`, `cli.py:46-49` and `cli.py:249-252` are **function-local**, so the module still imports cleanly, `leadminer --help` still works, and the three no-network commands still return sane exit codes. The failure is deferred to the moment the operator has already decided the environment is healthy and started a paid run. `cli.py:35` is the only eager dependency `cmd_run` has, and it is the one that is wrong.
- **Fix:** make `cmd_run` import its delegate at module scope from a real package (`from .pipeline import main`) so the error is a load-time error; and give `pyproject.toml` a `packages = ["leadminer"]` (or point `src` at the existing root) so the wheel and the console-script target name the same package.

### S2 — The scraper layer imports the enrichment layer; the cycle is dormant only because `scrapers/__init__.py` is empty

- **Where:** `scrapers/google_places.py:26` (`from enricher import infer_region`); consumed at `scrapers/google_places.py:275`; `scrapers/__init__.py` is 0 bytes; the reverse edge `enricher` → `httpclient` at `enricher.py:128`
- **Breaks:** `infer_region` is a pure function over `(address, lat, lon, country)` with no I/O. It belongs in a shared module that both the scraper and the enricher import — `leadminer/geo.py` or `scrapers/geo.py`. Instead it lives in the enrichment stage, so the *collection* layer depends on the *enrichment* layer. `main.py:25-31` imports `scrapers.*` before `enricher`, so the graph reads bottom-up as though scrapers are the foundation; they are not.
- **Trigger:** two edits that packaging work is about to make, each of which detonates it.
  1. Give `scrapers/__init__.py` an `__all__` and eager re-exports (the standard way to make `scrapers` a shippable package; `pyproject.toml:37` already ships it as one). Reproduced on an isolated copy:
     ```
     ImportError: cannot import name 'infer_region' from 'enricher'
     (consider renaming '.../enricher.py' if it has the same name as a library
     you intended to import)
     ```
  2. Type `enricher`'s record functions with the shared record type it should have been using all along — `enricher.py:1-3`, `from scrapers.base import BusinessRecord`. Reproduced the same way; the cycle fires because `enricher` is entered before `scrapers`, and `enricher` → `scrapers.base` → `scrapers/__init__` → `google_places` → back into a half-initialised `enricher`.
- **Honest mitigation:** the existing suite does catch this, but only incidentally — `tests/test_lead_signal.py:66` imports `enricher` before `main`, which happens to be the failing direction. Nothing asserts the import order, so a future reordering of those four lines would silently stop catching it.
- **Fix:** move `infer_region`, `_REGION_MAP`, `_LB_COORD_REGIONS`, `_KSA_COORD_REGIONS` (`enricher.py:10-94`) into a leaf module both layers import; nothing in it needs `requests`, `re`-over-HTML, or any of `enricher`'s other state.

### S2 — `httpclient` is not the HTTP client for the largest source

- **Where:** `httpclient.py:1` ("Shared HTTP client for every outbound request"); `httpclient.py:11-15` (the retry thesis); `httpclient.py:74-77` (the User-Agent/compliance thesis); versus `scrapers/google_places.py:24`, `:159-166`, `:189`, `:227`, `:249-252`
- **Breaks:** `GooglePlacesScraper` builds its own `requests.Session` (`scrapers/google_places.py:159-166`), never touches `get_session()` or `fetch_with_retry()`, and issues its calls with `session.post(API_URL, json=body, timeout=30)` (`:227`). So every guarantee `cmd_run` appears to inherit is absent for 68 queries (`LEBANON_QUERIES` 33 + `KSA_QUERIES` 35) × N pages — the largest and only metered source in the run:
  - **No retry.** `resp.raise_for_status()` (`:249`) raises; the `except requests.RequestException` (`:250`) does `return records` (`:252`), abandoning the query and every remaining page. One transient 500 or one socket reset permanently drops that query for the run. OSM and Wikidata get 3 attempts with jittered backoff (`osm.py:39-46`, `wikidata.py:70-78`) from the very helper this module was written to centralise.
  - **No User-Agent.** `_make_session` (`:161-165`) sets `X-Goog-Api-Key`, `X-Goog-FieldMask`, `Content-Type` and nothing else, so Google receives `python-requests/<version>` attached to a **billed** API key. `httpclient.py:74-77` argues at length for being identifiable to API operators; that argument does not reach the one operator this project bills.
  - **No body cap.** `resp.json()` (`:254`) on an uncapped, non-streamed response.
- **Trigger:** a single `HTTP 503` from `places.googleapis.com` on `"restaurants in Lebanon"` → that query contributes zero records for the whole run, with no retry, no `[Google] FAILED after N attempts` line (the OSM/Wikidata failure signature at `osm.py:51-55`), and nothing in the summary at `main.py:219-226` that distinguishes it from "there are no restaurants in Lebanon".
- **Fix:** route `google_places` through `fetch_with_retry` like its siblings, and let `get_session()` own the User-Agent; keep a per-thread Places session but populate its headers from `_user_agent()`.

### S2 — The pipeline's data root is two independent CWD-relative constants, so running from the wrong directory is a silent first run

- **Where:** `main.py:41`; `cli.py:26`; `main.py:79-80`; `main.py:179`; `main.py:209`; `cli.py:217-222`
- **Breaks:** `main.DATA_DIR` and `cli.DATA_DIR` are two separate `pathlib.Path("data")` objects (`main.DATA_DIR is cli.DATA_DIR` → `False`, verified) that happen to agree only because both are resolved against `os.getcwd()` at use time. There is no shared config. Combined with `main.py:79-80` (`load_master` returns `[]` for a missing path), any `leadminer run` from a directory other than the project root is a **first run**: `combined = raw_filtered + master` (`main.py:179`) with `master == []`, then `write_csv(DATA_DIR / "all_businesses.csv", ...)` (`main.py:209`) writes a brand-new master containing only this run's rows. That is exactly the catastrophic outcome `scrape.yml:60-61` refuses to allow at the workflow level — and the pipeline itself has no equivalent guard.
- **Trigger:** `cd /tmp && leadminer run`. Verified: `load_master` → `[]`; after the write, `/tmp/data/all_businesses.csv` holds one row and the repo's `data/` is untouched. Then `leadminer doctor` run from `/tmp` reports `OK   data exists` (verified) while reporting on the wrong directory entirely; run from the repo root it reports `MISSING  data`.
- **Fix:** one module owns the resolved root (`LEADMINER_DATA_DIR`, defaulting to the package's own directory, overridable by env var); `cli.DATA_DIR` becomes an import of it, and `main.load_master` distinguishes "absent" from "empty" so a missing master on an established install is an error rather than a silent reset.

### S3 — `cmd_run` declares `-> int` and returns `None`

- **Where:** `cli.py:33` vs `main.py:148`; rescued by `cli.py:315`
- **Breaks:** `main.main()` is annotated `-> None` (`main.py:148`), so `return pipeline.main()` returns `None` from a function declared `-> int`. Verified: `cmd_run(Namespace())` → `None`. The process exit code is 0 only because `cli.py:315` writes `int(args.func(args) or 0)`, and `None or 0` → `0`. That coercion also maps every falsy value to 0, so the moment `main.main()` grows a real failure signal (`False`, `None` on partial failure) the CLI cannot distinguish it from success. `pyproject.toml:64-68` declares mypy `strict = true`; this line is an instant error, and the tree is nowhere near strict-clean (`main.py:50` `record: dict`, `enricher.py:168` `contacts: dict`, `dedup.py:79` `_is_missing(value)` are all bare/untyped generics), so the config is aspirational and nothing runs it.
- **Trigger:** `mypy cli.py` on a clean checkout → `[return-value] Incompatible return value type (got "None", expected "int")`, plus a large pre-existing backlog.
- **Fix:** make `main.main() -> int` return 0 on success and non-zero on a partial or total source failure; drop the `or 0` coercion at `cli.py:315`.

### S3 — `cmd_run` binds the process-global module name `main`, inside a module that itself defines a function named `main`

- **Where:** `cli.py:35`; `cli.py:312`
- **Breaks:** `import main` resolves against `sys.path`, and `sys.modules["main"]` is a process-global key. Verified: pre-seeding `sys.modules["main"]` with any module that has a `main()` makes `cmd_run` call **that** module's `main()` — return code `None`, no error, no warning. The name is also gratuitously collision-prone next to `cli.main` at `cli.py:312`, which is the console-script target: `pyproject.toml:33` (`cli:main`) and `cli.py:35` (`main as pipeline`) refer to two different things called "main", and only one of them is a module.
- **Trigger:** any host that already owns the name `main` — an IPython/Jupyter kernel, a plugin host, a test runner that imports a fixture named `main`, or a future `src/` layout where `leadminer.main` and top-level `main` coexist.
- **Fix:** rename `main.py` → `pipeline.py` (or `runner.py`) and import it as `from . import pipeline`; the module then no longer collides with `cli.main`, and the S1 fix falls out for free.

### S3 — `cmd_run` ignores its `args` entirely

## Not a bug, but worth knowing

- **A dependency-ordering fact inside `cmd_run`'s call chain:** `dedup` runs at `main.py:180` and reads `record.get("country")` to build its phone key (`dedup.py:205`), but country is only resolved afterwards at `main.py:183-184`, and the phone actually *stored* is normalised at `main.py:194` using the resolved country. So the number used as the dedup key and the number written to the CSV are produced by two normalisations at two different times from two possibly different country values. `dedup.py:58-60` scanning `_KNOWN_COUNTRY_CODES` for an explicit international prefix papers over the common cases, which is why this has not caused visible damage. Audits 012/095 cover the ordering; flagging it here because it is a property of `cmd_run`'s dependency graph.
- **`osm.py:35` + `httpclient.py:165`**: `fetch_with_retry` accepts `session=` but every caller already holds a session from `get_session()`, and the function defaults it anyway. The parameter is one more thing to get wrong and buys nothing today.
- **`httpclient.py:34`**: `import email.utils` binds the name `email`, which shadows nothing but reads as if `email` is a local module. Fine, just surprising next to `email.utils.parsedate_to_datetime` at `:130`.
- **`enricher.py:225` `check_websites(records, workers=40)`** has a hard-coded default that `main.main()` never overrides and the CLI cannot, despite `cmd_run`'s docstring promising "one code path". `_WORKERS` in `google_places.py:142` is likewise a module constant with no override. Both are the kind of thing a `config.py` (see audit 036) would fix in one place.
- **The brief's "22 columns" is 23.** `main.FIELDS` (`main.py:33-40`) and `BusinessRecord` (`scrapers/base.py:5-28`) both declare 23 and they agree exactly, so nothing is broken — but the documentation is off by one and a reader diffing the two against the brief will waste time on it.
