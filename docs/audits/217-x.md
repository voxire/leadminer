# 217 — `cmd_scrape` (cli.py:40) hostile-input and boundary audit

## Verdict

`cmd_scrape` has **no input validation of its own** — it delegates all of it to
`argparse` (`choices=`, `required=`, `cli.py:289-290`), and that delegation is
complete, so every hostile value that reaches the function body via `argv` is
already rejected before line 46. The interesting surface is the *other* input:
the records the three scrapers yield, and the `args.source not in registry`
guard at `cli.py:56-59` which argparse makes permanently unreachable.

The single most dangerous input is **an HTTP 200 response whose body is not a
JSON object** — most sharply, **an empty body**, because
`httpclient.py:185` (`ok=resp.status_code < 400`) and `httpclient.py:188`
(`body=body or b""`) together make `ok=True, body=b""` a representable state.
`FetchResult.json()` (`httpclient.py:110-113`) then runs `json.loads("")`, and
the resulting `json.JSONDecodeError` propagates from `osm.py:58` /
`wikidata.py:87` through `cli.py:61` to the top of the process, because
`main()` (`cli.py:314-318`) catches only `KeyboardInterrupt`. Python's
unhandled-exception exit status is **1**, which is the *same* status the
intentional zero-records failure returns at `cli.py:66`. That is the dangerous
part: the one command whose docstring (`cli.py:42-44`) says it exists for
"checking a single source after an API change" fails with a bare traceback,
and the failure is indistinguishable to any wrapper script from "the source
legitimately had nothing".

Everything below was verified by driving the real `cli.py` with injected fake
scraper modules. No network. Source unmodified.

---

## The contract, and what the function actually reads

```python
def cmd_scrape(args: argparse.Namespace) -> int:      # cli.py:40
    from scrapers.base import BaseScraper             # cli.py:46
    from scrapers.google_places import GooglePlacesScraper   # cli.py:47
    from scrapers.osm import OSMScraper               # cli.py:48
    from scrapers.wikidata import WikidataScraper     # cli.py:49
    registry = {"osm": ..., "wikidata": ..., "google_places": ...}   # cli.py:51-55
    if args.source not in registry: ... return 2      # cli.py:56-59
    records = list(registry[args.source]().scrape())  # cli.py:61
```

Two inputs, only two:

| Input | Where consumed | Fields read |
|---|---|---|
| `args.source` | `cli.py:56`, `cli.py:61` | one string, one of three literals |
| each yielded record | `cli.py:68-70` | **exactly three keys**, all via `.get`: `category`, `phone`, `website` |

`BaseScraper.scrape()` (`scrapers/base.py:31-33`) is declared
`Iterator[BusinessRecord]` and `BusinessRecord` (`scrapers/base.py:5-28`) is a
`total=True` TypedDict — i.e. all 23 keys are guaranteed present and
`category` is `str | None`. `cmd_scrape` therefore promises to receive a dict
for every element. It does not check that promise anywhere.

## Findings

### S1 — A 200 response with a non-JSON body kills the only source-health command in the product, with the same exit code as "zero records"

- **Where:** `cli.py:61` (`records = list(registry[args.source]().scrape())`),
  with no handler in `main()` except `KeyboardInterrupt` at `cli.py:316-318`.
  The crash originates at `osm.py:58`
  (`elements = result.json().get("elements", [])`) and `wikidata.py:87`
  (`results = result.json().get("results", {}).get("bindings", [])`), both of
  which are fed by `FetchResult.json()` at `httpclient.py:110-113`.
- **Breaks:** `fetch_with_retry` decides success from the **status code only**
  (`httpclient.py:185`: `ok=resp.status_code < 400`) and normalises an empty
  body to `b""` (`httpclient.py:188`: `body=body or b""`). So `ok=True,
  body=b""` is a state the type permits and the code produces. `json()` then
  does `json.loads(self.body.decode(...))` with no guard, and there is no
  content-type check. `osm.py:58` additionally assumes the decoded value is a
  **dict** (it calls `.get` on it).
  Verified shapes, all reachable from a 2xx and none catchable by
  `raise_for_status()`:
  ```
  b''                                  -> JSONDecodeError: Expecting value: line 1 column 1 (char 0)
  b'runtime error: Query timed out'    -> JSONDecodeError: Expecting value: line 1 column 1 (char 0)
  b'<html>502</html>'                  -> JSONDecodeError: Expecting value: line 1 column 1 (char 0)
  b'null'                              -> json=None -> AttributeError: 'NoneType' object has no attribute 'get'
  b'[]'                                -> json=[]   -> AttributeError: 'list' object has no attribute 'get'
  ```
  Driving the real `cli.main(["scrape","--source","osm"])` with a scraper that
  raises the first of those:
  ```
  Traceback (most recent call last):
    File ".../cli.py", line 315, in main
      return int(args.func(args) or 0)
    File ".../cli.py", line 61, in cmd_scrape
      records = list(registry[args.source]().scrape())
  json.decoder.JSONDecodeError: Expecting value: line 1 column 1 (char 0)
  ```
  A generic `RuntimeError` behaves identically: `ESCAPED to top level`.
  `KeyboardInterrupt` is the **only** thing handled — it correctly returns 130.
- **Trigger:** `leadminer scrape --source osm` while Overpass or Wikidata is
  degrading. Realistic producers of a 2xx non-JSON body: an Overpass query
  timeout reported in-band (the query already declares `[timeout:180]`,
  `osm.py:12`, so server-side timeout is the expected failure), or an
  HTTPS-intercepting proxy / captive portal returning an HTML page — common on
  Gulf and Levant corporate networks. An empty 200 needs no speculation at all;
  it falls straight out of `httpclient.py:188`.
- **Why S1, not S2:** the brief's bar is "a run that dies". This is the run
  that dies, and it dies in the specific circumstance the command exists to
  diagnose. Worse, the exit status is **1** (verified: an unhandled exception
  exits 1), which is byte-identical to the deliberate
  `return 1` at `cli.py:66`. `leadminer scrape --source osm || alert` cannot
  distinguish *source broken* from *source empty* from *our parser is wrong*.
  For `--source google_places` it is also **silent data loss within the run**:
  any worker raising unwinds the `with ThreadPoolExecutor` block at
  `google_places.py:194` **before** `yield from all_records` at
  `google_places.py:199`, so records already collected by the other four
  workers under `records_lock` (`google_places.py:191-192`) are discarded —
  and then the operator sees a traceback rather than "partial results".
  (203-x.md:212 and 200-fn-cli-py-main-ops.md:350 already flag the missing
  handler; the exit-code collision and the OSM/Wikidata empty-body case are
  new.)
- **Fix:** wrap `cli.py:61` in `try/except Exception as e:` and `return 3` — a
  status distinct from both 1 and 2 — and separately make
  `FetchResult.json()` (`httpclient.py:110-113`) raise a typed
  `FetchResult`-level error for empty/non-dict bodies so `osm.py:58` and
  `wikidata.py:87` can use the existing "a broken source must not look like an
  empty one" pattern they already implement for `ok=False`
  (`osm.py:47-56`, `wikidata.py:79-85`).

### S2 — `None`, `""` and whitespace-only categories are counted as real categories and occupy the top-10 panel

- **Where:** `cli.py:68` (`collections.Counter(r.get("category") for r in records)`)
  rendered at `cli.py:74-75`.
- **Breaks:** the `Counter` keys on the raw value, and `None`, `""`, `" "`,
  `"\t"` and `"\t\n"` are five distinct hashable keys. `str(cat):<28>` then
  renders `""` and `"  "` as visually identical runs of 28 spaces, so the
  operator cannot even read the counts correctly off the panel. Driving the
  real `cmd_scrape` with 11 records of which exactly one has
  `category="restaurants"`:
  ```
  [osm] 11 records
    top categories:
      None                         2
                                     2
                                     2

      (tab+newline)                2
      restaurants                  1
  ```
  Six of seven rows are blank-category bookkeeping and the single real category
  is ranked last. The operator's reasonable conclusion — "the source's
  taxonomy is broken" — is wrong; the panel is just unnormalised.
- **Trigger:** not hypothetical. Every Wikidata record whose `?category`
  OPTIONAL (`wikidata.py:35-39`) is unbound yields
  `row.get("categoryLabel", {}).get("value")` → `None` (`wikidata.py:100`).
  The query has no other category source and `LIMIT 5000` (`wikidata.py:43`),
  so for `--source wikidata` a `None` top-line is the *expected* result, not an
  edge case.
- **Second, compounding effect:** `most_common(10)` (`cli.py:74`) silently
  discards the tail for any source with >10 distinct categories, and ties at the
  rank-10 boundary are broken by first-encountered order (the documented
  `Counter` contract). For `google_places` the encounter order is
  thread-completion order (`google_places.py:196-199`), so **the top-10 panel
  for `--source google_places` is not reproducible between runs** whenever
  there is a tie at the cutoff.
- **Fix:** normalise before counting — `collections.Counter((r.get("category") or "").strip() or "(blank)" for r in records)`
  — and print the blank total as its own line. `cmd_stats` already does exactly
  this shape at `cli.py:124` (`r.get("region") or "Unknown"`); the two commands
  should share one helper.

### S2 — `with phone` / `with site` use truthiness, so `cmd_scrape` and `cmd_stats` disagree about the same rows

- **Where:** `cli.py:69-70` (`sum(1 for r in records if r.get("phone"))`)
  versus `cli.py:96` (`sum(1 for r in rows if (r.get(field) or "").strip())`).
- **Breaks:** truthiness accepts any non-empty string, including
  whitespace-only. Verified on four rows
  `[{"phone":"   "}, {"phone":""}, {"phone":None}, {"phone":"+9613112345"}]`:
  ```
  cmd_scrape (cli.py:69)  -> 2
  cmd_stats  (cli.py:96)  -> 1
  ```
  Two numbers in the same binary, describing the same data, off by 100% on a
  garbage row. These are precisely the two numbers an operator uses to decide
  whether a source is still worth its API cost, and the CLI module docstring
  (`cli.py:14-15`) markets `stats` as "the first thing to check".
- **Trigger:** OSM `phone` / `contact:phone` are free-text tag values read
  verbatim at `osm.py:89`, and `osm.py:95-96`
  (`if website and not website.startswith("http"): website = "https://" + website`)
  turns a whitespace-padded value into truthy garbage:
  `website="  example.com"` → `"https://  example.com"` → counted as
  **with site**. `cmd_stats` counts 0 for that row. End-to-end verified:
  `[{"phone": "   ", "website": "\t"}]` → `with phone : 1`, `with site : 1`.
- **Fix:** use the `cmd_stats` predicate — `(r.get(f) or "").strip()` — in both
  commands; ideally one shared `count()` so the two can never drift again.

### S2 — All three scrapers are imported unconditionally, so `--source osm` dies on a Google Places import failure

- **Where:** `cli.py:46-49`, before the registry is built at `cli.py:51-55` and
  long before `args.source` is consulted at `cli.py:56`.
- **Breaks:** the lazy-import discipline this file otherwise keeps (per-command
  at `cli.py:35`, `cli.py:226`, `cli.py:249-252`) is applied at the granularity
  of the *command*, not the *source*. A broken `scrapers.google_places` makes
  `leadminer scrape --source osm` — which needs no Google code whatsoever —
  die with an uncaught `ImportError`. Verified by stubbing the module:
  ```
  File ".../cli.py", line 47, in cmd_scrape
      from scrapers.google_places import GooglePlacesScraper
  ImportError: cannot import name 'GooglePlacesScraper' from 'scrapers.google_places'
  ```
  This is not hypothetical in this checkout: **`requests` is not installed
  here**, and `scrapers/google_places.py:24` is a module-level `import requests`,
  so `leadminer scrape --source osm` currently tracebacks on
  `ModuleNotFoundError: No module named 'requests'` — for a command whose
  advertised sources are Overpass and Wikidata.
- **The irony worth acting on:** `cmd_doctor` guards exactly this, at
  `cli.py:227-231`, with the rationale already written down —
  *"doctor exists to diagnose a broken environment, so it must never be the
  thing that tracebacks"* — and prints
  `FAIL  requests is not installed - run: pip install -e '.[dev]'`.
  `cmd_scrape` is the command `README.md:12` tells the operator to run next
  (`leadminer doctor` then `leadminer scrape --source osm`, README.md:95-96),
  and it has no such guard. Also `cli.py:46`,
  `from scrapers.base import BaseScraper  # noqa: F401  (import check)`, is a
  bare import whose sole purpose is to smoke-test an ABC; as written it
  produces a traceback, not a message.
- **Fix:** build the registry from lazy factories —
  `"osm": lambda: _load("scrapers.osm", "OSMScraper")` — or minimally wrap
  `cli.py:46-49` in `try/except ImportError` and reuse doctor's message.

### S3 — `cli.py:56-59` is unreachable; the source list is declared twice and the friendly error can never print

- **Where:** `cli.py:56-59` vs the argparse declaration at `cli.py:289-290`
  (`choices=["osm", "wikidata", "google_places"]`, `required=True`).
- **Breaks:** argparse rejects everything first. Every value I could construct
  as `argv` is handled at the parser, with exit status 2 and a message that
  already names the valid choices:

  | argv after `scrape` | result |
  |---|---|
  | *(omitted)* | `SystemExit 2: ... the following arguments are required: --source` |
  | `--source ''` | `SystemExit 2: ... invalid choice: '' (choose from 'osm', 'wikidata', 'google_places')` |
  | `--source '   '` | `SystemExit 2: ... invalid choice: '   '` |
  | `--source ' osm'` | `SystemExit 2: ... invalid choice: ' osm'` |
  | `--source 'osm '` | `SystemExit 2: ... invalid choice: 'osm '` |
  | `--source $'osm\nwikidata'` | `SystemExit 2: ... invalid choice: 'osm\nwikidata'` |
  | `--source 'أ osm'` | `SystemExit 2: ... invalid choice: 'أ osm'` |
  | `--source '🥘'` | `SystemExit 2: ... invalid choice: '🥘'` |
  | `--source 'OSM'` | `SystemExit 2: ... invalid choice: 'OSM'` |
  | `--source 'osm;wikidata'` | `SystemExit 2: ... invalid choice: 'osm;wikidata'` |
  | `--source osm --source wikidata` | accepted, last wins → `source='wikidata'` |

  **The `if args.source not in registry` block never executes through the CLI.**
  It is reachable only if `cmd_scrape` is called as a library function with a
  hand-built `Namespace` — which the packaging actively invites: `main(argv)`
  at `cli.py:312-313` takes a list, and `pyproject.toml:35` exposes
  `leadminer = "cli:main"`.
- **Concrete cost:** two sources of truth for the same set — the registry keys
  at `cli.py:52-54` and the `choices` list at `cli.py:290`. They match today.
  Add a fourth scraper to the registry and forget `:290`, and the new scraper is
  reachable **only** by bypassing argparse, i.e. the dead branch becomes the
  only way in — with an error message that says "choose from osm, wikidata,
  google_places" while `sorted(registry)` on the next line would have listed the
  new one. Duplicated literals in `--help` too.
- **One unsafe input in the dead branch itself:** the membership test is
  `in` on a dict, which hashes the argument. Verified
  `[] not in registry` → `TypeError: cannot use 'list' as a dict key
  (unhashable type: 'list')` (same for `{}`). Unreachable from `argv` — argparse
  always hands this a `str` — but reachable from a programmatic caller, and the
  guard it was written to make safe does not make it safe.
- **Fix:** `choices=sorted(_SOURCES)` where `_SOURCES` is a module-level
  constant the registry is built from; or delete `cli.py:56-59` and keep
  argparse as the single validator.

### S3 — Category text is written to the terminal unescaped: ANSI clears, newline injection, and bidi spoofing

- **Where:** `cli.py:75` — `print(f"    {str(cat):<28} {n}")`.
- **Breaks:** the raw string reaches a TTY. Verified renderings:

  | `category` value | what the operator's terminal does |
  |---|---|
  | `"\x1b[2J\x1b[Hr00t"` | clear screen, home cursor, overwrite the panel |
  | `"restau\n    99999 INJECTED"` | breaks the one-row-per-category contract and can forge an extra output line |
  | `"shop\u202egnippihs"` | U+202E RIGHT-TO-LEFT OVERRIDE reverses the label visually — Trojan Source, CVE-2021-42574 class |

  This is the only CLI command that writes remote-sourced data straight to a
  terminal with no sanitisation. `cli.py:57` gets this right — it uses
  `{args.source!r}`.
- **Producer:** OSM `shop=` / `amenity=` / `craft=` values are free text
  authored by any OpenStreetMap editor and returned verbatim at
  `osm.py:71-78`. Wikidata is lower risk (`categoryLabel` is filtered to
  `LANG="en")`, `wikidata.py:38`).
- **Why S3, not S2:** impact is confined to the operator's own screen, and only
  10 lines are emitted. Nothing is written to disk and no exit code changes. It
  is a trust-of-output problem, not a data problem — but it belongs in the same
  fix as the S2 above, because both are "normalise `cat` before you use it".
- **Fix:** one line before `cli.py:75` —
  `cat = "".join(ch if ch.isprintable() else "?" for ch in str(cat))`.

### On the Unicode classes specifically

Arabic, French and emoji are all handled correctly by the mechanism — `Counter`
hashes them, `str()` passes them through, and `{s:<28}` never raises on any of
them. I could not construct a crash from a well-formed Unicode category, and I
am not going to pretend otherwise.

Two caveats, both honest rather than severe:

- **Display width.** `f"{s:<28}"` pads to 28 *code points*, not 28 *columns*,
  so a category containing Arabic or an emoji pushes the count to the right.
  Cosmetic.
- **It is theoretical today.** All three sources currently emit ASCII category
  keys: OSM tag keys (`osm.py:71-78`), Google type slugs
  (`google_places.py:315-321`), and English-only Wikidata labels
  (`wikidata.py:38`). So even the alignment drift is unreachable until a source
  starts feeding real-language labels into `category` — which the `categoryLabel`
  OPTIONAL is one SPARQL edit away from doing for Arabic.

The genuinely reachable Unicode-adjacent risk is the **untrusted, unescaped
write to the terminal** (S3), not the Unicode handling itself.

## Not a bug, but worth knowing

- **The zero-record path is the best code in the function.** `cli.py:63-66`
  detects an empty source, names both plausible causes on stderr, and returns a
  non-zero status — the exact behaviour `osm.py:48-50` and `httpclient.py:17-19`
  say the project wants everywhere. 200-fn-cli-py-main-ops.md:344-352 already
  notes the inversion that `cmd_run` (`main.py:148`) has no equivalent. Keep
  `cli.py:63-66` exactly as it is when fixing S1; the fix is to give the
  traceback path a *third* status, not to weaken this one.
- **`str(cat):<28}` is not truncation.** `f"{'A'*200:<28}"` renders 200
  characters. If the intent was column clipping, it does not exist; if the
  intent was a minimum-width pad (which is what makes `None` and the long
  Google type slugs line up), it is correct. Worth a comment saying which.
- **`cmd_scrape` reports pre-dedup, pre-whitelist records.** `cli.py:61-75`
  counts whatever the scraper yields. `main.py:172-181` then drops non-business
  categories and dedups, so the number `cmd_scrape` prints and the number the
  CSVs contain are different quantities. Defensible for a "check one source"
  command — but the panel never says so, and an operator comparing
  `leadminer scrape --source osm` against `leadminer stats` will conclude a
  large number of records were lost.
- **`cmd_scrape` has no baseline and therefore no anomaly signal.** The only
  `--source` argument is declared at `cli.py:289-290`; there is no
  `--min-records` / `--expect`. A source that degrades from 18,000 records to
  12 exits **0** at `cli.py:76`. The one case that is checked (zero) is the one
  case that a well-behaved API does not produce. This is the same gap 041
  covers for the pipeline; for the CLI it is cheap to close because this command
  is already the manual tripwire.
- **`cli.py:21` (`collections`) is used only here and in `cmd_stats`** — worth
  remembering if anyone ever proposes deleting it, since `cmd_validate`, the
  only command documented as a hard gate (`cli.py:297`, `README.md:14`), has no
  use for it.
