# 247 — `cmd_doctor`: the health check that cannot fail, watching the pipeline that cannot fail

## Verdict

`cmd_doctor` (`cli.py:204-244`) reports health but **never computes it**. The `ok`
flag is mutated in exactly one place — `cli.py:213-214`, a presence test for
`GOOGLE_PLACES_API_KEY` — so `leadminer doctor` exits **0 on a total network
outage**, exits **0 when all three upstreams are returning HTTP 403**, and exits
**0 with an invalid Google API key**, which means 100% of the Saudi market is
being silently dropped. Worse, all three connectivity probes are structurally
incapable of detecting the failure they were written to detect: the Google probe
issues a **`GET` to a POST-only endpoint without the API key**
(`cli.py:236`), the Overpass probe reads a **status page whose entire health
report lives in a response body that `cli.py:240` throws away**, and the
Wikidata probe omits the `format=json` param and `Accept` header that
`wikidata.py:74-77` actually sends. Run unattended on a cron, this function is
worse than no doctor at all, because it manufactures the specific false
reassurance — "I checked, it's fine" — that stops anyone from investigating the
six-hour run it was supposed to be watching.

---

## 1. Exactly what it prints

Healthy cron, fresh checkout (`data/` is gitignored at `.gitignore:10` and does
not exist in the repo), key present:

```
credentials:
  OK   GOOGLE_PLACES_API_KEY
  MISSING  SCRAPER_EMAIL

data directory:
  MISSING  data (no run has produced output yet)

connectivity (5s timeout each):
  OK   Overpass        
  OK   Wikidata         
  OK   Google Places    
```

Note what that transcript claims, all at once, and all falsely in the general
case:

- `SCRAPER_EMAIL` is `MISSING` and the command exits **0** (`cli.py:213` gates
  `ok = False` on `var == "GOOGLE_PLACES_API_KEY"` only).
- `data` is `MISSING` and the command exits **0** (the `else` at `cli.py:221-222`
  prints but never touches `ok`).
- No HTTP status code, no latency, no body, and a trailing-whitespace hole
  where the note would be, on any of the three `OK` lines (`cli.py:240-241`).

And the column alignment is broken precisely on the failure rows:
`"  " + "OK " + "  "` = column 8 (`cli.py:212`, `cli.py:218`, `cli.py:241`),
but `"  " + "MISSING" + "  "` = column 11 (`cli.py:212`, `cli.py:222`). The
words a human scans for are the ones that break the grid.

## Findings

### S1 — Connectivity failures cannot change the exit code

- **Where:** `cli.py:208`, `cli.py:240-244`. `ok = True` at `cli.py:208`; the
  only mutation is `cli.py:213-214`. The connectivity loop at `cli.py:238-243`
  writes to `stdout` only. `return 0 if ok else 1` at `cli.py:244`.
- **Breaks:** Every one of these exits **0**:

  | Condition | What doctor prints |
  |---|---|
  | Total network outage | three `FAIL` lines |
  | Corporate proxy, `HTTPS_PROXY` set, returning 407 | three `OK` lines |
  | Upstreams 403 (Overpass/Wikidata UA policy block) | three `OK` lines |
  | Google key revoked / Places API disabled / quota exhausted | `OK  Google Places` |
  | `data/` deleted by a bad rclone step | `MISSING  data (...)` |

  A health check whose only failure mode is "the API key string is absent from
  the environment" cannot be used as a gate, an alert, or a cron precondition.
- **Trigger:**
  ```bash
  GOOGLE_PLACES_API_KEY=AIzaSyD-not-a-real-key leadminer doctor; echo "exit=$?"
  # with the network unplugged:
  #   FAIL  Overpass       ConnectionError
  #   FAIL  Wikidata       ConnectionError
  #   FAIL  Google Places  ConnectionError
  # exit=0
  ```
- **Fix:** Set `ok = False` on any `FAIL` (line 243) and on any `4xx/5xx` (line
  240); distinguish `WARN` (degraded) from `FAIL` (unusable) and exit non-zero on
  `FAIL`. Return a distinct code (e.g. `3` for config/credentials) so cron can
  branch on the cause.

### S1 — The Google Places probe can never detect a Google problem

- **Where:** `cli.py:236`.
- **Breaks:** Three independent defects in one line:
  1. **Wrong method.** Places API v1 `searchText` is POST-only. Google's own
     REST reference lists it as `POST /v1/places:searchText` (also
     [Migrate to Text Search](https://developers.google.com/maps/documentation/places/web-service/legacy/migrate-text):
     *"Text Search (New) uses HTTP POST requests"*). The scraper correctly
     POSTs (`google_places.py:227`). `cli.py:239` sends `requests.get`. Google's
     frontend answers an unregistered method on that resource with 404 or 405.
  2. **No key.** No `X-Goog-Api-Key` header is sent, so the response is a
     `403 PERMISSION_DENIED` regardless of the key's actual validity.
  3. **Any `< 500` is `OK`** (`cli.py:240`), so 403/404/405/429 all print
     `OK   Google Places` with an empty note.

  This check has **no input under which it reports anything but OK**, other than
  a Google 5xx or a transport error. It is a decorative line.
- **Trigger:** Revoke the Google Cloud API key in the console. `doctor` prints
  `OK   Google Places`. The next run logs
  `[Google] FATAL: invalid API key (401)` (`google_places.py:231-232`) for each of
  the 68 queries and returns **zero Saudi records** — because OSM is
  Lebanon-only (`osm.py:13`, `area["ISO3166-1"="LB"]`) and Wikidata is
  Lebanon-only (`wikidata.py:27`, `wdt:P17 wd:Q822`). Google is the *only*
  source for Riyadh/Jeddah/Dammam.
- **Fix:** Probe with the production request: `session.post(API_URL,
  json={"textQuery": "cafe"}, headers={"X-Goog-Api-Key": key, "X-Goog-FieldMask":
  FIELD_MASK})` and fail on any non-2xx.

### S1 — Overpass's only health signal is discarded, and the CI row guard cannot catch the loss

- **Where:** `cli.py:234` probes `https://overpass-api.de/api/status`; the
  pipeline uses `https://overpass-api.de/api/interpreter`
  (`osm.py:9`). `cli.py:240` sets `note = ""` for any status `< 500` and never
  reads `r.text`.
- **Breaks:** Per the [Overpass status docs](https://dev.overpass-api.de/overpass-doc/en/preface/commons.html),
  `/api/status` **returns HTTP 200 and reports availability in the body**:

  ```
  Connected as: 866011160
  Rate limit: 2
  Slot available after: 2021-03-15T09:30:24Z, in 968 seconds.
  ```

  "Requests that are denied due to the rate limit are answered with the HTTP
  status code 429" — but only the `/api/interpreter` POST gets that; the status
  page itself is 200 while it cheerfully reports zero free slots for the next
  16 minutes. `cli.py:240` reduces that to `note = ""` and prints `OK`.
  Meanwhile `osm.py:39-46` issues one POST with `[timeout:180]` and
  `retries=3`; when the slots are gone it burns ~3 minutes of jittered backoff
  and returns an **empty generator**. `main.py:166` extends `raw` with nothing,
  the run completes, five CSVs are written, Drive is updated.

  The CI guard cannot catch this. `scrape.yml:78-83` fails only if
  `ROWS < 100`, but `all_businesses.csv` is **cumulative** (`main.py:150` loads
  the master, `main.py:179` merges it in, `main.py:209` writes it back). A run
  that scrapes *zero* records still emits a file with every row from last month.
  The guard is structurally incapable of detecting source death.
- **Trigger:** Run `leadminer scrape --source osm` at the same moment
  `/api/status` reports `Slot available after: ..., in 968 seconds.` Doctor says
  `OK  Overpass`; the real POST returns 429 three times; OSM contributes 0.
- **Fix:** Parse `r.text` for `slots available now` vs `Slot available after`,
  report the wait in seconds, and WARN when no slot is currently free.

### S1 — Credentials are checked for presence, never for validity

- **Where:** `cli.py:210-214`.
- **Breaks:** `bool(os.environ.get(var))` is a string-emptiness test. It cannot
  distinguish a valid key from a revoked one, one with the Places API disabled,
  one with billing disabled, one that has exhausted its daily quota, or the
  literal placeholder `"TODO"`. `SCRAPER_EMAIL` is reported `MISSING` but never
  affects the exit code — even though it is the only thing that makes this
  project's User-Agent compliant (`httpclient.py:81-85`) and Overpass's policy
  requires a contact address and asks commercial users to self-host. A
  systematically non-compliant scraper is the documented cause of Overpass
  429-ing, which is exactly failure S1-3. The `if var == "GOOGLE_PLACES_API_KEY"`
  guard at `cli.py:213` hardcodes a variable name inside a loop over two
  variables, so any future third variable defaults to silently non-fatal.
- **Trigger:** `SCRAPER_EMAIL="" GOOGLE_PLACES_API_KEY=AIza... leadminer doctor;
  echo $?` → prints `MISSING  SCRAPER_EMAIL`, exits `0`. The run then scrapes
  with `leadminer/0.2 (+https://github.com/voxire/leadminer)` — no contact —
  and is the sort of client that gets throttled.
- **Fix:** Make each credential carry a `(required, validator)` pair; validate
  the Google key by actually calling the API (S1-2), and make a missing
  `SCRAPER_EMAIL` at least a `WARN` on the exit code.

### S2 — The probes are not the requests the pipeline makes

- **Where:** `cli.py:233-239`, against `osm.py:39-46`, `wikidata.py:70-78`,
  `google_places.py:227`.
- **Breaks:** Every probe differs from production in method, headers, or
  endpoint, so a green doctor certifies a code path the pipeline never exercises:

  | Probe (`cli.py`) | Production | Divergence |
  |---|---|---|
  | `GET /api/status` | `POST /api/interpreter` | different endpoint; the one that 429s is untested |
  | `GET /sparql?query=ASK{}` | `GET /sparql` + `params={"format":"json"}` + `Accept: application/sparql-results+json` (`wikidata.py:74-77`) | no `format`, no `Accept`; WDQS defaults to `text/html`, so the JSON decode path is never tested. `ASK{}` is trivial and can never exhibit the cold-start latency of the real `LIMIT 5000` query. |
  | `GET searchText`, no headers | `POST` + `X-Goog-Api-Key` + `X-Goog-FieldMask` | wrong method, no auth (see S1-2) |

  Compounding this: `overpass-api.de` is a **DNS round-robin alias for
  `lz4.overpass-api.de` and `z.overpass-api.de`** ([drolbr/Overpass-API#580](https://github.com/drolbr/Overpass-API/issues/580)),
  so doctor's status answer can describe a *different server* than the one the
  scraper's POST landed on. And the endpoint set is a hardcoded tuple literal —
  not overridable by env var, flag, or config — so you cannot check a mirror,
  add a source, or run offline.
- **Trigger:** Change `SPARQL_ENDPOINT` in `wikidata.py:9` to a mirror, or break
  the scraper's `Accept` header. `doctor` keeps printing `OK  Wikidata`.
- **Fix:** Import the endpoints and headers from the scraper modules instead of
  re-declaring them, so the probe cannot drift from production.

### S2 — `except Exception` discards the one string that makes the check useful

- **Where:** `cli.py:242-243`, `f"...{type(e).__name__}"`.
- **Breaks:** Only the class name is printed; `str(e)` and `e.__cause__` are
  dropped. The difference between a 10-second diagnosis and a 2-hour one is
  usually in the message:
  - `[Errno -3] Temporary failure in name resolution` → local DNS broken
  - `Connection refused` → host refusing, firewall/proxy policy
  - `Max retries exceeded ... (Caused by SSLError: certificate verify failed)` → expired CA bundle, `pip`/certifi mismatch, TLS interception
  - `407 Proxy Authentication Required` → corporate proxy needs credentials

  All four collapse to `ConnectionError`. Note the codebase already does this
  correctly elsewhere: `httpclient.py:177` builds `f"{type(e).__name__}: {e}"`.
- **Trigger:** Corporate MITM proxy with an untrusted CA →
  `FAIL  Overpass       SSLError` and nothing else.
- **Fix:** `f"  FAIL  {name:<14} {type(e).__name__}: {e}"`, truncated to one
  line, with `e.__cause__` chained.

### S2 — "5s timeout each" is false, and cron has no wall clock

- **Where:** `cli.py:224` prints the promise; `cli.py:239` makes it.
- **Breaks:** Three separate falsehoods:
  1. `timeout=5` is a **per-operation** value (connect, read), not a wall clock.
     requests' own maintainers: *"This isn't a wall clock, as specified in the
     docs, it's for each operation"* ([psf/requests#5450](https://github.com/psf/requests/issues/5450)).
     Worst case is ~30s per endpoint, not 5.
  2. It **does not cover DNS resolution**. `socket.getaddrinfo` is a blocking C
     call with no timeout parameter — tracked as [psf/requests#4531 "timeout
     does not apply to name resolution"](https://github.com/psf/requests/issues/4531),
     with documented hangs of *"upwards of 90 seconds, despite specifying a
     timeout value"*. Three hostnames → up to ~4.5 minutes.
  3. **SIGTERM is not handled.** There is no signal handler and no `finally`.
     Ctrl-C is fine (`KeyboardInterrupt` is a `BaseException`, so `except
     Exception` at `cli.py:242` correctly does not swallow it; it reaches
     `cli.py:316-318` → `130`). SIGTERM — what systemd, a cron supervisor, and
     GitHub Actions job cancellation send — kills the process outright.
- **Trigger:** Unreachable resolver, then `kill $(pgrep -f leadminer)`. Doctor
  has printed `connectivity (5s timeout each):` and nothing else for four
  minutes, then dies.
- **Fix:** Wrap the whole section in a wall-clock deadline, print elapsed
  seconds per probe, install a SIGTERM handler that raises, and change the header
  to `connectivity (per-request timeout 5s, wall clock 60s)`.

### S2 — In cron, doctor's output is not durable evidence

- **Where:** `cli.py:209-243` — every line is `print()` to stdout. Nothing is
  timestamped, written to a file, or emitted as JSON. `build_parser`
  (`cli.py:301-302`) offers no `--json`, `--log`, `--timeout`, or `--offline`.
- **Breaks:** Four compounding problems, all specific to unattended operation:
  1. **No timestamps.** Nothing records when a probe ran or how long it took, so
     "it was fine yesterday" is unprovable.
  2. **Block buffering.** Under cron, stdout is a pipe, so Python block-buffers
     it. The whole connectivity section is ~100 bytes — far under the 4–8 KB
     buffer. **A SIGTERM'd or SIGKILL'd doctor emits an empty log**, identical to
     one that was never scheduled. The scrapers already got this right
     (`osm.py:54`, `wikidata.py:83`, `google_places.py:232` all pass
     `flush=True`); doctor does not.
  3. **Nothing calls it.** `grep doctor .github/workflows/` returns nothing;
     `scrape.yml:69` runs `python main.py` directly, and `scrape.yml:39`
     installs `requirements.txt` rather than `-e .`, so the `leadminer` console
     script (`pyproject.toml:33`) does not even exist in CI. Doctor is
     human-invoked only.
  4. **No `--json`.** Even if a human did run it in cron, there is no output a
     monitor could assert on — only the exit code, which S1-1 has already shown
     is always 0.
- **Fix:** Add `--json`, print a UTC ISO timestamp per line, pass `flush=True`,
and add a `doctor` step to `scrape.yml` before the scrape step.

### S2 — `DATA_DIR` is resolved against the current working directory

- **Where:** `cli.py:26` (`DATA_DIR = pathlib.Path("data")`), used at
  `cli.py:217` and `cli.py:219`.
- **Breaks:** A relative path resolves against `os.getcwd()`. Cron's default cwd
  is `$HOME`; the workflow's is `$GITHUB_WORKSPACE`. Run from cron without an
  explicit `cd`, doctor reports on `$HOME/data`, which does not exist, and
  prints the flatly false `MISSING  data (no run has produced output yet)` —
  about a system holding months of cumulative leads. Exit code: 0. This is the
  one finding here that produces *actively misleading prose* rather than just a
  missed alarm.
- **Trigger:**
  ```bash
  cd /tmp && GOOGLE_PLACES_API_KEY=x leadminer /path/to/cli.py doctor
  #   MISSING  data (no run has produced output yet)
  ```
- **Fix:** Resolve from the package location (`Path(__file__).parent / "data"`)
  or require `--data-dir`, and make the missing-directory case non-fatal but
  explicitly labelled as *"wrong cwd"*.

### S2 — `f.stat()` can traceback, violating the function's own stated invariant

- **Where:** `cli.py:219-220`, against the comment at `cli.py:228-229`:
  *"doctor exists to diagnose a broken environment, so it must never be the thing
  that tracebacks."*
- **Breaks:** `DATA_DIR.glob("*.csv")` at `cli.py:219` is lazy and `f.stat()` at
  `cli.py:220` is unguarded — a TOCTOU window with nothing around it. This is
  reachable: `scrape.yml:56` runs `rclone copy` directly into `data/` while a
  concurrent manual run is writing, and `main.write_csv` (`main.py:121-133`)
  creates and removes files in the same directory. A file that vanishes between
  glob and stat raises `FileNotFoundError`, which `main()` does **not** catch —
  it only catches `KeyboardInterrupt` (`cli.py:314-318`) — so doctor dies with
  a traceback and exit 1. A health check that crashes is a false alarm, and it
  does so in the one situation where an operator is already stressed.
- **Trigger:** `rm data/qualified_businesses.csv` while `doctor` is in the glob
  loop.
- **Fix:** Wrap the listing in `try/except OSError as e` and print `WARN
  <f.name>: <e>`, continuing to the next file.

### S2 — Zero retries on shared public endpoints makes doctor cry wolf

- **Where:** `cli.py:239` — `requests.get(url, timeout=5)`, bare, bypassing the
  project's own client.
- **Breaks:** `overpass-api.de` and `query.wikidata.org` are free, shared,
  frequently-slow public services. A single 5s sample with no retry will
  intermittently report `FAIL` on a perfectly healthy system — and a `FAIL`
  costs the operator nothing, so people learn to skip the line. Meanwhile the
  `OK` line costs the operator everything, so people stop running doctor. Both
  failure directions are wrong, which is worse than either alone. The codebase
  already has the correct primitive: `httpclient.fetch_with_retry`
  (`httpclient.py:149-217`), which retries 429/5xx with exponential backoff and
  full jitter and returns a typed `FetchResult` whose docstring says
  *"Callers must not treat that as the server saying no"*.
- **Trigger:** Wikidata's WDQS cold-starts frequently exceed 5s. `doctor` prints
  `FAIL  Wikidata       ReadTimeout`.
- **Fix:** Use `httpclient.fetch_with_retry(..., retries=3)` and report
  `elapsed` and `attempts` from the `FetchResult`.

### S3 — An `OK` line carries no information

- **Where:** `cli.py:240-241`, `note = "" if r.status_code < 500 else ...`.
- **Breaks:** The status code is printed only on the `WARN` path. On the `OK`
  path, 200 and 403 and 407 and 429 are visually identical, and the trailing
  `{note}` leaves two trailing spaces of nothing. A reader cannot tell a healthy
  200 from a rate-limited 429 without re-running with `curl`.
- **Fix:** Always print `r.status_code` and the elapsed time; reserve the note for
  the body-derived verdict.

### S3 — No test coverage

- **Where:** `tests/test_lead_signal.py` contains no `cmd_doctor` case, matching
  the gap already recorded at `docs/audits/087-SYNTH-test-gap.md:19` and `:84`.
- **Breaks:** Every finding above is one `monkeypatch` away from a regression
  test, and the function is pure enough to test entirely offline except for the

- **Fix:** Four tests, no network: (1) missing key → exit 1; (2) all probes
  raising → exit 1; (3) a 403 response → exit 1; (4) a disappearing file in the
  data dir → no traceback.

## Called with an empty list

`cmd_doctor(args)` (`cli.py:204`) takes an `argparse.Namespace` and **never
reads it** — `args` is unreferenced in the entire body. There is no list
parameter and no way to supply one. The two check sets are hardcoded literals:
the credential tuple at `cli.py:210` and the endpoint tuple at `cli.py:233-237`.
So the function cannot currently be called with an empty list, and that is
itself the finding: **the check set is not injectable.**

Two concrete consequences:

1. **Latent silent pass.** The obvious fix for S2-2 (externalise the endpoint
   list) walks straight into a guard that does not exist. If that tuple is ever
   driven from config and the config is missing or empty, the `for` body at
   `cli.py:238-243` never executes, nothing is printed under the
   `connectivity (5s timeout each):` header, `ok` stays `True`, and the command
   exits **0 having checked nothing**. There is no `if not targets:` guard. Any
   fix that makes the list dynamic must add one.
2. **The real "empty" case that ships today.** A `data/` directory that exists
   but contains no `*.csv` — the normal state of any fresh CI checkout, since
   `data/` is gitignored (`.gitignore:10`) and absent from the repo. The
   directory-present branch at `cli.py:217-220` prints `  OK   data exists`,
   the glob yields nothing, and the loop body never runs. **No line is printed
   to say zero files were found.** An empty data directory prints the same `OK`
   as a directory holding five populated CSVs. The directory-*missing* branch at
   `cli.py:222` has an explanatory message; the directory-*empty* case has none.

## Ranking: silent failures by how long a human takes to notice

Ordered worst-first. The inversion at the bottom is the real finding: the failures
that destroy the most data take the longest to notice, and the failures that are
noticed instantly are the harmless ones.

| # | Silent failure | Where | Detection time | Why |
|---|---|---|---|---|
| 1 | **Google key revoked/disabled.** Entire Saudi market → 0 records. | S1-2, S1-4 | **Weeks–months** | Google is the *only* KSA source (`osm.py:13`, `wikidata.py:27` are Lebanon-only). Cumulative master keeps `ROWS > 100` (`scrape.yml:80`), so CI passes. Noticed when someone opens the KSA sheet or a customer says "you had nothing in Riyadh". |
| 2 | **Overpass slots exhausted.** Entire OSM source → 0 records. | S1-3 | **Weeks–months** | Same cumulative-master blindness. `overpass-api.de` returns 429 daily; this is a *recurring* condition, not an edge case. |
| 3 | **Total network outage at run time.** All three sources → 0. | S1-1 | **Weeks–months** | Doctor already exited 0. `main.py:167-168` prints a per-source ERROR to stderr and continues; the run writes five CSVs and uploads. Row guard passes on the master. |
| 4 | **Wikidata outage.** | S1-5 | **Effectively never** | Per `docs/audits/027-whitelist-taxonomy.md:18-19`, the SPARQL query's label service never binds labels for URL/literal variables, so this source already yields almost nothing. A Wikidata outage is *observationally identical to normal operation*. A check that cannot detect a change that produces no visible change is not a check. |
| 5 | **Permanent false-OK from the probe/request mismatch.** Doctor can never validate the Wikidata JSON path or the Google POST path even in principle. | S2-2 | **Never** | Not a transient — a permanent blind spot that reports green forever. |
| 6 | **New proxy / captive portal.** All probes return 200 HTML or 407. | S1-1, S3-1 | **Hours–1 day, if only cron** | A manual `leadminer run` fails loudly and someone investigates within the hour. If only the cron egress path changed, nobody runs it by hand for weeks. |
| 7 | **Wrong cwd.** False `MISSING data (no run has produced output yet)`. | S2-6 | **Minutes if read; never if not** | Actively false prose, but visible in the transcript. Exit 0 means no monitor catches it. |
| 8 | **`f.stat()` traceback.** | S2-7 | **Immediate — and wrong** | Loud, but a crash rather than a finding, in the one function whose docstring promises it never tracebacks. Trains people to treat doctor output as noise. |
| 9 | **False `FAIL` on a slow public endpoint.** | S2-8 | **Immediate — and wrong** | The dangerous direction. Costs the operator nothing to ignore, so they will. |

## Not a bug, but worth knowing

- **Interrupt handling is correct.** `except Exception` at `cli.py:242` does not
  catch `KeyboardInterrupt` (a `BaseException`), so Ctrl-C propagates to
  `cli.py:316-318` and exits `130` with `\ninterrupted`. This is right, and it is
  the only signal-handling path in the function — there is no SIGTERM handler and
  no `finally`.
- **The `requests`-missing advice is correct.** `pyproject.toml:20-28` does define
  a `dev` extra, so `pip install -e '.[dev]'` at `cli.py:230` is a valid command.
  It is stylistically inconsistent with `README.md:80` (`uv pip install`) and
  with `scrape.yml:39` (`requirements.txt`), which means doctor cannot tell you
  which of the three install paths you are actually on.
- **The `ImportError` guard at `cli.py:226-231` is the right instinct** and the
  comment explaining it (`cli.py:228-229`) is exactly right — it is just not
  honoured by the unguarded `f.stat()` at `cli.py:220`.
- **`args` being ignored is currently harmless** because `build_parser`
  (`cli.py:301-302`) adds no options. It becomes a latent bug the moment anyone
  adds `--json` or `--timeout` and forgets to thread it through.
- **`WARN` is a warning nobody sees.** Even the one condition the function does
  classify as degraded — `status_code >= 500` at `cli.py:240` — leaves `ok` at
  `True` and exits 0. A warning that does not change the exit code is decoration.

## Recommended order of work

1. **Make connectivity affect the exit code** (`cli.py:238-244`). One-line
   change, removes failure modes #1, #3, #6. Everything below is worthless until
   the command can fail.
2. **Probe the real requests.** Replace the three literals at `cli.py:233-237`
   with the scrapers' own endpoints, methods, and headers — `POST` + `X-Goog-Api-Key`
   for Places (`cli.py:236`), `format=json` + `Accept` for Wikidata
   (`cli.py:235`). Import them from `scrapers.*` so they cannot drift.
