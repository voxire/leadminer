# 207 — `_fmt` (cli.py:29): the run's only diagnostic, structurally unable to report a regression

## Verdict

`_fmt` itself is four characters of correct code and has **no bug of its own** — for the
`int` it is actually given it always prints the right string. The S1 is the contract around
it: the `"n/a"` branch at `cli.py:30` is **unreachable dead code**, because all six callers
feed it `sum(...)` via `count()` (`cli.py:96`), which has already coerced the real
missing-data sentinel (an absent or blank CSV cell) to `0`. So the one case `_fmt` was
written to handle never fires, and the one case it cannot express — *"this column isn't in
your file"* — prints as a confident business claim (*"zero leads have Instagram"*).

Compounding it: `cmd_stats` prints only **absolute** counts over a **cumulative** all-time
master (`main.py:150`), so a 100% failure of the current run leaves every number `_fmt`
prints completely unchanged, and `cmd_stats` returns `0` (`cli.py:132`). Ranked by how long
before a human notices: **a total run failure is invisible, indefinitely.**

## Answers to the specific questions asked

**What does it print?** `f"{n:,}{suffix}"` — thousands separators, no rounding, no width,
no alignment. `_fmt(1234567)` → `'1,234,567'`. It never prints; it returns a `str`, and all
six call sites paste the result into an f-string (`cli.py:98-103`).

**What does it swallow?** Four things silently, verified against the live interpreter
(Python 3.14.8; identical on the project's 3.12):

| Input | Result | Silent? |
|---|---|---|
| `True` / `False` | `'1'` / `'0'` | **yes** — a bool silently becomes a count |
| `float('nan')` | `'nan'` | **yes** |
| `float('-inf')` | `'-inf'` | **yes** |
| `1234.5678` | `'1,234.5678'` | **yes** — 16 sig digits, no rounding |
| `Fraction(1,3)` | `'1/3'` | **yes** |
| `Decimal('1234.5')` | `'1,234.5'` | **yes** |
| `10**30` | a 32-character line | **yes** — wraps a stats block |

None of these are reachable from `cmd_stats` today, because `count()` returns `int`. They are
**latent**, not live — but the annotation `int | float | None` at `cli.py:29` invites the
float case, so the next caller to pass a ratio gets unrounded precision with no warning.

**Empty list?** `_fmt([])` **raises** `TypeError: unsupported format string passed to
list.__format__`. Same for `()`, `{}`, `set()`. Loud and correct — a caller who writes
`_fmt(records)` instead of `_fmt(len(records))` gets a traceback, not a wrong number.

**Dependency returns garbage (a `str`)?** `_fmt("1,234")` **raises**
`ValueError: Cannot specify ',' with 's'.` Also loud. `cmd_stats` has no `try/except`
(`cli.py:86-131`) and `main()` catches only `KeyboardInterrupt` (`cli.py:314-318`), so it
surfaces as a full traceback.

**Network drops halfway?** `_fmt` is pure and cannot be affected. The exposure is one level
up: its input is a file on disk written by the run that just died. `write_csv` is properly
atomic — temp file, `flush`, `os.fsync`, `os.replace` (`main.py:108-133`) — so the master
is not truncated by a mid-write crash. `data/` is also rclone-synced to and from Drive
(`scrape.yml:50-51`, `scrape.yml:85-89`), and **nothing in `cmd_stats` verifies the column
set** before printing. That is the bridge to S1-01.

**Interrupted?** `_fmt` is atomic — no partial string. But the block it feeds is 12 bare
`print()` calls with no `try/finally`, no explicit `flush`, and **no terminator line**
(`cli.py:93-131`). At the workflow's `timeout-minutes: 300` (`scrape.yml:25`) the runner
sends SIGTERM; Python's default handler kills the process outright. `main()`'s
`except KeyboardInterrupt` (`cli.py:316-318`) **does not catch SIGTERM** — nothing in the
repo installs a signal handler (grep for `signal|SIGTERM|atexit` across `*.py`: zero hits).
So the operator gets exit 143 and a stats block that stops mid-report and looks finished.

**The uncomfortable asymmetry.** `_fmt` is **stricter at runtime than its type hint** (it
raises on `str`/`list`/`bytes`, all excluded by the annotation) and **looser about missing
data than the annotation implies** (it accepts `bool`/`nan` at runtime, and it never sees
the `None` it was written for). That inversion is the root cause of S1-01.

## Findings

### S1 — `"0"` is emitted for an absent column, inventing a business fact
- **Where:** `cli.py:29-30` (dead `None` branch), `cli.py:96` (`count` coerces), `cli.py:98-103` (print sites)
- **Breaks:** `count()` is `sum(1 for r in rows if (r.get(field) or "").strip())`. A missing key and a blank cell both yield `""` → `0`. `_fmt` then renders `'0'`. The output asserts *"0 of our leads have Instagram"* — a confident, plausible, entirely fabricated business claim — rather than *"this column is not in your file."*
- **Trigger:** a CSV written by an older version without the `instagram` column. Verified:
  `"instagram" in rows[0]` → `False`, and `_fmt(count('instagram'))` → `'0'`, `_fmt(count('email'))` → `'0'`. Same for a `utf-8`-vs-`utf-8-sig` header mismatch that shifts every column name.
- **Notice time:** **indefinitely.** A count drifting toward zero is a normal sales
  narrative; nobody opens a ticket for it.
- **Fix:** make the sentinel explicit — have `count()` return `None` when the field is
  absent from `rows[0]`, so the existing `n/a` branch finally fires; and have `cmd_stats`
  exit non-zero if any tracked field is absent.

### S1 — Absolute counts over a cumulative master cannot show a per-run regression
- **Where:** `cli.py:98-103`, `cli.py:132`, `main.py:150`, `main.py:108-133`
- **Breaks:** `all_businesses.csv` is all-time (`main.py:150` loads and accumulates into it). If all three scrapers return zero, or `GOOGLE_PLACES_API_KEY` is revoked, or `check_websites` fails 100%, last month's rows are still in the file — so every number `_fmt` prints is **byte-identical to last week's**, and `cmd_stats` returns `0`.
- **Trigger:** revoke the API key, run the cron. Master still holds 50,000 rows; the workflow's only gate is `ROWS < 100` on a **cumulative** count (`scrape.yml:78-83`), so it passes and the run publishes.
- **Notice time:** **months, or never** — it takes a human to realize `with email: 1,204` is the number from March.
- **Fix:** report deltas, not absolutes — `_fmt` should format `new_rows = len(after) - len(before)` alongside the absolute, and the gate must compare per-run row counts, not cumulative ones.

### S2 — No timestamp, run id, or log level anywhere in the output
- **Where:** `cli.py:20-24` (imports are `argparse`, `collections`, `csv`, `pathlib`, `sys` — no `logging`), `cli.py:93-131`
- **Breaks:** every line is a bare `print()` to stdout. In a weekly cron log there is no way to tell whether `with phone : 1,204` was written now or six hours into a run, and no run id to correlate two `stats` invocations against a specific pipeline run. (`httpclient.py:35`, `scrapers/osm.py:1`, `scrapers/wikidata.py:1` already use `logging`; `cli.py` did not follow.)
- **Fix:** `logging.info("with phone=%d", count("phone"))` with a run-id prefix, or at minimum stamp one header line with UTC ISO-8601.

### S2 — Partial output is indistinguishable from complete output
- **Where:** `cli.py:93-131` (12 bare `print`s, no `finally`, no terminator), `cli.py:314-318` (`except KeyboardInterrupt` only), `scrape.yml:25` (`timeout-minutes: 300`)
- **Breaks:** SIGTERM is not caught, so the `"\ninterrupted"` line at `cli.py:317` is dead for the cron path. A run killed at minute 299 prints, say, eight of twelve lines and exits 143. Eight correct-looking lines read as a finished report.
- **Fix:** install `signal.signal(signal.SIGTERM, ...)` raising `KeyboardInterrupt` in `main()`, and print a final `"--- stats complete: {path} ---"` line inside a `try/finally`.

### S2 — No nonzero exit when the data is obviously wrong
- **Where:** `cli.py:132` (`return 0` unconditionally), `cli.py:88-90` (only catches a fully empty file)
- **Breaks:** a CSV with a header and five rows of pure garbage yields five rows, every count `0`, a perfectly formatted report, and **exit 0**. There is no threshold, no comparison, and no alarm path — `_fmt` returns a `str`, so even the output is not machine-comparable.
- **Fix:** return `1` if any count that should be non-zero is zero, or if the column set is incomplete.

### S2 — `cmd_validate` exists but is not wired into the cron
- **Where:** `cli.py:135-201`; `scrape.yml:65-69` runs `python main.py`; grep for `cli.py|leadminer|validate|stats|doctor` in `scrape.yml` returns **no matches**
- **Breaks:** the entire `cli.py` surface — `_fmt`, `cmd_stats`, `cmd_validate`, `cmd_doctor` — is human-invoked only. The automated quality gate that exists in the repo never runs in production, which is why every failure above is silent rather than merely unnoticed.
- **Fix:** add `python cli.py validate` to the "Validate output before publishing" step (`scrape.yml:71-83`) after the row-count check.

### S3 — `suffix` is dead, and the `None` branch is dead
- **Where:** `cli.py:29`; all six call sites pass exactly one argument (`cli.py:98-103`)
- **Breaks:** the `None` → `"n/a"` path can never execute (see S1-01), and `suffix` has no caller. Both give a false impression of input validation while `_fmt` performs none.
- **Fix:** delete `suffix`; once S1-01 is fixed, the `None` branch earns its keep.

### S3 — Two formats for the same number
- **Where:** `main.py:134` (`print(f"  Written: {path} ({len(records)} records)")`), `cli.py:93`
- **Breaks:** the production log writes `500000 records`; the stats block writes `500,000 rows`. Same quantity, two renderings, so a human eyeballing the two has to strip separators to compare them.
- **Fix:** use `_fmt` in `main.py:134`.

## Not a bug, but worth knowing

- `write_csv` is genuinely well built — temp file, `flush`, `os.fsync`, `os.replace`, plus
  `except BaseException` cleanup (`main.py:108-133`). The truncated-CSV scenario I was asked
  to consider does **not** arise from a mid-write crash on the export path.
- `_fmt`'s runtime strictness on `str`/`list`/`bytes` is accidental but valuable. Don't add
  a broad `except` around its call sites; that would convert today's loud traceback into
  exactly the silent `"0"` this report is about.
- Because `_fmt` returns `str`, any future alerting rule ("alert if `_fmt(x) == '0'`")
  compares text, not numbers. If stats output ever needs to be parsed, return the number
  and format at the print site.

## Recommended order of work

1. **S1-01** — make `count()` return `None` for an absent column so the existing `n/a`
   branch fires, and fail the command when a tracked column is missing.
2. **S1-02** — add per-run deltas to `cmd_stats`; the cumulative absolute is not a
   regression detector. Change the `scrape.yml:80` gate to a per-run row count.
3. **S2-04** — wire `python cli.py validate` into `scrape.yml:71-83` so the repo's own
   quality gate runs unattended. This is the cheapest single change on this list and it
   subsumes most of S1-01's operational cost.
4. **S2-03** — SIGTERM handler + `try/finally` terminator line, so a killed run cannot look
   like a complete one.
5. **S2-02** — `logging` with a UTC timestamp and run id.
6. **S2-05** — nonzero exit on obviously-wrong stats.
7. **S3** — delete `suffix`, use `_fmt` in `main.py:134`.
