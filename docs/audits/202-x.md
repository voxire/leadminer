# 202 — `_fmt` (`cli.py:29`): the one helper with zero coverage, two unreachable branches, and a neighbouring report that contradicts itself

## Verdict

`_fmt` is three characters long and is *correct*, but it has **no direct test**, and no
indirect test exercises the only behaviour it adds beyond `str()` — the `,` grouping
separator. Deleting `:,` from `cli.py:30` would leave all 22 tests in
`tests/test_lead_signal.py` green. Worse, its two distinguishing features (`None` →
`"n/a"`, and `suffix`) are **unreachable from all six call sites**, because the only
thing that ever feeds it is `count()` at `cli.py:95-96`, which returns `int` and coerces
a missing CSV column to `0` before `_fmt` sees it. So the "missing column" case the
helper was written for prints a confident `0`. And the six numbers `_fmt` formats are
computed over a **different row population** than the five printed immediately below them
(`cli.py:107-113`), so `leadminer stats` prints `with website : 3` next to
`website live : 2 / website dead : 2 / unreachable : 1` — which sums to 5.

---

## The function and its complete call graph

```python
# cli.py:29-30
def _fmt(n: int | float | None, suffix: str = "") -> str:
    return "n/a" if n is None else f"{n:,}{suffix}"
```

Every call site in the repository — there are exactly six, all inside `cmd_stats`:

| Call site | Argument expression | Static type |
|---|---|---|
| `cli.py:98` | `_fmt(count('phone'))` | `int` |
| `cli.py:99` | `_fmt(count('email'))` | `int` |
| `cli.py:100` | `_fmt(count('website'))` | `int` |
| `cli.py:101` | `_fmt(count('instagram'))` | `int` |
| `cli.py:102` | `_fmt(count('whatsapp'))` | `int` |
| `cli.py:103` | `_fmt(count('region'))` | `int` |

The producer, `cli.py:95-96`:

```python
def count(field: str) -> int:
    return sum(1 for r in rows if (r.get(field) or "").strip())
```

`sum()` over a generator of `1`s is always a non-negative `int`. Consequences:

- **The `None` branch (`cli.py:30`, `"n/a"`) can never execute from any code path in the
  repo.** A grep for `_fmt` returns only `cli.py:29-30` and `cli.py:98-103`.
- **The `suffix` parameter is never passed by anyone.** Default `""` at all six sites.
- **The `float` arm of the annotation is never exercised.** `count()` cannot return a float.

Verified behaviour across the whole input space (executed, not reasoned):

```
0 -> '0'        999 -> '999'       1000 -> '1,000'      1000000 -> '1,000,000'
-1 -> '-1'      -1234567 -> '-1,234,567'
0.5 -> '0.5'    1234.5 -> '1,234.5'
None -> 'n/a'
None, ' bytes' -> 'n/a'        # <-- suffix silently DROPPED
0, ' bytes' -> '0 bytes'
True -> '1'     False -> '0'   # bool is an int subclass
'5' -> RAISES ValueError: Cannot specify ',' with 's'.
```

## Findings

### S1 — `cmd_stats` prints `with website` and its `live`/`dead`/`unreachable` siblings over different row populations, so the report contradicts itself

- **Where:** `cli.py:100` (via `_fmt`) vs `cli.py:107-110`
- **Breaks:** `_fmt(count('website'))` at `cli.py:100` counts rows with a non-blank
  `website`. `live` (`cli.py:107`) and `dead` (`cli.py:108`) count rows whose
  `website_live` cell is the literal string `"True"`/`"False"` — **with no `website`
  guard at all**. Only `unknown` (`cli.py:109-110`) is guarded by `r.get("website")`.
  So the three buckets do not partition the `with website` set, and
  `live + dead + unreachable ≠ with website`. An operator sizing the "how many broken
  sites do we have to pitch" number reads two contradictory figures from the same screen.
- **Why this is reachable and not theoretical:** `_merge` is per-field survivorship
  (`dedup.py`, and pinned by `tests/test_lead_signal.py:278-284`), so a record can
  legitimately lose its `website` URL while retaining a stale `website_live=False` from an
  earlier run — that is exactly the merge semantics the current suite mandates.
  `main.py:103` also coerces every non-canonical liveness cell to `None`, so drift between
  the URL and the flag is a routine steady state, not a corner case.
- **Trigger (executed; 6-row fixture, exit code 0):**

  | row | `website` | `website_live` |
  |---|---|---|
  | 1 | `https://a.example` | `True` |
  | 2 | `https://b.example` | `False` |
  | 3 | `https://c.example` | *(blank)* |
  | 4 | *(blank)* | `False` |
  | 5 | *(blank)* | `True` |
  | 6 | *(blank)* | *(blank)* |

  Literal output:

  ```
    with website    : 3
    website live    : 2
    website dead    : 2
    unreachable     : 1  (not the same as dead)
  ```

  Rows 4 and 5 have **no website** yet are counted as live and dead. `2 + 2 + 1 = 5 ≠ 3`.
- **Fix:** gate all three buckets on `r.get("website")`, or derive them from a single
  partitioned comprehension so the invariant is structural:

  ```python
  with_site = [r for r in rows if (r.get("website") or "").strip()]
  live = sum(1 for r in with_site if (r.get("website_live") or "").strip() == "True")
  dead = sum(1 for r in with_site if (r.get("website_live") or "").strip() == "False")
  unknown = len(with_site) - live - dead
  ```

### S1 — a non-canonical `website_live` cell makes a row vanish from all three buckets

- **Where:** `cli.py:107-110`
- **Breaks:** `"true"`, `"TRUE"`, `"1"`, `"0"`, `"yes"` satisfy none of the three
  predicates. `unknown` requires a *blank* cell, so the row is counted nowhere. The
  report simultaneously asserts `with website : 2` and `live 0 / dead 0 / unreachable 0`.
  This is the exact inverse of the regression the code comments about at `cli.py:105-106`
  ("Collapsing blank into False was the original bug"): values are now collapsing into
  *no bucket at all* instead of the wrong one.
- **Why reachable:** audits `021-csv-roundtrip-fidelity.md:41` and
  `028-csv-roundtrip-fidelity.md:109` both document that Excel and Google Sheets
  re-export booleans in forms other than the literal `"True"`/`"False"` the code matches,
  and `043-scoring-upgrade.md` / `049-data-dictionary.md:196-202` flag the tri-state
  serialisation as the project's most fragile contract. These CSVs are handed to sales
  reps and come back edited.
- **Trigger (executed; 2-row fixture, exit code 0):**

  | row | `website` | `website_live` |
  |---|---|---|
  | 1 | `https://a.example` | `true` |
  | 2 | `https://b.example` | `TRUE` |

  Literal output:

  ```
    with website    : 2
    website live    : 0
    website dead    : 0
    unreachable     : 0  (not the same as dead)
  ```

  `2` websites exist; `0` rows are classified. Silent, and the gate exits 0.
- **Fix:** normalise once, case- and alias-insensitively, before comparing:
  `wl = (r.get("website_live") or "").strip().lower()` and match
  `{"true","1","yes"}` / `{"false","0","no"}`. Fix `main.py:103` in the same change so
  `load_master` and `cmd_stats` cannot disagree.

### S2 — the `,` grouping separator is protected by no test in the entire suite

- **Where:** `cli.py:30`
- **Breaks:** `_fmt`'s only reason to exist is `f"{n:,}"`. There is no test that asserts a
  grouped number. `tests/test_lead_signal.py:211-226` (`test_stats_handles_tri_state_website_live`)
  is the only test that reaches `_fmt`, and its `_fixture` (`tests/test_lead_signal.py:195-209`)
  writes exactly **one** row, so every `_fmt` call returns a single digit
  (`'0'`/`'1'`). `tests/test_lead_signal.py:225` asserts `"website live    : 1"`, and that
  line is printed by `{live:,}` at `cli.py:111` — which does not go through `_fmt` at all.
  Rewriting `cli.py:30` as `return "n/a" if n is None else f"{n}{suffix}"` passes all
  22 tests.
- **Why it matters:** at the real corpus scale — `065-python-312-modernisation.md:87`
  projects 20,000–50,000+ businesses — grouping is the only thing that makes a six-digit
  count readable at a glance in a terminal or a GitHub Actions log.
- **Trigger:** delete `,` from `cli.py:30`. `python3 -m unittest discover -s tests` → 22/22
  still pass.
- **Fix:** the three property tests in group A below.

### S2 — mixed number formats inside one 12-line report

- **Where:** `cli.py:98-103` (grouped) vs `cli.py:93`, `cli.py:111-113`, `cli.py:117`,
  `cli.py:121`, `cli.py:126`, `cli.py:131`, `cli.py:194`, `cli.py:220`, `cli.py:276`
  (all bare `:,` or unformatted)
- **Breaks:** a 12,345-row master prints `with phone : 8,230` immediately above
  `website live : 3,087` and `high 12,345`. Two magnitudes on the same screen, two
  different notations, no shared column alignment. Half the numbers in `stats` go through
  the project's one formatting helper and half bypass it.
- **Trigger (executed; 12,345-row synthetic master, exit code 0):**

  ```
  /var/.../big.csv  (12,345 rows)

    with phone      : 8,230      <-- _fmt
    with email      : 0          <-- _fmt
    with website    : 6,172      <-- _fmt
    with instagram  : 0          <-- _fmt
    with whatsapp   : 0          <-- _fmt
    with region     : 12,345     <-- _fmt

    website live    : 3,087      <-- bare {live:,}
    website dead    : 3,086      <-- bare {dead:,}
    unreachable     : 3,086      <-- bare {unknown:,}

    by priority:
      high       12,345         <-- bare {v:,}
  ```
- **Fix:** route all eleven numbers through `_fmt`, or delete `_fmt` and use `:,`
  everywhere. Do not keep both. The tests in group B lock the decision either way.

### S3 — `_fmt`'s `"n/a"` branch is wired one layer too low; a missing column prints a confident `0`

- **Where:** `cli.py:29-30` vs `cli.py:95-96`
- **Breaks:** `"n/a"` exists to distinguish "no value" from "zero". But `count()` already
  collapsed the distinction: `r.get('region')` returns `None` for a CSV that has no
  `region` column at all, `None or ""` makes it `""`, `"".strip()` is falsy, and the sum
  is `0`. `cmd_stats` reads raw `csv.DictReader` (`cli.py:86-87`), it does **not** go
  through `load_master` (`main.py:77-105`), and `write_csv` writes `extrasaction="ignore"`
  (`main.py:125`) against a fixed 22-column `fieldnames` list. So a master produced by an
  older schema — or one handed over by a client — silently reports "no business has a
  region", which is a false statement about the pipeline, not about the data.
- **Trigger (executed; 3 rows, header written without the `region` column, exit code 0):**

  ```
  /var/.../f.csv  (3 rows)

    with phone      : 0
    ...
    with region     : 0        <-- indistinguishable from "3 rows, all blank region"
  ```
- **Fix:** check column presence *before* counting and let `_fmt` earn its `None` branch:

  ```python
  def count(field: str) -> int | None:
      if not rows or field not in rows[0]:
          return None            # -> _fmt prints "n/a"
      return sum(1 for r in rows if (r.get(field) or "").strip())
  ```
  This is the only change that makes `"n/a"` reachable, and it makes the two dead
  branches of `_fmt` live code with a test target.

### S3 — `_fmt(None, suffix)` silently drops the suffix; the two branches are asymmetric

- **Where:** `cli.py:30`
- **Breaks:** `_fmt(None, " bytes")` → `'n/a'`, not `'n/a bytes'`. A caller that adopts
  the natural idiom gets a unit-less value. Unreachable today only because nobody passes
  a suffix — which is the point: the parameter is untested, unexercised, and wrong.
- **Fix:** `return f"n/a{suffix}" if n is None else f"{n:,}{suffix}"`, or delete the
  parameter (see *Not a bug, but worth knowing*).

## What genuinely cannot be tested here, and why

1. **The `"n/a"` branch cannot be reached by any test that calls a real command.** No
   code path in the repo produces `None` at a `_fmt` call site — `count()` is
   `sum(1 for ...)`, an `int` by construction. Until `count()` is changed to return
   `int | None` (S3 fix), A3 is a direct unit test of an unreachable branch and nothing
   more. There is no integration test for it; there cannot be one.
2. **The `suffix` parameter has no caller, so no integration test can pin it.** A4 is the
   only kind of test available: a direct characterisation of a dead parameter. Whether
   `"n/a"` or `"n/a bytes"` is *correct* is a product decision about future CLI flags
   (`037-cli-design.md:395` proposes `--format json|markdown`), not a property of the code.
3. **Whether `"n/a"` is the right sentinel for an operator is not a code property.** It is
   a UX/HUD decision — `"n/a"` is fine for a human, wrong for a `--format json` consumer
   (`037-cli-design.md:162`, `396`). No assertion can decide it; a product decision must,
   and then a test should pin whatever is chosen.
4. **Locale behaviour needs no test and cannot fail.** Python's `,` format spec is
   locale-independent — unlike `%d`, it never consults `locale.setlocale`. A
   "French operator sees `1 000`" test would assert something that cannot happen. Worth
   stating explicitly so nobody writes it.
5. **Whether the counts are *true* is not testable from the CLI.** `cmd_stats` reports what
   the CSV says. It cannot verify that `phone` is a real phone number or that `region` is
   the correct governorate — that is `cmd_validate` (`cli.py:135-201`) and the
   enricher's job. A `_fmt` test that "checks correctness" of the underlying data is
   testing the wrong layer.
6. **Thread-safety and I/O are not applicable.** `_fmt` is pure: no I/O, no clock, no
   randomness, no shared state. Every property in group A is deterministic and needs no
   fixtures. There is no concurrency or mocking to be done here, and the `requests`
   stubbing at `tests/test_lead_signal.py:23-63` is irrelevant to these tests.

## Not a bug, but worth knowing

- **`_fmt` is dead-weight as written and should probably not exist.** Two of its three
  features — the `None` sentinel and the `suffix` — have zero callers. Either wire the
  sentinel up properly (the S3 `count()` fix, which makes it genuinely useful and makes
  group B3 writable) and delete `suffix`, or delete `_fmt` and use `:,` inline at all
  eleven sites. A helper with two unreachable branches and one caller shape is a net
  liability: it looks like an abstraction but pins nothing.
- **`_fmt` was born in the same commit as the CLI and has never had a bug.** `git log -S"_fmt" -- cli.py`
  returns exactly one commit, `43ddb2c "feat: add pyproject packaging and a real CLI"`.
  There is no "original bug" it fixed. Every past bug referenced above belongs to the
  *data* it formats, not to the formatter — which is precisely why it has drifted
  unguarded.
- **`cmd_scrape` does not use `_fmt` at all.** `cli.py:71-72` prints raw counts
  (`print(f"  with phone : {with_phone}")`) while `cmd_stats` formats the identical
  concept at `cli.py:98`. Same word, two formats, two commands. Out of `_fmt`'s blast
  radius but the same root cause as S2, and B5 should be extended to `cmd_scrape` when
  that command gains a test.
- **`cmd_validate` does check for a missing BOM** (`cli.py:154-156`) but neither
  `cmd_stats` nor `cmd_validate` checks for a *missing column*. `cmd_validate` reads
  `r["lat"]`/`r["lon"]` under a `KeyError` guard (`cli.py:167-168`) and silently
  `continue`s, so a master with no coordinate columns passes the gate with zero
  coordinate findings. Same class as S3, different command.
- **`BRIEF.md:11` says "Zero tests" and is now stale.** `tests/test_lead_signal.py`
  holds 22 tests. Not a code defect, but the brief is the first document every new agent
  reads and it currently understates the safety net.
- **087 already scoped the CLI gap without closing it.** `087-SYNTH-test-gap.md:19` lists
  `TestCli` at 4 tests with omitted scope "`cmd_run`, `cmd_scrape`, `cmd_score`,
  `cmd_doctor`, anomaly detection, duplicate thresholds" — it never proposes a `_fmt`
  test or a `cmd_stats` output-shape test. This report fills that specific hole.
