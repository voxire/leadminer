# 237 — cmd_validate cost model: O(n) time, O(n) memory, 1.9 KB/row

## Verdict

`cmd_validate` is **O(n) time and O(n) memory in the number of businesses — there is
no quadratic term anywhere**, and I looked hard for one. What it *does* have is a
pathological constant: `list(csv.DictReader(f))` at `cli.py:143` materialises the
whole master as 23-key dicts, costing **~1.9 KB of RSS per row** — 960 MB peak for
a 500k-row / 128 MB CSV, and **77% of the function's runtime**. The single change
with the largest speedup is to replace the materialised `DictReader` list with one
streaming `csv.reader` pass that indexes only the 5 columns the checks read:
**1.8× faster and 11× less memory** (4.87 s → 2.64 s, 962 MB → 85 MB at 500k).

---

## Complexity verdict, with proof

Measured on `cli.cmd_validate` itself, against synthetic CSVs shaped exactly like
`main.FIELDS` (`main.py:33-40`, 23 fields — note `BRIEF.md:57-62` says "22
columns"; it is 23), page cache warmed, min-of-7 CPU seconds, Python 3.14.8:

| rows | file on disk | CPU (current) | peak RSS | CPU (streaming rewrite) | peak RSS |
|------:|-------------:|--------------:|---------:|------------------------:|---------:|
| 10,000 | 2.5 MB | **0.084 s** | 35 MB | 0.051 s | 19 MB |
| 100,000 | 25.5 MB | **0.864 s** | 206 MB | 0.515 s | 30 MB |
| 500,000 | 128.2 MB | **4.87 s** | **960 MB** | 2.64 s | 85 MB |

Memory is exactly linear: delta-RSS per row was **1.91 KB / 1.91 KB / 1.89 KB** at
10k / 100k / 500k. 500k × 1.9 KB ≈ 950 MB for a 128 MB file — a **7.5× blowup**.

Time is linear too, proven by the ratio test rather than assertion:

```
n=10,000   0.077s    7.65 us/row
n=100,000  0.877s    8.77 us/row
n=500,000  4.746s    9.49 us/row

time ratio 500k/10k = 62.0x     (n ratio 50x; O(n^2) would be 2500x)
time ratio 500k/100k = 5.41x    (n ratio 5x)
```

The per-row cost drifts up 7.65 → 9.49 µs (+24%). That is **not** algorithmic — it
is TLB/cache pressure from walking a ~950 MB list-of-dicts four separate times. The
streaming rewrite holds per-row cost flat at **5.10 → 5.28 µs/row (+3.5%)** over the
same 50× range, which is what a genuinely linear function looks like.

### Where I looked for a quadratic, and what I found

Every candidate was measured directly; all are linear.

- **`cli.py:190`** `{(r.get("name"), r.get("phone")) for r in rows}` — the only
  structure that grows with n. 500k distinct keys: **0.87 s**. 500k rows collapsing
  to 7 unique keys: **0.32 s**. 500k distinct keys with ~200-char names: **0.94 s**.
  All linear. `str.__hash__` is O(len) once per string and cached in the object
  header; CPython SipHash-randomises str/bytes so adversarial collisions are not
  constructible from CSV input; set insert is amortised O(1).
- **`r.get("name")` on a 23-key dict** (`cli.py:151,154,190`) — O(1) dict probe.
- **The two `for` loops** (`cli.py:165`, `cli.py:176`) — single pass, no nested loop.
- **`in_box()`** (`cli.py:159-162`) — two chained comparisons, called once per row.
- **Packing `(name, phone)` into one `"name\0phone"` string** — I expected a win and
  measured **0.871 s vs 0.870 s**: none. Skip it.

### Cost attribution at 500k (4.87 s total)

| what | where | CPU | share |
|---|---|---:|---:|
| `list(csv.DictReader(f))` | `cli.py:142-143` | 3.75 s | **77%** |
| &nbsp;&nbsp;…of which a bare `csv.reader` pass costs | — | 2.09 s | 43% |
| &nbsp;&nbsp;…so `DictReader`'s 23-key dict + `zip` overhead is | — | ~1.66 s | **34%** |
| dup `(name, phone)` set build | `cli.py:190` | 0.40 s | 8% |
| coordinate box scan | `cli.py:164-171` | 0.25 s | 5% |
| rating range scan | `cli.py:175-186` | 0.20 s | 4% |
| BOM name scan | `cli.py:154` | 0.12 s | 2% |
| `any(name)` — correctly short-circuits | `cli.py:151` | 0.000 s | 0% |

The parse floor is 2.09 s. **Every check `cmd_validate` performs costs 0.4 s
combined.** The function is a CSV parser wearing a validator's clothes.

## Findings

### S1 — `list(csv.DictReader)` at `cli.py:143` makes a 128 MB gate a ~1 GB process

- **Where:** `cli.py:142-143`
  ```python
  with open(path, newline="", encoding="utf-8-sig") as f:
      rows = list(csv.DictReader(f))
  ```
- **Breaks:** peak RSS is **960 MB at 500k rows** (946 MB delta over interpreter
  baseline) — 1.9 KB per row for 23 fields the validator never looks at. Five of the
  23 columns are read; the other 18 are built, boxed and kept alive. On GitHub's
  `ubuntu-latest` (7 GB, and `.github/workflows/scrape.yml` already holds the full
  `records` list in memory during a run) this survives, but on any 512 MB–1 GB
  container, dev laptop with a browser open, or CI job with a 1 GB limit,
  `leadminer validate` is the command that gets OOM-killed. `README.md:14` and the
  module docstring at `cli.py:10` both sell `validate` as the safe, always-runnable
  diagnostic — "Cheap data-quality gate" (`cli.py:136`). At 500k it costs 3.6 GB
  more than the file it is reading. This is the failure mode that matters: the
  diagnostic dies on the data it is supposed to be diagnosing.
- **Trigger:** `leadminer validate data/all_businesses.csv` with 500,000 rows.
  Measured peak RSS 962 MB, 4.87 s CPU.
- **Fix:** iterate the file once instead of materialising it — see the patch sketch
  below. 962 MB → 85 MB.

### S1 — the coordinate loop pays a raised exception per blank field, and silently passes when the column is missing

- **Where:** `cli.py:165-171`
  ```python
  for r in rows:
      try:
          lat, lon = float(r["lat"]), float(r["lon"])
      except (ValueError, TypeError, KeyError):
          continue
  ```
- **Breaks (cost):** `float("")` raises `ValueError`; `float(None)` raises
  `TypeError`; a missing column raises `KeyError`. CPython exception raise+catch is
  ~0.75 µs. Measured at 500k rows:
  ```
  coords, all rows have lat/lon                 0.582s
  coords, ALL rows blank lat/lon (raises)       0.856s
  coords, all blank, pre-checked (no raise)     0.089s   <- 9.6x faster
  ```
  This check has a **9.6× data-dependent cost multiplier**, in both directions. A
  master CSV where coords are mostly missing (OSM `ways` without a `center` per
  `scrapers/osm.py:68`, Wikidata rows without `coord` per `scrapers/wikidata.py:101`,
  Places rows without `location` per `scrapers/google_places.py:273`) pays up to
  2,000 exceptions per 1,000 rows. At 10% blanks that is a ~1.9× penalty on this loop
  alone.
- **Breaks (correctness, same lines):** if the CSV has **no `lat`/`lon` columns at
  all**, every row raises `KeyError`, `continue` swallows it, `bad_coords` stays `0`,
  and the gate prints **`all checks passed`** and exits **0**. The `KeyError` is in
  the `except` clause purely for this case, so the code was written expecting a
  missing column — and then treats a missing column as a clean bill of health.
- **Trigger (demonstrated):** a 50,000-row CSV with `lat`/`lon` removed from the
  header:
  ```
  a) 50k rows, NO lat/lon column -> rc=0 cpu=0.168s
     output: checked 50,000 rows in csvs/no_coords.csv | all checks passed
  ```
- **Fix:** distinguish "column absent" (report it, return 2) from "cell blank"
  (`if not raw_lat or not raw_lon: continue`, which skips the parse and the raise
  entirely) from "unparseable" (count it as `bad_coords` instead of `continue`).

### S2 — 1.8× available by not building 23-key dicts for the 18 columns `validate` never reads

- **Where:** `cli.py:143` (and the 4 post-passes at `cli.py:151,154,165,176,190`)
- **Breaks:** `csv.DictReader.__next__` does `dict(zip(self.fieldnames, row))`
  per row — 23 hash-free stores plus a 23-slot dict allocation. Measured in
  isolation at 500k:
  ```
  DictReader iterate, discard (23 cols)   3.127s
  list(DictReader)  <- cli.py:143         3.753s
  csv.reader iterate, discard             2.128s
  csv.reader, touch 5 cols                2.268s
  ```
  Touching the 5 columns the checks need costs only **0.14 s more than discarding
  every row**. The 18 unused columns cost 1.6 s.
- **End-to-end, all three sizes** (min CPU, page cache warm):

  | rows | A current | B streaming `DictReader` | C streaming `csv.reader` |
  |---:|---:|---:|---:|
  | 10,000 | 0.077 s / 36 MB | 0.073 s / 20 MB | **0.051 s / 19 MB** |
  | 100,000 | 0.865 s / 210 MB | 0.761 s / 42 MB | **0.555 s / 30 MB** |
  | 500,000 | 4.529 s / 965 MB | 3.786 s / 147 MB | **2.664 s / 85 MB** |

  Note B: dropping the `list()` **without** switching to `csv.reader` buys only
  1.20× time. The `DictReader`-vs-`reader` switch is the real lever (1.43× more),
  and it is only worth taking if you stop materialising anyway.
- **Trigger:** any master CSV. `data/all_businesses.csv` is the cumulative master
  (`BRIEF.md:51`) and grows without bound across runs.
- **Fix:** single streaming `csv.reader` pass, index into the header for
  `name/phone/lat/lon/rating` only.

### S3 — five separate passes over a ~950 MB list (`cli.py:151,154,165,176,190`)

- **Where:** `cli.py:151` (BOM/any), `:154` (BOM count), `:165` (coords), `:176`
  (rating), `:190` (dup set).
- **Breaks:** only ~19% of runtime combined (0.97 s of 4.87 s at 500k), so this is
  not a cost problem in isolation. It is a **memory-locality** problem: at 500k the
  list is ~950 MB, so each pass takes fresh TLB misses and page faults on data the
  previous pass already touched. That is precisely why per-row cost drifts 7.65 →
  9.49 µs in variant A while variant C stays flat at 5.10 → 5.28 µs. Collapsing to
  one pass removes the drift.
- **Fix:** fold all five checks into the single streaming loop.

### S3 — `cmd_stats` has the byte-identical pattern

- **Where:** `cli.py:86-87` (`list(csv.DictReader(f))`), then five `Counter` passes
  at `cli.py:98-130` and six full scans inside `count()` at `cli.py:95-96`.
- **Breaks:** same ~1.9 KB/row and same 960 MB at 500k, for a command that only ever
  prints aggregates. `README.md:13` and `cli.py:80` both present `stats` as the
  first thing to run when a run looks wrong. Fix it in the same commit with the same
  helper — the streaming reader is reusable by `cmd_validate`, `cmd_stats`, and
  `cmd_score`/`main.load_master` (`main.py:86-104`, which builds the *same*
  500k-row list, plus a per-row `list(row)` copy at `main.py:87`).
- **Trigger:** `leadminer stats data/all_businesses.csv` at 500k rows.
- **Fix:** one shared `_iter_rows(path)` generator in `cli.py`.

### S3 — no test exercises `cmd_validate` above one row, so a regression here is invisible

- **Where:** `tests/test_lead_signal.py:228-253`
- **Breaks:** the only `cmd_validate` tests build a **1-row** fixture via
  `_fixture()`. A regression to O(n²) — the obvious future edit, since a "dedupe
  against seen rows" loop over the materialised list is a natural thing to write —
  would pass CI. `test_validate_rejects_out_range_rating` and
  `test_validate_accepts_clean_data` cannot see scale at all.
- **Trigger:** any change to `cli.py:142-193`.
- **Fix:** one test that builds a 50k-row CSV and asserts the call completes, plus a
  timing-ratio assertion (`t(50k)/t(10k) < 12`) so quadratic growth fails CI.

## Not a bug, but worth knowing

- **`csv.reader` does NOT pad short rows; `DictReader` does.** A truncated final
  line (killed mid-write, exactly the failure `main.write_csv` guards against at
  `main.py:121-133`) yields a 1-field row from `csv.reader`:
  ```
  header width: 23   last row width: 1
  csv.reader last row has 1 fields; row[21] -> IndexError: list index out of range
  ```
  `DictReader` fills it with `None` (`restval`), which is why `cmd_validate` does not
  crash today — it raises `TypeError` and `continue`s. **Any rewrite using
  `csv.reader` must guard `i < len(row)`.** `cli.main` only catches
  `KeyboardInterrupt` (`cli.py:316`), so an `IndexError` here is an unhandled
  traceback.
- **The dup set is a memory cost, not a time cost.** On top of the 2.09 s parse
  floor it adds only **0.09 s (4%)** at 500k, but it retains the `name` and `phone`
  strings of every unique row — ~63 MB of the 67 MB variant C allocates. Since the
  check only fires above `total * 0.05` (`cli.py:191`), capping the set (stop adding
  once `len(seen) > cap`, with `cap` set from a first cheap `count` or a conservative
  constant) converts ~63 MB to ~0. It buys almost no time; do it for the memory, and
  do not expect it to show up in a benchmark.
- **Packing `(name, phone)` into a single string is not worth it.** Measured
  0.871 s (packed) vs 0.870 s (tuple) at 500k distinct keys. Two objects beat one
  longer string here because the strings are already alive.
- **`cli.py:151` is already correct.** `any()` short-circuits; it measured 0.000 s
  in every run, including the all-blank-names case where it must scan all n rows.
- **The absolute ceiling is architectural, not algorithmic.** `main.main()` holds
  the full `records` list in memory at `main.py:209` when it writes
  `all_businesses.csv`, then `leadminer validate` re-opens and re-parses that same
  file. Folding the validation into the write path would delete all 4.87 s. That is a
  `main.py` change and out of scope for this lens, but it is the only way to make the
  gate free.
- **No scale test exists anywhere.** `tests/` has one file,
  `tests/test_lead_signal.py`. Worth noting for whoever sequences the S1s.

## Recommended order of work

1. **Stream the file instead of materialising it** (`cli.py:142-193`). Replace
   `rows = list(csv.DictReader(f))` + five passes with one `csv.reader` loop that
   reads only `name`, `phone`, `lat`, `lon`, `rating`. Biggest single win:
   **1.8× time, 11× memory** (4.87 s → 2.64 s, 962 MB → 85 MB at 500k), and it makes
   per-row cost flat instead of drifting +24%. Sketch:

   ```python
   def _iter_rows(path: pathlib.Path):
       """Stream (row_list, column_index) pairs; never materialise the file."""
       with open(path, newline="", encoding="utf-8-sig") as f:
           reader = csv.reader(f)
           try:
               header = next(reader)
           except StopIteration:
               return None, iter(())
           idx = {name: i for i, name in enumerate(header)}
           yield reader, idx          # caller loops `for row in reader:`
   ```

   In `cmd_validate`, replace the `except (ValueError, TypeError, KeyError)` at
   `cli.py:168` with three separate branches: **missing column** → report and return
   2; **blank cell** → `if not raw_lat or not raw_lon: continue` (no parse, no raise,
   and this alone makes the check 9.6× cheaper on coord-poor data);
   **unparseable** → `bad_coords += 1`, not `continue`.

2. **Split "column absent" from "cell blank" at `cli.py:166-169`.** Right now a
   `lat`-less CSV exits 0 with `all checks passed`. Cheapest possible fix, and it
   removes the silent-pass from the same loop the perf fix touches.

3. **Apply the same streaming reader to `cmd_stats` (`cli.py:86-87`) and
   `main.load_master` (`main.py:86-104`).** Identical 1.9 KB/row cost; share one
   helper.

4. **Add a scale regression test** (`tests/test_lead_signal.py`, currently 1-row
   fixtures only). 50k rows + a `t(50k)/t(10k) < 12` timing assertion so the next
   quadratic rewrite fails CI instead of production.

## Measurement notes

Reproduce: `python3 -c "import cli; cli.main(['validate', 'big.csv'])"` under
`time.perf_counter`/`time.process_time` with `resource.getrusage(RUSAGE_SELF)
.ru_maxrss`. Synthetic CSVs were generated to match `main.FIELDS` exactly (23
columns, `utf-8-sig`, ~55% Lebanon box / 40% Saudi box / 2% blank coords / 2%
random-coord outliers per `cli.py:159-162`, 55-70 char `recommended_service`
strings, mixed Arabic in `name`/`address`, 128 MB at 500k).

All numbers are **CPU seconds, min-of-7, page cache warmed**. Wall-clock on this box
is unreliable — the brief states ~400 agents are running concurrently and wall-clock
varied by 4.4× (5.9 s vs 26.1 s for the same 500k invocation) while CPU time stayed
within 10%. Interpreter baseline RSS is ~17 MB and is included in the "peak RSS"
column; the `delta RSS` figures quoted in the text exclude it.
