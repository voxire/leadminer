# 243 — `cmd_doctor` (cli.py:204): safe, and structurally unable to detect anything that has actually broken

## Verdict

**`cmd_doctor` is safe.** It runs single-threaded in its own process (`leadminer doctor`,
`pyproject.toml:34` → `cli:main`), holds no module-level mutable state, mutates no dict,
shares no `Session` with any pool, takes no lock and needs none. There is **no
cross-thread hazard inside this function** — verified below, including the negative
result that the codebase has no unsynchronized dict mutation anywhere.

The problem is the opposite one, and it is worse for being quiet. `cmd_doctor` is a
pre-flight gate whose success criterion cannot fail: `ok` is cleared by exactly one
condition — a *missing environment variable* (`cli.py:213-214`) — and never by a
connectivity result, of which there are three, one per source (`cli.py:238-243`). A
doctor run with the network unplugged prints three `FAIL` lines and **exits 0**. It
cannot emit the non-zero exit that `docs/audits/037-cli-design.md:21,433` specifies for
it. Meanwhile the Google Places probe it *does* run cannot fail by construction: it
`GET`s a POST-only endpoint without the API key, and `cli.py:240` classifies anything
below 500 as `OK`.

So: nothing here corrupts, and nothing here races. The concurrency lens finds a
diagnostic that is blind to every concurrency failure this pipeline has — including one
real latent leak in `httpclient.py` — and reports success while blind.

## Answers to the specific questions asked

### Is it safe under this codebase's concurrency? Yes — and structurally, not by luck

`cmd_doctor` executes in a process that contains **no thread pool at all**. `main.main()`
dispatches exactly one subcommand per invocation (`cli.py:312-318`), so `leadminer doctor`
and `leadminer run` are different processes. The 40-thread pool (`enricher.py:237`),
the 5-worker Places pool (`google_places.py:194`) and the 3-scraper pool (`main.py:160`)
are in the *other* process. Nothing is shared but the filesystem.

| Lens question | Finding |
|---|---|
| **Shared mutable state** | None. `ok` is a local (`cli.py:208`). The only module global it touches is `DATA_DIR` (`cli.py:26`), a `pathlib.Path` that is never rebound. Verified: `cli.py` contains no `global` statement. |
| **Session reuse** | None, and correctly so. `requests.get` (`cli.py:239`) routes to `requests.api.request`, which is `with sessions.Session() as session: return session.request(...)` (psf/requests v2.32.3, `src/requests/api.py`). A fresh Session per call, closed on exit. **`cmd_doctor` is the only HTTP caller in this repo that gets session lifetime right.** Contrast `httpclient.py:88-91`, below. |
| **Dict mutation visible across threads** | `cmd_doctor` mutates no dict. In the rest of the codebase the answer is also clean, which is worth recording as a verified negative: `enricher.py:249-259` mutates `records[idx]` **only on the collecting thread** inside `as_completed` — workers return `(outcome, contacts)` and never touch `records` (`enricher.py:243`). `google_places.py:263-266` holds `seen_lock` across the *check-then-add* of `seen_ids`, so there is no TOCTOU. `google_places.py:191-192` holds `records_lock` across `extend`. `main.py:162-168` extends `raw` on the collecting thread. **No unsynchronized cross-thread dict mutation exists in this repo.** |
| **Resource lifetime** | This is the real gap. Doctor creates and closes 3 Sessions. The pools create up to ~113 and close none — see S3-01. |
| **Reentrancy** | Fine. `check_websites` returns the same list it was handed (`enricher.py:233,276`) and mutates in place; calling it twice re-fetches every site but converges. `GooglePlacesScraper.scrape()` allocates fresh `seen_ids`/`all_records` per call (`google_places.py:181-184`), so it is reentrant — except `self._api_key` is snapshotted in `__init__` (`google_places.py:157`), so a key rotated mid-run is never picked up. |

### What could actually corrupt?

Only one thing, and it is not corruption of the pipeline — it is a crash of the
diagnostic. `cli.py:219` materialises the directory listing, then `cli.py:220` stats each
entry. Between those two lines another process can rename or remove the file. `f.stat()`
raises `FileNotFoundError`, which nothing in `cmd_doctor` catches: `cli.py:225-231` guards
only the `requests` import, `cli.py:238-243` guards only the three GETs, and `cli.main()`
catches only `KeyboardInterrupt` (`cli.py:316-318`). Reproduced:

```
$ listing = sorted(d.glob("*.csv"))   # cli.py:219
$ (d / "a.csv").unlink()              # any concurrent actor
$ for f in listing: f.stat().st_size  # cli.py:220
UNGUARDED OSError -> FileNotFoundError [Errno 2] No such file or directory
```

This is the one place where the concurrent pipeline can make `cmd_doctor` misbehave, and
it violates the function's own stated contract three lines earlier (`cli.py:228-229`):
*"doctor exists to diagnose a broken environment, so it must never be the thing that
tracebacks."*

**The good news, stated because it is real:** the atomic write means doctor never sees a
partial file. `main.py:122` produces `data/all_businesses.csv.tmp`, and `glob("*.csv")`
does not match it — verified, `glob("*.csv") → []` when only the `.tmp` exists. The
rename at `main.py:130` is atomic. Doctor reads whole generations of the file, never a
half-written one. That is `write_csv` earning its keep.

## Findings

### S2 — Doctor's exit code is derived from one env var; all three connectivity checks are print-only
- **Where:** `cli.py:208` (`ok = True`), `cli.py:213-214` (the *only* `ok = False`), `cli.py:238-243` (loop body — no `ok` write), `cli.py:244` (`return 0 if ok else 1`)
- **Breaks:** the loop that performs every network check has no path to the return value. `requests.get` raising is caught at `cli.py:242` and turned into a `print`; a `5xx` is caught by the `r.status_code < 500` test at `cli.py:240` and turned into a `WARN`. Neither touches `ok`. So `leadminer doctor` returns **0 with three `FAIL` lines on screen**, and `leadminer doctor && leadminer run` proceeds to a four-hour scrape.
- **Trigger:** `unset HTTP_PROXY; python -c "import cli,argparse; cli.main(['doctor'])"` with no network, or simply `leadminer doctor` on a plane. Verified by reading `cli.py:238-244`: `ok` appears at 208, 214 and 244 only. Confirmed separately: `grep -c doctor .github/workflows/scrape.yml` → **0**, so nothing automated consumes this exit code *yet* — which is exactly why it can be wrong without anything breaking loudly.
- **Severity defence:** S2 not S1 because no CI step invokes it and it cannot itself write bad output. But it is the documented pre-flight gate (`docs/audits/037-cli-design.md:21` "fail with explicit, non-zero exit codes (e.g., exit code `3` for configuration/credential errors)"; `:433` "Aborts immediately on exit code `3` or `4` before any network queries are initiated"). A gate that cannot fail is worse than no gate: it converts "I checked" into a false reassurance.
- **Fix:** set `ok = False` on the `except` branch (`cli.py:242`) and on any `r.status_code >= 400`, and use a distinct exit code (3) for credential failure.

### S2 — The Google Places probe is a `GET` on a POST-only endpoint with no API key, and `< 500` scores it `OK`
- **Where:** `cli.py:236` (URL), `cli.py:239` (`requests.get`), `cli.py:240-241` (`< 500` → `OK`) — against the real client at `google_places.py:227` (`session.post(API_URL, json=body, timeout=30)`) and `google_places.py:161-166` (`_make_session` sets `X-Goog-Api-Key` and `X-Goog-FieldMask`)
- **Breaks:** Text Search **(New)** accepts POST only — Google's own reference states "The API uses POST requests to `https://places.googleapis.com/v1/places:searchText` with parameters in the request body" ([`places.searchText` REST reference](https://developers.google.com/maps/documentation/places/web-service/reference/rest/v1/places/searchText), published 2026-06-01); the migration guide notes the GET form existed only in Places API **(Legacy)** ([migrate-text](https://developers.google.com/maps/documentation/places/web-service/legacy/migrate-text)). A `GET` therefore yields a 4xx — and `cli.py:240` classifies every 4xx as `OK`. Combined with the missing `X-Goog-Api-Key` header, **the probe has no reachable outcome that prints anything but `OK`.** It is a constant.
- **Trigger:** `GOOGLE_PLACES_API_KEY` revoked or Places API disabled on the key. The pipeline then takes the 401 branch at `google_places.py:228-233` (`FATAL: invalid API key`, `return records` → zero records), `main.py:167` writes the failure to stderr and continues, `main.py:172` filters an empty batch, and the cumulative master still clears `scrape.yml:80` (`ROWS < 100`) because last month's rows are in it. `leadminer doctor` printed `OK Google Places` beforehand and exits 0.
- **Severity defence:** S2. The key is genuinely never validated by anything in the repo — `google_places.py:157` only reads it, and `main.py:167` converts the failure to a stderr line. Doctor is the designated place to catch it and is structurally incapable.
- **Fix:** probe with `httpclient.fetch_with_retry("POST", API_URL, json={"textQuery": "cafe in Beirut"}, headers={"X-Goog-Api-Key": key, "X-Goog-FieldMask": FIELD_MASK})` and require `status < 400`; treat `401`/`403` as a distinct credential failure.

### S2 — The data-directory read races the only writer, `f.stat()` is unguarded, and a torn 5-file export is invisible
- **Where:** `cli.py:217` (`DATA_DIR.exists()`), `cli.py:219` (`sorted(DATA_DIR.glob("*.csv"))`), `cli.py:220` (`f.stat().st_size`) — against the writer at `main.py:209-213` (five sequential `write_csv` calls)
- **Breaks:** two separate defects.
  1. **Crash.** TOCTOU between `cli.py:219` and `cli.py:220`, reproduced above. `FileNotFoundError` is not an `Exception` subclass caught anywhere in this path — `cli.py:225-231` catches `ImportError` only, `cli.py:242` catches `Exception` but only around the GETs, `cli.main()` catches `KeyboardInterrupt` only. The operator gets a traceback from the one command that promises never to traceback (`cli.py:228-229`).
  2. **Silent split-state.** `main.py:209-213` writes the five CSVs atomically *individually* but not *as a set* (`docs/audits/051-atomic-writes-and-concurrency.md`, S1 on split-state). Doctor reads sizes only, so a run killed between `main.py:210` and `main.py:213` leaves `all_businesses.csv` new and `sales_ready.csv` stale — and doctor prints five sizes that look exactly like a healthy run. Nothing in the repo would let it tell the difference: grep for `manifest|pidfile|lock|fcntl|flock|atexit|signal` across `*.py` returns **zero** functional hits, and `main.py:134` prints only path and count.
- **Trigger:** (1) run `leadminer doctor` while `leadminer run` is mid-export; or any external actor — `rclone copy` (`scrape.yml:88-89`), a `git clean`, a manual `rm`. (2) kill the run between `main.py:210` and `main.py:213`, then `leadminer doctor`.
- **Fix:** wrap the listing in `try/except OSError` and report `UNREADABLE` per file; and make the directory block report a **generation** — write a `data/MANIFEST.json` with a run id and the 5 row counts from `main.py:209-213`, then have doctor print and diff it. Sizes alone cannot detect a torn export.

### S3 — The probes test reachability, not the server-side capacity that actually fails
- **Where:** `cli.py:234` (`/api/status`), `cli.py:235` (`?query=ASK%7B%7D`), `cli.py:239` (`timeout=5`) — against the real requests at `osm.py:9,12,44` (`/api/interpreter`, `[timeout:180]`, `timeout=200`) and `wikidata.py:24-44,75` (`LIMIT 5000`, seven `OPTIONAL`s, a label `SERVICE`, `timeout=90`)
- **Breaks:** both probes hit the cheapest possible resource on their host. `/api/status` is a small static text endpoint that returns 200 while every interpreter slot is saturated — precisely when `osm.py:39-46` would get a 429 or 504, the condition `httpclient.py:142-146` (`_should_retry`) and `google_places.py:234-247` were written to absorb. `ASK{}` returns in milliseconds and can never trip WDQS's server-side query timeout that a `LIMIT 5000` join-heavy query would. Separately, `cli.py:239`'s `timeout=5` becomes both connect *and* read timeout (psf/requests `adapters.py`: `else: timeout = TimeoutSauce(connect=timeout, read=timeout)`), against a real budget of 200s (`osm.py:44`) and 90s (`wikidata.py:75`).
- **Trigger:** Overpass is rate-limiting the runner's IP; the 180-second query at `osm.py:12` will fail. `leadminer doctor` prints `OK Overpass`.
- **Severity defence:** S3, and explicitly **shares a root cause with the two S2s above** — the probe is not the request the client makes — so do not count it as independent evidence. It matters because it is the *reason* the operator's "is it me or them?" question gets the wrong answer, not because it can crash or corrupt.
- **Fix:** probe the real endpoint with the real query and the real timeout, or delete the connectivity block entirely and have doctor report only what is cheap and unambiguous (key present, key accepted by a 1-call authenticated POST, `data/` readable, disk space).

### S3-01 — Doctor checks none of the resource-lifetime state the three pools create; one of those is a genuine unclosed-Session leak
- **Where:** `cli.py:224-243` (the entire network section) versus `httpclient.py:58` (`_local = threading.local()`), `httpclient.py:61-71` (`get_session` caches a Session per thread), `httpclient.py:88-91` (`http_session()` closes nothing), `enricher.py:175` + `enricher.py:237` (40 threads × 1 Session), `google_places.py:189` (one Session **per query**, not per thread)
- **Breaks:** the pools create Sessions that nothing ever closes. `grep -rn "\.close()" --include=*.py` over the whole repo returns exactly **one** hit, `enricher.py:195` `r.close()` — that is a `Response.close()`, not `Session.close()`. `httpclient.py:88-91` is a `@contextmanager` that yields `get_session()` and closes nothing on exit, despite the `with http_session() as session:` in its own docstring at `httpclient.py:23` implying it does. So:
  - Up to **40** thread-local Sessions from `check_websites` (`enricher.py:225` default `workers=40`), each with its own `PoolManager(num_pools=10, maxsize=10)` (psf/requests `adapters.py`, `DEFAULT_POOLSIZE = 10`) → up to **400 pooled sockets**, each carrying cookie state harvested from an arbitrary third-party business site.
  - **68** Sessions from Google Places — `_make_session()` is called *inside* `fetch_query` (`google_places.py:189`), once per query, over `LEBANON_QUERIES` (34) + `KSA_QUERIES` (34) — each a fresh adapter, each stamped with the API key, none closed.
  - Their fate is left to whatever order CPython's cycle collector finalizes the adapters in. Nondeterministic lifetime on a `timeout-minutes: 300` job (`scrape.yml:25`).
- **Trigger:** any full `leadminer run`. Open `lsof -p <pid> | wc -l` during the enrichment phase; count `TCP ... CLOSE_WAIT` / `ESTABLISHED` to unrelated hosts.
- **Why it lands in *this* report:** the leak is `httpclient.py`'s to fix and another lens may already own it. What is mine is the **coverage gap**: `cmd_doctor` is the tool an operator reaches for when a run misbehaves, and it examines none of this — no fd count, no thread count, no Session count, no connection count, no run manifest (zero hits for `manifest|pidfile|lock|fcntl`). Every one of the pipeline's concurrency failure modes is invisible to it, by construction.
- **Fix:** in `httpclient`, either close the thread-local Session at pool shutdown or mount a single shared `HTTPAdapter` with a sized pool instead of one Session per thread; in doctor, add a `resources:` block reporting thread count, open fds, and free disk — the three things that actually break long runs.

## Not a bug, but worth knowing

- **`doctor` is the one place in this repo with correct session lifetime.** `requests.get` creates and closes a Session per call (psf/requests `src/requests/api.py`). The irony is worth stating: the diagnostic gets this right and the pipeline it diagnoses does not.
- **The atomic write makes doctor's directory scan safe against partial reads.** `main.py:122-130` writes `data/all_businesses.csv.tmp` and renames; `glob("*.csv")` does not match `.tmp` (verified). Doctor reads complete generations only. If `write_csv` is ever "simplified" back to `open(path, "w")`, doctor silently starts reporting truncated sizes — and nothing else would notice.
- **Doctor's three probes are sequential and always will be.** That is correct. Parallelising them would gain nothing (worst case today is 15s of a human's afternoon) and would be the *only* place in this codebase that introduced threads into `cli.py`.
- **`DATA_DIR` is CWD-relative** (`cli.py:26`, and identically `main.py:41`). Run `leadminer doctor` from anywhere but the repo root and it reports `MISSING data (no run has produced output yet)` (`cli.py:222`) — a confident false statement, not a warning. Same for the `stats`/`validate`/`score` defaults (`cli.py:294,298,305`). Resolving from `__file__` costs one line and removes a whole class of confusing report.
- **`docs/audits/037-cli-design.md` already specifies the right shape** — exit code 3 for credential errors, 4 for connectivity, `--allow-partial` to override (`:21`, `:433`). `cmd_doctor` implements none of it. Treat that document as the spec and this function as a first draft of it.
- **Doctor is not wired into CI.** `grep -c doctor .github/workflows/scrape.yml` → 0. Cross-referenced by `docs/audits/207-x.md:106-107`. Fixing the exit code is worth nothing until something consumes it; the natural place is a step before `scrape.yml:65`.

## Recommended order of work

1. **S2-01 — make `ok` reachable from the connectivity loop** (`cli.py:238-243`). Smallest diff in this report: two `ok = False` assignments. Until this lands, every other doctor fix is cosmetic, because nothing reads the result.
2. **S2-02 — replace the Places probe with an authenticated POST** through `httpclient.fetch_with_retry` and require `status < 400`. This is the only probe in the repo that can return a constant.
3. **S2-03 — guard the directory scan** (`try/except OSError` per file at `cli.py:220`) and add a `data/MANIFEST.json` written by `main.py:209-213` so doctor can report a run id and detect a torn 5-file export instead of printing five reassuring sizes.
4. **S3-01 — fix `httpclient`'s Session lifetime** (close at pool shutdown, or one shared sized adapter) *and* add doctor's `resources:` block. Different owner, same incident — the leak is invisible from the tool built to explain the run.
5. **S3 — either probe the real endpoints with real queries and real timeouts, or delete the connectivity block.** Half a probe that cannot fail is worse than none.
6. **Housekeeping** — anchor `DATA_DIR` to `__file__` in both `cli.py:26` and `main.py:41`; wire `leadminer doctor` into `scrape.yml` before the run step so its exit code finally has a consumer.
