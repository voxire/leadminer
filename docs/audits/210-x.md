# 210 — `cmd_run` (`cli.py:33`): the test cases it still needs

## Verdict

`cmd_run` is five lines that delegate everything and assert nothing, and it is the
**only** place where the pipeline's failure becomes an exit code — yet `cli.py:315`
discards that information with `int(args.func(args) or 0)`. Because `main.main()`
returns `None` (`main.py:148`) *and* swallows every scraper exception
(`main.py:167-168`), **`leadminer run` exits `0` after a total upstream outage and
has already overwritten all five exports with header-only files** (verified below).
The function needs a contract test for delegation, a failure-propagation test that
currently fails, and property tests for the cumulative-master invariant.

Note up front: `cmd_run` has **zero** existing tests. `tests/test_lead_signal.py:191`
`TestCli` covers only `cmd_stats` and `cmd_validate`; `docs/audits/087-SYNTH-test-gap.md:19`
lists `cmd_run` as a gap. The 28 existing tests never exercise it.

---

## Findings

### S1 — `leadminer run` reports success after every scraper fails, having destroyed the exports

- **Where:** `cli.py:33-37` (the wrapper), `cli.py:315` (`or 0`), `main.py:167-168`
  (exception swallow), `main.py:209-213` (unconditional export), `main.py:148`
  (`-> None`).
- **Breaks:** `main.main()` catches `Exception` per-future and prints to stderr
  (`main.py:167-168`), then continues. With `raw == []` the pipeline proceeds to
  `write_csv` for all five exports (`main.py:209-213`) and returns `None`.
  `cmd_run` returns that `None` (`cli.py:37`), and `cli.main` coerces it with
  `args.func(args) or 0` (`cli.py:315`) → **exit 0**. A green build, five
  header-only CSVs.
- **Trigger — verified, not hypothesised.** Three scraper stubs whose `scrape()`
  raises `RuntimeError("HTTP 504 Gateway Timeout (Overpass)")`, empty `data/`:

  ```
  main.main() returned: None  -> cli would coerce to 0
  data/ contents:
    all_businesses.csv               bytes=225   lines=1
    qualified_businesses.csv         bytes=225   lines=1
    sales_ready.csv                  bytes=225   lines=1
    with_websites.csv                bytes=225   lines=1
    without_websites.csv             bytes=225   lines=1
  ```

  Every file is a bare header. The real Overpass 504 is not hypothetical — it is
  the canonical Overpass failure and the exit-code matrix in
  `docs/audits/037-cli-design.md` already assigns it `4` (`EX_NOHOST`).
- **Aggravating:** with a non-empty master the run is *worse*, not better. `records`
  becomes just the stale master (`main.py:179-180`), so `all_businesses.csv` is
  non-empty, the shell guard at `.github/workflows/scrape.yml:80` (`ROWS -lt 100`)
  passes, and the run republishes months-old data to Drive as a fresh
  `gdrive:leads/data/$TIMESTAMP/` directory. Silent staleness.
- **Fix:** `cmd_run` must translate pipeline outcome into a code and must not let a
  run with zero successful sources return `0` — `main.main()` should return a
  summary (records added, sources failed) and `cmd_run` maps it to `0`/`4`/`6`;
  `cli.py:315`'s `or 0` should become an explicit `is None` check that raises rather
  than defaulting to success.

### S2 — The `-> int` annotation is false, and the integer contract lives in the caller

- **Where:** `cli.py:33` declares `-> int`; `cli.py:37` returns `pipeline.main()`,
  which `main.py:148` declares `-> None`.
- **Breaks:** the type lies, and the only reason anything works is the `or 0` at
  `cli.py:315`. Any future `cmd_*` returning `None` for a *different* reason inherits
  the same silent-zero. `mypy strict` is enabled (`pyproject.toml:66-68`) and would
  flag `return pipeline.main()` — so the codebase is not actually type-clean here.
- **Trigger — verified:** stubbed pipeline returning `None` →
  `cmd_run(Namespace(cmd='run'))` returns `None`, `cli.main(['run'])` returns `0`.
- **Fix:** have `main.main()` return `int` (or a result dataclass) so `cmd_run`'s
  annotation becomes true.

### S2 — `run` has no flags at all, so an operator's only lever for a flaky source is editing code

- **Where:** `cli.py:285-286` registers `run` with zero arguments.
- **Breaks:** `docs/audits/037-cli-design.md` §9 specifies `--source`, `--skip-enrich`,
  `--skip-scrape`, `--allow-partial`, `--clean`, and exit codes 0/1/3/4/5/6. None
  exist. `--allow-partial` in particular is the *designed* answer to the S1 above,
  and without it the choice is "all-or-nothing or edit the source".
- **Trigger — verified:** `['run','--source','osm']` → `SystemExit 2`;
  `['run','--skip-enrich']` → `SystemExit 2`.
- **Fix:** add `--allow-partial` (exit `6`) and `--skip-enrich`; at minimum surface
  per-source failure counts in `cmd_run`'s return value.

### S3 — Missing `requests` gives a raw traceback from `run`, while `doctor` handles it cleanly

- **Where:** `cli.py:35` (`import main as pipeline`) vs `cli.py:227-231`, which
  deliberately catches `ImportError` — "doctor exists to diagnose a broken
  environment, so it must never be the thing that tracebacks".
- **Breaks:** `cli.main` catches only `KeyboardInterrupt` (`cli.py:316`), so a
  `ModuleNotFoundError` from the deferred import escapes as a full traceback. The
  operator who correctly ran `leadminer doctor` first (README.md:95) and then `run`
  gets a worse error than the diagnostic they were just given.
- **Trigger — verified:** `cmd_run(Namespace(cmd='run'))` with `requests` absent →
  `ModuleNotFoundError: No module named 'requests'`. Same environment,
  `cmd_doctor` → `rc 1` and `"FAIL  requests is not installed - run: pip install -e '.[dev]'"`.
- **Fix:** wrap `cli.py:35` in the same `try/except ImportError` and return `1` with
  the identical message `cmd_doctor` uses.

### S3 — Output location is implicit and CWD-relative

- **Where:** `cli.py:26` (`DATA_DIR = pathlib.Path("data")`), `main.py:41` (same),
  and `cmd_run` exposing no override (`cli.py:285-286`).
- **Breaks:** `leadminer run` writes wherever it was invoked and `leadminer stats`
  reads `data/` relative to its own CWD (`cli.py:294`). Running the two from
  different directories silently reads a stale file. There is no `--data-dir`.
- **Fix:** resolve `DATA_DIR` once from an env var or `--data-dir`, and have
  `cmd_run` pass it explicitly rather than letting `main.main()` re-derive it.

## Not a bug, but worth knowing

- **`cmd_run` is not on the CI path.** `.github/workflows/scrape.yml:69` runs
  `python main.py`, never `leadminer run`. So the S1 exit-code defect is currently
  invisible to the scheduler, and the real backstop is the shell guard at
  `scrape.yml:74-82`. Every test in Group B below is only *load-bearing* once
  `scrape.yml:69` is switched to `leadminer run` — fix them together.
- **No test step in CI.** `scrape.yml` has no `pytest` / `unittest` invocation, so
  the 28 tests in `tests/test_lead_signal.py` never execute automatically. The tests
  below are worth writing but not worth much until CI runs them. `pyproject.toml:76`
  already sets `testpaths = ["tests"]`, so the runner just needs invoking.
- **`cmd_score` duplicates the tail of `main.main()` and has drifted.** `cli.py:264-272`
  vs `main.py:183-197`: `main.main()` normalizes the phone before scoring
  (`main.py:192-194`), `cmd_score` does not. Verified with one record:
  `run` → `phone='+966501234567'`, `cmd_score` → `phone='00966501234567'`
  (`lead_score` agrees at 60 because `enricher.py:286` only tests `len(phone) >= 7`,
  but the `phone` column means different things depending on which command wrote it).
  This is why Group D exists.
- **`main.py:206`'s `>= 1` is safe today only by accident.** `load_master` turns `""`
  into `None` (`main.py:88-89`), so a master row with a blank `completeness_score`
  does produce `None`, and `None >= 1` raises `TypeError` (verified). It does not fire
  only because `enricher.py:349` unconditionally overwrites the key. Nothing states
  or tests that dependency.
- **The console script works.** `pyproject.toml:33` maps `leadminer = "cli:main"`, so
  `sys.exit(cli.main())` gives the coerced `0` at `cli.py:315`.

## The test cases `cmd_run` still needs

### Prerequisite: a fixture that touches zero network

`main.main()` calls `enrich(records)` (`main.py:187`), which calls
`check_websites(records)` (`enricher.py:349` → `enricher.py:236`) with no seam.
`check_websites` builds `targets` from records having a website and returns early
when empty (`enricher.py:231-233`). **So: give every fixture record no `website`
key, and the whole pipeline runs offline.** The existing `TestCli._fixture`
(`tests/test_lead_signal.py:195`) hardcodes `"website": "https://x.com"`
(`tests/test_lead_signal.py:199`), so it must be overridden per test.

Reuse the suite's existing infrastructure rather than inventing new:
`_stub_requests()` (`tests/test_lead_signal.py:23-63`), the `sys.path` shim
(`tests/test_lead_signal.py:20`), `contextlib.redirect_stdout/stderr`, and the
`Boom(dict)` trick (`tests/test_lead_signal.py:160-164`) for injecting a mid-write
crash.

Stub the pipeline by injecting `sys.modules["main"]` **before** calling `cmd_run`,
because the import is deferred to call time (`cli.py:35`). This is what makes the
Group A tests hermetic.

## What genuinely cannot be tested here, and why

1. **The real HTTP behaviour of enrichment.** `cmd_run` calls `enrich(records)`
   (`main.py:187`) → `check_websites(records)` (`enricher.py:236`) with **no injection
   seam** — `workers` is a default parameter (`enricher.py:225`), not an argument
   `cmd_run` supplies. Testing timeouts, the 40-thread fan-out, TLS behaviour
   (`httpclient.py:43`), the SSRF guard, or contact regex precision would require
   patching `enricher.check_websites` wholesale — at which point the test is a test
   of `enricher`, not of `cmd_run`, and belongs in a different report. Only the
   *absence of a website* case (`enricher.py:231-233`) is reachable without patching.
2. **Real Overpass / Wikidata / Places protocol handling.** `cmd_run` hardcodes the
   three scrapers through `main.main()` (`main.py:155`). Unlike `cmd_scrape`, which
   builds a local `registry` dict (`cli.py:51-55`), `cmd_run` has no registry to
   override. Every Group C test must therefore monkeypatch `main.OSMScraper`,
   `main.WikidataScraper` and `main.GooglePlacesScraper` — module attributes, not an
   injected list. That is workable but it is global state: such tests cannot run in
   parallel and must restore the originals in `tearDown`.
3. **Whether the CSVs that reach Google Drive are the ones `cmd_run` wrote.** That
   boundary is `rclone copy` in `.github/workflows/scrape.yml:84-86`, outside the
   process. No in-process test can observe it. The closest proxy is C1+C3 (the files
   on disk are correct and complete), which is why those two matter more than they
   look.
4. **The exit code GitHub Actions actually observes for `run`.** Because
   `scrape.yml:69` invokes `python main.py`, `cmd_run`'s return value never reaches
   the scheduler — `python main.py` exits `0` via `main.py:245-246` regardless. Every
   Group B test is therefore currently *specification only*. **Land the Group B fix
   and the `scrape.yml:69` switch together, or neither has any effect.**
5. **`KeyboardInterrupt` in production.** `timeout-minutes: 300`
   (`.github/workflows/scrape.yml`) makes the runner send SIGTERM then SIGKILL.
   Python raises neither `KeyboardInterrupt` nor anything `cli.py:316` catches. B5 can
   only be tested by raising the exception directly; it proves the handler, not the
   production behaviour, and should not be read as covering the timeout path.
6. **Crash-consistency under real power loss / SIGKILL.** C2 covers the in-process
   exception path via `Boom`. `os.replace` (`main.py:130`) is atomic on POSIX, so the
   rename itself is sound, but "the fsync actually reached the platter" is not
   assertable from Python.
7. **Whether `leadminer run` is what an operator types.** Nothing in the repo asserts
   that the console script (`pyproject.toml:33`) resolves on `$PATH`. A packaging
   regression that drops `[project.scripts]` would make every Group A/B test still
   green while the documented command (`README.md:96`) stops existing. Only a
   `pip install -e .` smoke test in CI covers that, and that is out of scope here.

## Recommended order of work

1. **B2 + C1** first, together. B2 is the S1; C1 is the invariant that proves the fix
   did not introduce silent data loss. Neither requires new production flags.
2. **S2 fix (`main.main()` returns `int`)** then re-run **A1** — the type contract has
   to be true before A1 is anything other than a wish.
3. **B4, B6, B7** — cheap error-path tests that each name a distinct failure mode and
   each currently fail.
4. **A2, A3, A4** — cheap, hermetic, and they lock in the delegation seam every other
   test in this report depends on. Do them before adding flags.
5. **C2, C3, C4** — the property-based guards on the data contract.
6. **D1, D2** — parity between `run` and `score`; D1 fails today and is a one-line fix
