# 230 — `cmd_stats`: import-clean by duplication, and the duplicated contract fails silently

## Verdict

`cmd_stats` (`cli.py:79`) has a clean dependency map: **not one project module and not one
third-party module is reachable from it** (verified — `import cli` pulls only `argparse`, `csv`,
`collections`, `pathlib`, `sys`). That is the correct shape for a triage command, and it is worth
stating plainly rather than manufacturing a problem.

But the cleanliness is *purchased*, not designed. `cmd_stats` reaches its subject — the export
schema — only by re-typing 10 of the 22 column names as string literals (`cli.py:98-130`) and
re-implementing the `website_live` tri-state decoder with exact-case literals
(`cli.py:107-108`), duplicating `main.FIELDS` (`main.py:33-40`) and `main.load_master`'s decoder
(`main.py:103`) without importing either. The bill comes due silently: **any `website_live` cell
that is not byte-exactly `True` or `False` makes all three liveness buckets print `0` while
`with website` prints `N`, and the command still exits `0`.** The one command an operator reaches
for when a run looks wrong reports total, confident, wrongness about the product's headline
metric. S1.

## Findings

### S1 — `website_live` is decoded with exact-case literals, so all three liveness buckets read `0` and the command still exits `0`

- **Where:** `cli.py:107-110`. Producer: `enricher.py:250` sets a Python `bool | None`.
  Serializer: `csv.DictWriter` at `main.py:125` renders it via `str(bool)`.
  Canonical decoder it duplicates: `main.py:103`.
- **Breaks:** the three counts use `== "True"` / `== "False"`, i.e. byte-exact comparison
  against `str(True)`. The wire encoding is an *emergent property of `csv.DictWriter`*, not a
  declared constant, so nothing guarantees it. Any value that is not exactly those two strings
  falls into **no bucket at all**. `live + dead + unreachable` becomes `0` while `with website`
  stays `N`, and the report prints:

  ```
    with website    : 1
    website live    : 0
    website dead    : 0
    unreachable     : 0  (not the same as dead)
  ```

  The `(not the same as dead)` annotation actively invites the reader to trust the
  partition, which is precisely what just failed. Exit code is `0` (`cli.py:132`).
- **Trigger** (all four verified by running `cmd_stats` against a one-row CSV):
  | `website_live` cell | live | dead | unreachable | sum | exit |
  |---|---|---|---|---|---|
  | `True` (as `write_csv` emits) | 1 | 0 | 0 | **1** ✅ | 0 |
  | `TRUE` (Google Sheets re-export) | 0 | 0 | 0 | **0** ❌ | 0 |
  | `FALSE` (Google Sheets re-export) | 0 | 0 | 0 | **0** ❌ | 0 |
  | `true` (lowercase) | 0 | 0 | 0 | **0** ❌ | 0 |

  The Sheets round-trip is not hypothetical here: `scrape.yml:85-89` uploads these CSVs to
  Google Drive as the shared sales artifact, so a helper opening, sorting and re-saving the file
  in Sheets is a routine operation on this exact data. A lowercase `"true"` also appears the
  moment anyone adds a pandas/`to_csv` export step.
- **Why S1 and not S2:** silent data loss presented as authoritative, on the command the module
  docstring (`cli.py:9`) and `tests/test_lead_signal.py:192-193` both designate as "the first
  thing an operator reaches for when a run looks wrong". The operator's conclusion is "no sites
  are live and none are dead", i.e. the enrichment pass silently did nothing.
- **Fix:** decode case-insensitively and make the buckets provably partition `with website`:
  ```python
  wl = [(r.get("website") or "").strip(), (r.get("website_live") or "").strip().lower()]
  ```
  then bucket on `{"true": live, "false": dead}.get(wl[1], "unknown")` and assert the three
  counts sum to `count('website')`.

### S2 — the three buckets do not partition `with website`, and `unreachable` counts rows that were never fetched

- **Where:** `cli.py:109-110` uses a *different predicate* from `cli.py:107-108`.
- **Breaks:** `unknown` is defined as "has a website **and** blank `website_live`". That
  conflates two states the rest of the codebase goes to real trouble to keep apart — `UNKNOWN`
  ("we tried and were blocked", `enricher.py:151-153`) and *never attempted at all* (e.g. a
  legacy master row carried forward by `dedup`). Verified: a CSV whose header has **no**
  `website_live` column reports `unreachable : 1` for a site the pipeline never tried to fetch.
  Combined with S1, the report can print any of `(N,0,0)`, `(0,0,N)`, `(0,0,0)` or `(live,
  dead, ≤N)` with no consistency check anywhere.
- **Trigger:** the absent-column fixture above, or any row whose `website_live` was never
  populated — which is every row a scraper yields before enrichment (`osm.py:109`,
  `wikidata.py:114`, `google_places.py:292` all emit `website_live=None`).
- **Fix:** derive `unknown` as `with_website - live - dead`, and break out the never-attempted
  case separately.

### S2 — the default path is a CWD-relative duplicate of `main.DATA_DIR`, so `leadminer stats` with no argument fails from any other directory

- **Where:** `cli.py:26` (`DATA_DIR = pathlib.Path("data")`) feeding the default at
  `cli.py:294`; duplicates `main.py:41` and the filename at `main.py:209`. Consumed by three
  subcommands (`cli.py:294`, `298`, `305`).
- **Breaks:** `pathlib.Path("data")` is **relative**, so it resolves against the process CWD,
  not the package. Verified: `cli.DATA_DIR.is_absolute()` → `False`. Audit 020 S13 flags
  `main.py`'s copy; it does not flag that **`cli.py` declares a second, independent copy** that
  nothing keeps in sync — change one, and `stats`/`validate`/`score` silently read a path the
  writer never wrote to. `leadminer stats` is documented at `cli.py:9` as safe to "run anywhere",
  which is false: from any directory but the repo root it returns exit `2`,
  `no such file: data/all_businesses.csv`. In this checkout `data/` does not exist at all
  (gitignored, `BRIEF.md:11`), so even from the root it exits `2` until a run has happened —
  and the error text does not say "no run has produced output yet", although `cmd_doctor`
  (`cli.py:222`) knows exactly how to phrase that.
- **Trigger:** `cd /tmp && leadminer stats` → `no such file: data/all_businesses.csv`, exit 2.
- **Fix:** one owner. Put `DATA_DIR` in a leaf module (step 2 below), resolve it against the
  package, and have both `cli.py` and `main.py` import it.

### S3 — the export schema is declared a third time, and a missing column yields a confident zero or a `None` bucket

- **Where:** `cli.py:98-130` (10 literals) vs `main.py:33-40` vs `scrapers/base.py:5-28`.
  Audit 020 S3 already counts two declarations; the CLI is the third, and it is the only one
  that *reads data back*, so it is the only one where a divergence costs correctness.
- **Breaks:** because the coupling crosses a serialization boundary, **no static tool can see
  it.** `mypy --strict`, `ruff`, and the import graph are all blind: renaming `website` in
  `main.FIELDS` leaves `cli.py:100` compiling cleanly and reporting `with website : 0`
  forever. Verified: dropping `industry_priority` from the header yields a plausible-looking
  report containing a fabricated bucket —
  ```
    by priority:
      None       1
      high                                                 1
  ```
  `cmd_stats` performs no header validation at all, which is the same gap as 020 S1, one layer
  out.
- **Fix:** import the field names from a leaf schema module and assert membership once.

### S3 — the UTF-8 BOM contract is stated three contradictory ways, and `cmd_validate`'s BOM check is dead code

- **Where:** four statements about one encoding contract:
  `main.py:82-85` ("reading as plain utf-8 would leave the BOM glued to the first column"),
  `main.py:118-119` (writer *must* emit the BOM, for Excel/Sheets),
  `cli.py:86` (reader strips it — correct), and
  `cli.py:154-156` (**flags a BOM in `name` as a bug**, "written without utf-8-sig").
- **Breaks:** `write_csv` hardcodes `encoding="utf-8-sig"` (`main.py:124`), so every file the
  pipeline produces has a BOM. Verified: a file written exactly as `write_csv` writes it starts
  `EF BB BF`, and `cmd_validate` returns **exit 0, "all checks passed"** — the check at
  `cli.py:154` can never fire against any file this system produces.
  `tests/test_lead_signal.py:180-188` actively asserts the BOM *is* written, so the test suite
  and the validator now encode opposite beliefs about the same invariant. This matters beyond
  tidiness: `cmd_validate` is the CI-shaped gate (non-zero exit, `cli.py:136`), and a check that
  provably cannot fail is worse than an absent one, because it reads as coverage.
- **Fix:** delete `cli.py:154-156`; keep the write-side BOM unconditionally and keep exactly one
  documented reason for it.

### S3 — `enricher` imports `requests` without using it, which makes the module unimportable without it and forced a 40-line stub into the test suite

- **Where:** `enricher.py:2`. `ruff check` (0.16.10, repo config) reports
  `enricher.py:2:8: F401 'requests' imported but unused` — the module uses
  `get_session()` from `httpclient` (`enricher.py:175`) and never touches `requests`.
  Also dead: `enricher.py:4` `urljoin, urlparse` (F401).
- **Breaks:** because `scrapers/google_places.py:26` imports `enricher` at module scope, an
  unused import is a hard runtime requirement on the whole scrape stack for zero benefit. The
  measurable cost is in the test suite: `tests/test_lead_signal.py:23-63` is a 40-line
  hand-rolled `requests` + `urllib3` stub whose own docstring says why —
  *"enricher imports requests at module scope. Stub it if absent so these tests run in a bare
  checkout"* — existing solely to work around an import nothing uses. This is the mirror image of
  020 S10 (declared-but-unimported deps): here it is imported-but-undeclared.
- **Related, same module:** `enricher.py:327-328` does `import urllib3` inside `enrich()` purely
  to call `disable_warnings()` — an import that exists only for **logging**, and an undeclared
  transitive dependency (`pyproject.toml:16-18` declares only `requests`; `urllib3` survives only
  as a transitive of it, and `pyproject.toml:70-73` has to add a mypy override for it). It is
  also a library function mutating process-global warning filters as a side effect.
- **Fix:** delete `enricher.py:2` and `enricher.py:4`; then delete
  `tests/test_lead_signal.py:23-63` outright.

### S3 — the logging facility is entirely dead: three loggers, zero configuration, two `debug` calls

- **Where:** `osm.py:7`, `wikidata.py:7`, `httpclient.py:45` each create
  `log = logging.getLogger(__name__)`. Verified across the repo: **no `basicConfig`,
  `dictConfig`, or `fileConfig` anywhere.** The only two call sites are `log.debug` at
  `httpclient.py:178` and `httpclient.py:204`, both below the default `WARNING` threshold, so
  neither can ever emit.
- **Breaks:** the retry/transport diagnostics that `httpclient.py:96-99` and
  `osm.py:47-55` describe as the fix for "failures were indistinguishable" cannot be turned on
  without adding configuration that does not exist. Every other module communicates with bare
  `print` (`cli.py` has no logger at all). Two competing, mutually exclusive conventions, with
  the unused one looking like the modern one.
- **Fix:** configure logging once in `main()`/`cli.main()`, or delete the three loggers and the
  two `debug` calls rather than leaving dead instrumentation.

### S3 — `cmd_stats`'s exit codes and output are consumed by nothing, so its one real strength is unreachable

- **Where:** exit codes `0/1/2` at `cli.py:132`, `90`, `84`.
- **Breaks:** verified — CI runs `python main.py` (`.github/workflows/scrape.yml:69`), never the
  CLI. `.github/workflows/scrape.yml:71-83` gates on `wc -l` and `[ ! -s ... ]` in bash. So no
  automated consumer of `stats` exists, and `leadminer stats` has no `--json`/machine-readable
  mode — its output is fixed-width prose (`cli.py:111-131`), so it cannot be diffed between runs
  or asserted on even if something did call it. The commands `cli.py:14-15` advertises as "safe
  to run anywhere and are what you reach for when a run looks wrong" are the least exercised
  code in the repository.
- **Fix:** add `--json` to `stats` and call it from the workflow next to `scrape.yml:71`.

## Not a bug, but worth knowing

- **No `if TYPE_CHECKING:` block exists anywhere in the project** (verified by AST scan of all
  18 `.py` files). `from __future__ import annotations` (`cli.py:18`, `httpclient.py:32`) is the
  only deferral mechanism in use. Consequence: every typing import is a genuine runtime import
  even when it appears only in an annotation. The one genuinely annotation-only import is
  `httpclient.py:41 from typing import Any` — all three uses (`:110`, `:120`, `:158`) are
  annotations, stringified by PEP 563 — which a type checker still requires, so it stays.
  `argparse.Namespace` (`cli.py:20`) looks annotation-only at `cli.py:79` but is not: it is
  needed at runtime by `build_parser` (`cli.py:280-309`).
- **`cli.py:46` is an import used only as a smoke test** —
  `from scrapers.base import BaseScraper  # noqa: F401  (import check)`. It is also redundant:
  `registry` (`cli.py:51-55`) instantiates `OSMScraper`, `WikidataScraper` and
  `GooglePlacesScraper`, all of which subclass `BaseScraper`, so lines 47-49 already prove it
  imported. (In `cmd_scrape`, not `cmd_stats` — noted because it is the clearest instance of the
  pattern this lens asks about.)
- **`_fmt`'s `None → "n/a"` branch (`cli.py:30`) is unreachable from its only caller.**
  `_fmt` has exactly one call site, the six `count()` calls at `cli.py:98-103`, and `count()`
  (`cli.py:96`) returns `sum(...)` — always an `int`. Verified: no `_fmt(None)` in
  `cmd_stats`'s source. Half of a two-function helper's contract is dead.
- **The source-identity coupling between `dedup` and the adapters is by value, not by import, so
  no tool can see it.** `dedup.py:97-110` hardcodes `"google_places"`, `"osm"`, `"wikidata"` as
  `_SOURCE_TRUST` keys; those exact strings are produced at `google_places.py:302`,
  `osm.py:119` and `wikidata.py:127`, and `enricher.py:316` sniffs for them with
  `"|" in str(record.get("source"))`. Four modules agree on a wire vocabulary held in no shared
  constant. Today that is invisible to the import graph rather than cyclic; it is the cheapest
  thing on this page to fix and the first thing that will break silently.
- **`cmd_stats` materialises the whole file** (`cli.py:87`). For the cumulative master
  (`BRIEF.md:50`) at 40 workers × ~68 queries that is fine today; it is the same
  list-everything shape that audit 052 addresses for the pipeline, and `stats` inherits it.
- **`pyproject.toml:36-37` already documents this report's problem and then does not fix it.**
  `include = ["scrapers/"]` with the comment *"The package imports a top-level sibling module,
  so both must ship"* — but only **one** of the "both" is listed. `cli`, `main`, `dedup`,
  `enricher`, `pitch_recommender` and `httpclient` are not in the include list, while
  `pyproject.toml:33` declares the console script `leadminer = "cli:main"`. The entry point
  points at a module the wheel does not ship.
- **`requirements.txt` still lists `beautifulsoup4` and `lxml`, which nothing imports**
  (verified by full-tree grep). The only live third-party dependency is `requests`.

## Recommended order of work

1. **S1 + S2 (tri-state decode).** One predicate, case-insensitive, derived as
   `with_website - live - dead`, plus a `sum == count('website')` assertion. Smallest diff in
   this report and the only one that stops a confidently-wrong report. Add the four casing rows
   from the S1 trigger table as regression tests next to
   `tests/test_lead_signal.py:211-226`, which currently only covers the canonical `True`.
2. **Extract a leaf schema module — and do not import `main.FIELDS`.** Create
   `schema.py` (or `contracts.py`, per 020 S12 / 066 §1) exporting `FIELDS`, `DATA_DIR`, the
   five export filenames, and one `parse_website_live() -> WebsiteStatus` used by
   `main.load_master` (`main.py:103`), `enricher.check_websites` (`enricher.py:250`) and
   `cli.py:107-110`. It must import nothing from the project, so `cli.py` keeps its zero-project
   dependency count. Then have `cli.py:98-130` iterate `FIELDS` instead of re-typing names, and
   delete the second `DATA_DIR` at `cli.py:26`.
   *Why not `from main import FIELDS`:* verified above — `main.py:25-31` makes that pull all three
   scrapers, `dedup`, `enricher` and `pitch_recommender`, plus `requests`. It would convert
   `stats` from 0 third-party imports to all of them, and `ModuleNotFoundError` today where
   `requests` is absent. The leaf module is the only fix that keeps the property this report
   opened by calling correct.
3. **Delete the dead code:** `enricher.py:2` and `enricher.py:4` (F401), then
   `tests/test_lead_signal.py:23-63`; `cli.py:154-156` (unreachable BOM check);
   `cli.py:46` (redundant import check); the `_fmt` `None` branch at `cli.py:30`.
   `ruff check --fix` handles the first four mechanically and clears 28 of the repo's 42
   findings.
4. **One logging convention.** Either configure it in `main()`/`cli.main()` and migrate the
   `print` calls, or delete the three loggers. Do not leave both.
5. **`leadminer stats --json`,** then call it from `.github/workflows/scrape.yml` beside the
   existing `wc -l` gate at `:71-83` so the triage command is actually exercised.
6. **Only then move to `src/leadminer/`.** `cmd_stats` needs no import changes at all once step 2
   lands — that is the payoff for doing it in this order. The blocking work for the move is
   already scoped by 020 S11-S13 and 030 S1; this report adds the CLI's three lazy edges
   (`cli.py:35`, `249-252`) and the reminder that `pyproject.toml:36-37` must list every
   top-level module, not just `scrapers/`.
