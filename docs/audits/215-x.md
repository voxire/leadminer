# 215 — `cmd_run`: the production entry point that cannot fail

**Target:** `cmd_run` at `cli.py:33-37`
**Lens:** running for six hours on a cron job. What it prints, what it swallows, what
happens when the network drops halfway, when a dependency returns garbage, when it is
called with an empty list, and when it is interrupted.

## Verdict

`cmd_run` is four lines and one of them is a lie: it is annotated `-> int` (`cli.py:33`)
but `main.main()` is annotated `-> None` and returns `None` unconditionally
(`main.py:148`), which `cli.main` coerces to `0` at `cli.py:315`
(`int(args.func(args) or 0)`). **There is no code path by which `leadminer run` can exit
non-zero for a bad run.** Every catastrophic failure mode below — zero records from all
three sources, a master that reloads as empty, a network blip halfway through enrichment —
produces a fully-populated set of five CSVs, a cheerful `Summary:` block on stdout, and
exit status 0. The two guards that *do* exist (missing-master check, minimum-row check)
live in `.github/workflows/scrape.yml`, not in the command the cron job is documented to
run, and the workflow does not call `cmd_run` at all — it calls `python main.py`.

The second-order problem: for a six-hour run, stdout is block-buffered and never flushed,
so the most informative part of the log (the five `Written:` lines and the whole Summary)
is exactly the part that disappears when the run is killed.

## The function, and everything it does

```python
# cli.py:33-37
def cmd_run(args: argparse.Namespace) -> int:
    """Full pipeline. Thin wrapper over main.main so there is one code path."""
    import main as pipeline
    return pipeline.main()
```

Three observations, all of which matter:

1. **`args` is never read.** The signature promises configurability that does not exist.
   `cmd_run(None)`, `cmd_run([])`, and `cmd_run(argparse.Namespace())` all behave
   identically, because nothing dereferences `args`. That is the *empty list* case from
   the lens, and it is the best news in this report — the function cannot be misused via
   its argument. It is also the symptom: there is no `--sources`, no `--out-dir`, no
   `--deadline`, no `--dry-run`, no `--verbose`. For a cron entry point, none of those can
   be added later without a breaking change to the dispatch table, because `cmd_run` has
   no seam for them.
2. **`import main as pipeline` at `cli.py:35` is a runtime import.** It executes
   `main.py:25-31`, which imports all three scrapers, `dedup`, `enricher`, and
   `pitch_recommender`. Any `ImportError` there surfaces as a raw traceback out of
   `cmd_run`, exit 1 — whereas `cmd_doctor` (`cli.py:225-231`) explicitly guards its
   import of `requests` with a friendly message and the comment *"doctor exists to
   diagnose a broken environment, so it must never be the thing that tracebacks."* The
   run path has strictly worse diagnostics than the diagnostic path.
3. **The wheel may not ship the modules it imports.** `pyproject.toml:33` declares the
   console script `leadminer = "cli:main"`, and `cli.py:35` imports top-level `main`.
   But `[tool.hatch.build.targets.wheel]` at `pyproject.toml:35-37` declares only
   `include = ["scrapers/"]` with no `packages` or `only-include`, and its own comment
   says *"The package imports a top-level sibling module, so both must ship."* As written,
   `cli.py` and `main.py` are not guaranteed to be in the artifact. I could not verify this
   — hatchling is not installed in this environment and I was instructed not to install
   packages. One command settles it: `uv build && unzip -l dist/*.whl | grep -E 'cli|main'`.
   If they are absent, `leadminer run` fails at import on a real install while
   `python main.py` — what CI actually runs — keeps working, which is the worst possible
   split: green CI, broken cron.

**Never printed, anywhere in this pipeline:**

- **No timestamp on any line.** Every one of the ~25 possible output lines above is
  unlabelled in time. A six-hour log tells you *what* happened and not *when* or *how long*.
  You cannot tell "OSM took six hours" from "OSM returned in 40s and enrichment took
  five hours", because there are no phase boundaries and no elapsed times.
- **No exception traceback.** `main.py:168` prints `str(e)` and discards the traceback.
  A genuine bug in a scraper is reported as one line of the form
  `[OSMScraper] ERROR: 'NoneType' object is not subscriptable` with no file, no line.
- **Nothing from `httpclient.log`.** `httpclient.py:45` defines a module logger and every
  retry/backoff message in it is `log.debug` (`httpclient.py:178-179`, `204-205`). Neither
  `cli.py` nor `main.py` ever calls `logging.basicConfig` or adds a handler, so **every
  retry, every backoff duration, and every transport error in the central HTTP client is
  written to a logger with no handlers and goes nowhere.** Same for `osm.py:7` and
  `wikidata.py:7`. The observability that `httpclient.py` was carefully built to provide
  — its own docstring at `httpclient.py:17-19` frames exactly the "failures were
  indistinguishable" problem — is discarded at the entry point. For diagnosing a network
  drop six hours into a run, this is the single most painful gap in the file.

## The five scenarios the lens asks about

### 1. The network drops halfway

This is the worst one, because it **corrupts data that was previously correct** and
publishes the corruption atomically so it looks healthy.

`main.py:179` builds `combined = raw_filtered + master` and `main.py:187` runs
`records = enrich(records)` over the **whole cumulative set**, not just this run's new
records. So every run re-probes every website ever discovered.

`enricher.py:250` then assigns the verdict unconditionally:

```python
r["website_live"] = True if outcome == LIVE else (False if outcome == DEAD else None)
```

and `enricher.py:175` fetches with `timeout=8` and **no retry** — it calls
`get_session().get(...)` directly rather than going through `fetch_with_retry`, so the
retry-and-jitter machinery in `httpclient.py` does not apply to this call path at all.

Concrete input: a master CSV with 40,000 rows, 12,000 of them with websites, all
previously `website_live=True`. A switch/router blip at enrichment minute 31 causes the
remaining ~4,000 fetches to DNS-fail. Result:

- `website_live` flips `True → None` for every record probed after the blip
  (`enricher.py:250`, `UNKNOWN` from `enricher.py:176-178`).
- `lead_score` silently loses 10 points for each of them (`enricher.py:300-302`), and
  those rows fall in the ranking.
- `without_websites.csv` does not change (they still have `website`), but
  `qualified_businesses.csv` membership can change, because `completeness_score` is
  recomputed from scratch at `enricher.py:349`.
- `main.py:209` writes all of this over the good master.

The previous value is never retained, so there is no way to tell afterwards which rows
were degraded. `cli.py:107-113` (`cmd_stats`) and `main.py:215-217` both *report* the
`unreachable` count faithfully — the instrumentation exists and is correct — but nothing
**gates** on it. A tri-state column that is printed and never asserted on is a comment,
not a safety mechanism.

### 2. A dependency returns garbage

Three distinct sub-cases, all silent, all exit 0.

**(a) Overpass returns HTTP 200 with an error body.** Overpass's standard soft failure is
`200 OK` with `{"remark": "runtime error: Query timed out ..."}`. `osm.py:58` does
`elements = result.json().get("elements", [])` — the `.get` swallows the missing key and
yields `[]`. Output: `[OSM] Got 0 elements.` Then `main.py:165` prints
`[OSMScraper] collected 0 records`. There is no failure anywhere in the log. Identical
shape at `wikidata.py:87`. A timed-out Overpass query and a country with no businesses are
indistinguishable.

**(b) Google returns HTTP 200 with a non-JSON body.** `google_places.py:254` calls
`resp.json()` *outside* the `try` at `google_places.py:250`, whose handler catches only
`requests.RequestException`. `json.JSONDecodeError` subclasses `ValueError`, not
`RequestException`, so it escapes `_scrape_query` → escapes `fetch_query` →
`f.result()` at `google_places.py:197` re-raises it → it propagates out of
`GooglePlacesScraper.scrape`, through the `with ThreadPoolExecutor` at
`google_places.py:194` (`__exit__` does `shutdown(wait=True)`, so it first blocks for the
other four workers, up to 180s each) → to `main.py:164`, where `except Exception` at
`main.py:167` prints `[GooglePlacesScraper] ERROR: Expecting value: line 1 column 1 (char 0)`
and continues.

**One malformed response destroys all 68 queries**, including the 67 that succeeded, because
`all_records` (`google_places.py:183`) is abandoned mid-flight. Google Places is the only
source that supplies `rating`, `review_count`, and coordinates (`google_places.py:297-298`,
`:303-304`) — losing it degrades the entire product, not just one source's column.

**(c) A dependency raises `SystemExit`.** `SystemExit` is a `BaseException`, so it is not
caught by `main.py:167`, nor by `enricher.py:244`, nor by `cli.py:314-318` (which handles
`KeyboardInterrupt` only). It propagates out of `main()`, so `raise SystemExit(main())` at
`cli.py:322` never executes. If the `SystemExit` carried code 0 — a vendored helper or an
argparse-based library deciding "nothing to do" — **the process exits 0 having printed
nothing and written no CSVs.** A complete silent no-op that reports success.

### 3. Called with an empty list

Literally: nothing happens, because `args` is unused. See above.

Substantively — an empty pipeline — is catastrophic. `main.py:206-213` writes all five
CSVs unconditionally, and `write_csv` (`main.py:108-134`) is atomic, so an empty run
**replaces the master with a one-line CSV**:

```
$ wc -l data/all_businesses.csv
1 data/all_businesses.csv
```

This is reachable in production because `load_master` returns `[]` for *three different
conditions that are indistinguishable from each other* (`main.py:79-80` returns `[]` when
`not path.exists()`):

1. the file genuinely does not exist (first run, or wrong `CWD` — see S1-4);
2. the file exists but is 0 bytes;
3. the file exists and contains only a BOM or a blank line, so `csv.DictReader`
   (`main.py:86`) yields zero rows.

In cases 2 and 3 the master is **destroyed**, and the only signal is the *absence* of the
line `Loaded N records from existing master CSV` (`main.py:152`) — a negative signal, in a
log where every other line is positive. Then `enrich([])` is a no-op: `check_websites`
returns early at `enricher.py:232-233` **before** its first `print`, so a total-failure run
has *zero* enricher output, and `main.py:219-226` prints a Summary of all zeros. Exit 0.

The workflow guards cases 1-3 for its own path (`if [ ! -s data/all_businesses.csv ]` and
the `ROWS -lt 100` check). `cmd_run` guards none of them.

### 4. Interrupted

**SIGINT / Ctrl-C: the command appears to ignore you.** `cli.py:316-318` catches
`KeyboardInterrupt` and prints `interrupted` — but only after the `with
ThreadPoolExecutor` at `enricher.py:237` exits, and
`ThreadPoolExecutor.__exit__` calls `shutdown(wait=True)`, which **waits for every
outstanding future and cancels none of them.**

`enricher.py:238` submits **one future per target up front**:

```python
futures = {pool.submit(_fetch_website, url): idx for idx, url in targets}
```

So there is no work-conserving queue — the entire backlog is already scheduled. Concrete
input: 50,000 websites, Ctrl-C at the halfway point. `R ≈ 25,000` futures remain. At
40 workers and `timeout=8` (`enricher.py:175`, `enricher.py:225`), shutdown waits
`ceil(25000/40) × 8s = 5,000s ≈ 83 minutes` before the word "interrupted" appears.
**The operator sits there for an hour and a half with no output and assumes it is hung.**
The same shape exists at `google_places.py:194-197`.

**SIGTERM (what `systemd`, `TimeoutStartSec`, and most process supervisors actually send):
not handled at all.** Default disposition, immediate death, `finally` blocks and
`except BaseException` handlers do not run. If the signal lands inside
`writer.writerows` (`main.py:127`), the `except BaseException: tmp.unlink()` at
`main.py:131-133` never fires and `data/all_businesses.csv.tmp` is left on disk. The
master itself survives — `write_csv`'s atomicity is correct and this is the one thing the
code gets right — but the five CSVs are written sequentially at `main.py:209-213`, so a
kill between them leaves a **torn export set**: a new `all_businesses.csv` next to
last-week's `sales_ready.csv`. Nothing anywhere compares mtimes or checks set consistency.
`leadminer stats` (`cli.py:79`) will happily summarise the stale one.

**SIGKILL (the GitHub Actions `timeout-minutes: 300`, `.github/workflows/scrape.yml`) plus
buffering: the evidence is destroyed.** See S2-1.

### 5. Nothing is bounded, and the bound is getting worse every week

Runtime arithmetic, from the code's own constants:

| Phase | Bound |
|---|---|
| OSM | `timeout=200, retries=3` (`osm.py:44-45`) → ≈ 603s worst case |
| Wikidata | `timeout=90, retries=3` (`wikidata.py:75-76`) → ≈ 273s worst case |
| Google | `_QUERY_BUDGET_SECONDS = 180.0` (`google_places.py:152`), 68 queries / 5 workers = 13.6 waves → ≈ 2,450s ≈ 41min minimum if every query exhausts its budget |
| **Enrich** | **`ceil(N_sites/40) × 8s`, with no ceiling anywhere** |

The enrichment phase is the problem, and it is *cumulative*: `main.py:179` merges this
run's records with the entire accumulated master before enriching.

| Master rows with websites | Worst-case enrichment |
|---|---|
| 1,000 | 200s |
| 10,000 | 33min |
| 50,000 | 2.8h |
| 100,000 | **5.6h — exceeds `timeout-minutes: 300` on its own** |

There is no deadline in `cmd_run` and no deadline in `main.py`. `as_completed(futures)` at
`main.py:162` takes no `timeout` argument. The only thing stopping the run is the Actions
runner killing it at 300 minutes — at which point `main.py:209-213` has never executed and
**the entire week's work is discarded**, because the only persistence in the pipeline is
those five write calls. Six hours is not a hypothetical for this system; it is the shape
of the curve.

Worse, there is a genuinely **unbounded** path. `timeout=8` in `requests` is a *socket
inactivity* timeout, not a total deadline. `enricher.py:188` caps bytes
(`r.raw.read(_MAX_BODY_BYTES, ...)` with `_MAX_BODY_BYTES = 200_000` from
`httpclient.py:54`) but caps nothing about time. A host that trickles one byte every seven
seconds holds a worker for `200,000 × 7s ≈ 16 days`. Ten such hosts and the run never
finishes. This is on the code path `cmd_run` invokes, and nothing anywhere defends it.

## Findings

### S1 — `cmd_run` returns success unconditionally; there is no failure channel
- **Where:** `cli.py:33-37`, `cli.py:315`, `main.py:148`
- **Breaks:** `cmd_run` is annotated `-> int` but `main.main()` is annotated `-> None` and
  returns `None` on every path (`main.py:148`). `cli.py:315` does
  `int(args.func(args) or 0)`, so `None` becomes `0`. `leadminer run` therefore exits 0
  after zero records from all three sources, after a destroyed master, and after a
  network-degraded enrichment pass. Every other subcommand returns a real code
  (`cli.py:59,66,84,90,131,201,244,262`), which makes `cmd_run` the odd one out and means
  the inconsistency is invisible from the dispatch table.
- **Trigger:** `GOOGLE_PLACES_API_KEY="" leadminer run` with Overpass rate-limiting. Output
  ends with a complete `Summary:` block full of zeros; `$?` is `0`.
- **Fix:** make `main.main()` return an int and have it return non-zero when any scraper
  raised, when `records` is empty, or when the master failed to load; `cmd_run` returns
  that value unchanged. Delete the `or 0` at `cli.py:315` so a `None` return is a
  `TypeError` in CI rather than a silent success.

### S1 — A master that reloads as empty is republished as a header-only CSV
- **Where:** `main.py:79-80`, `main.py:151`, `main.py:206-213`, `main.py:108-134`
- **Breaks:** `load_master` returns `[]` when `not path.exists()` and the caller cannot
  distinguish "absent" from "present but zero rows". `main.py:151` prints the `Loaded N`
  line only `if master`, so the failure mode is the *absence* of a line. `main.py:209`
  then unconditionally overwrites `all_businesses.csv` with `[]` — and because
  `write_csv` is atomic, the destruction is clean and irreversible. A 0-byte master, a
  master containing only a BOM, or a master with only a blank line all trigger this.
- **Trigger:** `data/all_businesses.csv` truncated to 3 bytes by a filesystem event, then
  `leadminer run`. Result: `wc -l` = 1, exit 0, no error anywhere.
- **Fix:** distinguish the cases in `load_master` (`raise`/`FileNotFoundError` on absent,
  `raise` on zero rows) and have `cmd_run` refuse to run — and never write — when the
  master exists but yielded zero records. This is the one guard that belongs in the entry
  point rather than in the workflow.

### S1 — Enrichment failures overwrite previously-correct values in the cumulative master
- **Where:** `enricher.py:175` (no retry), `enricher.py:250` (unconditional assignment),
  `enricher.py:176-178` (all transport failures → `UNKNOWN`), `main.py:179`, `main.py:187`,
  `main.py:209`
- **Breaks:** `enrich` runs over `raw_filtered + master`, so every run re-probes the whole
  accumulated history and unconditionally rewrites `website_live`. A transient failure
  converts a known-`True` site to `None`, drops 10 points of `lead_score`
  (`enricher.py:300-302`), and republishes the master. The prior value is discarded, so the
  degradation is unrecoverable and undetectable after the fact. Note the asymmetry:
  `enricher.py` is careful never to conflate UNKNOWN with DEAD (`enricher.py:145-156`) —
  and then `main.py:209` persists UNKNOWN over the truth with no equivalent care.
- **Trigger:** router blip during enrichment of a 12,000-website master.
- **Fix:** make the existing tri-state load-bearing — only overwrite a non-`None`
  `website_live` with a *positive* verdict, and record the newest non-`None` observation in
  a separate column (`website_live_checked_at`) so `True→None` transitions are auditable.
  Then gate the run on the `unreachable` delta that `main.py:215-217` already computes.

### S1 — `DATA_DIR` is CWD-relative, so a cron entry without `cd` silently resets history
- **Where:** `cli.py:26`, `main.py:41`, `main.py:150`, `main.py:208`
- **Breaks:** both `DATA_DIR` definitions are bare `pathlib.Path("data")`. A crontab line
  without `cd /srv/leadminer` resolves them against `$HOME`. `load_master` then finds no
  master and returns `[]` silently (`main.py:79-80`), and `main.py:208` creates
  `$HOME/data/`. The run succeeds, exits 0, and produces a valid-looking single-run master
  that a subsequent upload step publishes over months of accumulation. `cmd_doctor`
  compounds this: `cli.py:217` checks `DATA_DIR.exists()` against the same relative path,
  so it will report `MISSING data (no run has produced output yet)` — a confident false
  statement about a directory that is full of leads.
- **Trigger:** `0 3 * * 1 leadminer run` with no `cd`. First run: green. Second run:
  green, and the master is a single week of data.
- **Fix:** resolve `DATA_DIR` from an env var with a package-relative default, and have
  `cmd_run` `os.chdir()` to the resolved root before importing `main`. Add
  `--out-dir` while the signature is still safe to change.

### S1 — Overlapping runs share one temp path and can publish a corrupt master
- **Where:** `main.py:122` (`tmp = path.with_suffix(path.suffix + ".tmp")`),
  `main.py:123-133`, `cli.py:33-37`
- **Breaks:** the temp filename is derived from the target, not from the PID, so two
  concurrent runs on the same checkout use the *same inode* for `all_businesses.csv.tmp`.
  Run B's `open(tmp, "w")` truncates the file run A is mid-write on; A's `os.replace`
  then renames that inode into place while B keeps appending to it — which is now
  `all_businesses.csv`. The published master ends up as A's rows followed by B's from B's
  offset, with NUL padding where B truncated underneath A, and a duplicated header. B's own
  `os.replace` then fails with `FileNotFoundError`. `csv.DictReader` tolerates all of it,
  so the file still loads. `cmd_run` has no lockfile, no PID check, and no `--force`.
  `.github/workflows/scrape.yml` has `concurrency: group: leadminer-scrape`, which is why
  CI has not hit this — but the lens is a *cron job*, and crontab has no equivalent.
  Note the interaction with S1-4: a second run from a different `CWD` has a different temp
  path, so the two failure modes mask each other.
- **Trigger:** cron period shorter than the run duration. Given S2-5, the run *will*
  eventually exceed five hours, so this stops being hypothetical.
- **Fix:** `tmp = path.with_suffix(f".{os.getpid()}.tmp")`, and take an exclusive
  `fcntl.flock` on a lockfile in `DATA_DIR` in `cmd_run` — fail fast with a non-zero exit
  rather than running concurrently.

### S1 — No wall-clock bound, and `Ctrl-C` appears to hang for over an hour
- **Where:** `cli.py:33-37` (no deadline), `main.py:162` (`as_completed` with no
  `timeout`), `enricher.py:238` (all futures submitted up front),
  `enricher.py:237` (`__exit__` → `shutdown(wait=True)`), `enricher.py:175`,
  `cli.py:316-318`
- **Breaks:** the enrichment phase is bounded only by `ceil(N_sites/40) × 8s` against a
  master that grows monotonically every week; there is no deadline in the entry point or
  in `main.py`. On `KeyboardInterrupt`, `ThreadPoolExecutor.__exit__` waits for every
  already-submitted future — 25,000 of them is ~83 minutes of silence before
  `cli.py:317` prints anything. A trickle-feeding host (`enricher.py:188` caps bytes, not
  time) makes it truly unbounded.
- **Trigger:** 100,000 websites in the master; run is SIGKILLed at the Actions 300-minute
  limit with `main.py:209` never reached.
- **Fix:** a `--deadline`/watchdog in `cmd_run` that stops accepting new work and writes
  whatever is enriched so far; and pass `cancel_futures=True` semantics so `Ctrl-C`
  actually returns.

### S2 — stdout is block-buffered and never flushed, so a killed run loses its most useful output
- **Where:** `cli.py:33-37` (no `reconfigure`, no `flush=True`), versus
  `main.py:134` and `main.py:219-242`; contrast `osm.py:54`, `wikidata.py:83`,
  `google_places.py:232` which *do* use `flush=True` on the stderr path
- **Breaks:** under cron, stdout is block-buffered (8KB) while stderr is unbuffered. Two
  consequences. (1) **Ordering:** the failure lines from `main.py:168` and the `FAILED`
  lines from `osm.py:51-55` land at the *top* of the log, hours before the
  `Loaded N records` line they logically follow — so reading a failed log top-down shows
  errors first and a success-looking summary last. (2) **Loss:** if the process dies
  without flushing — SIGKILL from `timeout-minutes: 300`, SIGTERM from a supervisor, or
  an OOM kill — the final partial buffer is discarded. That buffer is exactly where the
  five `Written: ...` confirmations (`main.py:134`) and the entire `Summary:` block
  (`main.py:219-242`) live. The most informative part of the log is the part that
  disappears.
- **Trigger:** `leadminer run > /var/log/leadminer.log 2>&1` from a crontab, run killed
  by the supervisor at timeout. Tail of the log ends mid-`[Enricher] 4200/5000`.
- **Fix:** `sys.stdout.reconfigure(line_buffering=True)` at the top of `cli.main`.

### S2 — No logging is configured, so the HTTP client's diagnostics are discarded
- **Where:** `cli.py:33-37` and `cli.py:312-318` (no `logging.basicConfig` anywhere);
  `httpclient.py:45`, `httpclient.py:178-179`, `httpclient.py:204-205`;
  `osm.py:7`, `wikidata.py:7`
- **Breaks:** every retry, backoff duration, and transport error in the central HTTP client
  is emitted at `log.debug` to a logger with no handlers. Python's last-resort handler
  only emits `WARNING` and above, so all of it is dropped. The retry instrumentation that
  `httpclient.py` exists to provide is invisible from the command line.
- **Trigger:** any run. Visible only as the absence of information when diagnosing a slow
  phase.
- **Fix:** configure a handler in `cli.main` gated on `--verbose`/`LEADMINER_LOG`
  (stderr, timestamped), and add `-v` to the `run` subparser.

### S2 — `cmd_run` ignores `args`, so a cron entry cannot bound or redirect anything
- **Where:** `cli.py:33-37`; compare `cli.py:135-201` (`cmd_validate`) and
  `cli.py:204-244` (`cmd_doctor`), which both take real options
- **Breaks:** `args` is declared and never read. There is no way to select sources, set an
  output directory, impose a deadline, raise log level, or dry-run. `leadminer run --source
  osm` fails at argparse level with a usage error, so the operational workarounds are
  "call `python main.py`" (what CI does) or "run `leadminer scrape` first, separately" —
  both of which bypass every guard `cmd_run` should own.
- **Trigger:** an operator who needs to re-run only Google after a key rotation.
- **Fix:** give `run` the same option surface the other subcommands have, and have
  `main.main()` accept them. This is the right moment: `args` is already plumbed.

### S2 — One malformed Google response discards 68 successful queries
- **Where:** `google_places.py:250` (`except requests.RequestException`),
  `google_places.py:254` (`resp.json()` outside the `try`), `google_places.py:196-197`
  (`f.result()` re-raises), `google_places.py:183-192`
- **Breaks:** `json.JSONDecodeError` is a `ValueError`, not a `RequestException`, so a
  200-with-HTML-body from Google propagates out of the worker, past
  `google_places.py:197`, out of the `ThreadPoolExecutor`, and into `main.py:167`. The
  already-collected `all_records` from the other four workers is abandoned. Google is the
  sole source of `rating` and `review_count` (`google_places.py:297-298`), which feed
  `lead_score` (`enricher.py:312-314`), so the loss is not contained to one column.
- **Trigger:** an edge proxy returns an HTML interstitial with status 200 for one query.
- **Fix:** catch `ValueError` alongside `RequestException` in `_scrape_query` and return
  `records` as-is; and wrap the per-worker result in `fetch_query` so one query's failure
  cannot take down the source.

### S2 — HTTP-200-with-error-body is indistinguishable from an empty country
- **Where:** `osm.py:58`, `osm.py:59`, `wikidata.py:87`, `wikidata.py:88`;
  consumed at `main.py:164-165`
- **Breaks:** Overpass's standard soft failure is `200 OK` with
  `{"remark": "runtime error: Query timed out ..."}`. `.get("elements", [])` turns that
  into `[]`, and the log says `[OSM] Got 0 elements.` — byte-identical to a real empty
  result. There is no failure anywhere in the output, and `main.py:165` then reports
  `[OSMScraper] collected 0 records` as a success.
- **Trigger:** Overpass returns a `remark` body for a query over the timeout budget.
- **Fix:** check for a `remark` key (and for a missing `elements` key) and treat either as
  a failure, matching the treatment already given to non-2xx at `osm.py:47`.

### S2 — Nothing is persisted until the final minute
- **Where:** `main.py:209-213` (the only writes), `main.py:187` (the long phase)
- **Breaks:** the entire run — scraping, merging, enriching — accumulates in memory and is
  written only after the slowest phase completes. Combined with the unbounded enrichment
  cost above, the expected failure mode is "the runner kills the job at 300 minutes," and
  the expected consequence is "the week is lost." The 14-day artifact upload
  (`if: always()`) preserves a partial `data/` directory that contains the *downloaded*
  master, so the artifact looks like a successful run's output.
- **Fix:** checkpoint the scraped batch to `data/_staging/` as each source completes
  (`main.py:162-166` is the natural hook), so a killed run resumes rather than restarts.

### S2 — `SystemExit` from a dependency escapes every handler
- **Where:** `main.py:167` (`except Exception`), `enricher.py:244`, `cli.py:314-318`
- **Breaks:** `SystemExit` derives from `BaseException`. It is not caught by any of the
  three handlers, and `cli.py:314-318` handles `KeyboardInterrupt` only. It propagates out
  of `main()`, so `raise SystemExit(main())` at `cli.py:322` never runs and the
  interpreter's top-level handling applies. `SystemExit(0)` from a dependency produces
  **exit 0, no output, no CSVs.**
- **Trigger:** any dependency in the call path that calls `sys.exit()`.
- **Fix:** catch `SystemExit` explicitly in `cli.main` and map a non-zero payload to a
  non-zero return, rather than letting it escape as a success.

### S3 — The traceback is discarded at the one place a bug would surface
- **Where:** `main.py:168` — `print(f"...ERROR: {e}", file=sys.stderr)`
- **Breaks:** only `str(e)`. No exception class, no traceback. A real defect in a scraper
  is reported as one anonymous line with no file or line number, and there is no run log
  file to grep.
- **Trigger:** any scraper bug. `[OSMScraper] ERROR: 'NoneType' object is not subscriptable`
- **Fix:** `traceback.print_exc()` to stderr, or `log.exception(...)` once logging exists.

### S3 — No test covers `cmd_run` or the exit-code path
- **Where:** `tests/test_lead_signal.py:211-263` tests `cmd_stats` and `cmd_validate`
  only; `grep` finds no reference to `cmd_run` or to `cli.main` anywhere outside `cli.py`
- **Breaks:** the five exit codes of the other five subcommands are exercised. The one
  command that runs the network, takes hours, and writes the product has no test, and the
  `int(... or 0)` coercion at `cli.py:315` is untested. Every S1 above is a two-line
  regression test away from being caught.
- **Fix:** tests asserting `cmd_run` returns non-zero when a scraper raises, when `records`
  is empty, and when `load_master` returns `[]` for a present-but-empty file — with
  `main.pipeline` monkeypatched, so no network.

### S3 — The wheel target may not ship the modules the console script imports
- **Where:** `pyproject.toml:33`, `pyproject.toml:35-37`, `cli.py:35`
- **Breaks:** `include = ["scrapers/"]` with no `packages`/`only-include` does not
  obviously include top-level `cli.py` and `main.py`, whose inclusion the adjacent comment
  claims is required. If they are absent, `leadminer run` fails at import on an installed
  wheel while `python main.py` — the path CI exercises (`.github/workflows/scrape.yml`,
  the "Run scrapers" step) — keeps passing.
- **Trigger:** `uv build && unzip -l dist/*.whl | grep -E '(^|/)(cli|main)\.py'`
- **Fix:** confirm with that one command; if empty, add
  `packages = ["scrapers"]` plus `force-include` for the two modules, or move to a
  `src/` layout so the dependency is structural.

## Not a bug, but worth knowing

- **`cmd_run` is not on the CI production path.** `.github/workflows/scrape.yml` invokes
  `python main.py` in its "Run scrapers" step. `cmd_run` is reachable only via the
  `leadminer` console script, which only `README.md:11` and `README.md:96` tell anyone to
  use. So the brief's "six hours on a cron job" scenario is currently a *documented but
  unexercised* path — which is exactly why it has no guards. Whichever way this is
  reconciled, the guards belong in `cmd_run`, because the workflow's guards
  (`[ ! -s data/all_businesses.csv ]`, `ROWS -lt 100`) live in a YAML file that only the
  Actions path executes.
- **The atomic write is genuinely correct.** `write_csv` (`main.py:108-134`) writes to a
  temp file, `flush`es, `fsync`s, and `os.replace`s. `except BaseException`
  (`main.py:131`) correctly catches `KeyboardInterrupt` during the write and unlinks the
  temp. This is the one part of the crash story that works, and
  `tests/test_lead_signal.py:157` covers it. The residual gap is that the parent directory
  is never `fsync`ed, so the rename is not durable across power loss — harmless in
  practice, since the failure mode is "old file survives", not corruption.
- **The 401 path is the best diagnostic in the codebase.** `google_places.py:231-232`
  prints `FATAL: invalid API key (401)` with `flush=True` and is explicit that no Places
  data will be collected. The problem is only that (a) it repeats 68 times, (b) nothing
  gates on it, and (c) `cmd_doctor` (`cli.py:210-214`) checks only that the variable is
  *present*, so an expired key passes `doctor` and then fails 68 times inside `run`.
- **The tri-state `LIVE`/`DEAD`/`UNKNOWN` model is well built** (`enricher.py:145-156`,
  `enricher.py:161-222`) and the comment at `enricher.py:145-146` shows the reasoning was
  done carefully. The failure is entirely downstream, in `main.py` persisting the result
  without regard for what was there before.
- **`google_places.py`'s rate-limit bounding is correct and was clearly deliberate**
  (`google_places.py:144-152` documents the old infinite-429 loop it replaced). The
  `_QUERY_BUDGET_SECONDS` check at `google_places.py:217` is only evaluated between pages,
  so a query can overshoot by up to one `time.sleep(60)` plus one 30s request — bounded,
  but worth knowing when reading timing logs.
- **`bs4` and `lxml` are pinned in `requirements.txt` but imported nowhere.** A grep for
  `bs4`/`BeautifulSoup`/`lxml` across all `.py` files returns nothing, and
  `pyproject.toml:16-18` correctly depends only on `requests`. So the `ImportError` risk at
  `cli.py:35` is limited to `requests` itself, and the two stale pins in
  `requirements.txt` — which is what `.github/workflows/scrape.yml` actually installs —
  are dead weight.

## Recommended order of work

1. **Give `cmd_run` a failure channel.** Change `main.main()` to return an `int` and make
   it non-zero for: any scraper raising (`main.py:167`), `records` empty, master present
   but yielding zero rows. Remove the `or 0` at `cli.py:315`. Nothing else in this report
   matters if the command still cannot say "I failed." (S1-1, S1-2)
2. **Harden the empty-master path before it destroys data.** Make `load_master`
   distinguish absent from present-but-empty, and refuse to write when the master existed
   and yielded nothing. This is ledger items #1 and #2 — the two that are both weeks-to-
   notice and irreversible. (S1-2)
3. **Resolve `DATA_DIR` absolutely and add `--out-dir`,** so a crontab line cannot write
   the master to `$HOME`. Do this while `args` is still unread and the signature is still
   free to change. (S1-4, S2-2)
4. **Add a PID-unique temp name and an `flock` in `cmd_run`.** One line and one lockfile;
   removes the corrupt-master race outright. (S1-5)
5. **Flush stdout and configure logging,** then add timestamps. Turns "the log stops
   mid-line" into a diagnosable record, and surfaces the `httpclient` retry data that is
   currently thrown away. (S2-1, S2-2, S3-1)
6. **Stop persisting `UNKNOWN` over a known verdict,** and gate the run on the
   `unreachable` count `main.py:215-217` already computes. (S1-3)
7. **Add a deadline and make `Ctrl-C` cancel,** so a six-hour run can be stopped in
   seconds and a killed run still writes what it has. (S1-6, S2-4)
8. **Fix the two `except` clauses that are too narrow or too lossy** —
   `ValueError` in `_scrape_query`, `remark` detection in OSM/Wikidata, `SystemExit` in
   `cli.main`. (S2-2, S2-3, S2-5)
9. **Write the tests** for `cmd_run`'s exit codes with `main.pipeline` monkeypatched, and
   settle the wheel-packaging question with one `unzip -l`. (S3-2, S3-3)
