# 233 — `cmd_validate` boundary and hostile-input audit

**Target:** `cmd_validate` — `cli.py:135-201`
**Method:** ~120 hostile inputs executed against the real function (read-only import, no network, no installs). Every claim below is an observed result, not an inference.
**Interpreter caveat:** the only local interpreter is CPython **3.14.8**; the project targets 3.12 (`.github/workflows/scrape.yml:34`). The behaviours relied on here — `csv.field_size_limit()` default of 131072, `utf-8-sig` strict decoding, `pathlib` swallowing `OSError`/`ValueError` in `.exists()`, and `float()` accepting any Unicode `Nd` digit — are identical in 3.12–3.14. One case (NUL byte in content) is 3.14-only-observed; if 3.12 differs it is an *additional* crash case, not a removed one.

---

## Verdict

The numeric *judging* logic is genuinely good: `nan`, `inf`, `-inf`, `-1`, `0`, `5.0000001`, `1e309` and out-of-market coordinates are all correctly caught. The **I/O envelope and the "could not read" path are not.**

Five input families make the function either crash with a raw traceback, or — far worse — print `all checks passed` and exit `0` on data that is entirely wrong. The most dangerous single input is a CSV whose `lat`/`lon` are present but unparseable, because `cli.py:169`'s bare `continue` turns *"I could not read this coordinate"* into *"this coordinate is fine"*, silently disabling the one check that verifies the data belongs to the two markets this product sells.

Context that sets severity: `cmd_validate` is **never invoked by CI**. `.github/workflows/scrape.yml:71-83` does its own inline `wc -l` checks and never calls the CLI. So a crash here costs an operator's afternoon, not the pipeline — but `cli.py:14-15` sells this command as *"what you reach for when a run looks wrong"*, and a false `exit 0` from the one command whose job is to answer "is this data trustworthy?" is worse than no tool at all.

## Findings

### S1 — `continue` on an unparseable coordinate converts "unknown" into "good", silently disabling the geographic gate

- **Where:** `cli.py:164-173`, specifically the `except`/`continue` at `cli.py:168-169`
- **Breaks:** `bad_coords` counts only rows it *successfully parsed and found out of range*. Every row whose `lat`/`lon` cannot be parsed as an ASCII float increments nothing. There is no `parsed` counter, no `bad_coords + unparsed` denominator, and no third state. The result is that the coordinate check degrades from a hard assertion into a no-op that still prints a success message.
- **Five distinct triggers, all verified, all `exit 0`:**

  | Trigger (input value in the `lat` column) | `float()` result | Gate says |
  |---|---|---|
  | `"٤٨٫٨٥"` (U+066B ARABIC DECIMAL SEPARATOR) | `ValueError` | `all checks passed` |
  | `"48,85"` (French/comma decimal) | `ValueError` | `all checks passed` |
  | `"48 850"` with U+202F narrow no-break spaces | `ValueError` | `all checks passed` |
  | `""` on every row | `ValueError` | `all checks passed` |
  | `"N/A"` on every row | `ValueError` | `all checks passed` |

  And the same `KeyError → continue` branch fires when the column is **absent or renamed**: a 22-column file with `lat`/`lon` renamed to `latitude`/`longitude` containing 200 Paris coordinates returns `rc=0, "all checks passed"`. `KeyError` at `cli.py:168` is swallowed exactly like a parse failure.
- **The most realistic version of this is the whole file at once.** 5,000 rows, every `lat` written as `"٤٨٫٨٦"` (Arabic decimal separator — what you get from an Arabic-keyboard or Arabic-locale Excel export):
  ```
  checked 5,000 rows in .../arabic_sep.csv
    all checks passed
  ```
  100% of the records are in Paris. The tool says the data is fine.
- **The asymmetry is the sting.** The same file exported French-style (`lat="48,8566"`, `rating="4,2"`) does fail — but the *only* complaint is about the harmless cosmetic field:
  ```
  checked 5,000 rows in .../french.csv
    PROBLEMS:
      - 5000 rows have a rating outside 0-5
  ```
  The loud check fires on `rating`; the quiet check skips `lat`. The operator is sent to fix the wrong thing.
- **Fix (one line of intent, ~6 of code):** make the parse outcome tri-state and fail on a low parse rate, e.g.
  ```python
  parsed, bad, unparsed = 0, 0, 0
  for r in rows:
      try:
          lat, lon = float(r["lat"]), float(r["lon"])
      except (ValueError, TypeError, KeyError):
          unparsed += 1
          continue
      parsed += 1
      bad += not in_box(lat, lon)
  if parsed and unparsed / total > 0.01:
      problems.append(f"{unparsed} rows have unparseable/missing lat-lon")
  ```
  Plus an explicit schema assertion before the loop: `missing = set(FIELDS) - set(rows[0])` → fail. That closes the `KeyError` variant too.

### S2 — The duplicate check disagrees with the pipeline's own `dedup`, reporting 0 duplicates on files `dedup()` halves

- **Where:** `cli.py:190`
  ```python
  dupes = total - len({(r.get("name"), r.get("phone")) for r in rows})
  ```
  This keys on **raw strings**. `dedup.dedup()` (`dedup.py:197-232`) keys on `normalize_phone` (`dedup.py:33-63`) and `normalize_name` (`dedup.py:66-69`), which strip punctuation, collapse whitespace, strip accents and lowercase. The two tools answer different questions and the CLI's is the wrong one.
- **Trigger (verified against the real `dedup`):** 200 rows = 100 real businesses, each twice, phone written two ways.
  ```
  rows[0] = {'name': 'Cafe 42', 'phone': '9617000042'}
  rows[1] = {'name': 'Cafe 42', 'phone': '+961 70 000042'}
  ```
  ```
  dedup.dedup(rows)                  -> 100 records
  cmd_validate(...)                  -> rc=0, "all checks passed"
  ```
  `normalize_phone('9617000042') == normalize_phone('+961 70 000042') == '+9617000042'`, so the pipeline merges all 100 pairs. `cmd_validate` sees 200 distinct string tuples and reports **zero** duplicates. Same result for the accent/transliteration case (`'Cafe Beirut 42'` vs `'Café Beyrouth 42'`, identical phone): `dedup()` 200 → 100, `cmd_validate` reports 0.
- **Converse failure — the metric lies in the other direction too.** 200 rows with `name` and `phone` both blank produces `"199 duplicate (name, phone) pairs"`. Those are not duplicates; they are missing rows. The single metric conflates *identical records* with *absent identity*, so an operator cannot tell which problem they have.
- **Fix:** reuse the pipeline's key instead of re-deriving it —
  `{(normalize_phone(r.get("phone"), r.get("country") or "LB"), normalize_name(r.get("name") or ""), _extract_city(r.get("address"))) for r in rows}` — and report blank-identity rows as their own problem rather than as duplicates.

### S2 — Any non-UTF-8 / UTF-16 CSV crashes with `UnicodeDecodeError`

- **Where:** `cli.py:142`, `with open(path, newline="", encoding="utf-8-sig")` — strict errors, no `errors=` argument
- **Breaks:** `cli.py:314-318` catches only `KeyboardInterrupt`, so the decoder error escapes `main()` as a full traceback. This is the single most likely hostile input in this project's actual workflow: `.github/workflows/scrape.yml:56` pulls the master off Google Drive, and `main.py:118-119` states the explicit reason the CSVs are written `utf-8-sig` is so operators can open them in **Excel and Google Sheets**. An operator who opens the master on an Excel/Sheets install with a non-UTF-8 default (CP1256 is still the default for Arabic-script locales on legacy Office) and re-saves produces a file that this validator cannot open at all.
- **Triggers, all verified:**
  ```
  b"name,city\nCafé,Beirut\n".encode("latin-1")   -> UnicodeDecodeError: 'utf-8' codec can't decode byte 0xe9 in position 13
  "name\nمقهى\n".encode("cp1256")               -> UnicodeDecodeError: 'utf-8' codec can't decode byte 0xe3 in position 5
  "name\nCafe\n".encode("utf-16")               -> UnicodeDecodeError: 'utf-8' codec can't decode byte 0xff in position 0
  b"name,phone\n\xd9,701\n"                     -> UnicodeDecodeError   (truncated multibyte at EOF)
  ```
- **Amplifier:** the same `open()` call exists at `cli.py:86` in `cmd_stats`, so `stats` and `validate` fail identically on the same file — an operator gets no working diagnostic.
- **Fix:** `errors="replace"` on read plus a byte-level sniff of the first 4 bytes, or catch `(UnicodeDecodeError, csv.Error)` around `cli.py:142-143` and print `f"{path} is not readable as UTF-8 CSV ({type(e).__name__})"` with `return 2`.

### S2 — A field longer than 131072 characters crashes with `_csv.Error`, and `main.write_csv` can produce exactly that file

- **Where:** `cli.py:143`, `rows = list(csv.DictReader(f))`
- **Breaks:** `csv.field_size_limit()` is 131072 by default (measured). Any single field above it raises `_csv.Error`, which is **not** a `ValueError` subclass and is not caught anywhere on the path.
- **Triggers, measured at the boundary:**
  ```
  name = "A" * 131071   -> rc=0   (one under the limit, fine)
  name = "A" * 131072   -> rc=0   (exactly at the limit, fine)
  name = "A" * 131073   -> _csv.Error: field larger than field limit (131072)
  phone = "x" * 400000  -> _csv.Error: field larger than field limit (131072)
  ```
- **It is reachable from this repo's own output, not just hostile files.** The **reader** enforces the limit; `csv.DictWriter` does not. Writing a record with a 131073-char `address` through the exact `main.write_csv` body succeeds, producing a `data/*.csv` that `leadminer validate` then cannot read. One over-long scraped field anywhere in the 22-column contract (`main.py:33-40`) turns the quality gate into a traceback.
- **Correctly handled, for the record:** 100,000 emoji in `name`, 130,000 Arabic characters in `name`, and a 130,000-char `lat` all return `rc=1` with a clean message, no crash. `float("333…")` overflows to `inf`, which `in_box` correctly rejects at `cli.py:160-162`.
- **Fix:** either raise the limit for this read (`csv.field_size_limit(10_000_000)`) or catch `csv.Error` at `cli.py:143` and report `f"{path}: malformed CSV ({e})"` → `return 2`. Doing both is cheap.

### S3 — `IsADirectoryError` and `TypeError` reach the terminal as tracebacks

- **Where:** `cli.py:137` and `cli.py:142`
- **Triggers:**
  ```
  leadminer validate data/       -> IsADirectoryError: [Errno 21] Is a directory: 'data'
  leadminer validate ""          -> IsADirectoryError: [Errno 21] Is a directory: '.'
  cmd_validate(Namespace(file=None))  -> TypeError: argument should be a str or an os.PathLike ...
  cmd_validate(Namespace(file=12345)) -> TypeError: ... not 'int'
  ```
  `pathlib.Path("")` collapses to `.`, so an unset shell variable — `leadminer validate "$FILE"` with `FILE` unset — produces a traceback rather than the intended `no such file` message. `path.exists()` at `cli.py:138` is happy with a directory, so the guard never fires.
- **Aggravating detail worth fixing regardless:** an uncaught exception exits Python with status **1**, and `cmd_validate` returns **1** for "problems found" (`cli.py:201`). A crash and a genuine validation failure are indistinguishable by exit code. If this command is ever wired into a script, wrap the body once:
  ```python
  except (OSError, csv.Error, UnicodeDecodeError, TypeError) as e:
      print(f"validate failed: {type(e).__name__}: {e}", file=sys.stderr); return 2
  ```

### S3 — Three inconsistent thresholds, one of which has a hard cliff at exactly 100 and 200 rows

- **Where:** `cli.py:172` (`> total * 0.01`), `cli.py:191` (`> total * 0.05`), `cli.py:187` (`if bad_rating:` — no threshold)
- **Verified consequences:**
  ```
  200 rows, exactly 2 rows in Paris  -> rc=1  "2 rows have coordinates outside Lebanon/Saudi Arabia"
  200 rows, exactly 2 rows in Paris  -> rc=0  "all checks passed"      <-- same data
  100 rows, 1 bad rating             -> rc=1
  200,000 rows, 1 bad rating         -> rc=1
  ```
  The identical corruption flips verdict purely on file size. Separately, `rating` has no percentage gate at all, so a single `9.9` anywhere in a 200,000-row master fails the whole run, while a coordinate error needs to exceed 1% of a much bigger file to fail it. The severity of the three findings is inverted relative to their thresholds: coordinates (which decide whether a lead is sellable at all) get the loosest gate; `rating` (cosmetic, not in the sales path) gets the strictest.
- **Also S3, same line family:** the name check at `cli.py:151` is all-or-nothing — 200 rows with **199** blank names returns `rc=0, "all checks passed"`. A master that has lost its `name` column for all but one row is indistinguishable from a healthy one.
- **Fix:** one threshold table at module level, applied uniformly, with absolute floors:
  ```python
  _THRESHOLDS = {"coords": (0.01, 1), "dupes": (0.05, 1), "rating": (0.001, 1)}
  ```

### S3 — The BOM check at `cli.py:154` cannot detect the condition its own message names, and the message is inverted

- **Where:** `cli.py:154-156`, reading with `encoding="utf-8-sig"` at `cli.py:142`
- **Breaks:** `utf-8-sig` strips exactly one leading BOM at byte offset 0. Verified: a file produced by `main.write_csv` (which *always* writes a BOM, `main.py:124`) starts with `b"\xef\xbb\xbf"` and the check does not fire — `rc=0`. The message says `"written without utf-8-sig"`, but a file written without `utf-8-sig` has no BOM at all, so the named condition produces nothing to detect. The check only fires for a BOM *embedded mid-file*:
  ```
  b"\xef\xbb\xbfname,...\n" + "﻿Cafe,...".encode()  -> rc=1 "1 names carry a UTF-8 BOM"
  ```
  which is a real and different failure mode (two exports concatenated — plausible for the cumulative master, `scrape.yml:88-89` copies the same directory twice) but is described incorrectly.
- **The scenario the check was presumably written for — a header glued to `\ufeffname` — is already handled** by `utf-8-sig` at `cli.py:142`, so the code that looks like it guards it is dead. (That reasoning is exactly why `main.py:82-84` uses `utf-8-sig` too.)
- **Fix:** either delete the check, or re-read the first 3 bytes in binary to report a *missing* BOM, or reword to `"N names carry an embedded BOM (two exports concatenated?)"`.

### S3 — The reported row count can be a lie, and the whole file is materialised twice over

- **Where:** `cli.py:143` and `cli.py:194`
- **Row-count lie.** An unbalanced quote — exactly what a truncated write or a partial `rclone` download leaves behind (`scrape.yml:56` copies from Drive; a partial file is possible) — silently swallows the remaining rows into one field:
  ```
  name,lat,lon,phone\n"Cafe,33.89,35.50,701\nCafe2,48.85,2.35,702\nCafe3,48.85,2.35,703\n
  -> checked 1 rows ... all checks passed
  ```
  Three records collapsed to one, one of which is in Paris, and the gate reports `exit 0` on a file whose `wc -l` says 4. `csv` does not raise on an unterminated quote. A row-count reconciliation against `wc -l` would catch this class outright.
- **Memory.** `list(csv.DictReader(f))` holds every row as a `dict` of 22 `str`. Measured: a 66.8 MB / 300,000-row CSV took peak RSS from 330 MB to 911 MB — **+581 MB, ~8.7x the file size**. The cumulative master is the largest artifact here and grows without bound. On a 7 GB runner, a ~500 MB master means a ~4.3 GB spike.
- **Fix:** stream with `csv.DictReader` inside the existing loops and count as you go; compare the counted rows against the physical line count (both from `wc -l` and `csv`).

So whether a given row gets validated depends on which script the exporting tool happened to use.

## Not a bug, but worth knowing

- **`float()` and NaN behave correctly here.** `not 0 <= nan <= 5` is `True`, so `nan` ratings and `nan` coordinates are both flagged. This is the single most commonly mis-implemented boundary in this class of validator and it is right. Leave it alone when refactoring.
- **Missing/blank `rating` is legitimately allowed** and correctly skipped at `cli.py:178-179`. Do not "fix" this into a failure — most leads have no Google rating.
- **`in_box` at `cli.py:159-162` is right.** Swapped `lat`/`lon` (35.50, 33.89) is caught: `35.50` fails both the LB and SA latitude ranges. 200/200 swapped rows → `rc=1`.
- **Coordinate thresholds are correct as a percentage for parsed rows** — 200/200 Paris rows gives `rc=1`. Only the `continue` path defeats it.
- **The two existing tests cover the happy paths only.** `tests/test_lead_signal.py:228-240` (one `rating=9.9`) and `:242-253` (one clean row). Neither exercises a missing column, a blank `lat`, a non-UTF-8 byte, or a directory. `tests/test_lead_signal.py:255-264` asserts "missing file is an error not a traceback" for `cmd_stats` — the same intent was never applied to `cmd_validate`'s open, which is exactly where it now fails.
- **`cmd_validate` never runs in CI.** `.github/workflows/scrape.yml:71-83` duplicates two of its checks inline. If you fix any of the above, wire the CLI in and delete the inline shell so there is one gate, not two that disagree.
- **The exit-code contract should be three-valued and stable**: `0` clean, `1` data problems, `2` could-not-read (bad path, bad encoding, malformed CSV, directory). Today `2` means only "file not found" (`cli.py:140`) and a crash also yields `1`.

## The single most dangerous input

**A CSV in which every row's `lat`/`lon` is present, non-empty, and unparseable as an ASCII float — concretely `lat="٤٨٫٨٦"` (U+066B ARABIC DECIMAL SEPARATOR), or a French-locale `lat="48,8566"`, or a file where the columns have been renamed to `latitude`/`longitude`.**

Measured result: 5,000 rows, 100% of them in Paris, and `cmd_validate` prints

```
checked 5,000 rows in data/all_businesses.csv
  all checks passed
```

and exits **0**.

Why this one and not the crashes:

1. **It returns the exact success signal.** `rc=0` plus the literal string `all checks passed` (`cli.py:196`). A traceback is at least an event an operator investigates; this is indistinguishable from a clean file, and `cmd_validate` is documented at `cli.py:14-15` as the thing you reach for when a run looks wrong.
2. **Blast radius is the entire file, not one row.** Every crash here is per-file too, but a crash cannot mislead — it stops. This one scales with the corruption: one bad locale setting and the geographic assertion is gone for every row simultaneously.
3. **It is the highest-prioritisation corruption available.** `without_websites.csv` is the new-site pitch list (`docs/audits/BRIEF.md:54`), and `sales_ready.csv` is what the team works from. Lead quality depends on the lead being in Lebanon or Saudi Arabia. A master full of French coordinates is not a cosmetic problem; it is a sales team cold-calling the wrong country, or a client list uploaded to Drive by `scrape.yml:85-89`.
4. **Likelihood is not remote here.** `main.py:118-119` states the CSVs are written `utf-8-sig` *specifically so operators can open them in Excel and Google Sheets*. The stated consumer of this file is a spreadsheet editor on a machine whose locale and default encoding are outside the project's control. One round-trip through an Arabic- or French-locale Excel is enough.
5. **It fails in the direction that hides the damage.** `float()` accepts Arabic-Indic digits with an ASCII `.`, so a partial locale problem is judged correctly while a different, equally common spelling is skipped outright. And as shown in §D/E, the *rating* check does fire on the same file — so the operator gets a report and goes to fix `rating` while the coordinates, the thing that actually matters, go unexamined.

Runner-up, for completeness: the `_csv.Error` / `UnicodeDecodeError` crashes (`cli.py:142-143`). Those cost an operator an afternoon and are trivially fixed with one `except` clause — which is exactly why they rank below a defect that reports success on wrong data.
