# 228-x — `cmd_stats`: every declared type is wrong at the read boundary, and no shape can make it fail loudly

## Verdict

`cmd_stats` (`cli.py:79-132`) opens the file with a bare `csv.DictReader` (`cli.py:87`) and
never checks that the file is a leadminer export. All 23 types declared in `BusinessRecord`
(`scrapers/base.py:5-28`) are wrong at that boundary — the function is holding `str`, never
`float` / `int` / `bool` — and its only defence against an unexpected shape is the total
expression `(value or "").strip()` (`cli.py:96`). That expression **cannot raise**, which
means `cmd_stats` has no failure mode other than *a complete, confident, correctly-aligned
report of wrong numbers, at exit code 0*. The docstring calls it "the first thing to check"
(`cli.py:80`), so this is the single worst place in the codebase to be confidently wrong.

Direct answers to the assigned questions:

- **Fields read that are not in the `TypedDict`: none.** All 10 fields `cmd_stats` touches are
  declared in `BusinessRecord` and present in `main.FIELDS`. Verified mechanically:
  `set(FIELDS) ^ set(BusinessRecord.__annotations__) == set()`, 23 keys each. The honest answer
  to that half of the brief is an empty list.
- **Fields written: none.** `cmd_stats` never mutates a row; it only prints.
- **Can a caller violate the contract silently? Yes — four ways, all reproduced below**, none
  of which produce a non-zero exit. The worst one is *persistent*: a ragged row survives
  `cmd_score` and is written back to the master with its columns shifted.
- **Where the return value is used badly:** `cmd_stats` returns honest `0`/`1`/`2` and its only
  consumer (`cli.py:315`) handles that correctly. The sibling command `cmd_run` does not
  (`cli.py:33-37` + `main.py:148`), and that is the more serious return-value defect.

## Findings

### S1 — No header validation, so any non-leadminer CSV produces a complete, authoritative, all-zeros report at exit 0

- **Where:** `cli.py:86-87` (`list(csv.DictReader(f))`), wired up at `cli.py:293-295`.
- **Breaks:** `csv.DictReader` uses the first line as the header whatever it contains. If the
  header is not the 23 columns of `main.FIELDS` (`main.py:33-40`), then `r.get("phone")` returns
  `None` for every row, `(None or "")` short-circuits, and every count is `0`. There is no
  comparison against `main.FIELDS` anywhere in the function, so the command prints a
  well-formatted report indistinguishable from a real one.
- **Trigger (executed, verbatim):** point `stats` at a CRM export.

  ```
  $ leadminer stats data/contacts.csv          # file is:
  # full_name,company,email_address,phone_number
  # Ali Hassan,Acme,ali@acme.lb,+9613111222
  # Sara K,Gamma,sara@gamma.lb,+966555123456

  contacts.csv  (2 rows)

    with phone      : 0
    with email      : 0
    with website    : 0
    with instagram  : 0
    with whatsapp   : 0
    with region     : 0

    website live    : 0
    website dead    : 0
    unreachable     : 0  (not the same as dead)

    by priority:
      None       2
    ...
  rc = 0
  ```

  Also reproduced: a headerless two-column file (first data row silently becomes the header, 2
  bogus "rows" reported); a `;`-delimited file (the header collapses to one giant key, all
  zeros); and duplicate column names in the header (`phone,phone` → only the second value is
  ever read).
- **Reachability is structural, not hypothetical.** `.github/workflows/scrape.yml:56` runs
  `rclone copy "gdrive:leads/" data/ --max-depth 1 --include "*.csv"`, so `data/` is populated
  with *every* CSV a human has ever dropped into that Drive folder, and `cli.py:294` defaults
  `stats` to `data/all_businesses.csv` with tab-completion pulling in its neighbours. The
  exports are explicitly written for spreadsheet consumption — `main.py:118-119` says
  "encoding is utf-8-sig so Excel and Google Sheets detect UTF-8" — and `scrape.yml:88-89`
  copies them straight back to Drive.
- **Relationship to `020-type-contract-import-cycle.md` S1.** That report proposes validating
  the header inside `load_master` (`main.py:77-105`). That fix is correct but **incomplete**:
  `cmd_stats` (`cli.py:87`) and `cmd_validate` (`cli.py:143`) both bypass `load_master`
  entirely and open the file themselves. Applying 020's fix leaves both triage commands just as
  unprotected as they are now. The header check needs to live in a helper all three call.
- **Fix:** one `validate_header(path) -> list[str]` helper shared by `cmd_stats`,
  `cmd_validate`, and `load_master`; on mismatch print the set difference to stderr and return
  `2` before reading a single row.

### S1 — One short row shifts every later column, and `cmd_stats` prints the shifted values as fact — then `cmd_score` writes them back to disk

- **Where:** `cli.py:87` (`csv.DictReader` with the default `restval=None`), consumed at
  `cli.py:96`, `107`, `108`, `110`, `116`, `120`, `124`, `129`.
- **Breaks:** when a row has fewer fields than the header, `csv.DictReader` fills the tail with
  `None` **positionally**. The row's values do not go missing — they land one column to the
  left. Every aggregate after that column is silently reading the wrong field, and the report
  still looks internally plausible.
- **Trigger (executed, verbatim):** one row of 22 against a 23-column header — one deleted cell
  in a spreadsheet.

  ```
  row1 (23 cols): Acme Bakery ... industry_priority='high'  recommended_service='SEO audit + visibility upgrade'
  row2 (22 cols): Delta Bistro ... industry_priority='Digital marketing retainer (Meta + Google + content)'
                                     recommended_service='google_places'   source='2026-09-01T00:00:00Z'
                                     scraped_at=None

  $ leadminer stats b_ragged.csv
    by priority:
      high       1
      Digital marketing retainer (Meta + Google + content) 1   <-- a pitch string, in the priority table
    by source:
      google_places                1
      2026-09-01T00:00:00Z         1                           <-- a timestamp, in the source table
    by priority (top pitches):
      SEO audit + visibility upgrade                       1
      google_places                                        1   <-- a source name, in the pitch table
  rc = 0
  ```

  A human reading this at 3am concludes the data is fine. It is not — the row's
  `industry_priority` is a marketing string and its `source` is a date.
- **The damage is persistent, not display-only.** `cmd_score` (`cli.py:247-277`) reads the same
  file with `pipeline.load_master` (`cli.py:259`) and writes it back with `pipeline.write_csv`
  (`cli.py:275`), **in place by default** (`cli.py:274`). `load_master` has no header or row
  validation either — it just casts whatever keys the row happens to have (`main.py:86-104`).
  Executed end to end:

  ```
  BEFORE  row2: linkedin=''  rating='9'      review_count='4' completeness='75' lead_score='high'
                 industry_priority='Digital marketing retainer (…)'
                 recommended_service='google_places' source='2026-09-01T00:00:00Z' scraped_at=None

  AFTER `leadminer score b_ragged.csv` (no --out):
          row2: linkedin=''  rating='9.0'   review_count='4' completeness='75' lead_score='60'
                 industry_priority='Digital marketing retainer (…)'
                 recommended_service='google_places' source='2026-09-01T00:00:00Z' scraped_at=''
  ```

  A `review_count` of `9` is now a `rating` of `9.0` — a value `cmd_validate` (`cli.py:175-188`)
  will reject, and which `pitch_recommender._is_low_rating` (`pitch_recommender.py:135-140`)
  will read as `True`, pitching **"Reputation + SEO turnaround"** to a business with no reviews.
  The next run re-reads it, re-casts it, and carries it forward. One ragged row, one
  `leadminer score`, permanent corruption of the cumulative master.
- **Fix:** pass an explicit `restval` sentinel and reject (or count and report) any row whose
  parsed width differs from `len(reader.fieldnames)`; then make `cmd_score` refuse to write
  when the count is non-zero unless `--force` is passed.

### S2 — `live` / `dead` / `unreachable` is not a partition of anything, and it is asymmetric in exactly the wrong direction

- **Where:** `cli.py:107-110`. Compare the correct version at `main.py:215-217` and
  `enricher.py:264-266`.
- **Breaks:** the three counters are computed over different populations.
  `unknown` (`cli.py:109-110`) is gated on `r.get("website")`; `live` and `dead`
  (`cli.py:107-108`) are **not**. So a row with `website_live="False"` and no website is
  reported as a dead website, and `live + dead + unreachable` exceeds the number of rows that
  have a website at all. The comment at `cli.py:105-106` ("Collapsing blank into False was the
  original bug") shows the author was reasoning about exactly this triple; the under-count was
  fixed and the over-count was introduced in the same edit.
- **Trigger (executed, verbatim):** three rows, two of which have a website, one of which has a
  stale `website_live="False"` left over from an earlier run.

  ```
    with website    : 2
    website live    : 2
    website dead    : 1     <-- a row with NO website
    unreachable     : 0
                       ---
    live+dead+unknown = 3 != 2 rows with a website
  ```

- **Reachability:** `check_websites` only ever sets `website_live` for rows that *have* a
  website (`enricher.py:231`) and never clears it for rows that do not;
  `load_master` re-derives the two columns independently (`main.py:102-103`) and preserves the
  pairing verbatim. So once a `website="", website_live="False"` row exists, it survives every
  subsequent run forever. And per `cli.py:105-106` a previous version of this code produced
  exactly that row, so the master on disk right now plausibly contains some — unverifiable,
  because `data/` is gitignored (`.gitignore`) and there is no backup step.
- **Trigger, second form — under-count to zero:** the counters match the literal spellings
  `"True"` and `"False"` (`cli.py:107-108`). Any other non-blank spelling falls through *all
  three* buckets, because `unknown` requires the cell to be blank. Executed:

  ```
  # three rows whose website_live is: 'true'  'True'  'YES'
    with website    : 3
    website live    : 1
    website dead    : 0
    unreachable     : 0        <-- all three rows vanish; 3 - 1 = 2 unaccounted for
  ```

  A Google Sheets round-trip that lowercases booleans therefore reports "we could not reach
  these sites" — no wait, it reports *nothing at all* for them, which is worse: the operator
  cannot tell "we never tried" from "we tried and the answer was dropped on the floor".
- **Fix:** compute all three over one population, as `main.py:215-217` already does:
  `with_site = [r for r in rows if r.get("website")]`, then
  `live = sum(r.get("website_live") == "True" for r in with_site)` etc. Accept `true`/`1`/`yes`
  case-insensitively in the same place, and assert `live + dead + unknown == len(with_site)`.

### S2 — The declared type of every field is `str` in practice; the mismatch is latent today and becomes a crash the moment anyone adds a numeric stat

- **Where:** `cli.py:87` (the read) vs `scrapers/base.py:5-28` (the declaration).
- **Breaks:** `csv.DictReader` yields `dict[str, str]` for a well-formed row — `None` for
  columns absent from a short row, and a `list[str]` under the key `None` for a long row. The
  per-field mapping is:

  | `BusinessRecord` declaration | Actual type at `cli.py:87` | Where it bites |
  |---|---|---|
  | `lat`/`lon`: `float \| None` (`base.py:11-12`) | `str` | cannot be compared or averaged without a cast |
  | `rating`: `float \| None` (`base.py:21`) | `str` | same |
  | `review_count`: `int \| None` (`base.py:22`) | `str` | same |
  | `completeness_score`: `int` (`base.py:28`) | `str` | same |
  | `lead_score`: `int` (`base.py:25`) | `str` | same |
  | `website_live`: `bool \| None` (`base.py:16`) | `str` (`"True"`/`"False"`/`""`) | forces the inline cast at `cli.py:107-108` |
  | `source`: `str`, **non-optional** (`base.py:26`) | `str` **or `None`** | prints a literal `None` in the source table |
  | `scraped_at`: `str`, **non-optional** (`base.py:27`) | `str` **or `None`** | same |
  | the other 15 | `str` | agree by accident |

  This is currently **latent, not active**: `cmd_stats` only calls `.strip()`, `== "True"`, and
  truthiness on these values, all of which are total on `str`. It becomes an active bug the
  first time anyone writes the obvious next stat. `_fmt` is already annotated
  `n: int | float | None` (`cli.py:29`) and raises on a `str`:
  `_fmt("1000") -> ValueError: Cannot specify ',' with 's'.` (see `203-x.md` S3). The natural
  one-liner `f"mean rating {_fmt(r.get('rating'))}"` dies with a message that reads like a
  formatting bug rather than a type bug — which is exactly what the declaration invited.
- **Two implementations of one cast.** `cli.py:107-108` re-derives `website_live` from the
  string inline; `main.py:102-103` does the same thing in `load_master`. Only the second is
  covered by a test. `cmd_stats` is the only `cmd_*` that does not route through `load_master`
  (`cmd_score` does, `cli.py:259`; `cmd_validate` does not, `cli.py:143`) — so the same file
  gets two different views of the same column.
- **Fix:** have `cmd_stats` read through `main.load_master` (it already casts `lat`, `lon`,
  `rating`, `review_count`, `completeness_score`, `lead_score` and `website_live` at
  `main.py:90-103`) and delete the duplicate cast. Then annotate the local as
  `list[BusinessRecord]` so the next numeric stat gets the declared types for free.

### S2 — The report omits the two columns that would expose the two known systematic failures: `country` and `scraped_at`

- **Where:** `cli.py:98-131` reads 10 of the 23 fields. The 13 it skips are `name`, `category`,
  `country`, `address`, `lat`, `lon`, `facebook`, `linkedin`, `rating`, `review_count`,
  `completeness_score`, `lead_score`, `scraped_at`.
- **Breaks, case 1 — `country`.** `resolve_country` defaults to `_DEFAULT_COUNTRY = "LB"`
  (`main.py:47`, `main.py:74`) for any record it cannot place from an explicit code or an
  international phone prefix. If a batch of Saudi records defaults, the master becomes 100%
  `LB` and `cmd_stats` cannot show it, because it never prints a country breakdown. The
  downstream damage is real, not cosmetic: `infer_region` keys address-based inference on
  `country == "LB"` (`enricher.py:85`), so a mislabelled country silently changes the region
  values that `cmd_stats` *does* print — "Riyadh 12,000" and "LB" in the same row is not a
  state a reviewer is primed to catch.
- **Breaks, case 2 — `scraped_at`.** `all_businesses.csv` is cumulative-all-time
  (`main.py:150`, `main.py:209`) and the master on Drive is re-downloaded every run
  (`scrape.yml:56`). `cmd_stats` cannot report the age of what it is summarising, so a master
  that stopped refreshing six weeks ago prints exactly like one from ten minutes ago. For a
  command whose docstring is "This is the first thing to check" (`cli.py:80`), and in a repo
  whose cron was previously commented out while the README claimed it ran, that is the single
  most valuable missing line.
- **Trigger:** run `leadminer stats` on a master produced by a run where `SCRAPER_EMAIL` was
  unset and the OSM Overpass query returned 429s for all three retries (`osm.py:39-56`). The
  report looks structurally normal; nothing in it says the OSM slice is three months stale.
- **Fix:** add a `country` `Counter` next to the `by source` block, and print
  `scraped_at` min/max (lexicographic min/max is correct here — `httpclient.utc_now_iso`
  emits fixed-width ISO-8601 UTC).

### S3 — `None` and `""` leak into three of the four `Counter` blocks; only `region` is guarded

- **Where:** `cli.py:116` (`industry_priority`), `cli.py:120` (`source`), `cli.py:129-130`
  (`recommended_service`) versus the one that is handled correctly, `cli.py:124`
  (`r.get("region") or "Unknown"`).
- **Breaks:** when the column is absent, the counter key is `None` and the block prints a
  literal `None` with a row count. Executed on the CRM export from S1:

  ```
    by priority:
      None       2
    by source:
      None                         2
    top pitches:
      None                                                 2
  ```

  A `None` under "by source" reads as a data-quality observation when it is actually the tool
  reporting that it is looking at the wrong file. Three of the four blocks were written
  without the guard the fourth one got, which suggests the guard was added reactively to a
  single report rather than factored.
- **Fix:** extract the `or "Unknown"` default (or better, a `"(blank)"` label, since blank and
  missing are different problems) and apply it in all four.

### S3 — `most_common(8)` silently drops 3 of the 11 reachable pitch labels today

- **Where:** `cli.py:129-130` (`recommended_service`, `most_common(8)`); also `cli.py:120`
  (`source`, `most_common(8)`) and `cli.py:124-126` (`region`, `most_common(12)`).
- **Breaks:** `recommend_service` has **11** reachable return values across
  `pitch_recommender.py:58, 63, 66, 71, 74, 79, 86, 91, 96, 99`. The counter therefore has 11
  keys and `cmd_stats` prints 8 of them with no `... and 3 more` line. Executed with one row
  per reachable label:

  ```
    top pitches:
      Website rebuild + maintenance                        1
      E-commerce launch + Instagram-to-store funnel        1
      Website launch + capture their existing audience     1
      SEO audit + visibility upgrade                       1
      Reputation + SEO turnaround                          1
      RTYLR commerce OS (POS, online ordering, CRM)        1
      Lead-gen website + Google Ads launch                 1
      Lead-gen overhaul (landing pages + Google Ads + WhatsApp capture) 1
      # missing: "Digital marketing retainer (…)",
      #          "Full digital launch (…)",
      #          "Discovery call - scope the right service"
  ```

  Which three get hidden depends entirely on which are most common in the current master, so
  the block is not even stably wrong — it is a different wrong answer each run. The hidden set
  includes the default catch-all, which is the label most likely to indicate the recommender
  failed to classify something.
- **Formatting, same block:** `f"{str(k):<52}"` (`cli.py:131`) is narrower than the longest
  label. `"Lead-gen overhaul (landing pages + Google Ads + WhatsApp capture)"` is 65
  characters, so its count runs flush against the text and breaks the column alignment of every
  row above it — visible in the output above. Compare `main.py:242`, which uses `<55` for the
  same field, also too narrow, and `main.py:234`'s `<20` for region, which fits.
- **Fix:** size the field to `max(len(k) for k in counter)` at print time, and print
  `f"... and {n} more"` when the counter is longer than the cap.

### S3 — A single oversized cell kills the "first thing to check" with an uncaught `_csv.Error` traceback

- **Where:** `cli.py:86-87`; `main()` catches only `KeyboardInterrupt` (`cli.py:314-318`).
- **Breaks:** `csv.field_size_limit` defaults to `131072` (verified on this interpreter). One
  cell longer than that raises `csv.Error`, which nothing in `cli.main()` catches. Executed:

  ```
  >>> cli.cmd_stats(Namespace(file='huge.csv'))     # one 140,000-char name cell
  _csv.Error: field larger than field limit (131072)
  >>> cli.main(['stats', 'huge.csv'])
  _csv.Error: field larger than field limit (131072)
  ```

  Exit code 1 with a stack trace, from the command whose job is to tell you what is wrong.
- **Reachability is low** — `enricher.py:188` caps the fetched *response* body via
  `DEFAULT_MAX_BODY_BYTES`, but nothing caps a scraped cell, and Overpass tag values are not
  length-bounded server-side. Hence S3, not S2.
- **Fix:** `csv.field_size_limit(2 ** 24)` once at module scope, and wrap the read in
  `except csv.Error as e: print(f"cannot parse {path}: {e}", file=sys.stderr); return 2`.

## Not a bug, but worth knowing

- **`cmd_stats` cannot be crashed by any CSV shape.** Worth stating explicitly, because it
  changes what the type mismatch above costs you. `(x or "").strip()` (`cli.py:96`) only
  raises on a `list`, and `csv.DictReader` only ever produces a `list` under the `restkey`
  key — which defaults to `None` — so it is unreachable from `.get("phone")`. I checked the
  four shapes empirically (`headerless`, `short row`, `long row`, `duplicate names`,
  `semicolon delimiter`) and none of them raise. **Every defect in this report is
  silent-wrong-numbers, not a traceback.** That is worse, not better: there is no signal to
  alert on.
- **`leadminer run` always exits 0.** `cmd_run` returns `pipeline.main()`, which is annotated
  `-> None` (`main.py:148`), and `cli.py:315` coerces with `int(args.func(args) or 0)`, so
  `None` becomes `0`. A run in which all three scrapers failed — `main.py:167-168` catches the
  exception per future, prints to stderr, and continues — writes five empty CSVs and exits
  **0**. `scrape.yml:74-83` catches the empty-master case downstream, but a run that scrapes
  40 records and enriches 0 is indistinguishable from success at the process boundary. This is
  the one genuinely broken return-value contract in `cli.py`, and `cmd_stats` is the correct
  counter-example to copy. Cross-ref `072-run-failure-triage.md`.
- **The existing `cmd_stats` test cannot fail.** `test_stats_handles_tri_state_website_live`
  (`tests/test_lead_signal.py:211-226`) asserts `assertIn("unreachable", out)` — but the label
  is printed unconditionally at `cli.py:113`, so that assertion holds for any input at all. It
  does not assert the partition property, and its fixture is always produced by `write_csv`
  (`tests/test_lead_signal.py:208`), so no test in the repo can feed `cmd_stats` a wrong-shaped
  CSV. Full suite currently passes (`python3 -m unittest discover -s tests` → OK).
- **`_fmt` is only ever handed an `int`.** `count()` (`cli.py:95-96`) coerces via `sum()`, so
  the six `_fmt` call sites at `cli.py:98-103` are safe; the seven bypass sites use raw
  `f"{v:,}"` on `Counter`/`sum` results. Already covered by `203-x.md`; listed here only
  because it is the reason the `str`-vs-declared-numeric mismatch above is still dormant.
- **Field-name agreement between the two declarations is a coincidence, not a check.**
  `set(main.FIELDS) ^ set(BusinessRecord.__annotations__) == set()` is true today (23 keys
  each) but nothing enforces it. Already raised as S3 in `020-type-contract-import-cycle.md`;
  the fix (`FIELDS = list(BusinessRecord.__annotations__)`, or a single canonical contract
  module) is also the fix for the missing-header-check in S1 above.
- **`BRIEF.md` says 22 keys/columns (`BRIEF.md:18`, `BRIEF.md:57`); there are 23**
  (`scrapers/base.py:5-28`, `main.py:33-40`, and `BRIEF.md`'s own enumeration at
  `BRIEF.md:59-62`). Matches the note in `020-type-contract-import-cycle.md` S3 — worth
  correcting so nothing downstream is keyed on "22".
- **Scope note.** `.github/workflows/scrape.yml:69` runs `python main.py`, not
  `leadminer run`, so none of `cli.py` is in the CI path. `cmd_stats` misinforming a human is
  the realistic failure, not CI publishing bad data. That is why S1 here is about a tool
  *destroying* data via `cmd_score` (`cli.py:275`, in place by default) rather than about
  `stats` itself — and why the CI gate at `scrape.yml:74-83`, which checks only non-emptiness
  and a row floor, is worth strengthening separately.

## Recommended order of work

1. **Extract one header validator** (`validate_header(path) -> list[str]`) and call it from
   `cmd_stats` (`cli.py:86`), `cmd_validate` (`cli.py:142`), and `load_master`
   (`main.py:85`). This is 020-x's S1 fix generalised; as written it leaves both CLI triage
   commands unprotected. On mismatch: print the set difference to stderr, return `2`.
2. **Reject ragged rows.** Set an explicit `restval` and fail (or count and report) any row
   whose parsed width differs from `len(fieldnames)`. Then make `cmd_score` refuse to write
   unless `--force`, so a shifted master can never be written back.
3. **Route `cmd_stats` through `main.load_master`** and delete the duplicate `website_live`
   cast at `cli.py:107-108`, so the declared types in `BusinessRecord` become true at the point
   of use and the next numeric stat gets `float`/`int` for free.
4. **Fix the tri-state triple**: compute `live`/`dead`/`unreachable` over one
   `with_site` population as `main.py:215-217` does, accept case-insensitive truthy/falsey
   spellings, and assert `live + dead + unknown == len(with_site)` in a test.
5. **Add `country` and `scraped_at` min/max to the report**, and apply the `or "Unknown"`
   guard to all four `Counter` blocks.
6. **Add the two tests that would have caught all of the above**: a fixture with one
   deliberately short row, and a fixture that is not a leadminer CSV at all. Both must assert a
   non-zero return code, not just that the output contains a label.
