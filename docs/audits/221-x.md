# 221 — `cmd_scrape` at 500k: O(n) time, O(n) memory, and the one edit that returns 30% of peak RSS

## Verdict

`cmd_scrape` (`cli.py:40-76`) is **O(n) time and O(n) memory. There is no quadratic behaviour in it**, and I measured that rather than assuming it — the fitted growth exponent over 10k→500k is 0.19–0.65, nowhere near 2.0. Its aggregation costs **0.72–0.84 s at 500k records, which is 2.2% of the ~41 s of local CPU** the scrape itself burns, so optimising it for speed is not worth anyone's time. What *is* worth doing: `list()` at `cli.py:61` forces a second full copy of the dataset into memory — **~1,262 bytes per record, ~630 MB at 500k** — to compute four aggregates that a single streaming pass produces without ever holding the records. That is one edit, it is the only time win available here (1.9–2.3x on the aggregation at 500k), and it cuts measured peak RSS at 500k from **2,067 MB to 1,436 MB (−30.5%)**.

Second, and independent of scale: `cmd_scrape` **cannot tell "the source returned HTTP 504 after 3 attempts" from "the source is legitimately empty"**, and it burns up to 600 s of the workflow's 18,000 s budget finding out. That is a diagnosis bug in the one command whose stated purpose is diagnosis (`cli.py:41-45`).

### The three questions, answered directly

| Question | Answer | Evidence |
|---|---|---|
| O(1), O(n) or O(n²) in businesses? | **O(n)** — 3 linear traversals + one O(k·log 10) `most_common`, k = distinct categories | per-record cost measured flat-to-*falling* in total; fitted exponent 0.19 (100k→500k) and 0.65 (10k→100k) |
| Does it allocate proportionally? | **Yes — and that is the defect.** `list()` allocates ~1,262 B/record | 12.9 / 129 / 631 MB at 10k / 100k / 500k, measured three independent ways |
| Largest single speedup? | **Stream instead of materialise** (delete `list()`, fold `cli.py:68-70` into one loop) | 1.9–2.3x on the aggregation at 500k; ~0.4 s; plus −30.5% peak RSS |

### Measured timings — `cli.py:68-70` only

Apple M4 Pro, Python 3.14.8. Records are the only live allocation, pre-built and warm; best-of-11 inside a fresh process; three independent process launches shown as `a / b / c` because this machine is shared with ~400 other agents and variance is real.

| n | as written (3 passes) | ns/record | single pass | ns/record | speedup |
|---|---|---|---|---|---|
| 10,000 | 2.69 / 2.91 / 3.04 ms | 269–304 | 2.74 / 2.87 / 3.01 ms | 274–301 | **0.94–1.11x** (no win) |
| 100,000 | 85.7 / 129.7 / 131.3 ms | 857–1313 | 64.4 / 74.1 / 76.7 ms | 644–767 | **1.16–2.01x** |
| 500,000 | 717 / 790 / 811 ms | 1435–1621 | 351 / 375 / 407 ms | 702–814 | **1.91–2.31x** |

The win **grows with n** because at 500k the record list is 638 MB and no longer cache-resident: the three-pass version pays full DRAM latency three times, the one-pass version once. At 10k the whole list is 27 MB and fits in cache, so there is nothing to win — which is why a naive micro-benchmark at small n would have told you this change is worthless.

Per-pass breakdown at 500,000 (same harness): `Counter(category)` 154 ms, `sum(phone)` 198 ms, `sum(website)` 248 ms. `most_common(10)` is `heapq.nlargest` over the distinct-category keys — with 24 categories it is free; even with Wikidata's free-text `categoryLabel` (thousands of distinct values) it is bounded at O(k·log 10) and irrelevant.

### Measured memory — where the bytes go

Overpass-shaped elements, ~20 tags each, 768 B of JSON per element.

| n | JSON body | `elements` only (`osm.py:58`) | records only | `elements` + records = what `cli.py:61` really does | increment from `list()` |
|---|---|---|---|---|---|
| 10,000 | 7.5 MB | 42.5 MB | 44.5 MB | 51.8 MB | **12.9 MB** |
| 100,000 | 75.8 MB | 342.4 MB | 430.1 MB | 501.7 MB | **129 MB** |
| 500,000 | 383.9 MB | 1,436.2 MB | 1,476 MB | **2,067.0 MB** | **630.8 MB** |

The `list()` increment is 630.8 MB / 2067.0 MB = **30.5% of the measured combined peak**. The cleanest single number is the per-record constant: **1,262 B/record**, confirmed by two independent harnesses (601.4 MB for 500k records held alone; 638 MB total RSS in the timing harness).

### Where the CPU actually goes at 500k (`--source osm`)

| Stage | Time | Share of local CPU |
|---|---|---|
| `json.loads` (`osm.py:58` → `httpclient.py:113`) | 21.0 s | 51% |
| transform + `list()` (`osm.py:61-122`, `cli.py:61`) | 19.9 s | 49% |
| **aggregate (`cli.py:68-70`)** | **0.89 s** | **2.2%** |
| local CPU total | ~41.8 s | — |

Plus a 384 MB HTTPS download. So `cmd_scrape`'s own arithmetic is 2.2% of the work, and no rewrite of `cli.py:68-70` will make this command feel fast.

## Findings

### S2 — `list()` at `cli.py:61` duplicates the entire dataset to compute four aggregates

- **Where:** `cli.py:61`, consumed by `cli.py:68-70`
- **Breaks:** every scraper is declared `-> Iterator[BusinessRecord]` (`scrapers/base.py:33`) and OSM/Wikidata genuinely yield lazily (`scrapers/osm.py:98`, `scrapers/wikidata.py:106`). `cmd_scrape` throws that away on the very first line of real work. Worse, for OSM and Wikidata the generator frame also holds the raw payload — `result` (with `body` bytes) and `elements` at `scrapers/osm.py:39` and `:58`, `results` at `scrapers/wikidata.py:87` — so the moment `list()` finishes, **body + parsed payload + derived records all coexist**. Measured peak at 500k: **2,067 MB above interpreter baseline**, of which **631 MB is pure duplication**. The function needs exactly four numbers: total, non-empty phone, non-empty website, category histogram.
- **Trigger:** `leadminer scrape --source osm` on a query widened past Lebanon (`scrapers/osm.py:13` hardcodes `ISO3166-1="LB"`; adding `SA` is the obvious next step for a product that already scrapes KSA via Places). At 500k elements the process peaks at ~2.1 GB and the derived-record copy is 30% of that, for nothing.
- **Fix:** consume the iterator in one pass and never bind it to a name:

```python
    records = registry[args.source]().scrape()
    by_cat: collections.Counter[str | None] = collections.Counter()
    n = with_phone = with_site = 0
    for r in records:
        n += 1
        by_cat[r.get("category")] += 1          # None is a real bucket; see S3
        if r.get("phone"):
            with_phone += 1
        if r.get("website"):
            with_site += 1
    print(f"[{args.source}] {n} records")
    if not n:
        print("  WARNING: zero records. The source may be broken or blocked.",
              file=sys.stderr)
        return 1
    print(f"  with phone : {with_phone}")
    print(f"  with site  : {with_site}")
    print("  top categories:")
    for cat, c in by_cat.most_common(10):
        print(f"    {str(cat):<28} {c}")
    return 0
```

Verified **byte-identical stdout and identical exit codes across 9 record shapes** — empty, single row, all-`None` categories, 25 distinct categories, `None` outranking every real category, records with keys missing entirely, empty-string vs missing values, non-ASCII categories, and a 60-char category name. The one trap: a streaming rewrite must do `by_cat[r.get("category")] += 1` **unconditionally**. My first attempt guarded with `if c is not None:` and it silently changed the histogram — my own assertion caught it.

For `--source google_places` the win is smaller: `scrapers/google_places.py:183` already builds `all_records` and `:199` does `yield from all_records`, so `list()` re-references the same dicts and only adds an 8 B/entry pointer array (**3.8 MB at 500k, ~0.2% of peak**). The 30% applies to OSM and Wikidata. The single-pass rewrite is still worth doing for the time half (below), but the memory argument is specifically an OSM/Wikidata argument.

### S2 — three traversals of a cache-hostile working set (`cli.py:68-70`)

- **Where:** `cli.py:68`, `cli.py:69`, `cli.py:70` — three independent generator comprehensions over the same list
- **Breaks:** three full walks plus three `.get()` calls per record instead of one walk. At 500k the record list is 638 MB, so each traversal is DRAM-bound and the constant factor *degrades* with n: per-record cost rises from ~280 ns at 10k to ~1,435–1,621 ns at 500k for the three-pass version, against ~274 → ~702–814 ns for one pass. The gap widens with scale precisely where it hurts.
- **Trigger:** measured directly — 500k records: 717–811 ms as written vs 351–407 ms single-pass (**1.91–2.31x**, ~0.4 s saved).
- **Fix:** the same loop as above. **Honest caveat:** this is a 2x win on 2.2% of the local CPU. It is worth doing because it is free and it is the same edit as the S2 memory fix, not because anyone will notice 0.4 s.

### S2 — zero records conflates "broken" with "empty", after up to 600 s of futile retry

- **Where:** `cli.py:63-66`; the signal is destroyed at `scrapers/osm.py:47-56` and `scrapers/google_places.py:169-171`
- **Breaks:** `cmd_scrape`'s docstring (`cli.py:41-45`) says it exists to check "a single source after an API change". It cannot do that, because `FetchResult` carries the diagnosis (`httpclient.py:97` `status`, `:101` `error`) and the scraper throws it away: `osm.py:51` prints `FAILED after 3 attempts` to stdout and then bare-`return`s, so `cmd_scrape` receives `[]` and its `if not records:` at `cli.py:63` sees only emptiness. Overpass answers a query that blows past its own `[timeout:180]` (`osm.py:12`) with **HTTP 504**, which `_should_retry` treats as retryable (`httpclient.py:146`, `500 <= status < 600`), so `fetch_with_retry` makes **3 attempts** against a query that cannot succeed. I exercised the real `fetch_with_retry` with a stubbed session: 3 attempts, `status=504`, `error='HTTP 504'`, backoff sleeps `[0.17, 1.49]` s. The operator waits on **3 × 200 s = 600 s of server timeout** for a result that is a single line of text.
- **Trigger:** any Overpass response of 504 or 429. Measured worst case for 429 with `Retry-After: 120` — also 3 attempts, also 600 s.
- **Fix:** have the scrapers surface the outcome rather than collapsing to `[]`. Minimal version that keeps the diff inside `cli.py`: nothing in `cli.py` can recover it, so this needs either a `ScrapeOutcome` return from `BaseScraper.scrape` or `scrapers` setting a module-level `last_error`. Until then, use distinct exit codes — 1 for "ran fine, found nothing", 3 for "the source failed" — and read the `[OSM] FAILED after N attempts` line above the warning. 600 s is 3.3% of the 300-minute Actions budget (`.github/workflows/scrape.yml:25`) spent on a diagnostic command.

### S3 — a `None` category prints as though it were a category name

- **Where:** `cli.py:75` — `print(f"    {str(cat):<28} {n}")`
- **Breaks:** `Counter(r.get("category") ...)` at `cli.py:68` counts `None` as a real key, and `most_common(10)` will happily rank it first. Rendered output, verified by executing the exact expressions from `cli.py:68` and `cli.py:75`:

```
    |None                         41|
    |restaurant                   20|
```

  A reader cannot tell "41 records had no category" from "None is a category we track". This is reachable in production: `scrapers/wikidata.py:100` leaves `category` as `None` whenever the `OPTIONAL { ?item wdt:P31 ... }` block does not bind, and `scrapers/osm.py:71-78` leaves it `None` for any named element carrying none of the six queried tags.
- **Trigger:** any source whose records include untagged businesses. In my 500k set the `None` bucket held 20,833 records and would have printed as the second line of the table.
- **Fix:** render it explicitly — `label = "(uncategorised)" if cat is None else cat` — and print that bucket's size on its own line so it is not competing for a top-10 slot.

### S3 — the registry guard at `cli.py:56-59` is dead, and the source list is duplicated

- **Where:** `cli.py:51-55` vs `cli.py:289-290`
- **Breaks:** `--source` is `required=True` with `choices=["osm", "wikidata", "google_places"]`, so argparse rejects any other value before `cmd_scrape` runs. Verified: `parse_args(["scrape", "--source", "nope"])` → `SystemExit(2)`. The `if args.source not in registry: ... return 2` block at `cli.py:56-59` can never execute. Meanwhile the two lists are independent, so adding a scraper to `registry` without adding it to `choices` yields a command argparse refuses to run, and the reverse yields a registry entry argparse advertises but `cmd_scrape` rejects.
- **Fix:** derive `choices` from the registry instead of restating it — `s.add_argument("--source", required=True, choices=sorted(registry))` — which deletes the dead guard and the drift hazard together.

### S3 — 26 ms of imports that `--source osm` will never use

- **Where:** `cli.py:46-49` imports all three scrapers unconditionally
- **Breaks:** nothing measurable. With `requests`/`bs4`/`lxml` stubbed and min-of-9 fresh processes: interpreter + stub alone 44.9 ms, `+ scrapers.base` 52.9 ms, `+ scrapers.osm` (all `--source osm` needs) 93.1 ms, `+ all three` (what `cli.py:46-49` does) **118.7 ms**. So 26 ms of avoidable import — and it is fixed, entirely independent of n.
- **Fix:** lazy-import inside the branch, or accept it. I would accept it; 26 ms is not worth the indirection. Recorded here only so nobody else re-derives it.
- **Related, and genuinely free:** `cli.py:46` `from scrapers.base import BaseScraper  # noqa: F401 (import check)` asserts nothing. It imports the ABC and never checks that the registry entries subclass it, and `cli.py:47` already imports `scrapers.base` transitively. Either make it check (`issubclass(cls, BaseScraper)` for each registry value) or drop the line and its misleading comment.

## Not a bug, but worth knowing

- **500k is not reachable from any single source today.** This materially weakens every number above as a *prediction* — they are extrapolations, and the extrapolation only bites once someone widens a query.
  - `--source wikidata` is hard-capped by `LIMIT 5000` (`scrapers/wikidata.py:43`) → ≤5,000 rows.
  - `--source google_places` is capped at **60 results per query across all pages** by Google's own documentation ("Text Search (New) returns a maximum of 60 results across all pages", <https://developers.google.com/maps/documentation/places/web-service/text-search>). 68 queries (`scrapers/google_places.py:46-125`) → ≤4,080 rows, less still after `seen_ids` dedup (`scrapers/google_places.py:263-266`). The 180 s per-query budget (`scrapers/google_places.py:152`) can therefore never bind on pagination; 3 pages × `time.sleep(2)` (`scrapers/google_places.py:310`) = 6 s is the real ceiling. It can still bind on 429 backoff.
  - `--source osm` has no `LIMIT`, but is bounded server-side by `[timeout:180]` (`scrapers/osm.py:12`). Half a million elements would 504, not succeed.
- **The 500k dataset lives somewhere `cmd_scrape` never looks.** It is `data/all_businesses.csv`, accumulated weekly via `load_master` (`main.py:150`) and rewritten at `main.py:209`. `cmd_scrape` opens no CSV. So the scaling question that actually matters at 500k belongs to `cmd_score`/`cmd_stats`/`main.main`, not here. Do not spend more effort on this function's asymptotics.
- **`cmd_scrape` is the cheap path, by design.** Relative to `main.main()` it skips `load_master` (`main.py:150`), `dedup` (`main.py:180`) and `enrich` (`main.py:187`, one HTTP GET per website at 40 threads). Its docstring's claim that it avoids "a full enrichment pass" (`cli.py:43-45`) is accurate. As a scaling matter, this function is fine.
- **The dominant O(n) cost is in the scrapers, not here.** `FetchResult.json()` (`httpclient.py:110-113`) does `self.body.decode()` then `json.loads`, so at 500k the raw bytes, a decoded `str` copy, and the parsed structure all exist at once; and because `result` is a local of the `osm.py:39` generator frame it stays alive across every `yield`. Measured: 21.0 s to parse, 1,436 MB to hold `elements`. Another agent owns `osm.py`; flagging the shape so it is not rediscovered.
- **`--source google_places` output is written by 5 threads.** `google_places.py:257`, `:244`, `:218`, `:251`, `:231` all `print` from pool workers. To a TTY each print flushes per line and interleaves mid-line; to a pipe, lines interleave. For the one command whose output a human is expected to read, prefix each line with the query and serialise through a lock.
- **`cmd_scrape` writes nothing**, per `cli.py:41`. Every cost above is pure overhead paid for a summary — which is exactly why the S2 streaming fix is so cheap to justify: it removes work that buys nothing.

---

## Recommended order of work

1. **Stream instead of materialise** (`cli.py:61` + `cli.py:68-70` → one loop, patch above). One edit, verified byte-identical on 9 shapes. Buys 1.9–2.3x on the aggregation at 500k and −30.5% peak RSS (2,067 MB → 1,436 MB). Correct `None` handling is the only subtlety; do not guard the category increment.
2. **Split "empty" from "failed"** — distinct exit codes (1 vs 3) now, a proper `ScrapeOutcome` from `BaseScraper.scrape` (`scrapers/base.py:33`) later. Until the scrapers stop swallowing `FetchResult.status`/`error`, `cmd_scrape` cannot do the job its docstring claims. 600 s of futile retrying makes this worth more than its S2 label suggests.
3. **Render `(uncategorised)` instead of `None`** at `cli.py:75`, one line, removes a misleading diagnostic from the output people actually read.
4. **Derive `choices` from `registry`** — deletes the dead guard at `cli.py:56-59` and the two-lists drift in one edit.
5. **Leave the imports alone.** 26 ms, fixed cost, not worth the indirection. Only make `cli.py:46` assert what its comment claims, or delete it.

### Measurement notes

All timings on Apple M4 Pro, Python 3.14.8, no network, synthetic records carrying the full 22-key `BusinessRecord` shape (`scrapers/base.py:5-28`) with the Overpass tag layout of `scrapers/osm.py:62-96`. Benchmarks live outside the repo in a private directory (`/private/var/.../opencode/lens221/`); they read `cli.py`, `osm.py`, `google_places.py`, `wikidata.py` and `httpclient.py` and modify nothing. Note the shared-temp-dir hazard: the default temp path contained ~180 files from concurrent agents and a same-named script was overwritten mid-run, so re-runs must use a private subdirectory. Per-pass timings varied up to 2x between launches under that contention, which is why the tables above report three launches rather than a single number. Memory figures are `ru_maxrss` high-water marks (bytes on macOS) taken in fresh single-purpose processes.
