# 082 — Review text as a pain-point signal

## Verdict

Review text would improve personalization, but Google Places is not a compliant source for copying its public reviews into this lead-mining CSV or deriving outbound pitch content from them: Google's current Maps terms expressly prohibit saving user reviews and creating content based on Maps content. Technically, the cheapest way to retrieve a small sample is to add `places.reviews` to the existing Places Text Search field mask; it returns at most five relevance-ranked reviews and upgrades each request to Enterprise + Atmosphere. That technical path is **not** the recommended production path absent written Google permission/legal review. For general prospects, use a provider that contractually licenses storage and outbound analysis, or collect business-authorized/consented review data; otherwise keep using the existing rating/count signals and manually open the Google Maps listing.

## Findings

### S1 — Google Places review text cannot safely become a stored pitch feature
- **Where:** `scrapers/google_places.py:31-42` requests Google place content; `scrapers/google_places.py:249-72` maps only rating/count into records; `main.py:33-40` defines the fixed CSV columns; `scrapers/base.py:5-28` defines the record shape.
- **Breaks:** Google Maps Platform Terms §3.2.3(a) explicitly say customers must not scrape/export Google Maps content outside the services and give “copy and save ... user reviews” as a prohibited example. §3.2.3(b) bars caching except express exceptions; §3.2.3(c) bars creating content based on Google Maps Content. This makes the proposed persistent review-text field and a review-derived `pitch_angle` an apparent contractual conflict even when fetched through the official API. The narrow permission to display reviews is not a general license to export them to a sales CSV: Places policy requires author attribution and a direct Google Maps source link for each displayed review, along with review-order/filter disclosure. This is a terms/compliance blocker, not a claim that all review text is categorically unlawful to read.
- **Trigger:** Request `places.reviews`, write its text or a classifier's theme into `all_businesses.csv`, then use that text/theme in an outbound message.
- **Fix:** Do not persist or derive pitch fields from Google Places review content without written authorization from Google and counsel sign-off; retain only permitted place IDs and the existing separately assessed fields. If research is manual, open the Google Maps page and have the salesperson use it as a live source rather than copying review content into the system.
- **Sources:** [Google Maps Platform Terms, §3.2.3](https://cloud.google.com/maps-platform/terms/#3.-license.) (no scraping, caching, or creating content from Maps content); [Places API policies — Photos and reviews](https://developers.google.com/maps/documentation/places/web-service/policies#photos_and_reviews).

### S2 — Places API exposes a tiny, relevance-ranked sample, not a public review feed
- **Where:** `scrapers/google_places.py:29-42` is the current Text Search request/field mask; `scrapers/google_places.py:227-73` processes its returned place fields; `scrapers/google_places.py:275-79` paginates place search results, not reviews.
- **Breaks:** Places API (New) has no public paginated review-list method for arbitrary prospects. `reviews` is a field on Place Details, Text Search, or Nearby Search; the Place resource says it is relevance-sorted and capped at **five** reviews. Returned fields include `text` (localized text), `originalText`, `rating`, `publishTime`, relative publish time, author attribution (name/profile/photo), `googleMapsUri`, and `flagContentUri`. Text Search review samples are not guaranteed to include the worst or most recent complaints, and five reviews are poor support for a stable sentiment conclusion. The separate Business Profile `accounts.locations.reviews.list` endpoint is paginated (max page size 50), but is only valid for a **verified location** the caller manages and requires Business Profile OAuth; it is not a discovery endpoint for unrelated businesses.
- **Trigger:** A restaurant has hundreds of reviews but the Places response returns five positive/relevant reviews and no complaint; the system incorrectly concludes no pain point exists.
- **Fix:** Treat Places reviews as an incomplete preview only, never “all reviews” or a representative negative-review sample. For authorized owned/managed profiles use Business Profile API pagination; for prospect mining require a licensed source with review coverage and sort/filter behavior stated in its contract.
- **Sources:** [Places REST Place resource — Review and `reviews`](https://developers.google.com/maps/documentation/places/web-service/reference/rest/v1/places#Review); [Place Details (New)](https://developers.google.com/maps/documentation/places/web-service/place-details); [Business Profile reviews.list](https://developers.google.com/my-business/reference/rest/v4/accounts.locations.reviews/list) (verified locations only; 50/page).

### S2 — SERP review vendors are cheaper to try, but the API product is not proof of reuse rights
- **Where:** New provider integration (none exists today); downstream persistence would enter the fixed `BusinessRecord`/CSV pipeline (`scrapers/base.py:5-28`, `main.py:33-40`).
- **Breaks:** SerpApi documents a `google_maps_reviews` engine with review rating, date/ISO date, text `snippet`, author metadata, review link, optional topic data, and sorting (`qualityScore`, `newestFirst`, `ratingLow`, etc.). Its docs show pagination and up to 20 requested results per subsequent page, with initial results defaulting to eight. However, a vendor scraping Google SERPs does not thereby grant leadminer permission to reproduce or repurpose Google's review content; its service's availability or a “Legal Shield” feature is not equivalent to a license from Google or the reviewers, and the current plans describe Legal Shield as US coverage only. SERP scraping can therefore carry Google contract, copyright/database, provider-contract, and privacy exposure. Reviewer names/photos/profile links are personal data in many regimes and are unnecessary for the proposed business-level signal.
- **Trigger:** Treat a SERP API's JSON response as a rights-cleared dataset and store full text/author details indefinitely in lead CSVs, without checking license scope, retention, redistribution, territories, or provider terms.
- **Fix:** Use a SERP provider only after written confirmation that the purchased plan licenses this specific use: retain/derive business-level themes, put those themes in a CRM/CSV, and use them to personalize B2B outreach in Lebanon and Saudi Arabia; document retention and omit author identifiers. Otherwise, regard SERP endpoints as technically convenient but not a compliant path.
- **Cost comparison:** SerpApi currently lists a free plan of 250 searches/month and Starter at **$25/month for 1,000 searches**; a search counts once regardless of result count, while further pages consume further searches. This is an inexpensive pilot price, not the cheapest compliant option. Its `snippet` can be truncated; validate whether the plan returns complete review text before designing classifiers. Google Places' price for `places.reviews` is **$40/1,000 Text Search Enterprise + Atmosphere requests after a 1,000-request monthly free cap** (global price list); but that API's terms issue above makes its low marginal technical cost non-viable for this use. Prices and free caps can change.
- **Sources:** [SerpApi Google Maps Reviews API](https://serpapi.com/google-maps-reviews-api); [SerpApi pricing](https://serpapi.com/pricing); [Google Places global pricing](https://developers.google.com/maps/billing-and-pricing/pricing#places-pricing) (New Places table); [Google Maps Platform Terms, §3.2.3](https://cloud.google.com/maps-platform/terms/#3.-license.).

### S3 — Current code has no durable place key or review/pitch-angle output slot
- **Where:** `scrapers/google_places.py:227-35` reads and deduplicates on `place.get("id")` but does not retain it; record construction at `249-73` omits it. `main.py:33-40` writes a hard-coded field list, and `pitch_recommender.py:25-99` returns only a service label.
- **Breaks:** Even aside from rights, a later paid/authorized provider cannot reliably re-fetch or join reviews against a lead via Google place ID because the ID is discarded after per-run dedupe. There is no source URL, review count used for classification, theme evidence, confidence, or date/status for an angle. `extrasaction="ignore"` at `main.py:125` silently excludes any proposed extra keys until the canonical fields are changed.
- **Trigger:** Review data arrives under an added scraper key, but joins against next month's records rely only on normalized name/city; similar-name branches can be mixed or missed, and angle data silently disappears from CSV.
- **Fix:** If an approved data source is selected, first define a rights-aware schema and join key: store its own stable listing ID/provider and refreshed-at timestamp; only add a compact categorical angle, evidence count/window, confidence, and source URL if the license allows. Keep raw text and reviewer identity out of the master export unless expressly licensed and operationally necessary. Google place IDs themselves are exempt from Google caching restrictions, but the exemption does not extend to reviews.
- **Sources:** [Google Places caching policy](https://developers.google.com/maps/documentation/places/web-service/policies#exceptions_from_caching_restrictions); code references above.

## Cheapest viable path

1. **For a general prospect list now:** $0 incremental API spend—keep the current `rating` and `review_count` fields (`scrapers/google_places.py:265-66`) and give a salesperson a Google Maps listing link for live, manual research. The code currently doesn't retain `googleMapsUri` or place ID, so do not confuse its per-run `seen_ids` set with a persisted listing link/identity.
2. **If the business is a client/authorized managed profile:** use Business Profile `reviews.list` with the client's OAuth authorization and verified location. Google's Business Profile API is listed as no-charge; it gives paginated reviews up to 50 per page and rating/text/author/reply/timestamps (check current Review schema and Business Profile policies for permitted internal use). This does not cover cold prospects.
3. **For scalable cold-prospect review text:** negotiate a vendor contract with explicit rights for extraction, storage, transformation into categories, CRM export, outbound personalization, Lebanon/KSA coverage, retention/deletion, and any subprocessor use. Choose the lowest price for the expected search volume **after** validating these rights and sample coverage. SerpApi free 250 searches is the cheapest technical smoke test; it is not recommended for production without contractual rights confirmation. No public evidence reviewed establishes SerpApi or another SERP provider as Google's licensed review-distribution partner.

## Rule-based pitch angle (only for appropriately licensed or business-authorized text)

No LLM is needed. Do **not** run this transformation over Places API reviews under the current Maps terms. Once a source expressly permits it:

1. Normalize Unicode, case, punctuation, whitespace and common Arabic diacritics; detect language or maintain separately reviewed English/Arabic keyword lists (include Arabic spellings and locally validated transliterations rather than machine-translating literal tokens).
2. Map curated token/phrase dictionaries to a small set of operational themes, e.g. `wait_time`, `delivery`, `staff`, `booking_contact`, `website_information`, `pricing`, `quality_cleanliness`, `availability`, and `parking`. Negation/contrast rules must prevent phrases such as “no long wait” from counting as a complaint. Mark each review's theme at most once; deduplicate repeat text and retain only the count, low-star count, time window, and source permalink if rights permit.
3. Generate an angle only on repeated evidence: e.g. at least two distinct low-rated (1–3 star) reviews with the same theme in the recent window, otherwise `no defensible review angle`. Five-review samples are too small to imply a trend; show sample size and date freshness, and do not treat missing text as a positive signal.
4. Map themes conservatively to existing service labels using a deterministic table. Example: repeated delivery-friction terms at a restaurant may support a **“check whether online ordering / RTYLR could reduce ordering friction”** discovery question, not a claim that web development will fix kitchen delays. Repeated difficulty finding hours/menu/contact could support an SEO/site-information audit. For a repeated complaint outside Voxire's service scope, emit no service angle.
5. Store only the generated categorical result and evidence metadata (not quote or author) when license permits; require a human to verify current evidence and approve phrasing before outreach. Use calibrated copy such as “I noticed multiple recent comments about …” only where the evidence is real, current, and the source/license allows personalization.

## Not a bug, but worth knowing

- The existing numeric ratings/counts already influence `pitch_recommender.py:42-75` (low rating and review-count thresholds). They can support triage without review-text handling, but they do not say what the business should fix.
- Current Text Search mask includes `places.rating`, `places.userRatingCount`, phone, and website (`scrapers/google_places.py:31-42`), so it is already billed at Text Search Enterprise. Adding `places.reviews` raises the request to Enterprise + Atmosphere; it does not necessarily require an extra request if added to the existing mask, but it raises the applicable SKU rate and would still not solve licensing. Google bills at the highest requested field-mask SKU.
- A Google API-returned review includes attribution and source/report URLs. Rendering review cards inside a Google-Maps-using application has strict attribution and linkage requirements; those mechanics do not independently grant permission to export a review into CSV or reuse it as marketing copy.
- This is a product/contract conclusion from the linked public terms, not jurisdiction-specific legal advice. Before relying on a non-Google provider or outbound personalization in Lebanon/Saudi Arabia, have counsel check provider rights, local privacy/data protection and electronic marketing requirements.

## Recommended order of work

1. Decide and document the rights boundary before implementation: no Places API review text or derived angle in leadminer unless Google grants written permission; no SERP-provider production use without a license covering the stated processing and territories.
2. For a low-risk pilot, preserve current Google rating/count signals and add a manual listing-link research step outside the CSV; for owned/managed clients, prototype Business Profile API review pagination under authorized account access.
3. If licensed prospect-review data is approved, test the provider on LB and SA records (English and Arabic), verify text completeness, ordering/filters, stale/closed-listing behavior, usage pricing, and license scope; then specify the minimal categorical schema and keyword dictionaries.
4. Implement deterministic theme counting with conservative evidence thresholds and human review; test false positives for negation, dialect, transliteration, mixed languages, duplicate reviews, and non-serviceable issues before allowing the angle to affect pitches.
