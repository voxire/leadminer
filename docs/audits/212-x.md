# 212 — `cmd_run` returns `None` while promising `int`, and `BusinessRecord` is decorative

## Verdict

`cmd_run` is declared `-> int` (`cli.py:33`) and returns `pipeline.main()`, which is
declared `-> None` (`main.py:148`) and ends at `main.py:242` with no return statement.
The single consumer, `cli.py:315` (`return int(args.func(args) or 0)`), therefore
evaluates `int(None or 0)` and produces **exit code 0 for every possible outcome of the
full pipeline**, including the one where all three scrapers are dead. I ran that case:
3/3 sources raising, five header-only CSVs written, exit code 0. `leadminer run` cannot
report failure, and neither can `python main.py`, because the blindness is in
`main.main()` itself and the CI workflow substitutes a row-count heuristic written in
YAML for the missing exit code.

Secondary: `BusinessRecord` is used in exactly four places, all inside `scrapers/`. Past
`main.py:25-31` the record type is erased to bare `dict`, so nothing in the pipeline is
type-checked against the schema, and the actual runtime schema is the *CSV header*,
which is never validated against `FIELDS`. `load_master` can and does put `None` into
the three fields `BusinessRecord` declares non-optional.

## Findings

### S1 — `cmd_run` cannot report failure; every pipeline outcome becomes exit 0

- **Where:** `cli.py:33-37` (the function), consumed at `cli.py:315`
  ```python
  33: def cmd_run(args: argparse.Namespace) -> int:
  34:     """Full pipeline. Thin wrapper over main.main so there is one code path."""
  35:     import main as pipeline
  36:
  37:     return pipeline.main()
  ...
  315:         return int(args.func(args) or 0)
  ```
- **Declared vs actual:** declared `int`; actual `NoneType`. Verified:
  ```
  cmd_run annotation : int
  Namespace attrs    : ['cmd', 'func']      # built_parser().parse_args(["run"])
  cmd_run returned   : None NoneType
  cli.main(['run']) -> 0  == exit code 0
  ```
  `main.main()` is `def main() -> None` (`main.py:148`) with no value-returning `return`
  statement anywhere in its body, so `pipeline.main()` is statically and dynamically
  `None`. `mypy --strict` would reject `cli.py:37` as
  `error: Incompatible return value type (got "None", expected "int")  [return-value]`.
  I could not execute mypy to show this — it is not installed and the brief forbids
  installing — but nothing in CI runs it either (see S3).
- **Breaks:** the exit code is the only signal a scheduler, a CI job, a cron wrapper or
  a human running `leadminer run && echo ok` can see. Here it is structurally incapable
  of being non-zero for any soft failure. The three scrapers all fail *softly* by design:
  `osm.py:47-56` and `wikidata.py:79-85` `return` on a non-`ok` fetch, and
  `google_places.py:169-171` returns when the key is unset and `228-233` returns on 401.
  `main.py:167-168` catches any remaining exception per source and prints it. So the
  "all sources dead" path is a *normal return*, indistinguishable from success.
- **Trigger (demonstrated, no network, nothing written into the repo):** stubbed the
  three scraper classes in `main`'s namespace to raise, then called the real
  `cli.cmd_run` inside a `tempfile.TemporaryDirectory()` as cwd:
  ```
  [stub] pipeline ran and did nothing
  --- files produced in data/ ---
    all_businesses.csv                 225 bytes
    qualified_businesses.csv           225 bytes
    sales_ready.csv                    225 bytes
    with_websites.csv                  225 bytes
    without_websites.csv               225 bytes
  cmd_run() returned   : None
  process exit code    : 0  <-- ALL THREE SOURCES FAILED
  ```
  And the more insidious variant — 2 of 3 sources dead, the third healthy:
  ```
  [DeadGP] ERROR: Google: 401 invalid API key
  [DeadOSM] ERROR: Overpass API: HTTP 504
  [Ok] collected 4 records
  Total raw records from scrapers: 4
  After merge + dedup: 3 unique businesses

  rows=3  sources={'wikidata'}
  cmd_run returned: None -> exit code 0  (2 of 3 sources dead, run is GREEN)
  ```
  A master CSV in which `source` has exactly one distinct value, published as a success.
- **Fix:** make `main.main() -> int` return `0` on success and a non-zero code when any
  scraper produced zero records for a reason other than a legitimately empty result;
  `return int(pipeline.main() or 0)` in `cmd_run`; delete the `or 0` at `cli.py:315`.

### S2 — the root cause is `main.main() -> None`, and CI compensates with a YAML heuristic

- **Where:** `main.py:148` (`def main() -> None:`), `main.py:245-246`
  (`if __name__ == "__main__": raise SystemExit(main())`), and
  `.github/workflows/scrape.yml` → step **"Run scrapers"** which invokes
  `python main.py`.
- **Breaks:** `SystemExit(None)` exits 0 — verified:
  ```
  simulating main.py:245-246 (`raise SystemExit(main())`, main() -> None)
    stdout: ran | returncode: 0
  ```
  So the CLI is not a wrapper that loses the signal; the signal never existed. The
  workflow knows this and substitutes a proxy — the "Validate output before publishing"
  step fails only if `all_businesses.csv` is empty or has `ROWS < 100`. That check:
  1. lives in YAML, not in the code anyone can call from a laptop;
  2. fires on a *total* row count, so it cannot see a single-source outage unless the
     total also drops below 100 (demonstrated above: 2/3 dead, exit 0, all gates pass);
  3. is dead for local `leadminer run`, which README.md:96 tells operators to use.
- **Fix:** `main.main() -> int`; have the workflow call `leadminer run` so CI and local
  share one code path (which is what `cli.py:34` already claims), and replace the row
  heuristic with a per-source record-count assertion surfaced in a run manifest.

### S2 — `load_master` writes `None` into the three fields `BusinessRecord` declares non-optional

- **Where:** `main.py:96-101`, against `scrapers/base.py:25` (`lead_score: int`),
  `scrapers/base.py:28` (`completeness_score: int`) and
  `scrapers/base.py:22` (`review_count: int | None`).
  ```python
   96:             for field in _INT_FIELDS:
   97:                 if row.get(field) is not None:
   98:                     try:
   99:                         row[field] = int(float(row[field]))
  100:                     except (ValueError, TypeError):
  101:                         row[field] = None
  ```
- **Breaks:** every master row whose `lead_score` / `completeness_score` /
  `review_count` cell is blank or non-numeric becomes `None`, which contradicts the
  declared `int`. Nothing raises, nothing is logged. The declared invariant is only
  restored later and by accident, as a side effect of `enricher.py:349-350` recomputing
  both scores for every record. Between `main.py:180` (dedup) and `main.py:187` (enrich)
  the whole record set is in violation of its own type, and `enrich()` is the *only*
  thing holding the contract up.
- **Trigger:** a master CSV whose numeric cells are blank or dirty. Demonstrated against
  the real `load_master`:
  ```
  A {'lead_score': 30, 'completeness_score': 2, 'review_count': 12} ints
  B {'lead_score': None, 'completeness_score': None, 'review_count': None}   # blank cells
  C {'lead_score': None, 'completeness_score': None, 'review_count': 3}       # "oops" / "NaN"
  ```
- **Fix:** make the two computed fields `int | None` in `BusinessRecord` (they genuinely
  are nullable text round-trips), and coerce to `0` at the single point of use rather
  than relying on `enrich()` to happen to run.

### S2 — `main.py:206` guards the case that cannot happen and not the one that does

- **Where:** `main.py:206`
  ```python
  206:     qualified = [r for r in records if r.get("completeness_score", 0) >= 1]
  ```
- **Breaks:** the `, 0` default is dead code — `load_master` guarantees the key is
  present on every record (`main.py:87-89` only rewrites values, never removes keys), so
  `.get` always returns the stored value. When that value is `None` (the S2 finding
  above), the comparison raises. Demonstrated:
  ```
  main.py:206 raises: TypeError '>=' not supported between instances of 'NoneType' and 'int'
  ```
  Today this is masked, because `enricher.py:349` recomputes `completeness_score` for
  every record before `main.py:206` runs. It is one `--skip-enrich` flag, one early
  return in `enrich`, or one refactor that moves the export before enrichment away from
  a `TypeError` in the middle of a 5-hour run that has already burned the Google Places
  quota.
- **Fix:** `if (r.get("completeness_score") or 0) >= 1`.

### S3 — the CSV header is the real schema, and nothing checks it against `FIELDS`

- **Where:** `main.py:86-104` (`load_master` passes `csv.DictReader` rows through
  verbatim), `dedup.py:192` (`for key in set(a) | set(b)` — arbitrary keys survive the
  merge), `main.py:125` (`DictWriter(..., extrasaction="ignore")` — unknown keys are
  silently dropped at write time).
- **Breaks:** the set of keys on a live record is decided by whatever header the master
  CSV happens to have, and that set is never compared to `FIELDS` or to
  `BusinessRecord`. Two concrete, silent outcomes:
  - **Extra column** (`notes`, `owner`, `last_contacted` — plausible for a file the
    sales team reads per `pitch_recommender.py:8`): every record gains the key, it is
    merged and enriched like any real field, and then it is dropped at
    `write_csv` with no warning. Data the team typed in vanishes.
  - **Misspelled column** (`lnkdin`): `linkedin` is *absent* from every record. The
    pipeline runs to completion, exports, and prints a healthy summary, with the
    `linkedin` column empty on every row. `cmd_validate` exists and does not look at the
    header at all (`cli.py:135-201` checks name, BOM, coords, rating, dupes).
- **Trigger:** `data/all_businesses.csv` with header
  `...,linkedin,lnkdin,...` or `...,linkedin,notes`.
- **Fix:** in `load_master`, `unknown = set(row) - set(FIELDS)` and warn; in
  `cmd_validate`, add `missing = set(FIELDS) - set(rows[0])` and fail on either. One
  header line buys a whole schema gate.

### S3 — `args` is ignored, `run` takes no options, and `cli.py:315` is a conversion, not a safety net

- **Where:** `cli.py:33` (`args` never read), `cli.py:285-286` (`run` subparser adds no
  arguments), `cli.py:315`.
- **Breaks, three ways:**
  1. `leadminer run` cannot be told anything. `main.main()` takes no parameters, so the
     CLI exposes zero control over sources, limits, or dry-run — the "one code path" of
     `cli.py:34` is one unconfigurable code path.
  2. The docstring's "one code path" is already false for interrupts: `python main.py`
     under Ctrl-C raises `KeyboardInterrupt` out of `main()` (traceback, exit 1);
     `leadminer run` catches it at `cli.py:316-318`, prints `interrupted`, exits 130.
     Two entry points, two behaviours.
  3. `int(args.func(args) or 0)` is a *type conversion*, and it raises on any truthy
     non-int return — the one shape a future `cmd_run` is most likely to grow into
     (a stats dict, a record count plus a summary). It escapes `except KeyboardInterrupt`
     and tracebacks **after** `data/` has been overwritten. Verified for each shape:
     ```
     return [1, 2, 3]    -> TypeError: int() argument must be a string, ... not 'list'
     return {'rows': 42} -> TypeError: int() argument must be a string, ... not 'dict'
     return '42 records' -> ValueError: invalid literal for int() with base 10
     return 0.7          -> 0                      # silently truncated, not rejected
     ```
     So the one line standing between the pipeline and the exit code is simultaneously a
     no-op on the current shape and a crash on the plausible next one.
- **Fix:** drop the `or 0` and let `main() -> int` be checked; add `--source`, `--limit`,
  `--dry-run` to the `run` subparser, or delete the parameter and the docstring claim.

- **Breaks:** the S1 is a one-line `[return-value]` error that `mypy --strict` reports

- **Evidence:** ruff *is* installed in this environment and reports 9 findings across

  finding alone is not an S3 in effort.

## Not a bug, but worth knowing

- **The write side of `BusinessRecord` is currently honest.** All three scrapers build
  records with exactly the 23 declared keys — verified by AST, no missing, no extra:
  ```
  scrapers/osm.py:98         n=23 missing=[] extra=[]
  scrapers/wikidata.py:106   n=23 missing=[] extra=[]
  scrapers/google_places.py:281 n=23 missing=[] extra=[]
  ```
  So no scraper can violate the TypedDict today. The risk is entirely on the read side.
- **`FIELDS` and `BusinessRecord` are the same 23 names in different orders, and nothing
  asserts that.** Verified: `len(FIELDS) == 23`, `len(BusinessRecord) == 23`,
  set difference empty in both directions, `FIELDS == TD` is `False`. Two independent
  declarations of the same schema (order is irrelevant to `DictWriter`, which uses
  `FIELDS`), so a future column added to one and not the other fails silently — see S3.
- **`BRIEF.md` miscounts the schema twice**: `BRIEF.md:18` says
  "BusinessRecord TypedDict (22 keys)" and `BRIEF.md:57` says "The 22 columns" before
  listing 23. The real number is 23.
- **The only bracket access on a live record is safe.** `enricher.py:231`
  (`targets = [(i, r["website"]) ... if r.get("website")`) is guarded by the `.get` on the
  same line, so a record missing the `website` key entirely cannot `KeyError`. Same for
  `cli.py:167`, which catches `KeyError` explicitly.
- **`cmd_scrape` reads only in-schema fields, defensively**: `category`, `phone`,
  `website` at `cli.py:68-70`, all declared, all via `.get`.
- **Field-level defect already present but masked by `.get` semantics**:
  `main.py:103` coerces `website_live` by exact string match
  (`True` / `False`, anything else → `None`), so `"true"`, `"TRUE"`, `"1"` and `"yes"`
  all become "unreachable". Only externally-edited CSVs hit it; the three scrapers all
  write `None` (`osm.py:109`, `wikidata.py:117`, `google_places.py:292`).

## Field ledger for `cmd_run` and the function it returns from

`cmd_run` itself reads and writes **zero record fields** — it takes no record, returns
no record, and its `args` is unused. Everything below is the body it delegates to.

## Recommended order of work

1. **`main.main() -> int` and thread the status through.** Return non-zero when any
   scraper yields zero records, and when the whitelist filter or dedup drops more than
   an agreed fraction. This is the whole of S1 and S2-root and it is a small diff.
2. **Delete `or 0` at `cli.py:315`** and let `cli.main` trust the declared `int`. Add a
   regression test: `cmd_run` against a stubbed `main.main` that returns `1` must yield
   exit code 1. There is no such test today (`tests/test_lead_signal.py:191-264` covers
   `stats` and `validate` only).
3. **Add `ruff check .` and `mypy --strict .` to CI.** Finding 1 is a `[return-value]`
   error today; the type half of this report becomes enforceable rather than advisory.
4. **Switch the workflow to `leadminer run`** and replace the `ROWS < 100` heuristic with
   a per-source record count in a run manifest, so a 2-of-3 outage is distinguishable
   from a healthy run.
5. **Fix `main.py:206`** to `(r.get("completeness_score") or 0) >= 1` and decide whether
   `lead_score` / `completeness_score` are nullable in `BusinessRecord` (they are, after
   `load_master`).
6. **Header validation in `load_master` + `cmd_validate`** — warn on unknown columns,
   fail on missing ones. Cheap, and it makes the master CSV safe to hand-edit.
7. **Either give `run` real flags or drop `args`** and correct the "one code path"
   docstring at `cli.py:34`, which is already false for Ctrl-C behaviour.

## How this was verified

No network calls were made and no repository file other than this report was written.
`requests` and `urllib3` were replaced with in-process stubs using the same technique as
`tests/test_lead_signal.py:23-63`; the three scraper classes were replaced with raising
or fixture-yielding stand-ins *inside the imported `main` module's namespace*; and
`main.DATA_DIR` is the relative path `data` (`main.py:41`), so every pipeline execution
ran with `cwd` set to a `tempfile.TemporaryDirectory()`. All key-set comparisons were done
with `ast` rather than by executing the scrapers. Ruff was run read-only
(`--no-cache`). mypy is not installed in this environment and was not installed; its
verdict in the S1 finding is stated from the annotation alone, not from an execution.
