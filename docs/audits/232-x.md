# 232 — `cmd_validate` (`cli.py:135`) input-by-input audit

## Verdict

`cmd_validate` is not a data-quality gate; it is a **shape check that only
inspects the four columns it happens to read, and its most important check —
coordinates — is silently skipped for exactly the rows that have no
coordinates.** The single most dangerous property is that a file in which
**100% of rows have blank or missing `lat`/`lon` passes with `all checks
passed` and exit 0**, which is precisely the shape a run produces when Google
Places returns nothing and Wikidata/OSM carry the export. Secondary: the
duplicate check re-derives an identity model that disagrees with
`dedup.normalize_phone`/`normalize_name`, so it both false-positives on real
chains and false-negatives on the duplicates the pipeline actually merges.

Every claim below was executed, not reasoned about. Harness lives outside the
repo (`cli` imports only stdlib at module level, so it is importable without
`requests`; `main.py` could not be imported because `scrapers/osm.py:4` →
`httpclient.py:43` requires `requests`, which is not installed and I did not
install it — `FIELDS` was parsed out of `main.py:33-40` with `ast` instead).

## Findings

### S1 — A CSV with **zero** coordinates passes the coordinate check

- **Where:** `cli.py:166-169`. `float(r["lat"])` raises `ValueError` on `""`
  and `TypeError` on `None`; both are swallowed by `except
  (ValueError, TypeError, KeyError): continue`. `continue` means "not bad",
  not "cannot check".
- **Breaks:** `bad_coords` only ever counts rows that *have* coordinates and
  are wrong. A row with no coordinates is invisible to the check. The failure
  this is supposed to catch — a run where the geospatial sources died and the
  export has no `lat`/`lon` — is exactly the failure it reports as clean.
- **Trigger (executed):** 1,000 rows, `lat=""`, `lon=""` in every row, every
  other field perfect:
  ```
  $ leadminer validate CC_nocoord1000.csv
  checked 1,000 rows in .../CC_nocoord1000.csv
    all checks passed          # exit 0
  ```
  Production-shaped confirmation — 5,000 `wikidata`-source rows (Wikidata
  records have no `lat`/`lon` unless P625 is bound; `wikidata.py:101`
  `_parse_point` returns `(None, None)` otherwise) → same `all checks passed`,
  exit 0. Also passes with 200 rows where `lat`/`lon` columns do not exist at
  all (`KeyError` swallowed at `cli.py:168`), and with 1,000 rows whose
  `lat`/`lon` are whitespace-only `"   "`.
- **Fix:** count unparseable coordinates as a separate, always-reported
  `missing_coords` figure and fail when it exceeds a threshold, e.g. `except
  (ValueError, TypeError, KeyError): missing_coords += 1`.

### S1 — The geographic boxes swallow Syria, Jordan, Israel, Iraq, Kuwait, UAE, Qatar

- **Where:** `cli.py:159-162`. `lb = 33.0 <= lat <= 34.8 and 35.0 <= lon <= 36.9`;
  `sa = 16.0 <= lat <= 32.2 and 34.4 <= lon <= 55.7`.
- **Breaks:** these are axis-aligned rectangles, and both countries are
  neighbours. The check titled "coordinates outside Lebanon/Saudi Arabia"
  returns `True` for rows in at least eight other countries. Executed
  `in_box()` against real city coordinates:
  ```
  Damascus  SY (33.51, 36.29) -> PASSES      Amman    JO (31.95, 35.91) -> PASSES
  Tel Aviv  IL (32.08, 34.78) -> PASSES      Jerusalem IL (31.77, 35.21) -> PASSES
  Aqaba     JO (29.53, 35.01) -> PASSES      Basra    IQ (30.51, 47.78) -> PASSES
  Kuwait City KW (29.37, 47.98) -> PASSES    Abu Dhabi AE (24.45, 54.37) -> PASSES
  Dubai     AE (25.20, 55.27) -> PASSES      Doha     QA (25.29, 51.53) -> PASSES
  Eilat     IL (29.56, 34.95) -> PASSES      Petra    JO (30.33, 35.44) -> PASSES
  ```
  Only Baghdad, Muscat, Sharm el-Sheikh and Nicosia were flagged.
- **Trigger (executed):** 200 rows at Damascus `33.5131, 36.2765`, unique
  names and phones → `all checks passed`, exit 0. Same for 200 rows at Amman
  `31.9539, 35.9106`. A single `textSearch` result from the wrong market, or
  a Google query drifting across the border, lands in the master silently.
- **Fix:** replace the two rectangles with the actual country polygons (or at
  minimum require `country` to agree with the box that matched, and add
  exclusion boxes for the neighbours).

### S1 — Non-UTF-8 and oversized-field inputs crash with a traceback, and the
exit code is indistinguishable from a data failure

- **Where:** `cli.py:142-143`. The `open(...)`/`list(csv.DictReader(f))` pair
  is unguarded, and `main()` at `cli.py:314-318` only catches
  `KeyboardInterrupt`.
- **Breaks:** the validator's whole purpose is to be the thing that does not
  die on a bad file. It dies, and it dies with **exit code 1** — byte-for-byte
  the same exit code as "problems found". A CI step cannot distinguish "the
  data is bad" from "the validator is broken", and `cmd_doctor`'s own comment
  at `cli.py:228-229` ("must never be the thing that tracebacks") shows the
  author knew this rule for the neighbouring command.
- **Trigger (executed), all exit code 1, all with a raw traceback:**
  - cp1256 (Arabic Windows codepage — the realistic encoding for a local
    Excel export of Arabic business names): `name = "مطعم الحمصي"` →
    `UnicodeDecodeError: 'utf-8' codec can't decode byte 0xe3 in position 221`
    raised at `cli.py:143`.
  - cp1252, `name = "Café Beirut"` → `UnicodeDecodeError` at `cli.py:143`.
  - UTF-16 (Excel "Unicode Text") → `UnicodeDecodeError: ... byte 0xff in
    position 0` at `cli.py:143`.
  - One cell of 200,000 chars (default `csv.field_size_limit` is 131,072) →
    `_csv.Error: field larger than field limit (131072)`.
  - `args.file` pointing at a directory → `IsADirectoryError` at `cli.py:143`.
    `path.exists()` at `cli.py:138` is `True` for a directory.
- **Fix:** wrap the read in `except (OSError, UnicodeDecodeError, csv.Error)`
  and return a distinct non-1 code (e.g. 2) with a one-line message, matching
  the treatment `cli.py:82-84` already gives a missing file.

### S2 — The duplicate key disagrees with the pipeline's own identity model

- **Where:** `cli.py:190`. `{(r.get("name"), r.get("phone")) for r in rows}` —
  raw strings, no `dedup.normalize_phone`, no `dedup.normalize_name`, no city.
- **Breaks:** in both directions.

  **False negative — duplicates the pipeline really merges are invisible.**
  `dedup.normalize_phone` (`dedup.py:33-63`) strips non-digits and normalises
  country prefixes; `normalize_name` (`dedup.py:66-69`) NFKD-folds, drops
  combining marks and collapses whitespace. None of that happens here.
  Executed, 5 businesses each listed twice:
  ```
  rows: name "Cafe Hamdi", phone "+961 1 123 456"  and  name "Cafe Hamdi", phone "+9611123456"
  cmd_validate -> all checks passed, exit 0
  dedup.dedup() on the same records -> 1 row
  ```
  Also confirmed invisible: whitespace-padded names (`" Cafe Hamdi "` vs
  `"Cafe Hamdi"`, `dedup` → 5 rows) and combining-accent variants
  (`"Café X"` vs `"Cafe X"`, `dedup` → 5 rows).

  **False positive — real, deliberately-kept rows are reported as duplicates.**
  `dedup.dedup` keys blank-phone rows on `(normalize_name, city)`
  (`dedup.py:212-214`), so chains in different cities survive on purpose. The
  validator has no city in its key, so any two same-name/blank-phone rows
  collide. Executed: 300 OSM rows (`address=""`) + 300 Wikidata rows
  (`address="St i, Beirut, Lebanon"`), same 300 names, every phone blank:
  ```
  cmd_validate -> "- 300 duplicate (name, phone) pairs", exit 1
  dedup.dedup() -> keeps all 600 rows (cities differ; they are distinct businesses)
  ```
  A real `leadminer` run with two or three chains across Lebanon trips this.
  Scaling the same shape to 60 `"Al Baik"` rows in 1,000 also trips it, and
  the 1,200-row mixed Google+OSM+Wikidata export built from actual
  scraper output shapes reports `300 duplicate (name, phone) pairs` for rows
  the pipeline deliberately keeps.
- **Fix:** reuse the pipeline key —
  `dedup.normalize_phone(...) or (dedup.normalize_name(name), dedup._extract_city(address))` —
  or drop this check entirely and run `dedup.dedup` to measure it.

### S2 — `bad_rating` has no threshold; the other two checks do

- **Where:** `cli.py:187`. `if bad_rating:` — a bare truthiness test, while
  coords use `> total * 0.01` (`cli.py:172`) and dupes use `> total * 0.05`
  (`cli.py:191`).
- **Breaks:** one row out of a hundred thousand blocks publication. On a
  cumulative master that never shrinks, a single bad rating is permanent
  until someone hand-edits the master, and the natural operator response is
  to stop trusting the gate.
- **Trigger (executed):** 99,999 rows with `rating="4.1"` and **one** row
  with `rating="9.9"`:
  ```
  checked 99,999 rows in .../S_rating.csv
    PROBLEMS:
      - 1 rows have a rating outside 0-5
  ```
  exit 1.
- **Fix:** apply the same relative threshold used for the other two checks,
  e.g. `if bad_rating > max(1, total * 0.001):`.

### S3 — Threshold arithmetic is off-by-one against its own stated percentage

- **Where:** `cli.py:172` `bad_coords > total * 0.01`, `cli.py:191`
  `dupes > total * 0.05`.
- **Breaks:** the effective tolerance is `floor(total * frac) + 1`, so the
  smallest number of bad rows that trips the gate jumps around with file size:
  ```
  total=   99 -> need bad_coords >= 1   (1.01%)
  total=  100 -> need bad_coords >= 2   (2.00%)   <- 99-row file fails, 100-row passes
  total=  200 -> need bad_coords >= 3   (1.50%)
  total=1000 -> need bad_coords >= 11   (1.10%)
  total=50000 -> need bad_coords >= 501 (1.002%)
  ```
  Executed: 100 rows with 1 bad coordinate → exit 0; 50 rows with 1 bad
  coordinate → exit 1. Two files with the *same* 1-record defect get opposite
  verdicts purely from row count.
- **Fix:** compare rates, `bad_coords / total > 0.01`, not counts against a
  float product.

### S3 — `rating` accepts values no upstream source can emit

- **Where:** `cli.py:185` `if not 0 <= v <= 5`.
- **Breaks:** Google Places ratings are `1.0–5.0`; `0.0` is a sentinel/parse
  artifact, not a rating, and `enricher.lead_score` at `enricher.py:313`
  awards the +10 "low rating = pain point" bonus to any `rating < 4.0`. A
  `0.0` row therefore scores as a *bigger* pain point than a genuinely
  terrible 1-star business, and validate blesses it.
- **Trigger (executed):** 200 rows, one with `rating="0"` → `all checks
  passed`, exit 0. `rating="-1"` in the same shape → correctly flagged.
- **Fix:** tighten the accepted range to `1.0 <= v <= 5.0` for the
  `google_places` source, or flag `0` separately as a missing-value sentinel.

### S3 — Blank-name check is all-or-nothing and says nothing actionable

- **Where:** `cli.py:151-152` `if not any((r.get("name") or "").strip() ...)`.
- **Breaks:** the message is `"every row has a blank name"` — it fires only at
  100%. 99 blank names out of 100 is a broken export and reports nothing.
  There is no count, so an operator has no number to act on.
- **Trigger (executed):** 200 rows, 199 with `name=""` → the only PROBLEM
  reported is `198 duplicate (name, phone) pairs`; the 199 blank names are
  never mentioned.
- **Fix:** always report the count, e.g. `f"{blank} rows have a blank name"`,
  and fail on a rate rather than only at 100%.

### S3 — A renamed or truncated header is reported as a data problem, not a schema problem

- **Where:** `cli.py:167` `r["lat"]` raises `KeyError`, caught at `cli.py:168`.
  `cli.py:151` `r.get("name")` returns `None`.
- **Breaks:** a schema change is diagnosed as corrupt *values*.
- **Trigger (executed):** header `["biz_name","latitude","longitude","tel","score"]`,
  100 rows all at `48.85, 2.35` (Paris) with `score=9.9` → reported as
  `every row has a blank name` + `99 duplicate (name, phone) pairs`. The Paris
  coordinates and the 9.9 rating are never checked. Same for a file with `lat`
  but no `lon`: 200 rows all with `lat=48.85` → `all checks passed`, exit 0.
  And a file whose rows have one field each (`Short`) → 99 "duplicates",
  which is the only hint that the file is truncated at all.
- **Fix:** validate the header against `main.FIELDS` up front and fail with
  `missing columns: [...]` before reading any values.

### S3 — `duplicate (name, phone) pairs` is the wrong noun

- **Where:** `cli.py:190-192`.
- **Breaks:** `total - len(set)` counts *extra rows*, not duplicate pairs.
  Executed: 20 identical rows → `"19 duplicate (name, phone) pairs"`. There is
  exactly **one** duplicate pair and **19** surplus rows. An operator chasing
  19 pairs will not find 19.
- **Fix:** report both — the number of duplicated keys and the number of
  surplus rows — e.g. `f"{n_groups} duplicated keys, {dupes} surplus rows"`.

## Not a bug, but worth knowing

- **Lat/lon swap is caught for both markets** — `in_box(46.6753, 24.7136)`
  fails the SA test because 46.67 > 32.2, and `in_box(35.483, 33.895)` fails
  the LB test because 35.48 > 34.8. Executed on 200-row files for both
  markets: both correctly flagged. The rectangles are loose, but they are
  oriented the right way round. (Finding S1 is about *neighbouring* countries,
  not about transposition.)
- **`nan` / `inf` coordinates are flagged** — `float("nan")` parses, and
  `33.0 <= nan <= 34.8` is `False`, so `nan` fails `in_box`. Executed:
  `lat="nan"` and `lat="inf"` → both counted as `bad_coords`. Same for
  `rating="nan"`, `"Infinity"`, `"-Infinity"` → all three counted.
- **`Null Island` (0.0, 0.0) is flagged** — 1,000 rows → `1000 rows have
  coordinates outside Lebanon/Saudi Arabia`. Good.
- **`rating` range check is otherwise sound** — `-1` and `9.9` both caught;
  non-numeric (`ValueError` → `bad_rating += 1`) caught; blank correctly
  skipped via `cli.py:178`.
- **`--source`/schema knowledge is not the validator's job today.** It reads
  one file and knows nothing about which of the five exports it is. That is
  defensible, but it is why finding S2 exists: a `sales_ready.csv` row with no
  contact channel at all, `industry_priority="low"` and `lead_score=999`
  passes cleanly (executed, 500 rows, exit 0), even though `main.py:202-205`
  defines that file as "has a contact channel AND priority in (high, medium)".
  Consider a `--expect sales_ready` mode that asserts the export's own
  contract.
- **The BOM check works, but only by accident of encoding choice.**
  `cli.py:142` opens with `encoding="utf-8-sig"`, which strips the header
  BOM, so `cli.py:154`'s `startswith("\ufeff")` test can only fire on a BOM
  embedded in a *value*. Executed: a file with a UTF-8 BOM in the header
  (the Google-Sheets shape) → `all checks passed` (correct, `utf-8-sig` ate
  it); a file with U+FEFF glued to the front of a name value → correctly
  flagged, but the message `"written without utf-8-sig"` is the wrong
  diagnosis — a BOM in a *value* means the upstream data had one, not that the
  file was written without the codec. The check is a real check; its
  explanation is wrong.
- **`(name, phone)` with `phone=None`** (short rows, or no phone column)
  collapses to `(name, None)`, so a file of 200 `"Al Baik"` rows with no
  phone column reports `199 duplicate (name, phone) pairs`. Covered by S2.

## Recommended order of work

1. **S1-a** — Stop swallowing missing coordinates (`cli.py:166-169`). Add a
   `missing_coords` counter that is always reported. This is the finding that
   lets an entirely un-geolocated export pass as clean. ~5 lines.
2. **S1-b** — Catch `(OSError, UnicodeDecodeError, csv.Error)` around the read
   (`cli.py:142-143`) and return a distinct exit code. The gate must survive
   the files it exists to judge. ~5 lines.
3. **S1-c** — Replace the two rectangles (`cli.py:159-162`) with real country
   polygons, or at minimum add exclusion boxes and a `country`-vs-box
   agreement check. Largest effort, but it is the only thing making the
   coordinate check meaningful.
4. **S2-a** — Make the duplicate check use `dedup.normalize_phone` /
   `normalize_name` / `_extract_city` (`cli.py:190`), or drop it in favour of
   `dedup.dedup`. Removes both false positives and false negatives at once.
5. **S2-b** — Give `bad_rating` a threshold (`cli.py:187`) to match the other
   two checks.
6. **S3 batch** — rate-based thresholds, header validation against
   `main.FIELDS`, blank-name count, corrected duplicate wording, `1.0 <= rating <= 5.0`,
   and the corrected BOM message. All mechanical, all independently landable.
7. **Wire it into CI.** `.github/workflows/scrape.yml:71-83` should call
   `leadminer validate data/all_businesses.csv` (after fixes 1-5 land) instead
   of the hand-rolled `wc -l`. Until then every finding above is advisory.
