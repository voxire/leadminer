# 205 — `_fmt` is O(1); the O(n) cost is the twelve traversals it sits inside

## Verdict

`_fmt` (`cli.py:29-30`) is **O(1) in time and O(1) in allocation** in the number of
businesses. It is called exactly six times, all unconditional, all in the fixed
prologue of `cmd_stats` (`cli.py:98-103`) — never inside a loop over rows. Measured,
it costs ~404 ns per call and ~1.3 µs for all six, **identical at 10k, 100k and 500k
records**. There is no speedup available in this function; the answer to "identify the
single change with the largest speedup" is *none, because there is nothing to speed
up*. The real per-record cost lives one line away from the target, in
`cli.py:87` (`list(csv.DictReader(f))`) plus twelve redundant full traversals of that
list at `cli.py:96,107-110,116,120,124,129`. That is an S2, and it is explicitly
**outside** the assigned target — I flag it only so the report is actionable.

Measured on this box (macOS 27.0.1, Apple M4 Pro, CPython 3.14.8, median of 5 runs,
`gc` disabled during each run, synthetic 23-column CSV matching `main.py:33-40` with
realistic LB/SA names, `+961` phones, `example{i}.com` sites):

| rows | CSV size | `_fmt` x6 | read+parse | `count()` x6 | Counters x4 | **`cmd_stats` total** | peak RSS (traced) |
|---|---|---|---|---|---|---|---|
| 10,000 | 2.1 MB | **1.2 µs** | 0.035 s | 0.005 s | 0.004 s | **0.071–0.083 s** | 24 MiB |
| 100,000 | 21.3 MB | **1.4 µs** | 0.385 s | 0.123 s | 0.094 s | **0.86–1.01 s** | 245 MiB |
| 500,000 | 108.5 MB | **1.3 µs** | 2.578 s | 0.658 s | 0.507 s | **3.87–5.08 s** | **1,215 MiB** |

`_fmt`'s share of the 500k run is `2.4 µs / 3.87 s` = **0.000062 %**. Halving
`_fmt` would move `cmd_stats` at 500k by 1.2 µs — unmeasurable. Do not spend a
review cycle here.

## Findings

### S3 — `suffix` is a dead parameter; every call site passes one argument

- **Where:** `cli.py:29` (declaration) vs `cli.py:98-103` (the only six callers)
- **Breaks:** nothing at runtime. It is pure surface area. `grep -n '_fmt'` across the
  repo returns exactly seven hits: the definition at `cli.py:29` and six calls, all of
  the form `{_fmt(count('phone'))}` — one positional argument, `suffix` defaulted every
  time. No caller in the repo, no test, no docstring example passes it. Worse, it is
  *misleading*: `suffix` exists to support "12,345 ms" or "1,234 km", but the actual
  consumers of formatted counts at `cli.py:111-113` and `cli.py:117,121,126,131`
  interpolate `f"{v:,}"` by hand rather than call `_fmt`. So the codebase has both a
  formatter and a hand-rolled duplicate, and the formatter is the one nobody trusts
  with the extra argument. A reader must prove the negative to learn this.
- **Trigger:** `_fmt(1234, " ms")` — greppable, returns `'1,234 ms'`, and has never been
  executed by anything in this repository.
- **Fix:** delete `suffix` from the signature (`def _fmt(n: int | float | None) -> str:`),
  or route `cli.py:111-113,117,121,126,131` through `_fmt` and then the parameter earns
  its keep. Deleting is the smaller, safer change.

### S2 (outside the assigned target) — `cmd_stats` and `cmd_validate` are O(n) time **and** O(n) memory, and summarise 108 MB by holding 1.2 GiB

- **Where:** `cli.py:87` and `cli.py:143` (`rows = list(csv.DictReader(f))`), amplified by
  twelve further O(n) traversals of the materialised list at `cli.py:96` (six times, once
  per field via `count`), `cli.py:107-110` (three passes), and `cli.py:116,120,124,129`
  (four `Counter` passes). Same shape at `cli.py:190` in `cmd_validate`.
- **Breaks:** two separate problems that compound.
  1. **Time — 13 traversals where 1 suffices.** After the parse, `cmd_stats` walks the
     full `rows` list thirteen separate times. Each `Counter(...)`/`sum(...)` at
     `cli.py:96,107-110,116,120,124,129` re-reads all 23 dicts per row from memory,
     where one fused pass reads each row once. At 500k rows the redundant passes cost
     0.658 s (`count` x6) + 0.507 s (Counters) + ~0.5 s (`website_live` x3) ≈ 1.6 s of
     the 3.87 s, and the waste *grows with n*: the fused version is 1.17x faster at
     10k and 100k but 1.31x faster at 500k, because twelve extra passes over a 1.2 GiB
     working set miss cache progressively harder.
  2. **Memory — 11.7x blow-up.** `list(csv.DictReader(f))` materialises 500k 23-key dicts
     as 500k separate objects. Traced peak for `cmd_stats` is **1,215 MiB** to summarise a
     **103.5 MiB** file; `cmd_validate` peaks at **958 MiB**. Nothing here needs row-level
     residency — every output is an aggregate count or a `Counter`.
- **Trigger:** a 500,000-row `data/all_businesses.csv` (which is what the 500k target
  means — 108.5 MB at the column widths in `main.py:33-40`), then `leadminer stats`:
  ~3.9 s and ~1.2 GiB. Same file through `leadminer validate`: ~5.2 s and ~958 MiB.
  For contrast, the `(name, phone)` set at `cli.py:190` — the line that *looks* like the
  memory hog — costs only **47 MiB**, 0.07x the rows list. It is not the problem; the
  rows list is.
- **Fix:** replace `rows = list(csv.DictReader(f))` at `cli.py:87` with a single
  streaming pass that accumulates all thirteen aggregates in one `for r in
  csv.DictReader(f)` loop, keeping only the scalars and the Counters. For `cmd_validate`,
  accumulate the `(name, phone)` pairs into a set in the same pass and drop the
  `rows` list entirely.
- **Measured result:** 500k rows → **5.081 s → 3.866 s (1.31x)** and **1,215 MiB → 397 MiB
  (3.06x less)**. The memory win is the real prize, and it is the difference between
  O(n) resident objects and O(distinct values).
- **Severity defence:** S2, not S1. `ubuntu-latest` runners have 16 GB
  (`.github/workflows/scrape.yml:24`), so 1.2 GiB does not OOM CI, and neither
  `cmd_stats` nor `cmd_validate` is invoked by the workflow at all — `scrape.yml:69` runs
  `python main.py` directly, so the 300-minute budget at `scrape.yml:25` is untouched by
  this. It degrades cost and operability (an operator on a laptop, or a future
  `leadminer stats` step bolted onto CI), it produces no wrong output, and nothing dies.
  That is the definition of S2. It becomes S1 the moment a `stats`/`validate` step is added
  to `scrape.yml` or the master grows past ~2M rows.

## Complexity verdict on the target, stated precisely

- **Time in n (number of businesses): O(1).** `cli.py:29-30` is a two-branch expression
  with no loop, no comprehension, no accumulator. `n` arrives already-computed as the
  return value of `count()` at `cli.py:96` — an `int` that CPython stores inline in a
  fixed-size object. Work done is one `is None` identity test plus one `format()` call.
- **Space / allocation in n: O(1).** One `str` per call, `sys.getsizeof` **42 B** at
  `n<10`, **47 B** at 10k, **48 B** at 100k *and* 500k, **54 B** at `n=10^9`. Three
  objects appear in a tracemalloc window, but two are the format-spec and the argument
  tuple; the only thing that escapes is the string, 42–54 bytes.
- **The one genuine n-dependence is length, not count.** The result is O(log₁₀ n):
  `1` (1 char) → `100` (3) → `10,000` (6) → `500,000` (7) → `1,000,000,000` (13) →
  `1,000,000,000,000,000,000` (25). It is driven by n's *magnitude*, not n's
  *cardinality*, and it is bounded at 25 chars for any Python int. `len(_fmt(500_000))`
  is 7. This is not a scaling concern.
- **Empirical confirmation, not just inspection.** The `_fmt` x6 column above is flat at
  1.2 / 1.4 / 1.3 µs across a 50x growth in records — no trend, all three values inside
  run-to-run noise. That is what O(1) looks like on a stopwatch.

### The single change with the largest speedup

**For `_fmt`: none exists.** It is 404 ns of a 3.87 s command. The only edits available
to it (precomputing a format string, caching, `str.lstrip` tricks) would be pure noise
and would make the code worse.

**For the code it lives in:** the single highest-leverage change is at `cli.py:87` —
stop materialising the CSV. One streaming fused pass, replacing `list(...)` plus twelve
subsequent traversals, buys 1.31x CPU and **3.06x memory** at 500k rows, and it is the
only change that makes memory O(distinct values) instead of O(n). That is the change to
make, and it is a different finding from the one I was assigned.

## Not a bug, but worth knowing

- **Neither `cmd_stats` nor `cmd_validate` has a row cap or a warning.** Nothing stops
  someone pointing `leadminer stats` at a multi-GB file; they get an OOM `MemoryError`
  traceback, not a message. `cli.py:82-85` and `cli.py:139-142` check only for existence
  and emptiness.
- **`cli.py:111-113` bypasses `_fmt` entirely** while `cli.py:98-103` uses it. Six uses of
  a helper and seven hand-rolled `f"{v:,}"` in the same function — inconsistent, and the
  reason the `suffix` parameter died unused.
- **`_fmt`'s `"n/a"` branch is never taken in practice.** All six callers pass
  `count(...)`, and `sum()` over a generator of ints always returns `int`, never `None`
  (`cli.py:96`). The `None` guard and the `int | float` half of the annotation are
  unreachable from this codebase — they are API surface for a future caller. Not wrong,
  just currently unearned.
- **`cmd_stats` re-derives what `main.py` already printed.** `main.py:219-242` emits the
  same counts (`Total unique businesses`, `By region`, `By service`) at the end of every
  run. `cmd_stats` is for *historical* CSVs, so the overlap is intentional — worth
  knowing before anyone tries to optimise one into the other.

## Recommended order of work

1. **Ignore `_fmt`'s performance.** It is correct, O(1), and 0.00006% of the command.
   Nothing to do.
2. Delete the unused `suffix` parameter at `cli.py:29` (S3, one-line, zero risk).
3. Rewrite `cmd_stats` (`cli.py:87`) as one streaming fused pass. This is the real work:
   1.31x faster and 3.06x less memory at 500k rows, and it is what makes the 500k target
   comfortable rather than merely survivable.
4. Same treatment for `cmd_validate` (`cli.py:143`, `cli.py:190`): stream, and accumulate
   the `(name, phone)` set during the pass instead of after it.
5. Add a file-size guard to `cli.py:82` and `cli.py:139` that warns past ~250 MB and
   points at step 3/4, so the next person to drop a huge CSV on these commands gets a
   sentence instead of a `MemoryError`.
