# 229 — `cmd_stats` cost model at 500k rows

## Verdict

`cmd_stats` (`cli.py:79`) is **O(n) time and O(n) memory — it is not O(n²)**, and I
proved that both from the source and from a 100× scaling ladder. The problem is not the
complexity class, it is the constant: the function materialises every row as a `dict`
(`cli.py:86-87`), then walks that list **14 separate times** (1 parse + 6 `count()` calls +
3 liveness sums + 4 `Counter`s). At 500k rows that costs **3.75 s and 856 MB peak RSS for
a 102 MB file** — an 8.3× memory blowup, dead linear at 1.68 KB of RAM per 203-byte row.

**The single change with the largest speedup is to stop building a dict per row**: swap
`csv.DictReader` for `csv.reader` plus a one-time header→index map, and accumulate into
plain counters in a single loop. Measured: **2.2× wall clock at every size** (3.75 s →
1.68 s at 500k) and **52× less memory** (856 MB → 16 MB, i.e. O(1) instead of O(n)). It
transparently subsumes both obvious alternatives — fusing the 13 passes buys only 1.2×,
streaming alone buys 1.4×.

## Method (so you can re-derive this, or distrust it)

- **Fixture.** Synthetic `all_businesses.csv`-shaped files with the exact header from
  `main.py:33-40`, 203 B/row on disk. Fill rates approximate a real run: ~55% website,
  ~50% phone, ~22% email, ~18% instagram, ~30% whatsapp, with `region` (20 values),
  `source` (4), `industry_priority` (4) and `recommended_service` (7) drawn from bounded
  sets — `industry_priority` genuinely only ever returns `high`/`medium`/`low`
  (`scrapers/whitelist.py:138-145`), which matters for the `most_common()` analysis below.
- **Harness.** The real `cli.cmd_stats` imported from the repo and called directly, with
  stdout redirected to `/dev/null`. `min` of 9 interleaved repetitions per size, page cache
  warmed by reading the file first. `min` (not mean) is the estimator because this box has
  ~400 concurrent agents and that noise is additive; the spread between `min` and `median`
  was 3.7 s vs 3.9 s at 500k.
- **Environment.** macOS (darwin) arm64, CPython **3.14.8**. The project targets 3.12
  (`.github/workflows/scrape.yml`, `python-version: '3.12'`). Absolute numbers on the
  Ubuntu x86 runner will differ; the *shape* (flat µs/row) is what matters and that is
  interpreter-independent.
- **Not measured:** `pandas` is not installed here and brief rule 3 forbids installing it,
  so I have no `pd.read_csv` comparison. I also could not cap memory to demonstrate an
  OOM: this sandbox rejects `setrlimit(RLIMIT_AS/RLIMIT_DATA)` and macOS `ulimit -v`
  ("cannot modify limit: Invalid argument"), so the memory findings rest on measured
  `ru_maxrss` plus arithmetic, not on a reproduced `MemoryError`.
- **Reproduction:** fixture generator, benchmark and probes are throwaway scripts under
  `$TMPDIR/opencode/` (`bench_gen.py`, `stage.py`, `variants.py`, `rss1.py`,
  `decomp.py`, `probe/probe.py`, `probe/unbounded.py`). Nothing in the repo was touched.

## Complexity: O(n), confirmed twice

**From the source.** `csv.DictReader.__next__` (CPython 3.14 `Lib/csv.py:173`) does one
`dict(zip(self.fieldnames, row))` per row plus an O(columns) length fix-up — strictly
O(columns). `fieldnames` is memoised in `self._fieldnames` after the first call
(`csv.py:159`), so it is not re-read per row. `cmd_stats` has **no nested loop over
rows**: every one of the 14 traversals is a flat generator or `Counter` feed. The four
`most_common()` calls sort over *distinct values*, not over n, and their inputs are
bounded enums.

**From the ladder** (real `cmd_stats`, min of 9):

| rows | file | wall (min) | wall (med) | µs/row | peak RSS |
|---|---|---|---|---|---|
| 10,000 | 2.0 MB | 0.068 s | 0.071 s | 6.78 | 33.4 MB |
| 100,000 | 20.3 MB | 0.773 s | 0.787 s | 7.73 | 183.8 MB |
| 500,000 | 101.6 MB | 3.746 s | 3.868 s | 7.49 | 855.9 MB |
| 1,000,000 | 203.3 MB | 7.284 s | 8.100 s | 7.28 | 1,693.2 MB |

**100× the rows costs 107× the time.** µs/row is flat at 6.8 → 7.3. O(n²) would have cost
10,000×. There is no hidden quadratic and no high-cardinality `sort()` anywhere.

## Findings

### S2 — 14 traversals of a fully materialised row list: 3.75 s and 856 MB at 500k

- **Where:** `cli.py:86-87` (materialise), `cli.py:98-103` (6 separate `count()` calls
  over the list), `cli.py:107-110` (3 more full passes), `cli.py:116`, `cli.py:120`,
  `cli.py:124-125`, `cli.py:129-130` (4 more). The nested `count()` helper at
  `cli.py:95-96` is called six times in a row, each time re-walking all n rows.
- **Breaks:** two distinct costs. (1) Time: `list(csv.DictReader(f))` allocates and
  retains 500k dicts before a single number is printed. (2) Memory: peak RSS at 500k is
  **856 MB**, exactly linear at **1.68 KB per row** —

  | rows | RSS − 16 MB baseline | B/row |
  |---|---|---|
  | 10,000 | 17.2 MB | 1,720 |
  | 100,000 | 167.8 MB | 1,678 |
  | 500,000 | 839.6 MB | 1,679 |
  | 1,000,000 | 1,677.1 MB | 1,677 |

  `sys.getsizeof` accounts for it to within 2%: row dict **832 B** × 500k = 396.7 MB,
  non-empty cell strings (19 of 23 columns) **991 B/row** × 500k = 472.5 MB, outer list
  4.0 MB → predicted 873.2 MB vs measured 857.9 MB.
- **Trigger:** `leadminer stats` on the 500k-row master. That is 3.75 s and 856 MB today;
  the ceiling for a 7 GB GitHub `ubuntu-latest` runner is ~4.1M rows, which a *cumulative,
  all-time* master (`BRIEF.md:51`) refilled every Monday by
  `.github/workflows/scrape.yml` (`cron: '0 3 * * 1'`) will reach eventually. `leadminer
  validate` shares the pattern and is worse: 3.72 s and **920 MB** at 500k, because
  `cli.py:190` additionally builds a 500k-element `set` of `(name, phone)` tuples.
- **Fix:** `csv.reader` + a header index map + one fused accumulation loop (see below).

### S2 — the diagnostic silently reports 0 for every field when the header is wrong

- **Where:** `cli.py:95-96`. `r.get(field)` returns `None` for a column the file does not
  have, `(None or "").strip()` is falsy, `count()` returns 0 — with **no validation and
  exit code 0**.
- **Breaks:** the module docstring calls `stats` "the first thing to check"
  (`cli.py:80`), i.e. the tool you reach for when a run looks wrong. Fed a CSV with a
  different header it prints a clean, confident, entirely fabricated report and exits
  **0**, which in CI (audit `037-cli-design.md:653` recommends adding `stats` to
  `scrape.yml`) is a green check on garbage.
- **Trigger:** a one-column CSV.
  ```
  $ printf 'name\nA\nB\n' > /tmp/one.csv && python cli.py stats /tmp/one.csv ; echo $?
  ```
  ```
  one.csv  (2 rows)
    with phone      : 0
    with email      : 0
    with website    : 0
    ...
    by priority:
      None       2
  0
  ```
  Every line is wrong; exit 0. Note `by priority` / `by source` / `top pitches` print
  `None` as if it were a category, which is the only tell. A human who filters
  `sales_ready.csv` in Excel or Sheets and saves a 5-column version — exactly what
  `060-sales-handoff-contract.md` describes — gets this.
- **Fix:** after `rows = list(...)`, check `set(FIELDS) <= rows[0].keys()` where `FIELDS`
  is imported from `main.py:33-40`; print the missing names to stderr and return 2.

### S3 — whitespace-only website makes `live + dead + unreachable != with website`

- **Where:** `cli.py:110`. Every other predicate in the function strips before testing —
  `cli.py:96` does `(r.get(field) or "").strip()`, `cli.py:107-108` do the same on
  `website_live`. This one does `r.get("website")` raw.
- **Breaks:** a cell containing `"   "` is reported as *no website* by the
  `with website` line and as *unreachable* by the three-way breakdown, so the numbers do
  not reconcile and the operator concludes a business has a dead site when it has none.
- **Trigger:** one row with `website` = `"   "`, `website_live` = `""`:
  ```
    with website    : 0
    website live    : 0
    website dead    : 0
    unreachable     : 1  (not the same as dead)
  ```
- **Fix:** `if (r.get("website") or "").strip() and not wl:` — one `.strip()`, and the
  three-way split then sums to `with website` by construction.

### S3 — `most_common()` at `cli.py:116` is the only uncapped one

- **Where:** `cli.py:116` calls `.most_common()` with no argument; its siblings are capped
  at `8` (`cli.py:120`), `12` (`cli.py:124-125`) and `8` (`cli.py:129-130`). With no `n`,
  `collections.Counter.most_common` (`collections/__init__.py:628`) does
  `sorted(self.items(), ...)` over **every distinct value** instead of
  `heapq.nlargest(n, ...)` — O(n log n) and unbounded output where its siblings are
  O(k log n) and bounded.
- **Breaks:** harmless today because `industry_priority` only ever yields three values
  (`scrapers/whitelist.py:138-145`). It stops being harmless the moment that column ever
  holds free text — which is exactly what happens when someone round-trips the file
  through a spreadsheet.
- **Trigger:** 500k-row file whose `industry_priority` column holds 500k distinct values
  (a raw-category paste). Real `cmd_stats`, unmodified:
  ```
  cmd_stats exit=0 in 4.507s
  stdout lines produced : 500,044
  'by priority' alone emitted 500,000 lines
  peak RSS = 935 MB
  ```
  A "summarise a CSV" command that emits half a million lines of stdout.
- **Fix:** `.most_common(8)`, matching its siblings.

## The single change with the largest speedup

Stop materialising a `dict` per row. Four variants, same 500k-row input, same output,
min of 9 interleaved reps, three repeats of the whole bake-off:

| variant | min | µs/row | speedup | peak RSS |
|---|---|---|---|---|
| **A** current (`cli.py:79`) | 3.56–3.62 s | 7.1 | 1.00× | 856 MB |
| **B** fuse the 13 passes into 1, still keep `list(...)` | 2.94–3.21 s | 5.9–6.4 | 1.13–1.21× | 856 MB |
| **C** stream `csv.DictReader`, fused, O(1) memory | 2.58–2.60 s | 5.2 | 1.38–1.40× | 16 MB |
| **D** `csv.reader` + header index, fused, O(1) memory, no dicts | **1.55–1.58 s** | 3.1 | **2.29×** | **16 MB** |

The counter-intuitive part: **fusing the passes is not the win.** Where the 3.75 s goes
at 500k:

| stage | time | share |
|---|---|---|
| `csv.reader` floor — split 500k lines, build nothing, retain nothing | 1.53 s | — |
| `list(csv.DictReader(f))` — the materialisation (`cli.py:86-87`) | 2.82 s | 62% |
| the 13 downstream passes, rows already resident | 1.40 s | 31% (0.216 µs per pass per row) |
| `most_common()` sorts + `print()` | ~0.3 s | 7% |

The passes are only 31% of the cost, so fusing them caps out at ~1.2× (variant B). The
dict-per-row is the expensive thing, and it is pure overhead: `cmd_stats` only ever reads
10 of the 23 columns by name. Variant D is one conceptual edit that collects all three
wins at once, and it holds across the whole ladder:

| rows | current | variant D | speedup | RSS current → D |
|---|---|---|---|---|
| 10,000 | 0.068 s | 0.036 s | 1.89× | 33 MB → 16 MB |
| 100,000 | 0.773 s | 0.354 s | 2.18× | 184 MB → 16 MB |
| 500,000 | 3.746 s | 1.684 s | 2.22× | 856 MB → 16 MB |
| 1,000,000 | 7.284 s | 3.251 s | 2.24× | 1,693 MB → 16 MB |

Shape of the replacement (10 lines, no new dependency, identical printed output):

```python
with open(path, newline="", encoding="utf-8-sig") as f:
    reader = csv.reader(f)
    head = next(reader)
    col = {name: head.index(name) for name in head}
    i = lambda name: col.get(name, -1)          # -1 -> always absent
    # ... then a single `for row in reader:` accumulating plain ints and Counters.
    # Never bind `row` to anything outside the loop; nothing is retained.
```

Use `collections.Counter` for the four groupings (they are already the right data
structure) and plain ints for the six `count()` fields and the live/dead/unknown split.
Budget ~0.5 s above the 1.53 s `csv.reader` floor at 500k — variant D measured 1.68 s, so
there is no headroom left worth chasing in pure Python. `cmd_validate` (`cli.py:135-201`)
should get the same treatment; it costs 3.72 s / 920 MB at 500k today.

## Not a bug, but worth knowing

- **`cmd_stats` is genuinely linear.** If you were told to look for an O(n²) here, there
  isn't one, and the ladder is the evidence: 100× rows → 107× time. Do not spend more
  time on this axis.
- **The memory profile is the risk, not the CPU.** 3.75 s for a local diagnostic is an
  annoyance; 856 MB is a hard ceiling on the dataset size, and it is reached at the
  `list()` on `cli.py:87` before any work happens. Both go away with the same edit.
- **Audit `052-memory-streaming.md` already flagged this pattern for the pipeline**
  (`main.py:103`, `main.load_master`), and `cmd_score` (`cli.py:259`) routes through
  `load_master`, so it inherits the same materialisation. The CLI's three CSV readers are
  three copies of one problem; fix them as one.
- **`cmd_score` cannot be imported without the full scraping stack.** It does
  `import main as pipeline` at `cli.py:249`, `main.py:25` imports `scrapers.osm`, and
  `httpclient.py:43` imports `requests` at module level — so the "no network, works
  anywhere" commands in the docstring fail in any environment without the scraping deps
  installed. I hit this while benchmarking and had to abandon the `cmd_score` numbers.
  One lazy import would fix it; noting it only because it blocked this lens.
- **`most_common()` cardinality is safe on the other three calls** precisely because
  their columns are bounded enums. Worth preserving that property: if anyone adds a
  `--group-by <free-text-column>` flag (audit `037-cli-design.md:495`), cap `n` or the
  same 500k-line blowout arrives.

---

## Recommended order of work

1. Rewrite the body of `cmd_stats` as one `csv.reader` loop over a header index map
   (`cli.py:86-132`). 2.2× faster, 856 MB → 16 MB at 500k, one edit, no dependency.
2. Validate the header against `main.FIELDS` and return 2 on a mismatch
   (`cli.py:88`). A diagnostic that exits 0 on a file it cannot read is worse than no
   diagnostic.
3. `.strip()` the `website` test at `cli.py:110` so the three-way website split sums to
   `with website`.
4. Cap `.most_common()` at `cli.py:116` to `8`, matching `cli.py:120/124-125/129-130`.
5. Port the same reader to `cmd_validate` (`cli.py:142-143`): 920 MB and 3.72 s at 500k,
   plus the 500k-tuple set at `cli.py:190` if you want the memory back.
6. Add one regression test: a 50k-row fixture asserting `live + dead + unreachable ==
   with website` and that peak allocation stays flat as n doubles. Both properties are
   free to hold once (1) lands and are exactly what would catch a future reintroduction
   of `list(csv.DictReader(...))`.
