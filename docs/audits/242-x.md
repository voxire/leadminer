# 242 — Test-gap analysis for `cmd_doctor` (`cli.py:204`)

## Verdict

`cmd_doctor` has **zero tests** — `docs/audits/087-SYNTH-test-gap.md:19` already
lists it as an uncovered CLI command, and it is still uncovered today. The
function's exit code is decided by exactly one condition (a missing
`GOOGLE_PLACES_API_KEY` at `cli.py:213`); every other check it performs —
three connectivity probes, the data-directory listing — is print-only and cannot
change the result. I verified this end-to-end: with a valid key present and all
three upstreams raising `OSError`, `leadminer doctor` prints three `FAIL` lines
and **exits 0**. Its single most important line is also wrong by construction:
`cli.py:240` classifies every HTTP status `< 500` as `OK`, so Google Places
returning 403 (`PERMISSION_DENIED`, API disabled) or 400 (`API_KEY_INVALID`)
prints `OK   Google Places` three lines below `MISSING  GOOGLE_PLACES_API_KEY`.

The tests below are not hypothetical: each one is derived from a behaviour I
reproduced in a scratch harness with `requests.get` patched, so the "asserted
output" strings below are literal, not reconstructed.

---

## Findings

### S1 — Every check except the API key is print-only: `doctor` exits 0 with all three sources unreachable

- **Where:** `cli.py:208` (`ok = True`), `cli.py:213-214` (the only write of
  `ok = False`), `cli.py:238-243` (the connectivity loop, which never touches
  `ok`), `cli.py:244` (`return 0 if ok else 1`).
- **Breaks:** the diagnostic's exit status is uncorrelated with the thing it
  diagnoses. A runner with no egress, a laptop offline, or a CI job behind a
  proxy that blocks `*.googleapis.com` gets `FAIL Overpass`, `FAIL Wikidata`,
  `FAIL Google Places` on stdout and a **green exit code**. Anything that gates
  on `leadminer doctor` — the console script at `pyproject.toml:32-33`, the
  `README.md:95` "check keys and connectivity first" instruction, the CI
  preflight step specified at `docs/audits/037-cli-design.md:570-575` — is
  gated on nothing.
- **Trigger (literal):** `GOOGLE_PLACES_API_KEY="test-key"`,
  `SCRAPER_EMAIL="ops@voxire.com"`, and `requests.get` raising `OSError("Network
  is unreachable")` for all three URLs. Verified output:
  ```
  rc = 0
  credentials:
    OK   GOOGLE_PLACES_API_KEY
    OK   SCRAPER_EMAIL
  data directory:
    MISSING  data (no run has produced output yet)
  connectivity (5s timeout each):
    FAIL  Overpass       OSError
    FAIL  Wikidata       OSError
    FAIL  Google Places  OSError
  ```
  Three failures, exit 0. The same holds for HTTP 503 on all three (three
  `WARN HTTP 503` lines, `rc = 0`, verified).
- **Fix:** fold the connectivity outcome into the return value —
  `return 0 if ok else 1` where `ok` is also cleared by any `FAIL`/`WARN`, or
  adopt the exit codes already specified at `docs/audits/037-cli-design.md:463-466`
  (`3` = credential, `4` = network/upstream).

### S1 — Every HTTP 4xx is reported as `OK`, and the Google probe cannot detect an invalid key

- **Where:** `cli.py:240` (`note = "" if r.status_code < 500 else f"HTTP {r.status_code}"`)
  and `cli.py:241` (`'OK ' if r.status_code < 500 else 'WARN'`).
- **Breaks:** the threshold treats "the server answered, and the answer was a
  refusal" as success. Google Places documents `API_KEY_INVALID`,
  `PERMISSION_DENIED` (API not enabled on the project), `REQUEST_DENIED`
  (IP/referer restricted) and `RESOURCE_EXHAUSTED` (quota exhausted) as normal
  operational failures — all are 4xx, all print `OK`. Wikidata returns **429**
  under load (`< 500`) and prints `OK` while the pipeline is about to get an
  empty result set.
- **Trigger (literal):** `requests.get` returning `status_code = 403` for all
  three URLs, with `GOOGLE_PLACES_API_KEY` unset. Verified output:
  ```
  rc = 1
  credentials:
    MISSING  GOOGLE_PLACES_API_KEY
    MISSING  SCRAPER_EMAIL
  connectivity (5s timeout each):
    OK   Overpass
    OK   Wikidata
    OK   Google Places
  ```
  The command states the key is missing and, seven lines later, that Google
  Places is fine. A reader skimming the connectivity block — which is the block
  that looks authoritative — concludes Google is reachable and usable.
- **Compounding defect at the same site:** the probe is a bare `GET` with no
  `headers`. I captured the exact call: `args=('https://places.googleapis.com/v1/places:searchText',)
  kwargs={'timeout': 5}` — no `X-Goog-Api-Key`, no `X-Goog-FieldMask`, no
  `json=` body. The real scraper sets both headers at
  `scrapers/google_places.py:161-166` and `POST`s a JSON body. So doctor's Google
  check exercises a request shape the pipeline never issues, and by construction
  can never return 200, so it carries no information about authentication.
- **Fix:** classify explicitly — `< 300` is OK; `401/403` is a credential
  failure (exit 3); `429` is a quota/limit condition (exit 4); `5xx` is an
  upstream failure (exit 4); everything else is WARN. Send the probe with the
  real `X-Goog-Api-Key` header and `pageSize: 1`.

### S2 — The Overpass probe hits an endpoint the pipeline never uses

- **Where:** `cli.py:234` probes `https://overpass-api.de/api/status`;
  `scrapers/osm.py:9` posts its query to
  `https://overpass-api.de/api/interpreter` (`scrapers/osm.py:41-47`).
- **Breaks:** `/api/status` is a static status page. It is not the endpoint
  under rate limiting, and its availability says nothing about whether the
  interpreter will accept a query. The real OSM failure mode — `overpass-api.de`
  returning 429 under the `[timeout:180]` query at `scrapers/osm.py:12` — passes
  doctor's Overpass check untouched.
- **Trigger (literal):** assert the probed URLs against the constants the
  scrapers actually use: `osm.OVERPASS_URL`, `wikidata.SPARQL_ENDPOINT`,
  `google_places.API_URL`. Today doctor's Overpass URL is absent from the
  scraper module, so the assertion fails with
  `AssertionError: 'https://overpass-api.de/api/status' not in
  {'https://overpass-api.de/api/interpreter', ...}`.
- **Fix:** probe `scrapers.osm.OVERPASS_URL` with a trivial body
  (`data={"data": "[out:json];node(1,1,1,1);out;"}`) rather than hardcoding a
  third URL — and import the constants instead of duplicating them.

### S2 — The data-directory check cannot distinguish a full run from a half-written one

- **Where:** `cli.py:216-222`, specifically the bare `DATA_DIR.glob("*.csv")` at
  `cli.py:219`.
- **Breaks:** `main.py:209-213` writes five exports in sequence. A crash after
  the second — exactly what the 300-minute job timeout at
  `.github/workflows/scrape.yml` and the atomic-write rationale at
  `main.py:108-119` both describe — leaves `data/` holding `all_businesses.csv`
  and `qualified_businesses.csv` and nothing else. `leadminer doctor` prints
  `OK   data exists` and exits 0, byte-identical to the output for a complete
  run. The operator's first move after a failed run is `leadminer doctor`, and
  it reports success.
- **Trigger (literal):** `data/` containing exactly `all_businesses.csv` and
  `sales_ready.csv`. Verified output is indistinguishable from the 5-file case:
  ```
  data directory:
    OK   data exists
         all_businesses.csv               1,536 bytes
         sales_ready.csv                  1,536 bytes
  rc = 0
  ```
- **Fix:** check the five expected names from `main.py:209-213` explicitly and
  report which are missing; a missing `all_businesses.csv` must be at least a
  WARN, not silence.

### S2 — `DATA_DIR` is CWD-relative, so doctor's filesystem verdict is false from any subdirectory

- **Where:** `cli.py:26` (`DATA_DIR = pathlib.Path("data")`), consumed at
  `cli.py:217`; the identical constant is at `main.py:41`.
- **Breaks:** `Path("data")` resolves against the process working directory, not
  the package root. `leadminer doctor` from `docs/audits/` reports
  `MISSING  data (no run has produced output yet)` — a definitive false statement
  about a checkout that has data. The same relative default is shared by `stats`,
  `validate` and `score` (`cli.py:294`, `cli.py:298`, `cli.py:305`), so all four
  commands silently operate on different files depending on the invocation
  directory.
- **Trigger (literal):** `contextlib.chdir("<repo>/docs/audits")` with
  `GOOGLE_PLACES_API_KEY` set. Verified: the data section reads
  `MISSING  data (no run has produced output yet)`, `rc = 0`.
- **Fix:** resolve against the package root (`pathlib.Path(__file__).resolve().parent
  / "data"`) or add the `--data-dir` flag already specified at
  `docs/audits/037-cli-design.md:161`.

### S2 — The `_stub_requests()` harness makes doctor's behaviour environment-dependent, so the obvious test is unusable

- **Where:** `tests/test_lead_signal.py:23-63`, specifically the
  `try: import requests / except ImportError` guard at lines 26-30 and
  `mod.get = lambda *a, **k: None` at line 49.
- **Breaks:** the stub is installed **only when the real package is absent**, and
  its `get` returns `None`. `cmd_doctor` then evaluates `r.status_code`
  (`cli.py:240`) on `None`, raising `AttributeError`, which
  `except Exception` at `cli.py:242` swallows into
  `FAIL <name>       AttributeError`. So the same test body yields `rc = 0` with
  three `FAIL` lines on a machine without `requests` and something entirely
  different on a machine with it. I reproduced the stub path exactly:
  ```
  rc = 0
  connectivity (5s timeout each):
    FAIL  Overpass       AttributeError
    FAIL  Wikidata       AttributeError
    FAIL  Google Places  AttributeError
  ```
  (`requests` is in fact **not installed** in this checkout, so the stub path is
  the one that runs here.) There is a second trap: `mock.patch("requests.get")`
  raises `ModuleNotFoundError` in a bare checkout unless `_stub_requests()` has
  already executed at import time — I hit this while building the probes.
- **Fix:** doctor tests must inject a fake `requests` **module** with
  `mock.patch.dict(sys.modules, {"requests": fake})` rather than patching the
  attribute, so the result is identical whether or not the real package is
  present. The harness in the next section does this.

### S3 — A dangling symlink in `data/` makes `doctor` traceback

- **Where:** `cli.py:220` (`f.stat().st_size`), against the function's own stated
  invariant at `cli.py:228-229`: *"doctor exists to diagnose a broken
  environment, so it must never be the thing that tracebacks."*
- **Breaks:** `os.symlink("/nonexistent/ghost.csv", "data/ghost.csv")` — a
  truncated `rclone copy` (`.github/workflows/scrape.yml:78-79`) or a manual
  `ln -s` produces exactly this — makes `f.stat()` raise. Verified: `rc` never
  returned; `FileNotFoundError: [Errno 2] No such file or directory:
  'data/ghost.csv'` escaped `cmd_doctor` entirely.
- **Fix:** wrap the listing in `contextlib.suppress(OSError)`, or filter with
  `f.is_file()` and `try/except OSError` per entry.

### S3 — `doctor` bypasses the project's own HTTP layer, so its probes are unidentifiable

- **Where:** `cli.py:239` (`requests.get(url, timeout=5)`) versus
  `httpclient.py:66-69` and `httpclient.py:74-85`.
- **Breaks:** `httpclient._user_agent()` is explicit that "Overpass and Wikidata
  both ask for a contact address in the UA, and Overpass's policy explicitly
  says commercial use should self-host." Every pipeline request carries
  `leadminer/0.2 (+https://github.com/voxire/leadminer) (email)`. Doctor sends
  no headers, so the one command a support engineer runs to demonstrate we are a
  well-behaved client is the one that identifies us as `python-requests/2.32.3`.
  `timeout=5` also diverges from `DEFAULT_TIMEOUT = 15` (`httpclient.py:47`) and
  from `timeout=200` (`scrapers/osm.py:44`), so a healthy-but-slow Overpass
  reports `FAIL` while the real 200-second call would have succeeded.
- **Trigger (literal):** capture the call args. Verified:
  `args=('https://overpass-api.de/api/status',) kwargs={'timeout': 5}` — assert
  `'headers' in kwargs and 'User-Agent' in kwargs['headers']`; it fails today.
- **Fix:** call `httpclient.get_session().get(...)` instead of the bare module
  function, so the UA, `Accept-Language` and timeout policy are inherited.

### S3 — `SCRAPER_EMAIL` is non-fatal by an accident of the loop body, and nothing pins that decision

- **Where:** `cli.py:213` (`if var == "GOOGLE_PLACES_API_KEY" and not present:`).
- **Breaks:** the asymmetry is defensible — OSM and Wikidata work without a
  contact address — but `ok` exists *only* because of this line. Nothing in the
  suite pins it, so a future edit to the loop body can silently make the email
  fatal, or (the dangerous direction) drop the key check and leave `ok` permanently
  `True`. This is a decision that needs a test more than the S1s do, precisely
  because it is the sole load-bearing line in the function.

## Test cases this function still needs

### Shared harness (add to `tests/test_lead_signal.py`, alongside `_stub_requests`)

This must inject a module, not patch an attribute, for the reason in the S2 above.
It also gives every case the `DATA_DIR` fixture that `cli.py:26` demands — note
that `contextlib.chdir` is required (not just `patch`) precisely *because*
`DATA_DIR` is CWD-relative.

```python
class _FakeResponse:
    def __init__(self, status_code: int) -> None:
        self.status_code = status_code


class _FakeRequests(types.ModuleType):
    """Stands in for `requests` inside cmd_doctor (imported at cli.py:226).

    `behaviour(url)` returns a _FakeResponse, an exception instance to raise, or
    an exception class to raise.
    """

    def __init__(self, behaviour):
        super().__init__("requests")
        self.calls = []
        self._behaviour = behaviour

    def get(self, url, **kwargs):
        self.calls.append((url, kwargs))
        outcome = self._behaviour(url)
        if isinstance(outcome, BaseException):
            raise outcome
        if isinstance(outcome, type) and issubclass(outcome, BaseException):
            raise outcome(url)
        return outcome


ALL_200 = lambda url: _FakeResponse(200)          # noqa: E731
ALL_OFFLINE = lambda url: OSError("unreachable")  # noqa: E731


class TestDoctor(unittest.TestCase):
    def _doctor(self, behaviour=ALL_200, *, env=None,
                data_files=(), dangling=()):
        """Run cmd_doctor in an isolated cwd. Returns (rc, stdout, calls).

        data_files=None  -> no data/ directory at all
        data_files=()    -> empty data/ directory
        """
        import contextlib
        import io
        from unittest import mock

        from cli import cmd_doctor

        fake = _FakeRequests(behaviour)
        with tempfile.TemporaryDirectory() as d:
            root = Path(d)
            if data_files is not None:
                (root / "data").mkdir()
                for name in data_files:
                    (root / "data" / name).write_bytes(b"x" * 1536)
                for name in dangling:
                    os.symlink("/nonexistent/ghost.csv", root / "data" / name)
            buf = io.StringIO()
            with mock.patch.dict(sys.modules, {"requests": fake}), \
                 mock.patch.dict(os.environ, env or {}, clear=True), \
                 contextlib.chdir(root), \
                 contextlib.redirect_stdout(buf), contextlib.redirect_stderr(buf):
                rc = cmd_doctor(argparse.Namespace())
        return rc, buf.getvalue(), fake.calls
```

Imports this needs at module top of the file (none are present today):
`import contextlib, io, os` and `from unittest import mock` (`argparse`,
`sys`, `types`, `tempfile`, `unittest`, `Path` are already imported at
`tests/test_lead_signal.py:13-20`).

Note on assertions: the connectivity block uses
`f"  {'OK ' if ... else 'WARN'}  {name:<14} {note}"` (`cli.py:241`), which leaves
trailing whitespace when `note` is empty. Use `assertRegex` against
`buf.getvalue()` rather than `assertEqual` on the whole line, or the assertions
break the moment someone strips trailing spaces.

  - in all three: both variable names appear in the output, i.e. neither check is
    silently skipped
- **Pins:** the `var == "GOOGLE_PLACES_API_KEY"` guard at `cli.py:213`. Today all
  three pass, and that is the point: it converts a load-bearing asymmetry from an
  accident into a specification. Assert (b) and (c) explicitly — the natural
  "fix" for the S1 is to clear `ok` inside the loop, which would break (c), and
  only this test catches that.

### T11 — *`doctor` reports a transport failure as a failure, with the type preserved.*

- **Method:** `test_transport_failures_are_named_per_endpoint`
- **Literal input:** `behaviour` returning, in order for the three probes,

  `OSError("tls")`.
- **Asserted output:** three distinct `FAIL` lines naming `ConnectionError`,
  `Timeout`, `OSError` respectively, and `rc != 0`. Verified today: the type name

  must not abort the loop: all three lines must appear, which pins that
  `cli.py:242` catches per-request rather than around the loop.
- **Pins:** `cli.py:242-243` plus the exit-code hole.

### T12 — *One bad endpoint does not suppress the other two.*

- **Method:** `test_one_failing_endpoint_does_not_hide_the_others`

## What genuinely cannot be tested here, and why

These are not omissions from the list above; they are the parts of `cmd_doctor`
that no offline test can reach. State them in the ticket so nobody re-derives
them.

1. **The real status codes Overpass, Wikidata and Google Places return.** Any
   test that asserts `Google returns 403 for a disabled key` needs a live network
   call and a real project, which the brief forbids and CI would never be able to
   depend on. What *is* testable — and is what T2 does — is the classification of
   a given code: "given 403, does doctor say OK?". The mapping is ours to get
   right; the codes are the vendor's. Keep them separate or the suite becomes
   flaky and the mapping stops being tested at all.

2. **Whether `timeout=5` is too short.** This is a judgement call about Overpass
   latency, not a property. A test can pin that the timeout is at least some
   value, but the choice of that value cannot be asserted, only recorded. It
   belongs in a comment or a config constant, not in a test.

3. **What `DATA_DIR` *should* be.** T9 can assert `cli.DATA_DIR.is_absolute()`
   or that two working directories give the same verdict, but it cannot assert
   which of the three defensible answers the project wants: anchored to the
   package root, anchored to an invocation directory that must be supplied, or a
   required `--data-dir` flag (`docs/audits/037-cli-design.md:161`). Make that
   decision first, then let T9 assert the outcome. Until then the test pins the
   bug, not the fix.

4. **Corporate proxies, IPv6 preference, TLS trust stores, DNS resolution.** A
   `doctor` command's real value is often "this laptop is on a hotel wifi". None
   of that is reachable without the network layer the brief rules out. The closest
   testable proxy is the `OSError` shape in T11, which proves the *reporting* is
   correct, not that the *diagnosis* is.

5. **Wall-clock bound of the command.** `3 x timeout` is the current worst case
   (15s), but bounding it in a test requires either a real clock or a time-travel
   fake, and the function has no injected clock to fake. Testing it would mean
   asserting on `time.monotonic` call order, which tests the test. Skip it.

6. **Whether doctor's verdict correctly predicts whether `main.py` will
   succeed.** This is the property an operator actually cares about and it needs
   both a live network and the full pipeline (`main.py:148-213`, hours long). The
   surrogate tests (T2, T5, T7) pin the individual inputs; the correlation
   between them and a real run stays manual.

## Not a bug, but worth knowing

- **`except Exception` at `cli.py:242` is correct not to catch
  `KeyboardInterrupt`** — that is a `BaseException`, so it propagates to the
  handler at `cli.py:316-318` and `leadminer doctor` still exits 130 on Ctrl-C.
  No change wanted; T11 just guards that it stays that way.
- **`import os` inside the function (`cli.py:206`) is a non-issue** and is in
  fact helpful: it makes `os.environ` patchable per-call, which T10 relies on.
- **`ok` is a reasonable name for the concept** — the problem is its scope, not
  its spelling. The fix is one line (`ok = False` in the loop's failure branch),
  not a rename.
- **The `data_files` fixture in the harness is load-bearing, not cosmetic.**
  Because `DATA_DIR` is relative (`cli.py:26`), *every* data-directory test must
  either `contextlib.chdir` or patch `cli.DATA_DIR`. Forgetting the `chdir` makes
  the test read the real `data/` directory of whatever checkout it runs in, and
  the assertion silently passes for the wrong reason.
