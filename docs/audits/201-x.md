# 201 — `_fmt` (cli.py:29): the `None` guard covers an input that cannot arrive, and covers only half the signature

## Verdict

`_fmt` cannot be reached with a bad value today — all six callers pass `count(...)`,
which is `sum(1 for ...)` and therefore a strictly `int` (proved by execution, not just
by reading). The function is nonetheless wrong in a way that outlives that invariant: it
guards `None` on `n` and applies **no validation at all** to `suffix`, so `_fmt(5, None)`
returns the string `'5None'` — a *silent* wrong answer, not an error — and `f"{n:,}"`
delegates to the object's `__format__`, which for `datetime.date` renders a lead count as
the two-character string `','`. The `None → "n/a"` sentinel is simultaneously dead code
(never reachable) and aimed one layer away from where it is needed: the missing values
`cmd_stats` actually has to print are `""` (which crashes) and `str(None)` (which prints
the literal category name `"None"` at `cli.py:117`/`121`/`126`/`131`).

## Contract and callers

```
cli.py:29   def _fmt(n: int | float | None, suffix: str = "") -> str:
cli.py:30       return "n/a" if n is None else f"{n:,}{suffix}"
```

The declared contract has three claims, and the body honours exactly one of them:

| Claim | Honoured? |
|---|---|
| `n` may be `None`, and `None` renders as `"n/a"` | Yes — but see *Invariant*: no caller can pass `None` |
| `n` may be a `float` | Formatted as a general-format float, which is **not** a comma-grouped count for `>= 1e16`, `< 1e-4`, `nan`, `inf`, or any integral value |
| `suffix` is a `str` | **No** — never inspected, never coerced, `None` flows straight into the concatenation |

Python's specification for the `,` grouping option is explicit about the type contract
(<https://docs.python.org/3.12/library/string.html#format-specification-mini-language>):

> `','` — "Inserts a comma every 3 digits for integer presentation type 'd' and
> floating-point presentation types, excluding 'n'. **For other presentation types, this
> option is not supported.**"

`'s'` (string) and `None` (plain `object.__format__`) are "other presentation types".
That single sentence is the whole bug surface of line 30.

**Length is not a variable in this matrix.** Rows 31–39 all fail identically: the `,`
spec is rejected on the *type*, before any size consideration, so a 100 KB "record" and a
1 KB one fail the same way. There is no truncation path, no length cap, and no
memory-safety concern in `_fmt` — the only unbounded-output case is row 9 (`10**400` →
534 chars), which is still correct.

**Unicode is not a special case either.** Rows 35–38 are not special because they are
Arabic or emoji; they are special only because they are `str`. An ASCII `"12"` (row 33)
crashes with byte-identical output. The one genuinely locale-related property of `_fmt`
is that `,` is a hardcoded ASCII comma and is locale-independent by specification (the
Python docs direct you to the `'n'` presentation type for a locale-aware separator), so
`_fmt` is structurally incapable of rendering a number the way it appears in Lebanese or
Saudi source data — but that is a display preference, not a defect.

Row 49 is the sharp one. `_fmt` is a function whose stated job is to map a missing value
onto a sentinel. It performs that mapping for one of its two parameters and performs *no*
check whatsoever for the other, so the missing-value sentinel and the string `"None"`
end up **concatenated into the output**. That is the worst of both worlds: it is neither
an error you can detect nor a value you can interpret.

## Findings

### S2 — `suffix` is entirely unvalidated, so a `None` suffix produces `'5None'` instead of `'n/a'`
- **Where:** `cli.py:29-30`. The guard `n is None` at line 30 tests the first parameter
  only; `suffix` is interpolated into the same f-string with no test at all, despite the
  annotation `suffix: str = ""` at line 29.
- **Breaks:** `_fmt` is a two-parameter function with a single "value is missing → render
  `n/a`" rule, and that rule is wired to one of the two parameters. The moment any caller
  passes a `None` suffix — from a `None` default, a missing config key, a
  `dict.get("suffix")`, or a `row["unit"] or None` — the function does not raise, does not
  return the sentinel, and returns a **string containing the word "None"**. The caller
  receives a plausible-looking value that is wrong, and the report renders a number with
  `None` glued to it. The annotation does not help: `suffix=None` is a type error, but the
  annotation is not enforced at runtime and a `# type: ignore` or a
  dynamically-typed argument defeats it silently.
- **Trigger:** `_fmt(5, None)` → `'5None'`. Also `_fmt(5, 5)` → `'55'` (an int suffix is
  silently stringified rather than rejected).
- **Severity defence:** S3 because no caller passes `suffix` at all today — all six sites
  at `cli.py:98-103` are single-argument, so this is a latent hazard, not a current wrong
  number. Not lower, because it is a *silent* failure (no traceback, no non-zero exit) in
  the one function that exists specifically to render missing values, and because it is
  the single defect in `_fmt` that is not a one-line consequence of the `,` spec.
- **Fix:** make the sentinel rule cover both parameters and normalise the rest —
  `return "n/a" if n is None else f"{n:,}{suffix or ''}"` is not enough (it still lets
  `5` through as `'55'`); validate explicitly, e.g.
  `if not isinstance(suffix, str): suffix = str(suffix)`, or delete `suffix` entirely
  since nothing uses it.

### S2 — `f"{n:,}"` delegates to `__format__`, so for types that accept an arbitrary spec the result is arbitrary — `datetime.date` renders as `','`
- **Where:** `cli.py:30` — `f"{n:,}{suffix}`. The `,` is not applied by `_fmt`; it is
  forwarded as an opaque spec string to the value's `__format__`.
- **Breaks:** `_fmt` is the *only* numeric-formatting helper in `cli.py`, so it is the
  natural place a future caller reaches for when a value is not an `int` — a parsed
  `rating`, a `review_count` read as a `datetime`-adjacent type, a `Decimal` from a
  future JSON pipeline, anything at all. For every such type the function's contract is
  "the value, comma-grouped", and the guarantee it actually provides is "whatever that
  object's `__format__` decides to do with the characters `,`". For `date` and
  `datetime`, CPython's `__format__` forwards the spec to `strftime`, and `,` is not a
  `strftime` directive, so glibc echoes it back verbatim. The function returns the
  two-character string `','` — not an error, not a count, not a date. A caller that
  receives it has no way to tell that a real failure occurred.
- **Trigger:** `_fmt(datetime.date(2026, 1, 1))` → `','`. `_fmt(datetime.datetime(2026, 1, 1))`
  → `','`. Verified. Mechanism confirmed directly:
  `datetime.date(2026,1,1).__format__(',') == ','` and
  `datetime.date(2026,1,1).strftime(',') == ','`.
- **Contrast:** `timedelta` *rejects* the spec (`TypeError`), `Fraction` and `Decimal`
  accept it and produce odd-but-parseable output (`'1,234,567/3'`, `'1E+3'`), and any
  object with a user-defined `__format__` bypasses grouping entirely. So the same call
  yields four different failure modes across types that all satisfy `f"{x:,}"` without a
  `TypeError` — which is precisely why the annotation is not a safety net.
- **Severity defence:** S3 today (no caller passes such a value) but this is the finding
  most likely to become S1 the first time `_fmt` is used for its apparent purpose, and it
  fails *silently*, which the `str` crash at least does not.
- **Fix:** coerce at the boundary rather than trusting the annotation —
  `n = int(n)` on the non-`None` path, or narrow the signature to `n: int | None` so the
  compiler rejects the next caller.

### S3 — the `None → "n/a"` guard protects a value that can never arrive, while the missing values that *do* arrive are unguarded
- **Where:** guard at `cli.py:30`; the six call sites at `cli.py:98-103`; the category
  counters at `cli.py:116-117`, `cli.py:120-121`, `cli.py:129-131`; the missing-file
  guard at `cli.py:83-84` and `cli.py:256-257`.
- **Breaks:** `_fmt`'s `None` arm is unreachable — `count()` at `cli.py:95-96` is
  `sum(1 for r in rows if (r.get(field) or "").strip())`, which returns an `int` by
  construction, so `None` can never arrive. Meanwhile `csv.DictReader` **does** inject
  `None` into `cmd_stats` for any CSV whose header is missing a column, and two of the
  three category counters stringify it with no fallback. The result is a top-level report
  line that names a source called `"None"`.
- **Trigger (real `cmd_stats` run, 2-row CSV, header `name,phone,region,industry_priority,recommended_service,website_live` — i.e. no `source` column, exit code 0):**

  ```
    by priority:
      high       1
                 1          <- blank label: industry_priority="" at cli.py:117
    by source:
      None                         2      <- literal "None" as a source name, cli.py:121
    by region:
      Beirut               1
      Unknown              1      <- the or "Unknown" fallback exists, but only here, cli.py:124
    top pitches:
      SEO audit                                            1
                                                         1  <- blank label: cli.py:131
  ```

  And in the same run, the two values `_fmt` *should* have been asked about:
  `_fmt(None) == 'n/a'` and `_fmt("") ` raised
  `ValueError: Cannot specify ',' with 's'.`
- **Breaks, concretely:** a `sales_ready.csv` written without the `source` column, or any
  export whose header is reordered, makes `leadminer stats` report a fabricated source
  bucket literally named `None` alongside `osm` and `google_places`. An operator reading
  that line cannot distinguish "we have a source called None" from "the field is missing".
  The blank-label rows at `cli.py:117` and `cli.py:131` are the same defect with the
  evidence erased.
- **Why the sentinel was missed:** `cli.py:124` (`r.get("region") or "Unknown"`) shows the
  author knew the pattern for `region` and did not apply it at `cli.py:116` or
  `cli.py:129`. The `None → "n/a"` machinery was built and then never connected to the
  one place that needed it.
- **Fix:** apply the same fallback to all three counters —
  `r.get("industry_priority") or "unset"`, `r.get("source") or "unknown"`,
  `r.get("recommended_service") or "none"` — and then `_fmt` can be deleted or reduced to
  `f"{n:,}"` without losing anything, because the only thing it does that the file's nine
  inline `f"{x:,}"` sites do not is unreachable.

### S3 — type checking cannot catch any of this, so the annotation is not the guard it appears to be
- **Where:** `cli.py:29` annotation vs `cli.py:30` body; `pyproject.toml:64-68`
  (`[tool.mypy] strict = true`, `warn_unreachable = true`).
- **Breaks:** mypy's only hook into `f"{n:,}"` is the signature of `object.__format__`,
  which takes an opaque `format_spec: str`. The type checker has no model of *which* specs
  a given type supports, so no change to the annotation on `n` can make `f"{n:,}"`
  type-safe for `str` — `_fmt(x: str) -> f"{x:,}"` type-checks clean under `strict = true`
  and still raises at runtime. Conversely, the *current* annotation (`int | float | None`)
  is strict enough that mypy would reject a legitimate `str | None` argument and force the
  next author to add an ignore comment, which is exactly how the runtime crash becomes
  reachable later. The annotation gives the appearance of safety on line 29 while providing
  none on line 30.
- **Trigger:** the asymmetry is directly observable — `_fmt("")` raises
  `ValueError: Cannot specify ',' with 's'.` while `_fmt(object())` raises
  `TypeError: unsupported format string passed to object.__format__`; neither is a static
  error, and both are `n: int | float | None`-clean from the type checker's point of view
  only because the values are outside the annotation.
- **Fix:** do not rely on the annotation. Coerce or guard at runtime, and add the direct
  test from *Order of work* below so the behaviour is pinned.

## The single most dangerous input

**`_fmt("")` — the empty string. Dangerous because it is the only input that is both
guaranteed to be produced by the data layer and guaranteed to kill the report outright,
and because the guard that exists to prevent exactly this is aimed one layer away from
it.**

The argument, in order of weight:

1. **`""` is this file's own missing-value sentinel, used seven times.** `cmd_stats`
   normalises missing data to `""` at `cli.py:96`, `cli.py:107`, `cli.py:108`,
   `cli.py:110`, `cli.py:124`, `cli.py:129`, and `cli.py:177`. `""` is not an exotic
   input to this module; it is the shape the module *manufactures* out of every blank
   field in every CSV it reads.
2. **`str` is the native type of the data `_fmt` would naturally be pointed at.**
   `csv.DictReader` (`cli.py:87`, `cli.py:143`) returns `str` for every field. The moment
   anyone uses `_fmt` on a record value rather than on a `count()` — which is what the
   `suffix` parameter and the `None` branch both promise it is for — the input is a `str`,
   and per the specification above the `,` grouping option is "not supported" for the
   string presentation type.
3. **The failure is total, not partial.** Not one line of the report is written. The
   crash happens at the first of six identical call sites, `cli.py:98`, so `with phone`,
   `with email`, `with website`, `with instagram`, `with whatsapp` and `with region` are
   all lost, and none of the sections after them print either.
4. **It escapes as a traceback, not a diagnostic.** `main()` at `cli.py:314-318` catches
   only `KeyboardInterrupt`. A `ValueError` propagates out of `args.func(args)` and out of
   the entry point at `cli.py:322`, so the operator sees a CPython stack trace instead of
   the clean `no such file` / `is empty` messages that `cli.py:83-84`, `cli.py:89-90` and
   `cli.py:256-257` establish as this file's house style. `leadminer stats` is documented at
   `cli.py:9` and `cli.py:14-15` as the safe, always-available command — the one you reach
   for *because* a run looks wrong. It is the wrong command to be the one that tracebacks.
5. **The existing guard provides false comfort, which is what makes it dangerous rather
   than merely latent.** Line 30 reads `return "n/a" if n is None else ...`, which looks
   like a defensive guard on the value. It is `is None`, not `not n`, and it checks a value
   that provably never arrives while leaving `""` — the value that does arrive — completely
   exposed. A reviewer skimming line 30 concludes the function is None-safe. It is
   `None`-safe. It is not `""`-safe, and `""` is what this codebase produces.

Runner-up, for completeness: `_fmt(5, None)` → `'5None'` (S2-1) is *quieter* than the crash
and therefore in some ways worse once it is live, but it is strictly dominated today
because `suffix` is passed by nobody, whereas `""` is one refactor of `count()` away from
being live in every run. Third: `_fmt(datetime.date(...))` → `','` (S2-2), silent and
arbitrary, but it requires a caller that does not exist.

## Not a bug, but worth knowing

- **The invariant that keeps `_fmt` correct today, demonstrated rather than argued.**
  I ran the real `cmd_stats` over a hostile CSV containing, in the `phone` column: the
  Arabic-Indic string `"١٢٣"`, the narrow-nbsp-grouped `"1 234"`, the literal string
  `"nan"`, and the literal string `"0"`; and in the `name` column, a 100 000-character run
  of `x` followed by `😀🇱🇧`; plus a row whose every field is the literal `"None"`. The
  command exited **0**, printed all six `_fmt` lines with correct counts, and produced no
  traceback. A second, ragged CSV (`name,phone,region` header, short rows) also exited 0.
  The reason is structural: `count()` at `cli.py:95-96` is `sum(1 for r in rows if
  <bool>)` — no division (never `float`), no `None` term, no string, and `1` gates each
  element so the result is `>= 0`. `int.__format__(',')` is total over
  arbitrary-precision integers (verified at `10**400` and `-10**400`: 534 chars, 133
  commas, no exponent in either). So for every input `_fmt` can actually receive today it
  is exactly correct.
- **The whole guarantee rests on `count()` keeping its current shape.** Rewrite it as a
  ratio (`count(field) / total`) and four of the S2/S3 findings go live in one line. A
  rewrite as `return sum(...)` over a generator that can yield a non-`int` is equally
  fatal. Nothing enforces the shape — no test, no type narrowing, no runtime check.
- **`cmd_stats`'s tri-state `website_live` handling at `cli.py:105-113` is correct** and
  the comment records the right historical bug: blank/unreachable is counted separately
  at line 110 and is deliberately not folded into `dead`. My hostile-CSV run confirms
  `live + dead + unreachable` reconstructs. No issue here.
- **`_fmt` is private (leading underscore) and imported by nothing** — repo-wide grep
  across `tests/` and `scripts/` finds no external consumer. It is safe to change or
  delete without breaking a caller. That makes the fixes below unusually cheap.
- **`_fmt` is not the only reason numbers are formatted inconsistently.** Nine other
  sites inline the same formatting: `cli.py:93`, `cli.py:111`, `cli.py:112`, `cli.py:113`,
  `cli.py:117`, `cli.py:121`, `cli.py:126`, `cli.py:131`, `cli.py:194`, `cli.py:276`.
  For `int` arguments the two idioms are behaviourally identical (verified across
  `±10**e` for `e` in `0..40`), so this is duplication rather than a bug — but it is why
  the file reads as if `_fmt` has a purpose it does not have.
- **`cli.py:120-121` needs the `or "unknown"` guard, not `_fmt`.** That specific defect is
  in a category counter, not in the formatter; I flag it here only because it is the
  concrete reason `_fmt`'s dead sentinel matters, and it may be owned by whichever audit
  covers `cmd_stats` as a whole.

## Recommended order of work

1. **Make `_fmt` honest about its domain, or delete it.** Either
   `def _fmt(n: int | None, suffix: str = "") -> str: return "n/a" if n is None else
   f"{int(n):,}{suffix}"` — which removes every CRASH and every SILENT row in the matrix
   except the `None`/bool and the `nan` cases — or delete `_fmt` entirely and keep
   `f"{x:,}"` as the single idiom. Right now it is the worst of both: a helper that
   advertises generality it does not have. Highest value per byte in this report.
