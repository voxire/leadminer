# 222 — `cmd_scrape` (cli.py:40): transitive dependency map, and the three things it drags in that it should not

## Verdict

`cmd_scrape` is four lines of glue, but its transitive closure is 7 project modules and
1 third-party package, and three of those edges are wrong in ways that are invisible
from the function body. Two are **S1 by construction**: `scrapers/google_places.py:26`
(`from enricher import infer_region`) is a back-edge that turns the codebase's *own
prescribed* refactor into a hard circular import (proved below, not asserted), and
`pyproject.toml:33`/`:37` ship a console script whose module is not in the wheel, so
`cmd_scrape` is unreachable in any installed environment. The third is that
`cmd_scrape` reports **pre-whitelist** records, so its triage output is wrong by
construction — a healthy OSM run reported 7 records of which 2 survive
`main.py:172`, with `None` as the top category.

Everything below is measured by importing the real modules, not inferred. No scraper
was run and no network call was made: `requests` was absent from the interpreter, so
it was replaced with a `sys.modules` stub (or a `requests.py` shim in a temp copy)
to let the import graph resolve.

> **Duplication note.** The inverted import at `scrapers/google_places.py:26` is
> already reported in `020-type-contract-import-cycle.md` (S11),
> `030-packaging-import-hygiene.md`, `045-scraper-layer-refactor.md` and
> `088-SYNTH-migration-order.md`. All four stop at *"ModuleNotFoundError under a `src/`
> layout"*. That is the correct observation but it is the **weak** form of the claim,
> because the codebase today works. This report proves the **strong** form: applying
> the remediation those four reports prescribe produces a live circular import, and
> isolates the exact two-line condition that arms it. The wheel/`[project.scripts]`
> problem is reported in `215-x.md`; I confirm it and add the per-subcommand
> blast radius. Where this report and those agree, take the conservative severity.

## Findings

### S1 — `scrapers/google_places.py:26` is a back-edge that turns the prescribed src-layout refactor into a hard circular import

- **Where:** `scrapers/google_places.py:26` — `from enricher import infer_region`,
  sitting between `import requests` (`:24`) and the correct package-relative
  `from .base import ...` (`:28`).
- **Why it is a back-edge, not just a bad import:** `main.py:25-31` establishes the
  intended pipeline order as acyclic — `scrapers.*` → `dedup` → `enricher` →
  `pitch_recommender`. `google_places.py:26` adds an edge from the *first* stage to
  the *third*, skipping forward. Legal Python, wrong architecture, and it is the only
  such edge in the tree (verified: `enricher` imports nothing from `scrapers` today).
- **Breaks:** audits 020/030/045/088 all prescribe the same remediation: move to a
  `src/` layout **and** make `scrapers` a real package by re-exporting its public
  API from `scrapers/__init__.py`. Do those two things together and the tree stops
  importing. `enricher` is now the lower layer, so the natural typing fix at the
  `enricher → scrapers` boundary — `enricher.py:101`, `:225`, `:283`, `:326` all
  annotate `dict` where `BusinessRecord` (`scrapers/base.py:5`) is the actual type —
  creates a genuine cycle.
- **Proved, in three steps.** Each variant is a throwaway copy; the repo was not
  modified. `requests` is stubbed in each.
  - **1a — typing fix only, `scrapers/__init__.py` left empty (today's state):**
    `no cycle`. The empty `__init__.py` is the only thing keeping this alive.
  - **1b — typing fix + `__init__.py` re-exports (the prescribed fix):**

    ```
    $ python -c "import enricher"
      File ".../enricher.py", line 2, in <module>
        import requests
      File ".../enricher.py", line 3, in <module>
        from scrapers.base import BusinessRecord
      File ".../scrapers/__init__.py", line 4, in <module>
        from .google_places import GooglePlacesScraper
      File ".../scrapers/google_places.py", line 26, in <module>
        from enricher import infer_region
    ImportError: cannot import name 'infer_region' from 'enricher'
    ```

    The cycle is `enricher` → `scrapers/__init__` → `scrapers.google_places` →
    `enricher`, with `enricher` half-executed at `requests`.
  - **1c — same, but the `enricher` import moved under `if TYPE_CHECKING:`:**
    `no cycle`. So the escape hatch exists, but see S3-3 for why it is not free.
  - **Arming condition, precisely two edits:** (a) `enricher` acquires any `scrapers`
    import at runtime, **and** (b) `scrapers/__init__.py` eagerly imports
    `google_places`. Neither holds today. Both are individually near-certain:
    (a) is the last untyped boundary in a `mypy strict = true` tree
    (`pyproject.toml:66`); (b) is the ordinary Python package idiom, and `main.py:25-27`
    already does it by hand.
  - **The fix that works, verified:** move `infer_region` and the geo tables
    (`enricher.py:10-94`) into a shared module **and point both sides at it**. I tested
    the variant audit 045 suggests (`domain/geo.py`, i.e. a *new top-level* package):
    no cycle, because removing the `google_places → enricher` edge removes the cycle.
    If it lands as `scrapers/geo.py` **and** `enricher` imports it, the cycle returns
    via `enricher → scrapers.geo → scrapers/__init__ → google_places → enricher`.
    So *where the geo module lands is load-bearing*, and no report says so.
- **Trigger:** `import enricher` in a tree where `scrapers/__init__.py` re-exports
  `GooglePlacesScraper` and `enricher` has been typed against `BusinessRecord`. Both
  steps are individually unremarkable, which is the point.
- **Severity defence: S1.** Not for a current wrong number — the tree imports today.
  For three reasons: the failure is **deterministic**, not probabilistic; it is
  **caused by the remediation the repo's own audits prescribe**, so it will be hit by
  whoever does the work correctly; and the error names `enricher` and `infer_region`
  rather than the cycle, so it burns real debugging time before anyone looks at
  `scrapers/__init__.py`. A run that dies on import is the S1 definition.
- **Fix:** delete `scrapers/google_places.py:26` and yield `region=None`, letting
  `enricher.py:332` fill it exactly as it already does for OSM and Wikidata. That
  removes the back-edge outright, which is strictly better than relocating it. If the
  region must be known at ingest time, put the geo helpers in a **top-level** `geo.py`
  and import it absolutely from both sides — do not put them inside `scrapers/`.

### S1 — `cmd_scrape` is unreachable from the installed console script: the entry point's module is not in the wheel

- **Where:** `pyproject.toml:33` (`leadminer = "cli:main"`) vs `pyproject.toml:35-37`
  (`[tool.hatch.build.targets.wheel]` / `include = ["scrapers/"]`). The comment at
  `:36` — *"The package imports a top-level sibling module, so both must ship"* —
  states the exact hazard and then ships one of the two.
- **Breaks:** the wheel contains `scrapers/` only. `cli.py`, `main.py`, `httpclient.py`,
  `enricher.py`, `dedup.py`, `pitch_recommender.py` are all absent, so
  `leadminer scrape` dies at `ModuleNotFoundError: No module named 'cli'` before
  argparse runs. Even if `cli.py` were included, `cmd_scrape` additionally needs
  `httpclient` (via `osm.py:4`, `wikidata.py:4`) and `enricher` (via
  `google_places.py:26`) — so **`cmd_scrape` has the largest install-surface delta of
  any subcommand**: it is the one command that needs the shipped package *and* three
  unshipped siblings.
- **Trigger, and the per-subcommand blast radius.** Honest `src/` move via
  `git archive`, no import rewrites, `PYTHONPATH=src`:

  | Subcommand | First project import | Result |
  |---|---|---|
  | `stats` / `validate` | none | **still work** (`/dev/null is empty`) |
  | `scrape --source osm` | `cli.py:46` | `ModuleNotFoundError: No module named 'scrapers'` |
  | `score` | `cli.py:249` | `ModuleNotFoundError: No module named 'main'` |
  | `import leadminer.scrapers.osm` | `osm.py:4` | `No module named 'httpclient'` |
  | `import leadminer.scrapers.wikidata` | `wikidata.py:4` | `No module named 'httpclient'` |
  | `import leadminer.scrapers.google_places` | `google_places.py:26` | `No module named 'enricher'` |

  The split is exactly the lazy-import boundary: every project import in `cli.py` is
  inside a function body, so the two pure-CSV commands survive a `src/` move and the
  three pipeline commands do not. Note `osm.py:4` breaks **before** `.base` — the
  `.base` imports (`osm.py:5`, `wikidata.py:5`, `google_places.py:28`) are already
  package-relative and are the one thing here that is src-layout-clean.
- **Severity defence: S1.** The command is 100% unavailable as documented
  (`cli.py:8`, `pyproject.toml:33`). Confirmed with 215-x.md.
- **Fix:** one package, one import root. `src/leadminer/` with
  `[tool.hatch.build.targets.wheel] packages = ["src/leadminer"]`, entry point
  `leadminer = "leadminer.cli:main"`, and every `from httpclient` / `from enricher`
  rewritten to `from .httpclient` / `from .enricher`. Do S1-1 first — it is a
  prerequisite for the layout change to be stable.

### S2 — `cmd_scrape` reports pre-whitelist records, so the diagnostic is wrong by construction

- **Where:** `cli.py:61-75`. `main.py:172` filters with `is_business_category`
  before anything else; `cmd_scrape` has no whitelist import at all (verified across
  `cli.py:40-76`).
- **Breaks:** the docstring at `cli.py:41-45` states the purpose — *"Useful for
  checking a single source after an API change."* The reported record count and the
  category histogram are both pre-filter, so they describe a population the pipeline
  discards. `top categories` becomes a list of the tags the whitelist exists to
  reject.
- **Trigger (real `OSMScraper` fed a realistic Overpass 200 body, no network):**

  ```
  [OSM] Got 7 elements.
  [osm] 7 records
    with phone : 1
    with site  : 2
    top categories:
      None                         3      <- place=village / town / place_of_worship
      yes                          1      <- shop=yes  (whitelist.py:100)
      attraction                   1
      cafe                         1
      dentist                      1
    exit=0

  records surviving main.py:172 is_business_category(): ['Cafe Arabe', 'Beirut Dental']
  -> cmd_scrape reported 7; the pipeline keeps 2.
  ```

  7 reported, 2 kept, and the **top category is `None`** — `osm.py:71-78` leaves
  `category` unset for any element whose tags are `place=`, `place_of_worship=` etc.
  An operator checking whether OSM still works sees `7 records`, exit `0`, and a
  healthy-looking report. If the query had been quietly broken the same way, this
  output would be indistinguishable.
- **Severity defence: S2.** No product data is wrong — `cmd_scrape` writes nothing.
  But it is the designated triage instrument, it reports a 3.5× overcount with a
  meaningless headline number, and the failure is silent (exit `0`). Not S1 because
  nothing downstream consumes it; not S3 because the whole value of the command is the
  accuracy of the number it prints.
- **Fix:** apply the same filter as `main.py:172` and report both counts —
  `print(f"[{src}] {len(records)} records ({kept} after whitelist)")`. Reuse
  `is_business_category`; do not reimplement it.

### S2 — `cmd_scrape` inherits `httpclient`'s "any status < 400 is a success" contract with no decode guard, so a 200-with-HTML kills the CLI with a raw traceback

- **Where:** `httpclient.py:185` (`ok=resp.status_code < 400`) and
  `httpclient.py:110-113` (`FetchResult.json` → bare `_json.loads`, no guard);
  consumed unguarded at `osm.py:58` and `wikidata.py:87`; reached from `cli.py:61`
  where nothing catches it (`cli.py:314-318` catches only `KeyboardInterrupt`).
  Second instance: `google_places.py:254` (`data = resp.json()`) sits **after** the
  `except requests.RequestException` handler at `google_places.py:250-252`, so the
  handler cannot catch a decode failure from its own `try`.
- **Breaks:** a 2xx response with a non-JSON body is classified as success by
  `httpclient` and then explodes in the caller. Overpass returns HTML for several
  legitimate conditions (query timeout, server-side error page). Google returns an
  HTML interstitial to a proxied or rate-limited client. `main.py:167` catches this
  per-future and continues; `cmd_scrape` has no equivalent, so the *diagnostic*
  command tracebacks on an input the *production* command survives.
- **Trigger 1 — Overpass 200 + HTML (verified):**

  ```
  httpclient.fetch_with_retry = lambda *a, **k: FetchResult(
      ok=True, status=200, body=b"<html>...runtime error: Query timed out...</html>")
  cli.main(["scrape", "--source", "osm"])
  -> json.decoder.JSONDecodeError: Expecting value: line 1 column 1 (char 0)
     raised at osm.py:58, escaping cli.main() entirely
  ```
- **Trigger 2 — Places 200 + HTML (verified).** `requests.exceptions.JSONDecodeError`
  **is** a `RequestException`, but the `except` at `google_places.py:250` closed at
  line 252 before `google_places.py:254` ran:
  ```
  escaped _scrape_query: JSONDecodeError: ('Expecting value', '<html>interstitial</html>', 0)
  isinstance(e, requests.RequestException) == True
  -> google_places.py:197 f.result() re-raises -> cli.py:61 list() -> raw traceback
  ```
- **Also note, and this is the asymmetry 200-fn-cli-py-main-ops.md flagged without
  root-causing it:** `cli.py:63-66` handles the *empty* result correctly (exit `1`,
  loud warning). The *malformed* result — arguably the more likely failure — is
  unhandled. The command is strict about "nothing came back" and crashes about
  "something came back and was not JSON".
- **Severity defence: S2.** A traceback is loud and the command writes nothing, so
  there is no silent corruption — that keeps it out of S1. But it is a hard failure on
  a realistic input, it defeats the command's stated purpose, and the fix is one
  `except` clause.
- **Fix:** in `cmd_scrape`, wrap `cli.py:61` in `try/except Exception` and return `1`
  with `f"[{args.source}] raised {type(e).__name__}: {e}"` on stderr — mirroring
  `main.py:167`. Independently, make `httpclient.fetch_with_retry` set
  `ok=False` when `Content-Type` is not JSON-ish, and move `google_places.py:254`
  inside its `try`.

### S2 — `osm.py:7` and `wikidata.py:7` declare loggers that are never called, and nothing in the repo configures logging, so `httpclient`'s retry telemetry is invisible from `cmd_scrape`

- **Where:** `osm.py:1,7` and `wikidata.py:1,7` (`import logging` +
  `log = logging.getLogger(__name__)`); `httpclient.py:45`; the only `log.` call
  sites in the entire repository are `httpclient.py:178` and `httpclient.py:204`,
  both `log.debug`.
- **Breaks:** three of the four loggers have **zero** call sites — `osm.py` and
  `wikidata.py` report every outcome through `print` (`osm.py:33,51,59`;
  `wikidata.py:68,80,88`). The fourth logger's only output is at DEBUG, and
  `logging.basicConfig` is **never called anywhere in the repo** (verified: grep for
  `basicConfig|dictConfig|getLogger` returns exactly the three `getLogger` lines).
  So the retry instrumentation that commit `607e729` introduced — the module
  docstring at `httpclient.py:13-15` gives centralising retries as one of three
  reasons the module exists — produces **no observable output** from any command.
- **Trigger:** `leadminer scrape --source osm` against a rate-limited Overpass.
  `fetch_with_retry` makes 3 attempts with full-jitter backoff, logging twice at
  DEBUG to a logger with no handler. The operator sees `[OSM] Fetching Lebanon
  businesses from Overpass API...` (`osm.py:33`), then a silent pause of up to
  ~200s × 3 plus backoff, then either the result or `[OSM] FAILED after 3 attempts`
  (`osm.py:51-56`). Nothing distinguishes a 2-second blip that self-healed from a
  10-minute exhaustion — which is exactly the calibration signal
  200-fn-cli-py-main-ops.md ranks #3 and says "you can never distinguish a 2 s blip
  from a 4 h outage".
- **Severity defence: S2.** The single cheapest fix in this report (one
  `logging.basicConfig(level=logging.INFO, ...)` in `cli.main()`) buys back the entire
  retry layer's observability, and the current state makes a deliberate, documented
  design invisible in production. Overstated as S1 because nothing is *wrong*; the
  cost is purely diagnostic.
- **Fix:** configure logging once in `cli.main()`; delete the two unused
  `logging` imports and their `log` bindings from `osm.py`/`wikidata.py`, or convert
  their `print`s to `log.info`. Either way the two must not coexist.

### S3 — `cli.py:46`'s "import check" is unused, transitively redundant, and cannot detect the thing it claims to check

- **Where:** `cli.py:46` — `from scrapers.base import BaseScraper  # noqa: F401  (import check)`.
- **Breaks, three ways:**
  1. **Unused.** `BaseScraper` appears exactly once in `cli.py` (line 46). It is not
     used as a value, and it is not used as a type annotation either — `registry` at
     `cli.py:51-55` is inferred as `dict[str, type[OSMScraper] | type[WikidataScraper]
     | type[GooglePlacesScraper]]` and the name is never referenced. So this is not
     an annotation-only import; it is a **no-op import whose linter was silenced**.
  2. **Transitively redundant.** `cli.py:47-49` each run `from .base import ...`
     (`osm.py:5`, `wikidata.py:5`, `google_places.py:28`), which loads
     `scrapers/base.py` regardless. Line 46 can be deleted with zero behavioural
     change. It is the line most likely to be deleted by mistake, because a reviewer
     reading the comment concludes it does work.
  3. **It checks nothing that matters.** An "import check" whose purpose is to prove
     the scraper layer is importable is placed on the one module that is *always*
     importable. The imports that actually fail — `requests` at `google_places.py:24`
     and `httpclient.py:43` — are on lines 47-49, unguarded.
- **Trigger:** environment with no `requests` installed, `leadminer scrape --source osm`:

  ```
  ModuleNotFoundError: import of requests halted
    File ".../scrapers/google_places.py", line 24, in <module>
      import requests
  ```

  Line 46 succeeded. The check that "passed" and the check that would have caught the
  real failure are different lines. (Reported by `247-x.md` for `cmd_doctor`, which
  does guard its `requests` import at `cli.py:226-231`; `cmd_scrape` does not.)
- **Severity defence: S3.** Dead code and a misleading comment, no wrong output. Worth
  fixing because it is one line and because the comment actively misleads.
- **Fix:** delete line 46. If an import guard is wanted, put it around `cli.py:47-49`
  and emit `pip install -e '.[dev]'` the way `cli.py:228-231` already does.

### S3 — `cli.py:56-59` is unreachable, and it is the only thing that kept `--source` and the registry in agreement

- **Where:** `cli.py:56-59` versus `cli.py:290` —
  `s.add_argument("--source", required=True, choices=["osm", "wikidata", "google_places"])`.
- **Breaks:** argparse validates `--source` against a **hardcoded list that is a
  different object from the `registry` dict at `cli.py:51-55`**. The validation code
  that would reconcile the two can never run.
- **Trigger:** `cli.main(["scrape", "--source", "bogus"])` →
  `SystemExit(2)` from argparse, printed before `cmd_scrape` is entered:
  ```
  leadminer scrape: error: argument --source: invalid choice: 'bogus'
    (choose from 'osm', 'wikidata', 'google_places')
  ```
  The branch at `cli.py:56-59` never executes, and its `return 2` is dead.
- **Consequence for whoever adds a fourth source:** the natural edit is to add the

  self-registering. `leadminer scrape --source saudi` then fails with argparse's
  message listing only three choices, pointing at `cli.py:290` rather than at the
  registry the author just edited.
- **Fix:** make `registry` the single source of truth — build it at module scope and
  pass `choices=sorted(registry)` to `add_argument`, deleting `cli.py:56-59`. This is
  also the natural home for the lazy imports, so `cmd_scrape` stops paying for all
  three scrapers.

### S3 — `enricher.py:4` imports `urljoin` and `urlparse`, which nothing uses, and `requirements.txt` still ships the two libraries that replaced them

- **Where:** `enricher.py:4` — `from urllib.parse import urljoin, urlparse`.
- **Breaks:** neither name is referenced anywhere in `enricher.py` (grep: the only hit

### S3 — `httpclient.py:78-83` wraps `import os` in `try/except Exception`, and `enricher.py:327` imports an undeclared transitive dependency to silence a warning for a setting that no longer exists

- **Where:** `httpclient.py:78-83`; `enricher.py:327-328`.
- **First:** `import os` inside a `try: ... except Exception:`. `os` is a builtin
  module present in `sys.modules` at interpreter start; this import cannot raise. The
  `except Exception: email = ""` therefore guards nothing, and it is the only place in
  the file where a failure would be silently converted to a missing contact address.
  The genuinely fallible operation one line later is `os.environ.get(...)`, which is
  not the thing being guarded. Confusing the two is how a real bug would hide here.
- **Second:** `enricher.py:327` — `import urllib3; urllib3.disable_warnings(
  urllib3.exceptions.InsecureRequestWarning)`. Three problems: `urllib3` is not in
  `pyproject.toml:16-18` (it arrives transitively via `requests`, so this is an
  undeclared direct dependency); `mypy` cannot see it except via the
  `module = ["requests.*", "urllib3.*"]` escape hatch at `pyproject.toml:70-73`; and
  it suppresses a warning for `verify=False`, which commit `5222d32` removed — the
  comment at `enricher.py:170-174` documents restoring TLS verification, so the
  suppression is now guarding a condition the code no longer creates.
- **Fix:** hoist `import os` to `httpclient.py`'s module scope and delete the
  `try/except`; delete `enricher.py:327-328` (and drop `urllib3.*` from
  `pyproject.toml:72` when nothing else needs it).

### S3 — annotation strategy is inconsistent, which makes `BusinessRecord` a runtime dependency and blocks the cheapest fix for S1-1

- **Where:** `from __future__ import annotations` exists in exactly two of the ten
  application modules — `cli.py:18` and `httpclient.py:32`. It is absent from
  `scrapers/base.py`, `scrapers/osm.py`, `scrapers/wikidata.py`,
  `scrapers/google_places.py`, `scrapers/whitelist.py`, `enricher.py`, `main.py`,
  `dedup.py`, `pitch_recommender.py`.
- **Breaks:** without it, return annotations are evaluated at `def` time. So
  `Iterator[BusinessRecord]` at `osm.py:31`, `wikidata.py:66`,
  `google_places.py:168` and `base.py:33` are **runtime name lookups**, and
  `BusinessRecord` is a load-bearing runtime dependency of every scraper — not a
  typing-only one.
- **Why this matters for S1-1:** the natural way to break the demonstrated cycle is to
  make `enricher`'s use of `BusinessRecord` typing-only (probe 1c). That requires
  `TYPE_CHECKING` **plus** no eager annotation evaluation. Today `enricher` has
  neither, so the escape hatch is not free — and worse, someone may reach for
  `if TYPE_CHECKING:` in `enricher` alone and still get an eager `dict`-free
  annotation evaluation failure elsewhere. Add
  `from __future__ import annotations` to `enricher.py` and the three scrapers as
  part of the same change.
- **Related, one line:** `scrapers/whitelist.py:9` shows
  `from .whitelist import is_business_category` — but that is inside the **module
  docstring**, not code. `whitelist.py` has zero imports. It is therefore the one file
  in the package with no in-code demonstration of the package-relative convention
  that `osm.py:5`/`wikidata.py:5`/`google_places.py:28` follow correctly, and it is
  the file most likely to be missed in a `src/` migration (it needs no rewrite — but
  nobody will know that from reading it).

## Not a bug, but worth knowing

- **`cmd_scrape` reports pre-enrichment records, and the three sources disagree about
  `region`.** `google_places.py:275` computes `region = infer_region(None, lat, lon,
  country=country)`, so `leadminer scrape --source google_places` returns records with
  `region` populated. `osm.py:102` and `wikidata.py:110` both hard-code
  `region=None` and let `enricher.py:332` fill it later. `cmd_scrape` never reports
  `region` (`cli.py:68-75`), so the asymmetry is invisible — but the underlying
  inconsistency is real and is the same root cause as S1-1.
- **`cmd_scrape` collapses "not configured" into "broken".** With
  `GOOGLE_PLACES_API_KEY` unset, `google_places.py:169-171` prints
  `[Google] GOOGLE_PLACES_API_KEY not set, skipping.` and returns; verified:

  ```
  [Google] GOOGLE_PLACES_API_KEY not set, skipping.
  [google_places] 0 records
    WARNING: zero records. The source may be broken or blocked.
  -> cmd_scrape exit code = 1
  ```

  Exit `1` and "The source may be broken or blocked" for a missing credential. The
  zero-record branch at `cli.py:63-66` is correct for its actual trigger (the source
  ran and returned nothing) but is now the handler for a config error too. Have
  `scrape()` return a typed outcome — `httpclient.FetchResult` already models exactly
  this distinction (`httpclient.py:96-107`), and `google_places.py:231-233` already
  models it for 401.
- **`cli.py:61` materialises the whole source into memory** via `list(...)`, on top of
  `google_places.py:183`'s own `all_records` list. For `--source google_places` the
  full result set therefore exists twice. Not a problem at current scale (the
  Places quota caps it well below memory pressure), and `len()` at `cli.py:62` requires
  it — but `sum(1 for _ in gen)` plus a re-iteration, or a `Counter` fed in one pass,
  would remove the copy if volume ever grows.
- **The test suite never touches `cmd_scrape`.** `tests/test_lead_signal.py:65-68`
  imports `dedup`, `enricher`, `main`, `pitch_recommender` and exercises `cmd_stats`
  (`:211-215`) and `cmd_validate` (`:229-259`). `cmd_run`, `cmd_scrape`, `cmd_score`
  and `cmd_doctor` have no coverage — consistent with `087-SYNTH-test-gap.md`. Every
  finding in this report is therefore invisible to CI, which is why three of them
  survived the four commits that touched `cli.py` (`43ddb2c` through `99493b9`).
- **What this closure gets right.** The `.base` imports are package-relative and
  src-layout-clean (`osm.py:5`, `wikidata.py:5`, `google_places.py:28`). The lazy
  imports inside `cmd_scrape` genuinely limit the closure — `dedup`,
  `pitch_recommender` and `main` are correctly absent, and `stats`/`validate` still
  work after a `src/` move where `scrape`/`score`/`run` do not. `httpclient`'s
  thread-local session design (`httpclient.py:56-71`) is correct and is what makes
  `osm.py:35`'s `get_session()` safe. The problems in this report are about *which*
  modules are wired together, not about the HTTP layer itself.
