# 241 — Boundary and hostile-input audit of `cmd_doctor` (`cli.py:204`)

## Verdict

`cmd_doctor` has a three-part input surface — environment variables, the
filesystem under `DATA_DIR`, and three HTTP status codes — and it handles
**none** of them defensively. Two confirmed crash classes (a dangling or
looping `*.csv` symlink, and any non-ASCII filename under a non-UTF-8 stdout)
produce a traceback, directly violating the function's own stated invariant at
`cli.py:228-229` ("doctor exists to diagnose a broken environment, so it must
never be the thing that tracebacks"). The remaining hostile inputs are worse
than crashes because they are silent: `cli.py:241` labels **every** HTTP status
below 500 as `OK`, and the Google Places probe at `cli.py:236` is an
*unauthenticated GET*, so an HTTP 401 — which `scrapers/google_places.py:228-233`
declares `FATAL: invalid API key` — prints as `OK` and exits 0.

**The single most dangerous input is `HTTP 401` from
`https://places.googleapis.com/v1/places:searchText`**, because it is the one
value the pipeline itself classifies as fatal and the one value the diagnostic
classifies as healthy.

---

## Contract, as written in this repo

`cmd_doctor` is not implemented against the design contract in
`docs/audits/037-cli-design.md:149-179`. Reading that spec is the only way to
know what "correctly handled" means for this function, and the gap is wide
enough that most divergences below are not judgement calls.

| Spec (`037-cli-design.md`) | `cli.py` as built | |
|---|---|---|
| `--check-network` / `--no-check-network` flag (`:160`) | absent — probes always run | `:233-243` |
| `--strict`: exit `3` if optional check (e.g. `SCRAPER_EMAIL`) fails (`:161`) | absent; `SCRAPER_EMAIL` is cosmetic | `:210`, `:213` |
| `--format json` (`:162`) | absent | `:301-302` |
| Assert Python `>= 3.12` (`:165`) | absent | — |
| Validate `--data-dir` **exists or can be created** and has **read/write** permissions (`:166`) | bare `.exists()`; no `--data-dir`; no permission check | `:26`, `:217` |
| `GOOGLE_PLACES_API_KEY`: "presence **and string structure**" (`:168`) | presence only, via `bool()` | `:211` |
| Overpass: "asserts HTTP **200**" and available query slots (`:171`) | accepts any `< 500`; no slot check | `:240` |
| Wikidata: query `ASK { ?item wdt:P17 wd:Q822 }` (`:172`) | query `ASK{}` (asserts nothing about the data) | `:235` |
| Places: "**authenticated** test query with `pageSize: 1` … catches 400 invalid field mask or 401 unauthorized" (`:173`) | **unauthenticated GET**; accepts any `< 500` | `:236`, `:239` |
| Master CSV header-schema / UTF-8 integrity (`:174`) | absent (size only) | `:220` |
| Exit `3` = credential, exit `4` = network (`:176-179`) | only `0`/`1`; network failures never affect the code | `:244` |

Callers also treat `doctor` as a gate: `README.md:95` tells operators to run
`leadminer doctor  # check keys and connectivity first` immediately before
`leadminer run`, and `pyproject.toml:32-33` installs it as a console script, so
it is expected to be run from arbitrary working directories.

for the connectivity cases, `sys.modules["requests"]` replaced by a stub so that

env var. Arabic and emoji *values* are handled safely — `cli.py:212` prints only
the variable **name**, never the value, so the secret never reaches a
non-UTF-8 terminal and never leaks into CI logs. That is correct and deliberate;
the crash path for non-ASCII is filenames, not values (row F below).

## Findings

### S1 — `< 500` is reported as `OK`, so an invalid Places key reads as healthy

- **Where:** `cli.py:240-241`
  ```python
  note = "" if r.status_code < 500 else f"HTTP {r.status_code}"
  print(f"  {'OK ' if r.status_code < 500 else 'WARN'}  {name:<14} {note}")
  ```
- **Breaks:** the threshold is a *server-availability* threshold, applied to what
  the function's own docstring (`cli.py:205`) calls a *credentials and
  connectivity* check. Every authentication and authorisation failure —
  400, 401, 403, 404, 405, 407, 429 — is in the `OK` branch. `WARN` is
  reserved for 5xx, which is the one class of failure that is genuinely not the
  operator's fault. The check is therefore inverted relative to its purpose.
- **Trigger:** `scrapers/google_places.py:227-233` already defines the semantics
  this line contradicts:
  ```python
  resp = session.post(API_URL, json=body, timeout=30)
  if resp.status_code == 401:
      print("[Google] FATAL: invalid API key (401). "
            "No Places data will be collected.", flush=True)
  ```
  A revoked or malformed `GOOGLE_PLACES_API_KEY` produces 401 at run time and
  401 at `doctor` time. At run time it is `FATAL`; at `doctor` time it is `OK`,
  and because `ok` is only set false when the variable is *absent*
  (`cli.py:213-214`) the process still **exits 0**. The operator is told the key
  is fine, three lines below `MISSING  GOOGLE_PLACES_API_KEY` on the screen, in
  the run where it is present but invalid.
- **Fix:** compare against `200`/`204`, and treat `401`/`403` as a hard
  credential failure (non-zero exit, distinct label), `429` as rate-limited,
  `5xx` as upstream-down — i.e. `status == 200` per `037-cli-design.md:171-173`.

### S1 — The Places probe is an unauthenticated GET, so it cannot test the credential even in principle

- **Where:** `cli.py:236` (URL) and `cli.py:239` (`requests.get`)
  ```python
  ("Google Places", "https://places.googleapis.com/v1/places:searchText"),
  ...
  r = requests.get(url, timeout=5)
  ```
- **Breaks:** two independent defects stack.
  1. **No credential is sent.** `scrapers/google_places.py:159-165` puts the key
     in an `X-Goog-Api-Key` header; `requests.get` at `cli.py:239` sends no
     headers at all. Google documents Text Search (New) as **"an HTTP POST
     request"** ([Google, Text Search (New)](https://developers.google.com/maps/documentation/places/web-service/text-search)),
     and the endpoint is only reachable with `X-Goog-Api-Key` +
     `X-Goog-FieldMask` (`google_places.py:162-163`). So this probe is
     guaranteed to be rejected regardless of whether the key is valid, and the
     rejection lands in the `OK` branch per the finding above.
  2. **Wrong method.** `GET` on a POST-only path yields 404/405/400. Also `< 500`
     → `OK`.
  The result is that the one credential `doctor` claims to verify is the one
  credential it is structurally incapable of verifying. `037-cli-design.md:173`
  specified "an **authenticated** test query with `pageSize: 1` … catches 400
  invalid field mask or 401 unauthorized"; neither the authentication nor the
  error discrimination was implemented.
- **Trigger:** any value in `GOOGLE_PLACES_API_KEY` — correct, truncated, or
  `AAAA`. `leadminer doctor` prints `OK   Google Places` in all three cases.
- **Fix:** reuse the real session (`httpclient.get_session()`) and POST the
  minimal body `{"textQuery": "cafe", "pageSize": 1}` to `google_places.API_URL`
  with the same headers as `google_places.py:159-165`, then assert 200.

### S1 — `f.stat()` tracebacks on hostile or racy filesystem entries, violating the function's own invariant

- **Where:** `cli.py:219-220`
  ```python
  for f in sorted(DATA_DIR.glob("*.csv")):
      print(f"       {f.name:<32} {f.stat().st_size:,} bytes")
  ```
- **Breaks:** `glob` and `stat` are two syscalls with a TOCTOU window, and
  `Path.stat()` follows symlinks (`os.stat`, not `os.lstat`). Three distinct
  uncaught exceptions reach the user:
  - dangling symlink → `FileNotFoundError`
  - symlink loop → `OSError: [Errno 62] Too many levels of symbolic links`
  - non-ASCII filename + non-UTF-8 stdout → `UnicodeEncodeError`

  All three are bare tracebacks, because `cli.py:314-318` catches **only**
  `KeyboardInterrupt`:
  ```python
  try:
      return int(args.func(args) or 0)
  except KeyboardInterrupt:
  ```
  The comment at `cli.py:228-229` states the design rule this breaks: *"doctor
  exists to diagnose a broken environment, so it must never be the thing that
  tracebacks."* A broken `data/` directory is exactly the broken-environment case
  doctor is for, and the dangling-`master`-symlink case is realistic: the CI
  workflow materialises `data/` from Drive via `rclone copy` at
  `.github/workflows/scrape.yml:50-51`, and a developer reproducing a Drive
  sync locally, or an interrupted/aborted rclone transfer, can leave a partial
  or dangling entry behind.
- **Trigger (literal, reproduced):**
  ```
  $ ln -s /tmp/does_not_exist.csv data/all_businesses.csv
  $ leadminer doctor
  data directory:
    OK   data exists
  Traceback (most recent call last):
    File ".../cli.py", line 220, in cmd_doctor
      print(f"       {f.name:<32} {f.stat().st_size:,} bytes")
  FileNotFoundError: [Errno 2] No such file or directory: 'data/all_businesses.csv'
  ```
  And with `PYTHONIOENCODING=cp1252` (or any non-UTF-8 locale without PEP 538
  coercion) plus one Arabic-named CSV:
  `UnicodeEncodeError: 'charmap' codec can't encode characters in position 7-12`
- **Fix:** wrap the loop body in `try/except OSError` and print
  `f"{f.name} <unreadable: {type(e).__name__}>"`; use `f.lstat()` for the size
  so dangling links report their link size instead of raising; and set the label
  via a length-limited, `backslashreplace`-safe repr.

### S2 — Every finding except "key is absent" is cosmetic: the exit code does not reflect the report

- **Where:** `cli.py:208` (`ok = True`), `cli.py:213-214` (the only write of
  `ok = False`), `cli.py:242-243` (`except` branch never touches `ok`),
  `cli.py:244` (`return 0 if ok else 1`).
- **Breaks:** the `FAIL` path at `cli.py:243` prints and continues without
  recording anything. Verified: with a key present and all three upstreams
  raising `OSError`, output is `FAIL Overpass / FAIL Wikidata /
  FAIL Google Places` and **exit 0**. Same for all-`503` (`WARN` ×3, exit 0) and
  same for Overpass `429`. The only non-zero exit the function can produce is
  "the env var is unset". `037-cli-design.md:176-179` reserved distinct codes
  (`3` credential, `4` network); both are absent, and the network code is not
  merely wrong, it is unused.
  Note this overlaps `docs/audits/242-x.md`, which reached the same conclusion
  from the test-gap angle; I confirm it here from the hostile-input angle and
  add that the same defect hides `SCRAPER_EMAIL` (`cli.py:210` prints it,
  `cli.py:213` gates only on the Places key) — so a run with no contact address
  in its User-Agent exits 0 despite `httpclient.py:74-85` existing solely to
  make Overpass/Wikidata see one.
- **Trigger:** as in the table above. `SCRAPER_EMAIL` unset +
  `GOOGLE_PLACES_API_KEY` set → `MISSING  SCRAPER_EMAIL`, exit 0.
- **Fix:** `ok = False` in the `FAIL` branch and for a missing `SCRAPER_EMAIL`;
  return `3` for credential failures and `4` for network failures per
  `037-cli-design.md:176-179`.

### S2 — `DATA_DIR` is CWD-relative, and the MISSING message asserts a cause it cannot know

- **Where:** `cli.py:26` (`DATA_DIR = pathlib.Path("data")`), `cli.py:222`
  (`print(f"  MISSING  {DATA_DIR} (no run has produced output yet)")`).
- **Breaks:** the path is resolved against the process working directory, not the
  package or project root. `pyproject.toml:32-33` installs `leadminer` as a
  console script, so running it from anywhere other than the project root is the
  *normal* case, and there is no `--data-dir` override (`037-cli-design.md:166`
  specified one). The message then converts "I looked in `$PWD/data`" into a
  causal claim — "no run has produced output yet" — which is a statement about
  history that a single `exists()` call cannot support. An operator who ran
  `leadminer run` from the project root and then runs `doctor` from
  `~/Downloads` is told their entire lead history was never produced.
- **Trigger:** `cd /tmp && leadminer doctor` on a machine where
  `/Users/mhomsi/dev/dummy/leadminer/data/all_businesses.csv` exists →
  `MISSING  data (no run has produced output yet)`, exit unchanged.
- **Fix:** resolve `DATA_DIR` from `pathlib.Path(__file__).resolve().parent`,
  allow `--data-dir`, and change the message to name the absolute path actually
  inspected (`f"MISSING  {DATA_DIR.resolve()} — searched here"`).

### S2 — Credential presence is tested with `bool()`, so whitespace and garbage pass as `OK`

- **Where:** `cli.py:211` (`present = bool(os.environ.get(var))`).
- **Breaks:** `bool()` is a truthiness test, not a validity test. Every
  whitespace-only value, every literal `"0"`/`"false"`/`"None"` (common
  placeholders from a shell profile, a `.env` parser, or a CI secret left as a
  default), and every arbitrary 1-character string reports `OK`.
  `037-cli-design.md:168` asked for "presence **and string structure**" — only
  presence exists. `scrapers/google_places.py:169` guards on `if not
  self._api_key`, which `"   "` passes, so a whitespace secret produces the same
  silent empty-source outcome as no secret at all (that is the "FATAL vs. no
  results" confusion `google_places.py:229-230` was written to eliminate).
- **Trigger:** `GOOGLE_PLACES_API_KEY="   "` → `OK   GOOGLE_PLACES_API_KEY`,
  exit 0, no warning.
- **Fix:** `val = (os.environ.get(var) or "").strip()`; report `MISSING` when
  `not val`, and additionally report a length/shape warning for the key
  (e.g. `SUSPECT`) when it does not match `^[A-Za-z0-9_-]{20,}$`.

### S3 — The CSV listing mis-reports several ordinary filesystem states

- **Where:** `cli.py:219-220`.
- **Breaks:** four distinct silent-wrong cases, all reproduced above:
  - A **directory** named `*.csv` prints its own inode size:
    `backup.csv    64 bytes` — indistinguishable from a 64-byte CSV.
  - `glob("*.csv")` is case-sensitive on both ext4 and default APFS, so
    `ALL_BUSINESSES.CSV` or `all_businesses.Csv` is omitted with no hint. The
    five exports written at `main.py:209-213` are all lowercase today, so this
    only bites a hand-renamed or Drive-synced file — but the workflow's rclone
    `--include "*.csv"` has the same case-sensitivity.
  - A `data/` with mode `000` prints `OK data exists` and then **zero files**:
    `pathlib` swallows `PermissionError` inside `glob`, so an unreadable
    directory is indistinguishable from an empty one. `037-cli-design.md:166`
    asked for a read/write permission check; there is none.
  - `data` being a regular file also prints `OK data exists` then zero files
    (`ENOTDIR` is in pathlib's ignored-errno set). The check at `cli.py:217`
    should be `.is_dir()`.
  A fifth case is a benign-but-real TOCTOU: `main.py:209-213` rewrites all five
  CSVs in place, so `doctor` run concurrently with `run` reports partial sizes.
- **Trigger:** `mkdir data/backup.csv` → `backup.csv  64 bytes`.
- **Fix:** `if not DATA_DIR.is_dir(): …`; use `os.access(DATA_DIR, os.R_OK | os.W_OK)`;
  glob `*.csv` case-insensitively; skip non-files with `f.is_file()`; label
  directories and unreadable entries explicitly.

### S3 — The connectivity probes bypass the project's own HTTP layer

- **Where:** `cli.py:239` (`requests.get(url, timeout=5)`).
- **Breaks:** four small divergences from `httpclient.py` and from the rest of
  the codebase:
  - **No User-Agent.** `requests.get` sends `python-requests/2.32.3`. The
    project's UA — built at `httpclient.py:74-85` precisely because "Overpass and
    Wikidata both ask for a contact address in the UA" — is not sent, so a
    `403` from WDQS's UA policy prints as `OK`.
  - **No context manager.** `r` is never closed; the three responses rely on GC
    to release their connections. Minor at three calls, but `httpclient.py:181`
  uses `with resp:` correctly.
  - **`timeout=5` is a connect *and* read budget per host, serialised** →
    worst case ~15s with no per-host progress output before the first line.
  - **URL duplication.** `cli.py:236` hardcodes
    `https://places.googleapis.com/v1/places:searchText`, which is the same
    constant as `scrapers/google_places.py:30` `API_URL`. They can drift.
  The Wikidata probe's query is also `ASK{}` (`cli.py:235`), which asserts
  nothing about `wdt:P17 wd:Q822` as `037-cli-design.md:172` specified; it only
  proves the endpoint answered.
- **Fix:** probe via `httpclient.get_session()` (correct UA, session reuse) and
  import `API_URL` from `scrapers.google_places` instead of repeating it.

## Not a bug, but worth knowing

- **Credential values are never echoed.** `cli.py:212` prints only the variable
  name. This is the right call: the surrounding command prints to CI logs
  (`.github/workflows/scrape.yml:65-69` captures stdout into the run log), and
  echoing a live Places key into a retained log would be a credential leak.
  Arabic, emoji, and 4 KB values in the environment are therefore *safe* here —
  the non-ASCII crash path is filenames (`cli.py:220`), not values.
- **`cmd_doctor` correctly ignores `args`** (see section D). This is robust, but
  it is the mechanical reason the contract's `--data-dir`/`--strict`/`--format`
  flags could not exist. Adding them is a parser change plus three
  `getattr(args, ..., default)` reads at `cli.py:204`.
- **The `ImportError` guard at `cli.py:225-231` is the one piece of this function
  that is genuinely well built.** It is the only reason a broken environment
  yields a clean `FAIL  requests is not installed` and exit 1 rather than a
  traceback — and it is correct, in the right place, with the right message. It
  also shows the author knew the invariant; `cli.py:220` just was not held to it.
- **Doctor is not wired into CI.** `.github/workflows/scrape.yml:65-69` runs
  `python main.py` directly; `grep -n doctor .github/workflows/scrape.yml`
  returns nothing. So the exit-code defect is currently only observable by a
  human, which caps its blast radius today — but `037-cli-design.md:653`
  specifies adding it, and doing so before fixing S1/S2 would put a
  permanently-green preflight gate in front of the pipeline.

## Most dangerous input

**`HTTP 401` returned by `https://places.googleapis.com/v1/places:searchText`
during `cmd_doctor`'s probe at `cli.py:239`.**

Ranked against the alternatives:

1. **It is the only hostile input that is contradicted by the codebase itself.**
   `scrapers/google_places.py:228-233` treats 401 as
   `FATAL: invalid API key (401). No Places data will be collected.` and aborts
   the source. `cli.py:240-241` treats the identical status as `OK` and, because
   `ok` depends only on key *presence* (`cli.py:213-214`), exits 0. Two
   components of one repository define the same status code as fatal and as
   healthy. There is no argument from which one is right — the scraper's
   reading is the correct one, because it is the component that actually
   depends on the code working.
2. **It defeats the function's stated purpose.** `cli.py:205` — "Check
   credentials and connectivity before blaming the data." A 401 *is* the
   credential check; doctor is the only place that answers it, and it answers
   wrong. `README.md:95` instructs operators to run doctor first and then trust
   the result.
3. **It is silent.** Exit 0, an `OK` in the same column as the two genuinely
   healthy probes, no warning text. Nothing downstream surfaces it.
4. **It is reachable in normal operation.** Google revokes, restricts, or
   disables a key routinely: an expired Cloud billing trial, a key not yet
   allow-listed for the Places API (New), a quota exhausted on the wrong
   project, a secret rotated in GitHub Actions but not in the operator's local
   shell. Each of those yields 401/403 at run time and `OK` at doctor time.
5. **It is amplified by the probe being unauthenticated** (second S1). The
   status doctor sees has no relationship to the validity of the key, so the
   false all-clear is not a rare coincidence — it is what doctor reports on
   *every* invocation.

Runner-up, for contrast: the dangling-symlink traceback. It is loud, local, and
produces no wrong conclusions — it is strictly less dangerous than a green exit
code that hides a fatal misconfiguration, which is why it is not the headline
despite being the more mechanically dramatic failure.

## Recommended order of work

1. **Fix the status classification and the Places probe** (`cli.py:236-241`) —
   use the real endpoint via `httpclient`/`API_URL` with the key header, assert
   `200`, and separate 401/403 (credential) from 429 (rate limit) from 5xx
   (upstream). Nothing else in this report matters while doctor reports OK for
   the credential it exists to check.
2. **Make `ok` reflect the report** (`cli.py:208`, `213-214`, `242-243`) and
   return the contract's `3`/`4`. Then wire `doctor` into
   `.github/workflows/scrape.yml` ahead of `python main.py`.
3. **Harden `cli.py:219-220`** so no filesystem state can traceback: `is_dir()`
   check, `try/except OSError` per entry, `lstat()` for size, non-ASCII-safe
   printing. This closes the last route by which `cmd_doctor` can be the thing
   that tracebacks, per its own comment at `cli.py:228-229`.
