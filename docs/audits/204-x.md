# 204 — `_fmt` (cli.py:29): the "no data" arm is unwired, and one line inverts the product's core signal

## Verdict

`_fmt` is four characters of correct code and has no defect of its own — for the `int` it
actually receives it always prints the right string. **The S1 is not in `_fmt`, it is in the
line that bypasses `_fmt`:** `cli.py:109-110` computes `unreachable` from *"the `website_live`
cell is blank"* and therefore cannot distinguish that from *"this file has no `website_live`
column"*. Point `leadminer stats` at any CSV without that column and it asserts, exit-code
`0`, that every site in the file is unreachable — even when the row literally says
`website_live=True`. That is the exact UNKNOWN/DEAD conflation `enricher.py:145-156` records
as "the single worst bug in the pipeline" and that `tests/test_lead_signal.py:71-99` exists to
prevent in the scorer. `_fmt` already contains the machinery to say "n/a"; nobody wired it up.

Scope note: `docs/audits/200-x.md` covers the signature (`float >= 1e16`, `str` crash,
`suffix` dead) and `207-x.md` covers cumulative absolute counts. **This report adds** the
actual-vs-declared *type* analysis against `scrapers/base.py` (which neither report opens),
a reproduced end-to-end demonstration with exit `0`, and three findings unique to it.

## Actual types vs declared types

`_fmt`'s own contract, verified by importing the real module:

| | Declared | Actual in practice |
|---|---|---|
| in | `int \| float \| None` (`cli.py:29`) | **`int`, and nothing else** |
| out | `str` (`cli.py:29`) | `str` — always |

The input side is provable, not inferred: `count()` at `cli.py:95-96` is annotated `-> int`
and its body is `sum(1 for r in rows if <bool>)` — a generator yielding only the literal
`1`, so the result is `int`, `>= 0`, never `None`. All six call sites (`cli.py:98-103`) pass
`count(...)` and none pass `suffix`. **So `float` and `None` are unreachable arms, and the
`"n/a"` branch at `cli.py:30` is dead code.**

The real type mismatch is **one level up and neither report names it.** The rows `cmd_stats`
iterates are `csv.DictReader` output — `dict[str, str | list[str]]`, where every *declared*
column is a `str` and the TypedDict's `float | None` / `int | None` / `bool | None`
(`base.py:11, 16, 21, 22, 28`) **never apply on this path**. `website_live` is a string
`"True"` here, compared as a string at `cli.py:107-108`, while `enricher.py:250` wrote it as
a real `bool`. `cmd_stats` and `cmd_validate` never touch `BusinessRecord` and never import
it; they type their rows off `DictReader` alone.

Extending the question to its only enclosing function, `cmd_stats` reads exactly ten fields

## Unsafe uses of the return value

**None. Every one of the six uses is an f-string inside `print()`, and a `str` cannot break
an f-string.** The return-value side of this contract is trivially safe; the entire risk
lives on the input side. I checked for a consumer that indexes, slices, parses, or re-formats
the result, and there is none — `_fmt` is imported by nothing outside `cli.py` (verified by
repo-wide grep including `tests/` and `scripts/`).

## Findings

### S1 — `unreachable` is computed from "column absent" identically to "we never got an answer", so `stats` declares live sites unreachable
- **Where:** `cli.py:109-110` (the predicate), printed at `cli.py:113`
  ```python
  unknown = sum(1 for r in rows
                if r.get("website") and not (r.get("website_live") or "").strip())
  ```
  `r.get("website_live")` returns `None` both when the cell is blank *and* when the key does
  not exist. The tri-state discrimination at `cli.py:105-110` is correct **for a CSV this
  pipeline wrote** (verified: `main.py:125` uses `fieldnames=FIELDS`, so `website_live` is
  always present and `True`/`False`/`None` serialise to `"True"`/`"False"`/`""`). It is
  wrong for any other CSV, and `cli.py:294` accepts a free-form `file` argument.
- **Breaks:** a site the exporter recorded as **live** is reported as unreachable. This is
  the UNKNOWN/DEAD inversion in its most damaging direction, in the one command documented at
  `cli.py:80` as "the first thing to check" and at `cli.py:14-15` as "what you reach for when
  a run looks wrong" — so an operator debugging a scrape is told the sites are broken when
  the data says the opposite. Exit code `0`.
- **Trigger** (verified; one row, `website_live=True`, only the header differs):
  ```
  $ python3 - <<'PY'   # writes two files from one identical row
  ...                  # A: all 22 columns   B: FIELDS minus "website_live"
  $ python3 cli.py stats A.csv        $ python3 cli.py stats B.csv
    website live    : 1                 website live    : 0
    website dead    : 0                 website dead    : 0
    unreachable     : 0                 unreachable     : 1
  exit=0                                exit=0
  ```
- **Severity defence:** S1 because the number is not merely imprecise, it asserts the
  **opposite** of the recorded fact about the product's primary signal, silently, in the
  diagnostic tool, with a success exit code. Real-world trigger: a `sales_ready.csv` or
  subset rebuilt by hand or in Sheets (the CSVs go to Google Drive per `README`/workflow),
  or any CSV exported from another system. Not triggered by `leadminer run`'s own output.
- **Fix:** check the header, not the cell — `hdr = reader.fieldnames or []`, and if
  `"website_live" not in hdr`, print `n/a` for `live`/`dead`/`unreachable` and say so.

### S2 — the six `count()` columns print a confident `0` for a field the file does not contain
- **Where:** `cli.py:96` (`return sum(1 for r in rows if (r.get(field) or "").strip())`)
  rendered by `_fmt` at `cli.py:98-103`
- **Breaks:** `(None or "")` collapses *absent key* and *blank cell* to the same falsy value,
  so `count` cannot distinguish them, and `sum()` over an empty generator is `0`. Verified
  on a CSV with no `whatsapp` column: `with whatsapp : 0`. The reader concludes **"zero
  businesses have WhatsApp"** — a claim about the market — when the truth is **"this file has
  no WhatsApp column; we don't know."** `_fmt`'s `None → "n/a"` arm exists precisely to
  express the second thing and can never fire, because `count` has already destroyed the
  sentinel one layer upstream.
- **Trigger:** `leadminer stats /path/to/whatever.csv` where the file is not a
  pipeline export. Strongest case, verified — a CSV with a single `name` column yields a
  full, confident, all-zero report with `None` labels and **exit `0`**:
  ```
    with phone      : 0        by priority:
    ...                          None       1
  ```
- **Severity defence:** S2 not S1 — the number is wrong but not inverted, and it requires a
  non-pipeline input. Still S2 because it is a *diagnostic that misleads about data health*
  with a success exit code, in a repo whose stated blocker is trusting the output.
- **Fix:** in `count`, return `None` when `field not in reader.fieldnames` so the existing
  `"n/a"` arm finally becomes live. One-line change; `_fmt` needs no edit.

### S3 — `_fmt`'s over-wide annotation is precisely what suppresses the check that would catch a bad caller
- **Where:** `cli.py:29` — `n: int | float | None`
- **Breaks:** `pyproject.toml:64-68` runs `mypy strict`. Because `str` is *not* in the
  annotation, a future `_fmt(some_cell_value)` — where the cell is a `str`, the natural next
  caller — type-checks clean and blows up at runtime inside an f-string. `_fmt` does no
  coercion (unlike `cli.py:167` and `cli.py:181`, which both `try/except` their casts).
  Verified escapes: `_fmt('1234')` → `ValueError: Cannot specify ',' with 's'.`;
  `_fmt(b'12')` / `_fmt([1])` → `TypeError`. `main()` catches only `KeyboardInterrupt`
  (`cli.py:316`), so the exception escapes `leadminer` and Python exits `1` — **the same
  exit code `cmd_stats` returns for "`file` is empty" (`cli.py:90`)**, so a crash is
  indistinguishable from an empty file in a shell or CI step.
- **Trigger:** not reachable from any of the six current call sites. Latent.
- **Severity defence:** S3 — it is an API trap, not a live bug. Filed S2 in
  `200-x.md:110` only on the same reasoning; I keep S3 because the mitigation (add `str` to
  the annotation, or coerce in the body) is one line.
- **Fix:** `n: int = 0` if you trust the caller, or coerce defensively
  (`_fmt(int(n) if n is not None else None)`), and make `cmd_stats` reserve exit `1` for
  "empty" by returning a distinct code for internal errors.

### S3 — `csv.DictReader` raggedness leaks literal `None` labels into the report
- **Where:** `cli.py:116-131`
- **Breaks:** `DictReader` fills absent trailing cells with `restval=None`, and
  `collections.Counter(r.get("industry_priority") ...)` keys on that `None`; `str(None)` is
  `"None"`, so the report prints a category called **`None`** where it means *unrecorded*,
  and a blank cell prints an **empty** label (`cli.py:117` `f"    {str(k):<10} {v:,}"` →
  ten spaces then the count). Verified on a CSV with one short and one over-long row:
  ```
    by priority:
                 1
      None       1
      high       1
    by source:
      osm                          2
      None                         1
  ```
  `cmd_stats` exits `0`. Note this is *only* in the `Counter` blocks — the six `_fmt` lines
  absorb it via `(r.get(field) or "")`, so the same missing datum is reported as `0` in one
  section and as `None` in another. `cmd_score`'s sibling block at `main.py:230, 238` already
  uses the correct `or "Unknown"` idiom; `cli.py` does not.
- **Trigger:** any CSV with a truncated or over-long row. Reachable — `cmd_stats` takes any
  path, and Google Sheets round-trips regularly mangle trailing empty cells.
- **Fix:** `(r.get(k) or "Unknown")` at `cli.py:116, 120, 129`, matching `main.py:230`.

### S3 — `cmd_validate`'s BOM check at `cli.py:154-156` can never fire
- **Where:** `cli.py:142` opens with `encoding="utf-8-sig"`; `cli.py:154` then tests
  `(r.get("name") or "").startswith("\ufeff")`
- **Breaks:** `utf-8-sig` *strips* a leading BOM on read, which is the whole defence
  (`main.py:82-84` documents exactly this). Verified: a file whose first bytes are
  `EF BB BF` is read back as `"Acme"`, `bom_name == 0`, `validate` prints
  `all checks passed` and exits `0`. The gate is advertised as protecting against
  "written without utf-8-sig" and structurally cannot observe that condition.
- **Trigger:** any BOM-prefixed CSV. Not a false negative on good data — a dead check that
  reports success unconditionally.
- **Fix:** read once as raw `utf-8` to detect the BOM, or delete the check and rely on the
  reader. Note the two `cmd_validate` fixtures build files via `write_csv`
  (`tests/test_lead_signal.py:196-208`), which always emits the BOM correctly, so no test
  can ever catch this.

## Not a bug, but worth knowing

- **`_fmt` has zero field-level surface.** It is a scalar formatter; the `BusinessRecord`
  comparison the lens asks for resolves cleanly at ten of ten. The TypedDict's real defect is
  that `cmd_stats`/`cmd_validate` bypass it entirely and infer types off `DictReader` — a
  separate audit (`020-type-contract-import-cycle.md`, `021`/`028-csv-roundtrip-fidelity.md`)
  should own that.
- **The `None` arm is unreachable *because* `count` is well-behaved.** Both 200 and 207 flag
  the arm as dead; the sharper statement is that the deadness is **caused by** the defect in
  S2. `count` is doing the type collapse `_fmt` was built to display, so the information
  `_fmt` needs is destroyed before it can be used. Deleting the arm (200's recommendation)
  removes the last trace of the capability; wiring it (my S2 fix) restores it.
- **Silent non-count rendering exists but is unreachable today.** `_fmt` renders
  `True → '1'`, `False → '0'`, `float('nan') → 'nan'`, `float('inf') → 'inf'`,
  `-5 → '-5'`, `2.5 → '2.5'` with no error and no signal. All confirmed. None reachable from
  `count()`; listed only because the `float` arm in the signature invites them.
- **`test_stats_handles_tri_state_website_live` (`tests/test_lead_signal.py:211-226`) asserts
  on the `live`/`unreachable` lines, and its fixture is built by `write_csv`
  (`tests/test_lead_signal.py:196-208`), which always writes all 22 columns.** That is why the
  S1 survived: the one test touching this code path cannot construct a column-less CSV. It
  asserts `"website live    : 1" in out` — note that string will change if the S1 fix routes
  those lines through `_fmt`, so that assertion needs updating in the same commit.
- **The `suffix` parameter has no caller** (`cli.py:29`), as `200-x.md:124` also notes.

## Recommended order of work

1. **S1** — gate `live`/`dead`/`unreachable` on `"website_live" in reader.fieldnames`, and
   print `n/a` plus an explicit "this file has no liveness data" line otherwise. Three lines,
   and it stops `stats` from telling the operator the opposite of the truth. Update the
   assertion at `tests/test_lead_signal.py:225` in the same commit.
2. **S2** — make `count` return `None` for a field absent from `reader.fieldnames` so the
   existing `"n/a"` arm becomes live. One line; no `_fmt` change needed.
3. **S3 (DictReader labels)** — `or "Unknown"` at `cli.py:116, 120, 129`, matching
   `main.py:230`.
4. **S3 (BOM check)** — delete `cli.py:154-156` or make it read the raw bytes; a gate that
   cannot fail should not be in a gate.
5. **S3 (signature)** — narrow `_fmt` to `n: int` *after* 1 and 2 land, so `"n/a"` survives
   long enough to be used; and give internal errors an exit code distinct from
   `cmd_stats`' "empty file" `1`.
6. **Test gap worth closing with the above** — one fixture written by hand with a missing
   column, asserting `stats` says `n/a` rather than `0`. `write_csv`-built fixtures cannot
   express it.
